# 生产故障排查方法论与复盘（从慌乱到从容，工程师的核心竞争力）

> **一句话概括**：生产故障不可怕，可怕的是「每次都像第一次遇到」。好的工程师不是不出故障，而是能快速止血、精准定位、彻底修复、举一反三——把每一次故障都变成团队的资产。
>
> **适合谁**：线上出了问题就慌、排查全靠猜、复盘会变成「甩锅会」、面试被问「说一个你处理过的线上故障」讲不出完整逻辑的人。

---

## 零、先建立印象：把故障排查想象成「急诊室抢救」

| 急诊室 | 生产故障排查 |
|---|---|
| **先止血**：心肺复苏、输液、吸氧 | **先止损**：限流、降级、回滚、切流量 |
| **再诊断**：验血、CT、心电图 | **再定位**：看日志、看监控、看链路、抓现场 |
| **后治疗**：手术、吃药、观察 | **后修复**：改代码、发版本、验证、观察 |
| **病例归档**：写病历、讨论病例 | **复盘总结**：写复盘文档、改进措施、防再发 |

> 💡 **醍醐灌顶**：出故障时，90% 的人第一反应是「找根因」，但正确的第一反应是「先止血」。根因可以慢慢找，但用户正在受影响，每多一分钟都是损失。**先止损，再定位，后修复。**

---

## 一、故障排查的黄金 5 分钟（先做这 5 件事）

```
故障发生 → 0-5 分钟：止血 + 信息收集
```

### 1.1 第一步：确认故障范围（30 秒）

```bash
# 1. 是全量还是部分？
#    - 所有用户都受影响？还是部分用户？
#    - 所有接口都慢？还是某个接口慢？
#    - 所有机房都有问题？还是单个机房？

# 2. 影响面有多大？
#    - 错误率从 0.1% 升到了多少？5%？50%？100%？
#    - 影响了多少用户？多少订单？多少钱？

# 3. 什么时候开始的？
#    - 监控告警时间？
#    - 最近有没有发布？有没有变更？
```

> ⚠️ **关键问题**：「最近有没有变更？」—— 80% 的生产故障都是变更引起的（代码发布、配置修改、扩容缩容、依赖升级）。先确认最近的变更，能快速缩小范围。

### 1.2 第二步：紧急止血（2 分钟）

| 故障类型 | 止血手段 | 优先级 |
|---|---|---|
| **应用挂了/频繁重启** | 回滚到上一个稳定版本 | P0 |
| **CPU/内存飙高** | 扩容 + 限流非核心接口 | P0 |
| **数据库慢查询** | 杀掉慢 SQL + 限流 + 加缓存 | P0 |
| **下游依赖挂了** | 熔断 + 降级 + 返回兜底数据 | P0 |
| **消息堆积** | 临时扩容消费者 + 跳过非关键消息 | P1 |
| **磁盘满了** | 清理日志 + 扩容磁盘 | P1 |

**止血原则：**
1. **能回滚就回滚**：如果确认是刚发布的版本引起的，直接回滚，不要犹豫。回滚 1 分钟，排查 1 小时，选回滚。
2. **能限流就限流**：保护核心功能，牺牲非核心功能。比如电商故障时，保证下单和支付，关闭商品推荐和评价。
3. **能切流量就切流量**：多机房/多可用区部署时，把流量切到正常的机房。
4. **止血不是修复**：止血只是让用户不再受影响，根因还需要继续排查。

### 1.3 第三步：保留现场（1 分钟）

```bash
# 止血的同时，一定要保留现场！否则止血后现场就没了，无法根因分析。

# 1. 抓线程栈（CPU 飙高、死锁时）
jstack -l <pid> > /tmp/jstack_$(date +%Y%m%d_%H%M%S).txt
# 连续抓 3 次，间隔 5 秒，对比线程变化

# 2. 导出堆转储（内存溢出、内存泄漏时）
jmap -dump:live,format=b,file=/tmp/heap_$(date +%Y%m%d_%H%M%S).hprof <pid>

# 3. 保存日志
# 把出错时间段的日志拷出来，别被日志滚动覆盖了
cp /path/to/app.log /tmp/app_error_$(date +%Y%m%d).log

# 4. 截图监控面板
# 把监控大盘（CPU、内存、QPS、错误率、响应时间）截图保存
```

> ⚠️ **血泪教训**：很多人一上来就重启应用，结果故障消失了，但根因也没了。下次还会再出。**保留现场比快速重启重要 100 倍。**

### 1.4 第四步：快速定位（1-2 分钟）

```
看监控 → 看日志 → 看链路 → 猜原因 → 验证
```

**按这个顺序看：**
1. **监控大盘**：CPU？内存？磁盘？网络？QPS？错误率？响应时间？哪个指标先异常？
2. **应用日志**：ERROR 日志？异常堆栈？是哪个类哪个方法抛的？
3. **链路追踪**：SkyWalking/Zipkin，看请求在哪一步慢了、哪一步报错了。
4. **系统日志**：dmesg 看 OOM Killer？/var/log/messages 看系统错误？
5. **变更记录**：最近发布了什么？改了什么配置？

### 1.5 第五步：同步信息（持续）

```
故障处理过程中，及时同步信息，避免信息不对称导致混乱。
```

- **拉群/打电话**：把相关人拉到一个群里，统一信息出口。
- **定时同步**：每 5-10 分钟同步一次进展：「目前故障状态、已采取措施、下一步计划」。
- **指定指挥**：一个人负责指挥和决策，其他人负责执行。不要七嘴八舌。
- **记录时间线**：故障发生时间、发现时间、止血时间、恢复时间，都记下来。

## 二、常见故障类型与排查套路

### 2.1 CPU 飙高

```
排查路径：
1. top → 看哪个进程 CPU 高
2. top -Hp <pid> → 看哪个线程 CPU 高
3. jstack <pid> → 看线程在执行什么代码
4. 定位到具体方法 → 分析原因

常见原因：
- 死循环（while(true) 没退出条件）
- 正则表达式回溯（恶意输入导致 ReDoS）
- 频繁 Full GC（内存不足，GC 线程占 CPU）
- 大量计算（嵌套循环、大数据排序）
- 上下文切换频繁（线程太多）
```

### 2.2 内存溢出 / 内存泄漏

```
排查路径：
1. 监控看堆内存使用趋势 → 是持续上涨还是突然飙升？
2. jmap -heap <pid> → 看各区域内存使用
3. jmap -dump → 导出堆转储
4. MAT / JProfiler 分析堆转储 → 看哪个对象占内存最多、谁引用了它

常见原因：
- 内存泄漏：静态集合只加不删、ThreadLocal 不 remove、连接未关闭
- 缓存设计不合理：本地缓存无上限、Redis 缓存穿透
- 一次加载太多数据：全表查询、大文件读取
- 动态生成类：反射、CGLIB 导致 Metaspace 溢出
```

### 2.3 接口响应慢

```
排查路径：
1. 链路追踪 → 看请求在哪一步耗时最长
2. 是应用慢？还是数据库慢？还是下游依赖慢？
3. 应用慢 → 看 CPU、看线程栈、看 GC
4. 数据库慢 → 看慢查询、看锁等待、看连接池
5. 下游慢 → 看依赖服务的监控、考虑熔断降级

常见原因：
- 慢 SQL（全表扫描、没走索引、锁等待）
- 数据库连接池耗尽（连接泄漏、池太小）
- 下游依赖超时（没有合理设置超时时间）
- 频繁 Full GC（STW 导致应用停顿）
- 锁竞争（synchronized、分布式锁）
- 线程池满（队列积压、拒绝策略）
```

### 2.4 数据库故障

```
排查路径：
1. show processlist → 看有哪些线程在跑、有没有锁等待
2. show status like '%lock%' → 看锁状态
3. 慢查询日志 → 看哪些 SQL 慢
4. explain → 分析 SQL 执行计划
5. 看连接数、看 CPU、看磁盘 IO

常见原因：
- 慢 SQL（没索引、索引失效、大事务）
- 锁等待（行锁、表锁、死锁）
- 连接数满（应用连接泄漏、max_connections 太小）
- 磁盘满（binlog 没清理、数据文件太大）
- 主从延迟（大事务、网络问题、从库性能差）
```

### 2.5 消息队列故障

```
排查路径：
1. 看消息堆积量 → 是生产者太快还是消费者太慢？
2. 消费者日志 → 有没有报错？有没有卡住？
3. 消费者线程数 → 是不是消费能力不够？
4. Broker 状态 → 磁盘？内存？网络？

常见原因：
- 消费者处理慢（慢 SQL、下游超时）
- 消费者挂了（异常没捕获、OOM）
- 消费线程数不够
- 消息体太大（网络传输慢、序列化慢）
- Broker 磁盘满（消息没及时清理）
- 重复消费导致死循环（消费失败不断重试）
```

## 三、故障复盘：把事故变成资产

### 3.1 复盘的正确姿势

```
复盘不是为了追责，是为了：
1. 搞清楚到底发生了什么
2. 找到根本原因（不是表面原因）
3. 制定改进措施，防止再发
4. 沉淀经验，让团队所有人都学到
```

**复盘会流程（建议 1 小时内）：**
1. **时间线还原**（10 分钟）：按时间顺序还原故障从发生到恢复的全过程
2. **根因分析**（20 分钟）：用 5 Why 法，挖到根本原因
3. **改进措施**（20 分钟）：针对每个原因，制定具体的、可执行的改进措施
4. **经验总结**（10 分钟）：这次故障教会了我们什么？怎么让更多人知道？

### 3.2 5 Why 根因分析法

```
表面原因 → 问 5 个为什么 → 根本原因
```

**示例：数据库连接池耗尽导致应用挂了**
```
Why 1：应用为什么挂了？
→ 数据库连接池耗尽，获取连接超时

Why 2：连接池为什么耗尽？
→ 有几个线程持有连接后长时间不释放

Why 3：为什么持有连接不释放？
→ 这几个线程在执行一个慢 SQL，跑了 30 秒还没结束

Why 4：为什么 SQL 这么慢？
→ 这个查询没走索引，全表扫描了 500 万行数据

Why 5：为什么没走索引？
→ 上线前没有做 SQL 审核，DBA 没发现这个慢查询

根本原因：缺乏 SQL 上线审核机制
改进措施：
1. 上线前必须经过 SQL 审核（短期）
2. 集成 SQL 自动检测工具，CI 阶段拦截慢 SQL（中期）
3. 数据库加慢查询告警，超过 1 秒自动通知（长期）
```

> 💡 **关键**：不要停在「代码写得不好」「操作失误」这种表面原因。要挖到「机制」「流程」「架构」层面的根本原因。人会犯错，但好的机制能防止人犯错。

### 3.3 复盘文档模板

```markdown
# 【故障复盘】XXX 故障

## 一、故障概况
- 故障时间：2024-01-01 14:30 ~ 15:15（持续 45 分钟）
- 影响范围：下单接口不可用，影响约 5000 笔订单
- 故障等级：P1
- 负责人：XXX

## 二、时间线
| 时间 | 事件 |
|---|---|
| 14:30 | 监控告警，下单接口错误率飙升 |
| 14:32 | 值班同学确认故障，拉群 |
| 14:35 | 定位到数据库连接池耗尽 |
| 14:40 | 杀掉慢 SQL，临时恢复 |
| 14:45 | 加索引，彻底解决 |
| 15:15 | 观察 30 分钟无异常，故障结束 |

## 三、根因分析（5 Why）
（如上）

## 四、改进措施
| 措施 | 负责人 | 截止时间 | 状态 |
|---|---|---|---|
| 上线 SQL 审核流程 | DBA 负责人 | 1月15日 | 进行中 |
| 集成 SQL 自动检测 | 架构组 | 2月1日 | 待开始 |
| 慢查询告警配置 | DBA | 1月10日 | 已完成 |

## 五、经验总结
1. 上线前必须做 SQL 审核，不能只靠开发自测
2. 数据库要配置慢查询告警，提前发现问题
3. 应用要设置合理的连接超时和查询超时，避免被慢 SQL 拖垮
```

## 四、故障预防：把故障消灭在上线前

### 4.1 变更管理（80% 的故障来自变更）

```
1. 所有变更必须有记录：谁、什么时候、改了什么、为什么改
2. 变更前做影响评估：影响哪些接口？哪些用户？有没有回滚方案？
3. 变更后观察 30 分钟：监控、日志、错误率，确认没问题再走
4. 非紧急变更不在周五下午、节假日前发布
5. 灰度发布：先切 10% 流量，观察没问题再全量
```

### 4.2 监控告警（早发现，早处理）

```
1. 基础监控：CPU、内存、磁盘、网络
2. 应用监控：QPS、响应时间、错误率、JVM（堆、GC、线程）
3. 业务监控：订单量、支付成功率、库存告警
4. 告警分级：P0（电话+短信）、P1（短信+群）、P2（群）
5. 告警不能太多：太多告警会麻木，要持续优化告警阈值
```

### 4.3 容错设计（假设依赖一定会挂）

```
1. 超时设置：所有远程调用必须设置超时时间，不能无限等待
2. 重试机制：失败后重试，但要控制重试次数和间隔，避免雪崩
3. 熔断降级：下游挂了，熔断并返回兜底数据，不要被拖垮
4. 限流：保护系统不被流量冲垮，核心接口优先
5. 幂等：所有写操作必须幂等，防止重试导致重复
6. 多活/灾备：核心系统多机房部署，单机房故障不影响全局
```

### 4.4 混沌工程（主动制造故障，验证系统韧性）

```
1. 定期做故障演练：杀进程、断网络、满磁盘、慢响应
2. 验证系统的容错能力：熔断、降级、限流是否生效
3. 验证团队的应急能力：能不能快速发现、快速止血
4. 从演练中发现问题，持续改进
```

## 五、面试口述总结

> **说一个你处理过的线上故障？**
> （STAR 法则）
> - **S 场景**：什么时候、什么系统、什么现象
> - **T 任务**：你的角色和职责
> - **A 行动**：你做了什么——先止血（回滚/限流），再定位（看监控/日志/链路），后修复（改代码/加索引）
> - **R 结果**：多久恢复的、影响多大、根因是什么、改进措施是什么
>
> **故障排查的流程是什么？**
> 先止损再定位后修复。0-5 分钟黄金时间：确认故障范围→紧急止血→保留现场→快速定位→同步信息。止血手段包括回滚、限流、降级、熔断、切流量。
>
> **怎么避免重复故障？**
> 复盘 + 改进措施。用 5 Why 法挖到根本原因（不是表面原因），制定具体的可执行的改进措施，指定负责人和截止时间，跟踪落地。同时加强变更管理、监控告警、容错设计。
>
> **线上 CPU 飙高怎么排查？**
> top 确认 Java 进程 → top -Hp 找高 CPU 线程 → jstack 看线程栈 → 定位具体代码。常见原因：死循环、正则回溯、频繁 GC、大量计算。
