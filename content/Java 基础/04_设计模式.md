# 设计模式（原理 → 应用 → 进阶）

> **一句话概括**：设计模式不是什么高深武功，它就是一句话——**把"会变的东西"和"不变的东西"分开，让变化来了你只需要改一处**。23 种模式听着吓人，其实全在做同一件事：**找个地方把变化"包"起来**。
>
> **适合谁**：看得懂别人的代码，但自己写总是写成一坨 `if-else`，改需求时要翻遍全项目的人。
> **怎么读**：原理篇教你"什么情况该用什么"（这才是模式的真正价值）；应用篇四段代码**照着抄就能用**；进阶篇看 Spring 是怎么用这些模式的；避坑篇最重要——**别学完就开始滥用**。

---

## 零、先建立整体印象：把它想象成"装修一套房子"

设计模式之所以难记，是因为名字抽象（单例、策略、责任链）。我们用一个贯穿全文的场景——**装修一套房子**：

| 装修场景 | 对应模式 | 一句话 |
|---|---|---|
| **整栋楼只有一个总电闸** | 单例 | 全局唯一，谁都来这儿拉闸 |
| **建材厂按需生产门窗** | 工厂 | 你要什么规格，厂里给你造，你不管怎么造 |
| **套餐式装修（基础/豪华/尊享）** | 建造者 | 一步一步搭出来，可选配件自由组合 |
| **装修风格二选一（北欧 / 新中式）** | 策略 | 多种做法选一种，随时能换 |
| **验收关卡：水电 → 泥木 → 油漆** | 责任链 | 一关一关过，任一关不过就打回 |
| **基础装修上再贴壁纸、装灯带** | 装饰 | 一层层加料，不影响底下的 |
| **找装修公司替你跑建材市场** | 代理 | 你不用亲自去，它替你做还顺带加点控制 |
| **欧标插头插不进国标插座** | 适配器 | 加个转接头，让不兼容的能用 |
| **装修流程固定，每家细节不同** | 模板方法 | 骨架不变，具体步骤各家自己填 |
| **施工进度往业主群里发通知** | 观察者 | 一有变化，所有订阅的人自动收到 |

**记住这个类比，后面每节都能对号入座。**

## 一、原理篇：什么时候该用什么

**核心心法：先看"什么东西在变"，再选模式。** 别背 23 个名字，背这张表：

| 变的是什么 | 用什么模式 | 装修类比 | 典型场景 |
|---|---|---|---|
| **创建方式**在变 | **工厂 / 建造者** | 建材厂按需造 vs 套餐式搭配 | 对象构造复杂、参数多、要按条件造不同的类 |
| **行为 / 算法**在变 | **策略** | 装修风格换一种 | 支付方式、折扣算法、降级兜底方案 |
| **结构 / 增强**在变 | **装饰 / 代理 / 适配器** | 贴壁纸 / 找装修公司 / 加转接头 | 加日志、加缓存、加权限、兼容老接口 |
| **流程步骤**在变 | **模板方法** | 装修流程固定，每家细节不同 | 下单流程、审批流程、数据导入流程 |
| **多个对象协作** | **责任链 / 观察者** | 验收关卡 / 业主群通知 | 网关 Filter 链、事件通知机制 |

> 💡 **一句话选型口诀**：
> **创建对象找工厂，算法切换找策略，功能增强找装饰，流程固定找模板，层层过关找责任链。**

**五个最容易混的"近亲"，一张表分清**：

| 对比 | A | B | 关键区别 |
|---|---|---|---|
| 工厂 vs 建造者 | **一步**拿到成品 | **分步**搭，最后 `build()` | 参数多、可选配件多 → 用建造者 |
| 策略 vs 责任链 | **多选一**（只执行一个） | **依次过**（多个都执行） | 只选一种算法 → 策略；每个都要处理 → 责任链 |
| 装饰 vs 代理 | **增强功能**，可层层嵌套 | **控制访问**，一般只有一层 | 想加功能 → 装饰；想管控 → 代理 |
| 适配器 vs 装饰 | **改接口**让不兼容的能用 | **不改接口**，只加料 | 接口对不上 → 适配器 |
| 模板方法 vs 策略 | 复用**流程骨架** | 复用**单个算法** | 有固定步骤 → 模板方法 |

## 二、应用篇（代码）

### 2.1 单例：全局只有一个（DCL + volatile）

**类比**：整栋楼只有一个总电闸，谁都不能自己再装一个。

**为什么必须加 `volatile`？** 这是单例里最值钱的一个知识点。

```java
instance = new Singleton();
```
这一行看着是一步，实际是**三步**：
```
① 分配内存空间
② 初始化对象（执行构造器）
③ 把 instance 指向这块内存
```
**CPU 和 JIT 会重排指令**：②③ 顺序可能被调换（先指向内存，再初始化）。于是：

```java
// 线程 A 执行到一半，发生了指令重排：先执行了 ③，还没执行 ②
// 线程 B 此时进来，发现 instance != null，高兴地拿去用了
// —— 但对象还没初始化，字段全是默认值 → 炸了
```

**`volatile` 的作用就是禁止这次重排**，保证 ①②③ 按顺序对外可见。

```java
public class Singleton {
    private static volatile Singleton instance;   // ① volatile 禁止指令重排 + 保证可见性
    private Singleton() {}                        // ② 构造器私有：外面 new 不出来

    public static Singleton get() {
        if (instance == null) {                   // ③ 第一次检查（不加锁，快路径）
                                                  //    已经创建好后，后续调用直接返回，不进锁
            synchronized (Singleton.class) {      // ④ 加锁：只在首次创建时才竞争
                if (instance == null)             // ⑤ 第二次检查（有锁，防重复创建）
                                                  //    为什么要再查一次？A 和 B 可能都通过了 ③，
                                                  //    A 建完后 B 进来，不查就会再建一个
                    instance = new Singleton();
            }
        }
        return instance;
    }
}
```
**这就是传说中的"双重检查锁"（Double-Checked Locking，DCL）**，两处 `if` 各有各的职责，缺一不可。

> ✅ **更优解：枚举单例**（《Effective Java》推荐）
> ```java
> public enum Singleton {
>     INSTANCE;                    // 就这么一行
>     public void doSomething() { ... }
> }
> ```
> **为什么它最优？** 枚举由 JVM 保证唯一，**天然防反射攻击**（反射 `newInstance` 对枚举直接抛异常），**天然防反序列化破坏**（枚举的序列化只存名字，反序列化时按名字找同一个实例）。而 DCL 单例**能被反射和反序列化破坏**（反序列化会新建一个对象）。

### 2.2 策略：干掉 if-else（简历里的「服务降级策略兜底」）

**类比**：装修风格选北欧还是新中式，是"选一种做法"，不是"两个都要做"。

**痛点**：服务挂了怎么办？很多人写成这样——

```java
// ❌ 典型坏味道：每加一种兜底方案，就改一遍这段代码（违反开闭原则）
if ("cache".equals(type))        return queryFromCache(ctx);
else if ("default".equals(type)) return queryDirectly(ctx);
else if ("mock".equals(type))    return mockData(ctx);
```

**策略模式改造后**：每种算法独立成一个类，用 `Map` 存起来，运行时按 key 选。

```java
interface DegradeStrategy { Result exec(Context c); }   // ① 策略接口：所有算法长一个样
class CacheStrategy implements DegradeStrategy {        // ② 具体策略：走缓存兜底
    public Result exec(Context c) { return queryFromCache(c); }
}
class DefaultStrategy implements DegradeStrategy {      // ③ 具体策略：默认直连
    public Result exec(Context c) { return queryDirectly(c); }
}

// ④ 新增策略只要加个实现类，业务代码一行不动
Map<String, DegradeStrategy> strategies = ...;
return strategies.get(type).exec(ctx);   // 运行时按 type 选算法
```

> 💡 **Spring 里的甜点写法**：把策略类都交给 Spring 管理，启动时自动收集到一个 `Map` 里，连手动注册都省了：
> ```java
> // Spring 会自动把 key=bean 名、value=实现类 注入进来
> @Resource
> private Map<String, DegradeStrategy> strategies;
>
> public Result handle(String type, Context ctx) {
>     return strategies.get(type).exec(ctx);   // 就这一行
> }
> ```

### 2.3 责任链：层层过关（简历里的「Gateway 责任链作为网关」）

**类比**：装修验收要过关卡——水电 → 泥木 → 油漆。**每一关都要过，任何一关不过就直接打回**，不会继续往下走。

**和策略的区别**：策略是"多选一"（只执行被选中的那个），责任链是"依次过"（每个都有机会处理，也都有权中断）。

```java
interface Filter { void doFilter(Request req, Chain chain); }   // ① 处理器接口

class AuthFilter implements Filter {          // ② 认证：没登录直接返回 401
    public void doFilter(Request req, Chain chain) {
        if (!req.hasToken()) { req.response(401); return; }   // ← 中断，不再往下传
        chain.doFilter(req, chain);           // ← 放行，交给下一个
    }
}
class RateLimitFilter implements Filter {     // ③ 限流：超了直接返回 429
    public void doFilter(Request req, Chain chain) {
        if (overLimit(req)) { req.response(429); return; }
        chain.doFilter(req, chain);
    }
}
class RouteFilter implements Filter {         // ④ 路由：最后一关，转发到真正的服务
    public void doFilter(Request req, Chain chain) { forward(req); }
}
// 执行顺序：Auth → RateLimit → Route，任一中断即返回
```

**责任链的关键要素**（缺一不可）：
1. 每个处理器持有**下一个处理器**的引用（或统一的 `Chain`）
2. 处理器有两个选择：**处理完放行** or **直接中断**
3. 链条可以动态组装、调整顺序

> 💡 **Spring Cloud Gateway 的 `GlobalFilter`、Servlet 的 `Filter`、MyBatis 的 `Plugin`、Sentinel 的 `SlotChain`，全是责任链。**

### 2.4 模板方法：流程固定，细节填空（简历里的「模板开发」）

**类比**：装修流程是固定的——量房 → 水电 → 泥木 → 油漆 → 验收。**流程谁都不能改，但每一家怎么做由自己定。**

```java
abstract class OrderProcess {
    // ① final 锁住骨架：子类【不许】改流程顺序，只能填空
    public final void process() {
        validate();      // 固定步骤 1：校验（通用逻辑，父类实现）
        pay();           // 固定步骤 2：支付（各家不同，子类实现）
        afterPaid();     // 固定步骤 3：支付后处理（可选，子类想改就改）
    }

    abstract void pay();          // ② 抽象方法：子类【必须】实现
    void afterPaid() {}           // ③ 钩子方法 hook：空实现，子类【可选】重写
}

class AlipayProcess extends OrderProcess {
    @Override void pay() { callAlipay(); }        // 只填自己那一步
    @Override void afterPaid() { sendCoupon(); }  // 钩子：支付宝支付后发张券
}
```

**两个概念要分清**：

| | 抽象方法 | 钩子方法（Hook） |
|---|---|---|
| 子类必须实现？ | **必须** | **可选**（父类给了空实现） |
| 用途 | 流程中"必须各家自定义"的步骤 | 流程中的"可插拔扩展点" |

> 💡 **`final` 修饰 `process()` 是精髓**——它保证"流程不会被子类改乱"。这也是框架设计的常用手法：**框架定流程，业务填内容**（即"好莱坞原则"：别调用我们，我们来调用你）。

## 三、进阶篇：Spring 里藏着的模式

Spring 本身就是设计模式的博物馆。看懂这张表，再看 Spring 源码就不发怵了：

| 模式 | Spring 里的体现 | 人话解释 |
|---|---|---|
| **单例** | 默认 Bean 的 `scope="singleton"` | 一个 Bean 在容器里只创建一次，全局复用 |
| **工厂** | `BeanFactory` / `ApplicationContext` | 你只要 `getBean("xxx")`，怎么造的它管 |
| **代理** | AOP（JDK 动态代理 / CGLib） | 你调的是代理对象，它在前后悄悄加了事务、日志 |
| **模板方法** | `JdbcTemplate` / `RestTemplate` / `RedisTemplate` | 连接、关闭这类脏活框架干了，你只写 SQL / 回调 |
| **观察者** | `ApplicationEvent` + `@EventListener` | 发布一个事件，所有订阅者自动收到并执行 |
| **适配器** | `HandlerAdapter` | 各种千奇百怪的 Controller 写法，统一适配成同一种调用方式 |
| **责任链** | `HandlerInterceptor` 链 / Gateway Filter 链 | 请求依次过拦截器，任一可中断 |
| **策略** | `InstantiationStrategy`、事务隔离级别选择 | 不同情况用不同实例化/隔离策略 |

> ⚠️ **注意**：Spring 的"单例"是**容器级**的，不是 JVM 级的——**每个 Spring 容器一份**，两个容器就有两个实例。这和上面 2.1 的"单例"（ClassLoader 级）不是一回事，别混。

**再补两个日常开发里最常见的**：

| 模式 | 日常体现 |
|---|---|
| **建造者** | Lombok 的 `@Builder`、MyBatis-Plus 的 `LambdaQueryWrapper`、链式 `new User().name("a").age(1).build()` |
| **装饰** | `BufferedInputStream` 包 `FileInputStream`、MyBatis 的二级缓存包一级缓存 |

## 四、避坑：这些比会写模式更重要

### 4.1 别为模式而模式

**模式是有成本的**——它引入抽象层，代码从"一眼看懂"变成"要跳三四个类才看懂"。

> ✅ **判断标准**：**分支稳定且少于 3 个，直接 `if-else` 更清晰。**
> 模式是为了应对"未来会变"，如果这块代码三年没变过，那它当初就不该抽模式。

### 4.2 三组近亲别搞混

- **策略 vs 责任链**：策略是「**多选一**算法」（只执行被选中的那个）；责任链是「**多处理器依次过**」（每个都执行，且能中断）。
- **装饰 vs 代理**：装饰是「**增强功能**」，可以层层嵌套（`Buffered` 包 `Gzip` 包 `File`）；代理是「**控制访问**」，重点是管控（AOP 加事务、权限校验）。
- **工厂 vs 建造者**：参数少于 4 个用工厂（或静态工厂方法）；**参数多、可选参数多、有校验逻辑** → 用建造者。

### 4.3 过度设计是原罪（YAGNI 原则）

**YAGNI** = You Aren't Gonna Need It（你不会需要它的）。

**反面案例**（新人最爱犯）：需求是"做一个订单导出功能"。于是先抽个 `ExportStrategy` 接口 → 再写个抽象基类 → 再来个工厂 → 再来条责任链做数据加工 → 最后才写 `ExcelExportImpl`。**两年过去了，就只有 Excel 一种导出，那 5 个类全是负担。**

> ✅ **正确姿势（三步走）**：① 第一版**写直白代码**，能跑就行；② **第二次**遇到同类需求时，你才真正知道"哪里在变"，再抽模式；③ **第三次**确认抽象是对的，固化下来。
> **重构时抽模式，而不是一开始就设计模式**——你第一次猜的"变化点"，八成是错的。

### 4.4 一句话总结

> **模式是重构出来的，不是设计出来的。**
> 当你第三次写同样的 `if-else` 分支时，那个"变化点"才是真的——这时候再动手抽，抽出来的才是对的抽象。
