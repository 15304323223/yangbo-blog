# 分布式锁实现原理与实战

> 一句话概括：分布式锁就是「多个机器上的多个线程，抢同一把锁」。Redis 用得最多，ZooKeeper 最可靠，数据库最简单但性能最差。

## 一、分布式锁必须满足的五个条件

1. 互斥性：同一时间只有一个客户端持有锁
2. 防死锁：即使持有锁的客户端崩溃，锁也能自动释放
3. 解铃还须系铃人：只能由加锁的人解锁
4. 可重入：同一个线程可以多次获取同一把锁
5. 高可用：加锁/解锁操作本身不能成为单点故障

## 二、Redis 分布式锁（最常用）

### 正确实现：SET NX EX + UUID + Lua 原子解锁

```java
String lockKey = "lock:order:" + orderId;
String lockValue = UUID.randomUUID().toString();

// 加锁：不存在才设置，30秒过期
Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, lockValue, 30, TimeUnit.SECONDS);

if (!locked) {
    throw new BusinessException("操作太频繁");
}

try {
    doBusiness();
} finally {
    // 解锁：Lua 脚本保证判断+删除原子性
    String lua = "if redis.call('get', KEYS[1]) == ARGV[1] " +
                 "then return redis.call('del', KEYS[1]) else return 0 end";
    redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class),
            Collections.singletonList(lockKey), lockValue);
}
```

### Redisson + Watchdog 自动续期（生产推荐）

```java
RLock lock = redissonClient.getLock("lock:order:" + orderId);
try {
    // leaseTime 传 -1 开启 watchdog 自动续期
    boolean acquired = lock.tryLock(3, -1, TimeUnit.SECONDS);
    if (!acquired) throw new BusinessException("获取锁失败");
    doBusiness();
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

**Watchdog 原理**：加锁成功后启动后台线程，每 10 秒检查一次，如果当前线程还持有锁，就把过期时间重置为 30 秒。只要业务还在跑，锁就永远不会过期。

### Redis 锁的坑

| 坑 | 解法 |
|---|---|
| 锁过期业务没跑完 | Redisson watchdog 自动续期 |
| 误删别人的锁 | Lua 脚本原子解锁 + UUID |
| 主从切换丢锁 | RedLock 红锁（多节点多数派） |
| 不可重入 | Redisson 天然支持（Hash 存计数） |

## 三、ZooKeeper 分布式锁（最可靠）

**原理**：临时顺序节点 + watch 监听
1. 每个客户端在 /locks 下创建临时顺序节点
2. 序号最小的节点获取锁
3. 其他节点 watch 监听前一个节点
4. 前一个节点删除（业务完成或会话断开），收到通知后再次判断

```java
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order:" + orderId);
try {
    boolean acquired = lock.acquire(3, TimeUnit.SECONDS);
    if (!acquired) throw new BusinessException("获取锁失败");
    doBusiness();
} finally {
    if (lock.isAcquiredInThisProcess()) lock.release();
}
```

## 四、选型决策

| 对比项 | Redis 锁 | ZooKeeper 锁 | 数据库锁 |
|---|---|---|---|
| 性能 | 高（10万+ QPS） | 中（1万 QPS） | 低（几百 QPS） |
| 可靠性 | 较高（主从切换极小概率丢锁） | 高（ZAB 协议） | 高（事务） |
| 自动续期 | watchdog | 临时节点天然支持 | 需定时任务 |
| 等待队列 | 需自己实现 | 天然支持 | 不支持 |
| 适用场景 | 高并发、性能敏感 | 金融级、强一致 | 低并发、简单场景 |

> 选型结论：90% 的场景用 Redisson 就够了；金融支付等强一致场景用 ZooKeeper。

## 五、醍醐灌顶：能不用锁就不用锁

分布式锁不是银弹。优先用：
1. **Redis Lua 原子操作**（比如秒杀扣库存，不用锁直接原子判断+扣减）
2. **MQ 队列串行化**（把并发请求变成队列消费）
3. **乐观锁**（版本号，数据库 UPDATE ... WHERE version = ?）
4. **数据库唯一索引**（防重复插入）

锁是「没办法的办法」，加锁就意味着性能损耗和潜在的死锁风险。
