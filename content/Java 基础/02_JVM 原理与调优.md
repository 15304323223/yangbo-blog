# JVM 原理与调优（原理 → 应用 → 进阶）

> **一句话概括**：JVM 就是**替你管内存和打扫卫生的管家**——你只管 `new` 对象，它负责分配空间、判断哪些对象没用了、在不停工（或短暂停工）的前提下把垃圾清走。调优就是**给这个管家定规矩：给它多大地方、用什么打扫策略、多久打扫一次**。
>
> **适合谁**：会写 Java 但没调过 JVM 参数、线上 OOM 只知道重启、被问到"G1 和 ZGC 什么区别"只能背名词的人。
> **怎么读**：原理篇讲"内存怎么分、垃圾怎么判定、谁来清"；应用篇给你**能直接抄的生产参数模板**和排查套路；进阶篇是面试深挖。**看不懂代码先看文字和表格。**

---

## 零、先建立整体印象：把它想象成"一家工厂"

JVM 的术语很吓人（元空间、GC Roots、三色标记、Region），但本质就是工厂管理那点事。用**一家工厂**贯穿全文：

| 工厂里 | 对应 JVM | 一句话 |
|---|---|---|
| **厂区仓库** | 堆（Heap） | 原料和半成品堆放的主战场，最大一块地 |
| **新料暂存区 / 长期存放区** | 新生代 / 老年代 | 刚到的料先放暂存区，反复用的搬到长期区 |
| **图纸档案室** | 元空间（Metaspace） | 存放"这个产品怎么造"的设计图纸（类信息） |
| **每个工人的操作台** | 虚拟机栈 | 每人一份，台上摆着他正在用的工具和零件 |
| **工人贴身的进度贴纸** | 程序计数器 | 记着"我干到第几步了"，切换回来接着干 |
| **清洁队** | GC（垃圾回收器） | 定期巡场，把没人要的废料清走 |
| **停产大扫除** | STW（Stop The World） | 清洁时全员停工，效率差但干净 |
| **废料判定标准** | GC Roots 可达性分析 | 从"还在使用中的东西"往回追，追不到的就是废料 |

**记住这个类比，后面每节都能对号入座。**

## 一、原理篇

### 1.1 运行时数据区：内存是怎么切块的

**类比**：工厂的地皮要规划——仓库区、档案室、每个工人的操作台、外包人员通道，各占各的，不能混。

```
┌───────────────────────── 线程共享（所有工人共用）─────────────────────────┐
│  堆 Heap：所有对象实例，GC 主战场，最大一块                                  │
│    ├── 新生代 Young（约 1/3）：Eden 80% + Survivor0 10% + Survivor1 10%     │
│    └── 老年代 Old（约 2/3）：熬过多次 GC 的"老资格"对象                      │
│  元空间 Metaspace（JDK 8+，用的是本地内存不是堆）：类元信息、常量、静态变量    │
└──────────────────────────────────────────────────────────────────────┘
┌───────────────────────── 线程私有（每人一份）────────────────────────────┐
│  虚拟机栈：栈帧里存局部变量表、操作数栈、动态链接、方法出口                   │
│  本地方法栈：给 native 方法（调用 C/C++）用的                              │
│  程序计数器：记录当前执行到字节码的第几行（唯一不会 OOM 的区域）              │
└──────────────────────────────────────────────────────────────────────┘
```

**逐块讲人话：**

| 区域 | 大白话 | 常见问题 |
|---|---|---|
| **堆** | 你 `new` 出来的对象全在这儿，GC 主要在这儿干活 | 堆满了 → `OutOfMemoryError: Java heap space` |
| **元空间** | 存"类的设计图纸"：类名、方法字节码、常量池、静态变量。**JDK 8 起取代永久代，用本地内存** | 类加载太多（热部署、反射、动态代理）→ `Metaspace` OOM |
| **虚拟机栈** | 每个线程一份，方法调用就是"压一个栈帧"，方法返回就是"弹掉" | 递归没出口 → 栈帧越堆越高 → `StackOverflowError` |
| **本地方法栈** | 给 `native` 方法用的，原理同虚拟机栈 | 同上 |
| **程序计数器** | 线程切换后靠它知道"我刚干到哪了"，记的是字节码行号 | 唯一规范里没规定 OOM 的区域 |

> 💡 **为什么元空间取代永久代？** 永久代在堆里、大小固定，稍微多加载点类（比如大量用 CGLib 动态代理）就 `PermGen OOM`。元空间用**本地内存**，理论上只受机器内存限制，**不易 OOM**。
> ⚠️ **但"不易"不等于"不会"**：元空间如果不设上限，遇到类加载器泄漏会**吃掉整台机器的内存**。所以生产上 `-XX:MaxMetaspaceSize` 依然要设。

**对象在堆里的"晋升"流程**（记住 8:1:1 这个比例）：

```
new 出来 → 进 Eden
         ↓ Eden 满了，触发 Young GC
    活着的对象 → 复制到 Survivor0（年龄 +1）
         ↓ 下一次 Young GC
    S0 里还活着的 → 复制到 S1（年龄 +1），同时清空 S0
         ↓ 反复"左右互搏"
    年龄到 15 → 晋升 老年代
```
> ⚠️ **Survivor 区为什么要有两块？** 为了用**复制算法**——把活着的从一块完整搬到另一块，然后整块清空。**代价是永远有 10% 的空间空着不能用**，换来的是"清零"效率极高（对象大多朝生夕死，复制少数活着的比清理大量死掉的划算）。

### 1.2 对象的生死判定：怎么知道一个东西没人要了

**类比**：工厂盘点废料，不是挨个问"有人要你吗"，而是**从"正在生产的产品"出发，顺着物料清单往回追，追不到的就是废料**。

**专业说法：可达性分析**（Reachability Analysis）。从 **GC Roots** 出发，能顺着引用链摸到的对象 = 活着；摸不到的 = 死。

```
GC Roots（一定活着的东西）
  ├── 虚拟机栈里的引用（方法里正在用的局部变量、参数）
  ├── 静态变量（static 字段）
  ├── 常量（字符串常量池里的引用）
  ├── JNI 引用（native 方法持有的）
  └── 活跃的线程对象
        │
        ↓ 顺着引用链往下追
   对象A → 对象B → 对象C     ← 都追得到，都活着
   对象X（没人指向它）        ← 追不到，判定为垃圾
```

> ❌ **不是引用计数**：很多人以为 Java 数"有几个引用指向我"。不是。**引用计数解决不了循环引用**（A 引用 B、B 引用 A，但两者都没人用），Java 用的是可达性分析。

**`finalize()`：最后的自救机会**
对象被判死之后，如果它重写了 `finalize()`，JVM 会给它**一次**机会——在 `finalize` 里把自己重新挂到某个引用链上，就能活下来。

> ⚠️ **几乎不用它**：执行时机不确定、只调一次、拖慢 GC、还可能导致对象"复活"后再也收不掉。**忘记这个方法是最好的选择**，资源关闭请用 try-with-resources（见 [[01_Java 基础核心]]）。

### 1.3 GC 算法与收集器

**四种基础算法**：

| 算法 | 思路 | 类比 | 代表 |
|---|---|---|---|
| **标记-清除** | 先标记死对象，再直接清掉 | 在废料上贴条，然后扔掉 | CMS（已废弃） |
| **复制** | 活着的拷贝到新空间，整块清空 | 把还要用的搬到新仓库，旧仓库整个推平 | 新生代 Serial / ParNew |
| **标记-整理** | 活着的往前挪，清掉边界外的 | 把要用的往前排紧，后面全空出来 | 老年代 Serial Old |
| **分代** | 新生代用复制、老年代用整理 | 新料区天天大扫除，长期区很久才动一次 | 几乎所有现代收集器 |

**收集器演进**（一代比一代聪明，核心矛盾始终是**吞吐量 vs 停顿时间**）：

| 收集器 | 特点 | 人话 |
|---|---|---|
| **Serial** | 单线程 GC | 一个人打扫，全厂停工，适合小作坊（客户端程序） |
| **Parallel** | 多线程 GC | 一群人一起打扫，**追求吞吐量**（JDK 8 默认） |
| **G1** | Region 化，可预测停顿 | 把仓库切成小格，**哪格垃圾多先扫哪格**，还能承诺"最多停 200ms"（**JDK 9 起默认**） |
| **ZGC / Shenandoah** | 染色指针 / 读屏障 | **边生产边打扫**，几乎不停顿（亚毫秒级），适合超大堆 |

**G1 为什么能做到"可预测停顿"？**
把堆切成很多小格（Region），每次 GC 前先算一算**哪个 Region 垃圾最多、回收最划算**，然后在你给定的时间预算内（比如 200ms）挑若干个 Region 回收。**不是"扫完整个堆"，而是"在预算内扫最值的那几格"**——这就是 Garbage First（垃圾优先）名字的由来。

**三色标记**（并发标记的核心，理解它才能懂漏标问题）：

| 颜色 | 含义 |
|---|---|
| ⚪ **白色** | 还没访问过（如果标记结束还是白色 = 垃圾） |
| 🔘 **灰色** | 自己访问过了，但它引用的对象还没查完 |
| ⚫ **黑色** | 自己和它引用的都查完了，确定活着 |

> ⚠️ **漏标问题**：并发标记时用户线程还在改引用关系。想象灰色对象刚要查它的子对象，用户线程把这个子对象挪给了某个黑色对象——黑色对象已经扫完不会再看，这个子对象就**永远停在白色，被误当成垃圾清掉**。这是致命 bug。
>
> **两种解法**（面试高频）：
> - **增量更新**（Incremental Update，CMS 用）：黑色对象一旦新增指向白色对象的引用，就把它**重新变回灰色**，待会儿再扫一遍。
> - **原始快照 SATB**（Snapshot-At-The-Beginning，G1 用）：标记开始时给引用关系拍张快照，被删掉的引用**仍按快照当作活着**。宁可留点浮动垃圾，也不错杀。

## 二、应用篇（调优实战）

### 2.1 核心参数：一份能直接抄的生产模板

```bash
-Xms4g -Xmx4g                       # 堆的初始值和最大值设成一样
                                    # 为什么？避免 JVM 运行中动态扩缩容带来的抖动和额外 GC
-Xmn1536m                           # 新生代大小，约堆的 1/3 ~ 1/2
                                    # 太小 → Young GC 频繁；太大 → 老年代被挤小，Full GC 变多
-XX:MetaspaceSize=256m              # 元空间初始阈值
                                    # 作用：防止元空间动态扩容触发 Full GC（扩容就要 GC 一次）
-XX:+UseG1GC                        # 选 G1，JDK 9+ 本来就是默认，JDK 8 要显式指定
-XX:MaxGCPauseMillis=200            # 目标停顿时间（毫秒）
                                    # 注意：这是【目标】不是【保证】，G1 会尽力靠近，达不到就多花点时间
-Xlog:gc*:time,level,tags:file=gc.log:time=trace:filecount=5,filesize=100M
                                    # GC 日志：打印时间+级别+标签，滚动保留 5 个文件每个 100M
                                    # ⚠️ 生产务必开，出事时这是唯一的"行车记录仪"
                                    # JDK 8 的老写法是 -XX:+PrintGCDetails -Xloggc:gc.log
-XX:+HeapDumpOnOutOfMemoryError     # OOM 时自动 dump 堆快照，否则重启后现场就没了
-XX:HeapDumpPath=/logs/dump.hprof   # dump 文件放哪（记得挂到有足够空间的盘）
```

> 💡 **调优的第一步不是调参数，是开日志**。没有 GC 日志的调优都是拍脑袋。

### 2.2 容器化部署的坑（Docker / K8s 必看）

**问题**：早期 JVM **不认识容器**。你在 K8s 里给 Pod 限了 2G 内存，但 JVM 读的是**宿主机的 128G**，于是它按 128G 的 1/4 给自己划了 32G 堆。结果 Pod 内存一超 2G，**直接被 CGroup 一枪毙掉（OOMKilled）**，连 `OutOfMemoryError` 都来不及抛——日志干干净净，人一脸懵。

**解法**：
- **JDK 8u191+** 支持 `-XX:+UseContainerSupport`，**默认开启**，能感知容器内存上限
- 更稳妥的做法是**用百分比而不是固定值**：
```bash
-XX:MaxRAMPercentage=75.0    # 堆上限 = 容器限制的 75%，给元空间、栈、堆外留 25%
-XX:InitialRAMPercentage=75.0
# ❌ 别再写死 -Xmx4g：容器一缩容就出事
```

> ⚠️ **另一个坑**：容器里 CPU 也是受限的，但 JVM 读到的可能是宿主机核数，于是 `Runtime.availableProcessors()` 偏大，导致**线程池、GC 线程数都开多了**。JDK 10+ 已修复（`UseContainerSupport` 同样管 CPU）。

### 2.3 线上排查流程：RT 陡增 / CPU 飙高怎么办

**类比**：工厂突然出货变慢，排查顺序是——先看是不是全厂在停工大扫除（GC），再看是哪个工位卡住了（慢方法），最后看是不是仓库堆满了（内存泄漏）。

```bash
# 第 1 步：定位进程，看整体状况
top                          # 看 CPU / 内存占用最高的进程
jps -l                       # 列出所有 Java 进程及其主类
jstat -gcutil <pid> 1s       # 每秒刷一次：各代占用百分比 + YGC/FGC 次数与耗时
                             # 关键看：FGC 列是不是一直在涨？OU（老年代）是不是只升不降？

# 第 2 步：看 GC 日志，判断停顿时间和频率
#   Young GC 频繁  → 新生代太小，或对象创建太快
#   Full GC 频繁   → 老年代不足、内存泄漏、或元空间扩容

# 第 3 步：找大对象
jmap -histo:live <pid> | head -20    # 按类统计对象数量和占用，谁最多一目了然
jmap -dump:format=b,file=/tmp/heap.hprof <pid>   # 抓堆快照
# ⚠️ jmap -dump 会触发 Full GC 且暂停应用，【线上高峰期慎用】，先在预发或从节点上抓

# 第 4 步：用 Arthas 跟慢方法（详见 [[18_开发工具链]]）
dashboard                    # 总览：线程、内存、GC 一屏看完
thread -n 3                  # 最忙的 3 个线程（CPU 高的元凶）
thread <id>                  # 看某个线程的完整调用栈（找死锁、找阻塞点）
trace 类 方法                # 跟踪方法内部每个子调用的耗时，精确定位慢在哪一行

# 第 5 步：MAT 打开 dump 文件
#   看【支配树 Dominator Tree】→ 谁占了大部分内存
#   看【重复对象】→ 是不是同一个类 new 了几百万个
#   看【泄漏根 Leak Suspects】→ MAT 会直接给你一份"疑似泄漏报告"
```

> 💡 **经验顺序**：**先 `jstat` 判断是不是 GC 问题，再决定要不要 dump**。
> 如果 GC 正常但 RT 高，那多半是**慢 SQL / 慢方法 / 锁竞争**，抓堆没用，直接上 Arthas `trace`。

## 三、进阶篇（面试深挖）

**① GC Roots 具体有哪些？**
虚拟机栈中的引用、静态变量、常量池引用、JNI（native）引用、活跃的 Java 线程。

**② STW（Stop The World）是什么？**
GC 时必须**暂停所有用户线程**，否则引用关系一直在变，没法准确标记。线程会在**安全点（Safepoint）**停下——不是随叫随停，而是跑到"我知道自己状态是安全的"那个位置才停。
> 💡 **ZGC 的牛逼之处就是把 STW 压到 1ms 以内**（几乎全靠并发完成），代价是吞吐略降、内存占用略高。

**③ Young GC 什么时候触发？对象什么时候进老年代？**
- **触发**：Eden 区满了
- **晋升老年代的三种情况**：
  1. 年龄达到 `MaxTenuringThreshold`（**默认 15**）
  2. **大对象直接进老年代**（`-XX:PretenureSizeThreshold`）——省得在新生代来回复制
  3. **动态年龄判定**：Survivor 里同龄对象总大小超过 Survivor 一半，年龄 ≥ 该年龄的对象直接晋级

**④ G1 的 Region 机制**
堆被切成 1M~32M 的小格子（Region），每个 Region 可以是 Eden / Survivor / Old / Humongous（存大对象）。**优先回收垃圾最多（回收价值最高）的 Region**，配合停顿预测模型，实现"可控的停顿时间"。

**⑤ ZGC 的染色指针（Colored Pointer）**
传统做法把"这对象标记过了"记在对象头里，ZGC 直接**把标记信息塞进 64 位指针的空闲位**里。好处：**移动对象时不用访问对象本身，只要读指针就知道状态**，配合读屏障（Load Barrier），实现"边搬边跑"，停顿极短。

**⑥ TLAB（线程本地分配缓冲）**
堆是共享的，多个线程同时 `new` 对象会抢同一根分配指针。TLAB 给**每个线程在 Eden 里划一小块专属区域**，先在自己那块分配，用完了才去加锁申请新的。把内存分配从"每次都抢锁"变成"基本不用抢"。

**⑦ 逃逸分析**（JIT 编译器的优化）
分析对象的作用域——**如果这个对象没逃出方法**（不会被外部引用），JVM 就能做三件事：
- **栈上分配**：直接在栈帧里分配，方法结束自动销毁，**连 GC 都不用参与**
- **锁消除**：这对象只有我用，那 `synchronized` 就是白加锁，**直接去掉**
- **标量替换**：干脆不创建完整对象，把它拆成几个独立的局部变量
> 💡 这也是为什么微基准测试里"循环 new 一个局部对象"几乎不产生 GC 压力的原因。

**⑧ 偏向锁：JDK 15 起被废弃**
偏向锁的设计初衷是：**大多数锁从头到尾只有一个线程在用**，那就连 CAS 都省了，把线程 ID 直接记在对象头里。
**为什么废弃？** 维护成本极高（撤销偏向锁要走安全点），而且在真实应用里**竞争普遍存在**，偏向锁带来的收益远不如它的维护代价，**低并发场景反而更慢**。JDK 15 起默认关闭。

**⑨ 四种常见 OOM，看报错信息秒判**：

| 报错信息 | 原因 | 排查方向 |
|---|---|---|
| `Java heap space` | 堆满了 / 内存泄漏 | dump 堆，MAT 看支配树 |
| `Metaspace` | 加载的类太多 | 检查热部署、CGLib 动态代理、反射生成类 |
| `unable to create native thread` | 线程数超系统 limit | 检查线程池是否无界创建；调 `ulimit -u` 或减小 `-Xss` 栈大小 |
| `Direct buffer memory` | NIO 堆外内存耗尽 | 检查 Netty 等框架的堆外缓冲区；调 `-XX:MaxDirectMemorySize` |
