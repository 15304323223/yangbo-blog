# 接口幂等设计与防重实战（从前端到后端，从HTTP到MQ）

> **一句话概括**：幂等就是「同一个请求，执行一次和执行一百次，结果一样」。用户重复点击、网络重试、MQ 重复消费，都会导致重复执行——幂等不是「要不要做」的问题，而是「怎么做」的问题。
>
> **适合谁**：遇到过用户重复下单、支付重复扣款、MQ 重复消费导致数据重复，面试被问「你们系统怎么做幂等」答不出具体方案的人。

---

## 零、先建立印象：把它想象成「自动取款机」

你去 ATM 取钱，网络卡了，你点了两次「确认取款」。好的 ATM 会只吐一次钱——这就是幂等。

| 场景 | 不做幂等的后果 | 幂等方案 |
|---|---|---|
| 用户重复点击提交订单 | 生成多个订单 | 前端按钮置灰 + 后端防重 Token |
| 网络超时客户端重试 | 重复扣款、重复下单 | 唯一请求 ID + 状态机 |
| MQ 重复消费 | 数据重复插入 | 消费记录表 + 唯一索引 |
| 定时任务重复执行 | 重复发消息、重复统计 | 分布式锁 |
| 第三方回调重复通知 | 重复处理 | 回调记录表 + 状态判断 |

## 一、原理篇：什么是幂等？哪些操作天然幂等？

```
幂等 = f(x) = f(f(x)) = f(f(f(x))) ...
同一个输入，执行多少次结果都一样。
```

**HTTP 方法的幂等性：**
| 方法 | 幂等？ | 说明 |
|---|---|---|
| GET | ✅ 天然幂等 | 查询，不改变数据 |
| PUT | ✅ 天然幂等 | 全量替换，替换多少次结果一样 |
| DELETE | ✅ 天然幂等 | 删除，删一次和删一百次结果都是「不存在」 |
| POST | ❌ 非幂等 | 新增，每次都会创建新数据 |
| PATCH | ⚠️ 不一定 | 部分更新，取决于实现 |

> 💡 **醍醐灌顶**：不是所有接口都需要做幂等。GET/PUT/DELETE 天然幂等，只有 POST（新增）和部分 PATCH 需要额外处理。但现实中，很多人把更新也写成 POST，这就需要注意了。

## 二、方案一：前端防重（第一道防线，最简单）

### 2.1 按钮置灰 + Loading

```javascript
// 提交按钮点击后置灰，请求返回后恢复
async function submitOrder() {
    const btn = document.getElementById('submitBtn');
    btn.disabled = true;
    btn.innerText = '提交中...';
    try {
        await api.submitOrder(orderData);
        alert('提交成功');
    } finally {
        btn.disabled = false;
        btn.innerText = '提交订单';
    }
}
```

### 2.2 防抖（Debounce）

```javascript
// 300ms 内多次点击只执行最后一次
function debounce(fn, delay = 300) {
    let timer = null;
    return function(...args) {
        clearTimeout(timer);
        timer = setTimeout(() => fn.apply(this, args), delay);
    };
}
```

> ⚠️ **前端防重只是「防君子不防小人」**：用户可以用 Postman 直接调接口、可以刷新页面重发、可以抓包重放。所以后端幂等才是根本。

## 三、方案二：唯一请求 ID + Redis 防重（最常用，通用方案）

### 3.1 原理

```
1. 进入页面时，后端生成一个唯一 Token，返回给前端
2. 前端提交请求时，把这个 Token 放在 Header 里
3. 后端收到请求，用 Redis SETNX 判断这个 Token 是否已经被使用过
   - 没使用过：标记为已使用，执行业务
   - 已使用过：直接返回「请勿重复提交」
```

### 3.2 代码实现

```java
// 1. 生成防重 Token 的接口
@GetMapping("/token")
public Result<String> getToken() {
    String token = UUID.randomUUID().toString();
    // 存入 Redis，5分钟过期
    redisTemplate.opsForValue().set("idempotent:token:" + token, "1", 5, TimeUnit.MINUTES);
    return Result.success(token);
}

// 2. 提交接口，校验 Token
@PostMapping("/order/submit")
public Result submitOrder(@RequestHeader("Idempotent-Token") String token,
                          @RequestBody OrderDTO order) {
    // 用 Lua 脚本原子判断并删除 Token
    String lua = "if redis.call('get', KEYS[1]) then " +
                 "  redis.call('del', KEYS[1]) return 1 " +
                 "else return 0 end";
    Long result = redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class),
            Collections.singletonList("idempotent:token:" + token));

    if (result == 0) {
        return Result.error("请勿重复提交");
    }

    // 执行业务
    orderService.createOrder(order);
    return Result.success();
}
```

> ⚠️ **为什么用 Lua 脚本？** `get` 和 `del` 必须原子执行。如果 get 之后、del 之前又来一个请求，两个请求都会判断为「未使用」，就失效了。

### 3.3 注解化封装（优雅写法）

```java
// 自定义注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    String value() default "";  // 业务标识
    long expire() default 300;  // 过期时间，秒
}

// AOP 切面
@Aspect
@Component
public class IdempotentAspect {
    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    @Around("@annotation(idempotent)")
    public Object around(ProceedingJoinPoint point, Idempotent idempotent) throws Throwable {
        HttpServletRequest request = ((ServletRequestAttributes) RequestContextHolder.getRequestAttributes()).getRequest();
        String token = request.getHeader("Idempotent-Token");
        String key = "idempotent:" + idempotent.value() + ":" + token;

        String lua = "if redis.call('get', KEYS[1]) then redis.call('del', KEYS[1]) return 1 else return 0 end";
        Long result = redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class),
                Collections.singletonList(key));

        if (result == 0) {
            throw new BusinessException("请勿重复提交");
        }
        return point.proceed();
    }
}

// 使用
@Idempotent("orderSubmit")
@PostMapping("/order/submit")
public Result submitOrder(@RequestBody OrderDTO order) {
    orderService.createOrder(order);
    return Result.success();
}
```

## 四、方案三：数据库唯一索引（最可靠，适合新增操作）

### 4.1 原理

利用数据库唯一索引，重复插入会抛 `DuplicateKeyException`，捕获后直接返回成功。

```sql
-- 订单表，用户ID + 商品ID + 日期 作为唯一键，防止同一天重复下单
CREATE TABLE `order` (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    order_date DATE NOT NULL,
    -- 唯一索引：同一个用户同一天同一个商品只能下一单
    UNIQUE KEY uk_user_product_date (user_id, product_id, order_date)
);
```

```java
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    // 唯一索引冲突，说明已经下过单了，直接返回成功
    log.warn("重复下单，user_id={}, product_id={}", order.getUserId(), order.getProductId());
    return Result.success("下单成功");
}
```

### 4.2 适用场景

| 场景 | 唯一键设计 |
|---|---|
| 防止重复注册 | 手机号 / 邮箱 唯一索引 |
| 防止重复下单 | 用户ID + 商品ID + 日期 |
| 防止重复支付 | 订单ID 唯一（一个订单只能支付一次） |
| MQ 防重复消费 | 消息ID 唯一索引 |

> 💡 **唯一索引是幂等的「最后一道防线」**：即使前面的 Redis 防重失效了，数据库唯一索引也能保证数据不重复。生产环境建议「Redis 防重 + 数据库唯一索引」双保险。

## 五、方案四：状态机（适合有状态流转的业务）

### 5.1 原理

很多业务都有状态流转：订单（待支付→已支付→已发货→已完成）、支付（待支付→支付中→已支付→已退款）。

**只有特定状态才能执行特定操作**，状态不匹配直接拒绝。

```sql
-- 支付：只有「待支付」状态才能支付，支付成功后改为「已支付」
UPDATE payment
SET status = 'PAID', pay_time = NOW()
WHERE id = #{paymentId} AND status = 'UNPAID';
-- 影响行数为 0，说明状态不对，要么已经支付了，要么订单不存在
```

```java
int rows = paymentMapper.pay(paymentId);
if (rows == 0) {
    // 可能是重复支付，查询当前状态
    Payment payment = paymentMapper.selectById(paymentId);
    if ("PAID".equals(payment.getStatus())) {
        return Result.success("支付成功"); // 已经支付过了，返回成功
    }
    throw new BusinessException("支付失败，订单状态异常");
}
```

### 5.2 状态机的核心思想

```
不是「先查状态，再更新」，而是「更新时带状态条件」
—— 查和更必须是原子的，否则并发下会出问题。
```

> ⚠️ **经典 Bug**：先 SELECT 查状态，如果是待支付就 UPDATE。两个请求同时 SELECT 都查到「待支付」，然后都 UPDATE，就重复支付了。正确做法是 UPDATE 时带 WHERE status = 'UNPAID'，靠数据库行锁保证原子性。

## 六、方案五：MQ 消费幂等（消息队列必做）

### 6.1 为什么 MQ 一定会重复消费？

```
1. 生产者重试：网络超时，生产者重发消息
2. Broker 重试：消费者处理超时，Broker 重新投递
3. 消费者 Rebalance：消费者重启，offset 还没提交，重新消费
4. 人工补偿：运维手动重发消息
```

> 💡 **MQ 的 At-Least-Once 语义决定了：消息至少会被消费一次，可能多次。所以消费端必须做幂等。**

### 6.2 方案 A：消费记录表 + 唯一索引

```sql
-- 消息消费记录表
CREATE TABLE mq_consume_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    msg_id VARCHAR(128) NOT NULL COMMENT '消息唯一ID',
    biz_type VARCHAR(64) NOT NULL COMMENT '业务类型',
    consume_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_msg_type (msg_id, biz_type)
);
```

```java
@RabbitListener(queues = "order.pay.queue")
public void handlePayMessage(Message message) {
    String msgId = message.getMessageProperties().getMessageId();
    String bizType = "orderPay";

    try {
        // 插入消费记录，唯一索引冲突说明已经消费过
        consumeLogMapper.insert(new MqConsumeLog(msgId, bizType));
    } catch (DuplicateKeyException e) {
        log.warn("消息重复消费，msgId={}", msgId);
        return; // 直接返回，不处理
    }

    // 执行业务逻辑
    doBusiness(message);
}
```

### 6.3 方案 B：业务表自带唯一键（更优雅）

如果业务表本身就有唯一键（比如订单号），不需要额外的消费记录表：

```java
@RabbitListener(queues = "order.create.queue")
public void handleCreateOrder(OrderMessage msg) {
    try {
        orderMapper.insert(buildOrder(msg));
    } catch (DuplicateKeyException e) {
        // 订单号唯一索引冲突，说明已经创建过了
        log.warn("订单重复创建，orderNo={}", msg.getOrderNo());
        return;
    }
}
```

## 七、方案对比与选型

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 前端防重 | 简单，用户体验好 | 防不住接口重放 | 所有表单提交 |
| Redis Token 防重 | 通用，性能好 | Redis 宕机可能失效 | 新增类接口 |
| 数据库唯一索引 | 最可靠，持久化 | 只能防重复插入 | 新增操作、MQ消费 |
| 状态机 | 天然幂等，性能好 | 只适合有状态的业务 | 订单、支付、审批 |
| 乐观锁（版本号） | 适合并发更新 | 有冲突概率，需重试 | 库存扣减、余额更新 |

**生产推荐组合：**
```
新增操作：前端防重 + Redis Token + 数据库唯一索引
更新操作：状态机 / 乐观锁
MQ 消费：消费记录表 + 唯一索引 / 业务表唯一键
```

## 八、面试口述总结

> **什么是幂等？**
> 同一个请求执行一次和执行多次结果一样。用户重复点击、网络重试、MQ 重复消费都会导致重复执行。
>
> **你们怎么做幂等？**
> 分场景：新增操作用「Redis 防重 Token + 数据库唯一索引」双保险；有状态流转的业务（订单支付）用状态机，UPDATE 时带状态条件；MQ 消费用消费记录表+唯一索引，或者业务表自带唯一键。
>
> **Redis 防重 Token 怎么实现？**
> 进入页面时后端生成 Token 存 Redis，提交时前端带 Token，后端用 Lua 脚本原子判断并删除 Token。判断和删除必须原子，否则并发下会失效。
>
> **状态机幂等要注意什么？**
> 不能「先查再更」，要「更新时带状态条件」。先查再更在并发下两个请求都能查到旧状态，导致重复执行。UPDATE ... WHERE status = 'xxx' 靠数据库行锁保证原子性。
>
> **MQ 为什么一定要做幂等？**
> MQ 是 At-Least-Once 语义，消息至少消费一次。生产者重试、Broker 超时重投、消费者 Rebalance 都会导致重复消费。
