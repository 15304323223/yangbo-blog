# Java 8 / 17 / 21 特性全解（三个 LTS 版本，从语法糖到虚拟线程）

> **一句话概括**：Java 8 是「**函数式革命**」（Lambda + Stream），Java 17 是「**语法舒适化**」（record + 文本块 + 模式匹配），Java 21 是「**并发模型革命**」（虚拟线程）。这三个版本是当前企业开发的「三代同堂」，也是面试与升级迁移的必考点。
>
> **适合谁**：还在用 Java 8 写 `for` 循环遍历集合、听说过 `record` 但说不清它和普通类有啥区别、被问「虚拟线程解决了什么问题」只能答「线程变轻了」、准备从 8 升级到 17/21 但不知道会踩哪些坑的人。
> **怎么读**：**零（建立印象）→ 一（Java 8）→ 二（9~16 过渡）→ 三（Java 17）→ 四（Java 21）→ 五（三版对比速查）→ 六（升级迁移）→ 七（踩坑）→ 八（动手路线）**。
> 如果你只用过 Java 8，**第三章和第四章是重点**；如果准备升级，**第六章先看**。

## 零、先建立整体印象：把 Java 版本演进想象成「手机系统大版本升级」

### 0.1 为什么只盯 LTS（长期支持版）

Java 从 Java 9 开始改成**每 6 个月发一版**，但绝大多数版本**只支持半年**，企业根本不敢用。真正值得投入的是 **LTS（Long-Term Support，长期支持版）**：

| 版本 | 发布时间 | 类型 | 一句话定位 | 现状 |
|---|---|---|---|---|
| **Java 8** | 2014-03 | **LTS** | **函数式革命**：Lambda + Stream | 仍是存量项目主力（Oracle 商业支持已结束，但生态仍广） |
| Java 11 | 2018-09 | **LTS** | 过渡版：HttpClient、String 增强 | 不少项目的「中间站」 |
| **Java 17** | 2021-09 | **LTS** | **语法舒适化**：record / 文本块 / 模式匹配 | ⭐ **当前企业升级的首选目标** |
| **Java 21** | 2023-09 | **LTS** | **并发革命**：虚拟线程 | ⭐ **新项目的推荐版本** |
| Java 25 | 2025-09 | **LTS** | 最新 LTS | 前沿项目 |

> 💡 **一句话决策**：
> - **存量项目** → 优先升到 **17**（生态最成熟，Spring Boot 3 的最低要求）
> - **新项目** → 直接上 **21**（虚拟线程能显著提升 IO 密集型吞吐）
> - **还在 8** → 至少规划升到 17（**Spring Boot 3 / Spring Cloud 2022+ 强制要求 JDK 17**）

### 0.2 三个版本的「性格」对比

| | Java 8 | Java 17 | Java 21 |
|---|---|---|---|
| 核心关键词 | **Lambda / Stream** | **record / 文本块 / 模式匹配** | **虚拟线程 / 结构化并发** |
| 解决的核心痛点 | 集合操作太啰嗦、回调地狱 | 样板代码太多、类型判断太繁琐 | **线程太贵，高并发 IO 撑不住** |
| 写代码的体感 | 「终于能像函数式语言一样写」 | 「终于不用写一堆 getter/setter 了」 | 「终于能一个请求一个线程了」 |
| 类比 | 给自行车装上变速器 | 把手动挡换成自动挡 | 把「一个司机一台车」变成「一个司机能开一百台车」 |

## 一、Java 8 特性（2014）——函数式革命

> Java 8 是 Java 历史上**最大的一次语言变革**。哪怕你现在用 17/21，日常写的代码里 80% 的「现代感」都来自 Java 8。

### 1.1 Lambda 表达式：把「行为」当参数传

**没有 Lambda 之前**（匿名内部类，啰嗦）：

```java
// 想给按钮加个点击事件，得写一大堆样板代码
button.addActionListener(new ActionListener() {
    @Override
    public void actionPerformed(ActionEvent e) {
        System.out.println("按钮被点击了");
    }
});
```

**有了 Lambda 之后**：

```java
button.addActionListener(e -> System.out.println("按钮被点击了"));
```

**类比**：以前你想让同事「帮我带杯咖啡」，得先**写一份正式的委托书**（定义一个类、实现接口、写方法）；Lambda 让你**直接开口说**（「带杯咖啡」）——**省掉了「包装」的过程**。

**Lambda 的语法**：

```java
// 完整形式：  (参数列表) -> { 方法体 }
(int a, int b) -> { return a + b; }

// 省略参数类型（编译器能推断）：  (a, b) -> { return a + b; }
// 单表达式可省略 return 和花括号：  (a, b) -> a + b
// 单参数可省略括号：                x -> x * 2
// 无参数：                          () -> System.out.println("hi")
```

> ⚠️ **关键限制**：Lambda 只能用于**函数式接口**（只有一个抽象方法的接口）。这也是为什么 Java 8 同时引入了 `@FunctionalInterface`。

### 1.2 函数式接口：Lambda 的「容器」

**函数式接口 = 只有一个抽象方法的接口**。Java 8 内置了四大核心函数式接口：

| 接口 | 签名 | 含义 | 典型用途 |
|---|---|---|---|
| **`Function<T,R>`** | `R apply(T t)` | **有入有出**（转换） | `String::length` |
| **`Consumer<T>`** | `void accept(T t)` | **有入无出**（消费） | `list.forEach(System.out::println)` |
| **`Supplier<T>`** | `T get()` | **无入有出**（生产） | `() -> new User()` |
| **`Predicate<T>`** | `boolean test(T t)` | **有入有布尔**（判断） | `x -> x > 0` |

**记忆法**：
```
Function   → 函数：输入 x，输出 y          （转换）
Consumer   → 消费者：只吃不吐              （消费）
Supplier   → 供应商：只吐不吃              （生产）
Predicate  → 判定器：输入一个值，回答 是/否  （判断）
```

**其他常用**：`BiFunction`（两入一出）、`UnaryOperator`（一入一出，同类型）、`BinaryOperator`（两入一出，同类型）、`IntFunction` 等原始类型特化版本（避免装箱）。

**自定义函数式接口**：

```java
@FunctionalInterface          // ⭐ 加这个注解，编译器会检查「是否只有一个抽象方法」
public interface OrderHandler {
    void handle(Order order);  // 唯一的抽象方法

    // 可以有不限数量的 default / static 方法（不算抽象方法）
    default void log(String msg) { System.out.println(msg); }
}
```

### 1.3 Stream API：集合操作的「流水线」

**类比**：Stream 就像**工厂流水线**——原料（集合）从一端进去，经过一道道工序（filter → map → sorted），成品从另一端出来。**每道工序只关心自己那一步，不关心上下游。**

**对比：传统写法 vs Stream**

```java
// ❌ 传统写法：想拿到「年龄 > 18 的用户名，按年龄排序」
List<String> names = new ArrayList<>();
for (User u : users) {                       // ① 遍历
    if (u.getAge() > 18) {                   // ② 过滤
        names.add(u.getName());              // ③ 提取
    }
}
Collections.sort(names);                     // ④ 排序（还得另起一行）
```

```java
// ✅ Stream 写法：一条链读完，意图一眼可见
List<String> names = users.stream()
    .filter(u -> u.getAge() > 18)   // 过滤：留下年龄 > 18 的
    .map(User::getName)             // 映射：User → 用户名
    .sorted()                       // 排序
    .collect(Collectors.toList());  // 收集成 List
```

**Stream 的三段结构**：

```
数据源 ──► 中间操作（惰性，可 0~N 个）──► 终止操作（触发执行，必须 1 个）
stream()   filter / map / sorted /        collect / forEach /
           distinct / limit / skip         count / reduce / anyMatch
```

> ⚠️ **最重要的两个概念**：
> 1. **惰性求值**：**没有终止操作，中间操作一行都不会执行**。所以 `stream().filter(...)` 单独写是没有任何效果的。
> 2. **流不可复用**：一个 Stream 只能消费一次，用完再 `stream()` 拿新的。

**高频操作速查**：

| 操作 | 作用 | 示例 |
|---|---|---|
| `filter` | 过滤 | `.filter(u -> u.getAge() > 18)` |
| `map` | 转换 | `.map(User::getName)` |
| `flatMap` | **扁平化**（把嵌套集合摊平） | `.flatMap(o -> o.getItems().stream())` |
| `distinct` | 去重（靠 equals/hashCode） | `.distinct()` |
| `sorted` | 排序 | `.sorted(Comparator.comparing(User::getAge))` |
| `limit` / `skip` | 取前 N / 跳过前 N | `.limit(10)` |
| `collect` | 收集 | `.collect(Collectors.toList())` |
| `reduce` | 归约（合并成一个值） | `.reduce(0, Integer::sum)` |
| `groupingBy` | **分组**（返回 Map） | `.collect(Collectors.groupingBy(User::getCity))` |
| `toMap` | 转 Map | `.collect(Collectors.toMap(User::getId, u -> u))` |
| `anyMatch` / `allMatch` / `noneMatch` | 短路判断 | `.anyMatch(u -> u.isVip())` |
| `findFirst` / `findAny` | 取一个 | `.findFirst().orElse(null)` |

**`Collectors` 最常用的几个**：

```java
// ① 分组：按城市分组
Map<String, List<User>> byCity = users.stream()
    .collect(Collectors.groupingBy(User::getCity));

// ② 分组 + 计数
Map<String, Long> countByCity = users.stream()
    .collect(Collectors.groupingBy(User::getCity, Collectors.counting()));

// ③ 分组 + 取某个字段的集合
Map<String, List<String>> namesByCity = users.stream()
    .collect(Collectors.groupingBy(User::getCity,
             Collectors.mapping(User::getName, Collectors.toList())));

// ④ 转 Map（⚠️ key 重复会抛 IllegalStateException，必须给合并函数）
Map<Long, User> userMap = users.stream()
    .collect(Collectors.toMap(User::getId, u -> u, (a, b) -> a));  // (a,b)->a = 冲突时保留先出现的

// ⑤ 分区：按条件分成 true/false 两组
Map<Boolean, List<User>> partition = users.stream()
    .collect(Collectors.partitioningBy(u -> u.getAge() >= 18));

// ⑥ 拼接字符串
String names = users.stream().map(User::getName).collect(Collectors.joining(", ", "[", "]"));
```

> ⚠️ **`Collectors.toMap` 的经典坑**：**value 为 null 会抛 NPE**（`HashMap.merge` 不允许 null value）。如果 value 可能为 null，要么先过滤，要么手动 `forEach` 组装。

**并行流（`parallelStream`）——不要乱用**：

```java
list.parallelStream().filter(...).collect(...)   // 底层用 ForkJoinPool.commonPool()
```

> ⚠️ **并行流三大坑**：
> 1. **共用 commonPool**（默认线程数 = CPU 核数 - 1），**一个地方用慢 IO 阻塞，会拖垮全应用的并行流**；
> 2. **数据量小的时候更慢**（拆分 + 合并的开销 > 收益），一般**要十万级以上元素才值得考虑**；
> 3. **有状态/顺序敏感的操作会出错**（如 `forEach` 里累加共享变量）。
> ✅ **结论：默认用串行流；确实要并行，优先用自定义线程池 + `CompletableFuture`。**

### 1.4 方法引用：Lambda 的「进一步简写」

**当 Lambda 体只是「调用一个已有方法」时，可以再简化**：

| 类型 | 语法 | 例子 | 等价 Lambda |
|---|---|---|---|
| **静态方法引用** | `类::静态方法` | `Integer::parseInt` | `s -> Integer.parseInt(s)` |
| **实例方法引用**（特定对象） | `对象::方法` | `System.out::println` | `x -> System.out.println(x)` |
| **实例方法引用**（任意对象） | `类::实例方法` | `String::length` | `s -> s.length()` |
| **构造器引用** | `类::new` | `User::new` | `() -> new User()` |
| **数组构造器引用** | `类型[]::new` | `String[]::new` | `n -> new String[n]` |

**记忆法**：**「能省则省」**——只要参数能一一对应上，就能用方法引用。

### 1.5 `Optional`：把「可能为空」写进类型里

**问题**：`user.getAddress().getCity()` —— 中间任何一环为 null，就抛 NPE。

**解法**：用 `Optional` **显式表达「这个值可能不存在」**，强迫调用方处理。

```java
// ① 创建
Optional<User> opt = Optional.of(user);          // user 不能为 null（为 null 直接抛 NPE）
Optional<User> opt2 = Optional.ofNullable(user); // user 可以为 null ⭐ 最常用
Optional<User> empty = Optional.empty();         // 一个空 Optional

// ② 取值（安全）
String name = opt.map(User::getName)   // 有值才映射
                .orElse("匿名用户");    // 为空时给默认值
String name2 = opt.map(User::getName).orElseGet(() -> loadFromDb());  // 惰性求值版
String name3 = opt.map(User::getName).orElseThrow(() -> new BizException("用户不存在"));

// ③ 判断与消费
opt.isPresent();                       // 是否有值（❌ 不推荐这样用）
opt.ifPresent(u -> System.out.println(u.getName()));   // 有值才执行 ⭐
opt.ifPresentOrElse(                   // Java 9+
    u -> System.out.println("有值"),
    () -> System.out.println("没值")
);
```

> ⚠️ **`Optional` 的三个反模式**：
> 1. **`optional.get()` 直接用** → 没值时抛 `NoSuchElementException`，等于白用；
> 2. **`if (opt.isPresent()) { opt.get() }`** → 这是「穿着 Optional 外衣的 null 判断」，没体现价值；
> 3. **`Optional` 当字段/方法参数** → **设计初衷只用于「方法返回值」**。字段用 `Optional` 会**不可序列化**（很多序列化框架会炸）。
> ✅ **正确姿势**：`Optional` 只做**返回值**，链式 `map` + `orElse`，别 `get()`。

### 1.6 接口的 `default` / `static` 方法

**问题**：接口加一个新方法，所有实现类都得改（破坏兼容性）。

**解法**：`default` 方法——**接口可以给方法提供默认实现**。

```java
public interface Notifier {
    void send(String msg);                       // 抽象方法：实现类必须实现

    default void sendWithRetry(String msg) {     // default 方法：实现类可不重写
        for (int i = 0; i < 3; i++) {
            try { send(msg); return; }
            catch (Exception e) { /* 重试 */ }
        }
    }

    static Notifier sms() {                      // static 方法：通过接口名调用
        return msg -> System.out.println("短信：" + msg);
    }
}
```

> 💡 **这就是 Java 8 能在不破坏兼容性的前提下，给 `Collection` 加上 `stream()` / `forEach()` 的原因**。
> ⚠️ **菱形继承冲突**：如果一个类实现的**两个接口都有同签名的 default 方法**，编译器会强制要求你**显式重写**并指明用哪个（`InterfaceA.super.method()`）。

### 1.7 新日期时间 API（`java.time`）

**老 API（`Date` / `Calendar`）的三宗罪**：可变（线程不安全）、月份从 0 开始（反人类）、格式化线程不安全（`SimpleDateFormat`）。

```java
// ① 本地日期时间（不带时区）
LocalDate date = LocalDate.now();                       // 2026-09-12
LocalTime time = LocalTime.now();                       // 14:30:00
LocalDateTime dt = LocalDateTime.of(2026, 9, 12, 14, 30);

// ② 计算（不可变，每次返回新对象 ⭐ 线程安全）
LocalDate tomorrow = date.plusDays(1);
LocalDate lastMonth = date.minusMonths(1);
boolean isBefore = date.isBefore(tomorrow);

// ③ 格式化 / 解析（DateTimeFormatter 是【不可变且线程安全】的，可做静态常量）
DateTimeFormatter fmt = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
String s = dt.format(fmt);                              // 格式化
LocalDateTime parsed = LocalDateTime.parse("2026-09-12 14:30:00", fmt);

// ④ 时区
ZonedDateTime bj = ZonedDateTime.now(ZoneId.of("Asia/Shanghai"));
Instant instant = Instant.now();                        // UTC 时间戳（机器用）

// ⑤ 时间差
Duration d = Duration.between(start, end);              // 两个时刻的间隔（时分秒）
Period p = Period.between(LocalDate.of(2020,1,1), LocalDate.now());  // 两个日期的间隔（年月日）
long days = ChronoUnit.DAYS.between(startDate, endDate);
```

> ⚠️ **注意**：`LocalDateTime` **不带时区信息**，跨时区系统交互时要用 `ZonedDateTime` 或 `Instant`，否则会出现「差 8 小时」的经典事故。

### 1.8 `CompletableFuture`：异步编排

**问题**：`Future.get()` 是**阻塞**的，且不能组合多个异步任务。

```java
// ① 创建异步任务
CompletableFuture<User> f1 = CompletableFuture.supplyAsync(() -> queryUser(id));
CompletableFuture<Order> f2 = CompletableFuture.supplyAsync(() -> queryOrder(id));

// ② 串联（上一个的结果作为下一个的输入）
CompletableFuture<String> f3 = f1.thenApply(User::getName)
                                  .thenApply(String::toUpperCase);

// ③ 组合两个任务（都完成后再合并）
CompletableFuture<String> f4 = f1.thenCombine(f2,
        (user, order) -> user.getName() + " 的订单数：" + order.getCount());

// ④ 异常处理（否则异常会被「吞掉」）
CompletableFuture<String> f5 = f1.exceptionally(ex -> "查询失败：" + ex.getMessage())
                                 .thenApply(String::toUpperCase);

// ⑤ 等待全部完成 / 任一完成
CompletableFuture.allOf(f1, f2).join();     // 全部完成（join 不抛受检异常）
CompletableFuture.anyOf(f1, f2).join();     // 任一完成
```

> ⚠️ **`CompletableFuture` 三大坑**：
> 1. **默认用 `ForkJoinPool.commonPool()`**（线程数 = CPU 核数 - 1）→ **IO 密集任务会把公共池占满，拖垮其他并行流**。✅ 生产环境**必须传自定义线程池**：`supplyAsync(task, myExecutor)`；
> 2. **不处理异常会被静默吞掉** → 必须加 `exceptionally` / `handle`；
> 3. **`get()` 会抛受检异常且阻塞** → 用 `join()` 或 `whenComplete`。

### 1.9 其他重要变化

| 特性 | 说明 |
|---|---|
| **`Metaspace` 取代 `PermGen`** | 永久代移到本地内存，不再受 `-XX:MaxPermSize` 限制（**JVM 面试高频**，见 [[02_JVM 原理与调优]]） |
| **`HashMap` 链表转红黑树** | 单桶链表长度 ≥ 8 且总容量 ≥ 64 时转红黑树，查询从 O(n) 降到 O(log n) |
| **`@Repeatable` 重复注解** | 同一个注解可以在一个位置写多次 |
| **类型注解** | 注解可以用在类型上（如 `@NonNull String`） |
| **`String.join`** | `String.join(",", list)` 一行搞定拼接 |
| **`Arrays.parallelSort`** | 并行排序（大数组更快） |
| **`Base64` 工具类** | `java.util.Base64` 替代 `sun.misc.BASE64Encoder` |

### 1.10 Java 8 踩坑清单

| 坑 | 说明 | 正确做法 |
|---|---|---|
| **Stream 忘记终止操作** | `stream().filter(...)` 什么都不会发生 | 必须加 `collect` / `forEach` / `count` |
| **Stream 重复使用** | `stream` 已消费，再操作抛 `IllegalStateException` | 每次重新 `stream()` |
| **`Collectors.toMap` value 为 null** | 抛 NPE | 先过滤 null，或手动组装 |
| **`Collectors.toMap` key 重复** | 抛 `IllegalStateException` | 必须给第三个参数（合并函数） |
| **`parallelStream` 里做 IO** | 占满 commonPool，拖垮全应用 | 用自定义线程池 |
| **`Optional.get()` 直接用** | 没值时抛异常 | 用 `orElse` / `ifPresent` |
| **`SimpleDateFormat` 当静态变量** | **线程不安全**，多线程下解析出错乱时间 | 用 `DateTimeFormatter` 或每次 new |
| **`CompletableFuture` 不传线程池** | 占满 commonPool | 传自定义 `Executor` |
| **`Arrays.asList()` 返回的 List 不可变** | `add` 会抛 `UnsupportedOperationException` | 用 `new ArrayList<>(Arrays.asList(...))` |

## 二、Java 9 ~ 16 过渡：为 17 铺路的变化

> 这些版本不是 LTS，但**其中的变化在 17 里成了正式特性**。**只需要记住「哪些东西是从哪来的」**，不用背版本号。

| 版本 | 值得知道的变化 | 现在状态 |
|---|---|---|
| **9** | **模块系统 JPMS**（`module-info.java`）、集合工厂 `List.of()` / `Map.of()`、接口私有方法、`Optional.ifPresentOrElse`、`Stream.takeWhile/dropWhile/ofNullable`、**G1 成为默认 GC** | 集合工厂 ⭐ 日常必用 |
| **10** | **`var` 局部变量类型推断**、不可变集合 `copyOf` | ⭐ 日常必用 |
| **11**（LTS） | **`HttpClient` 正式**（替代 `HttpURLConnection`）、`String` 增强（`isBlank` / `lines` / `strip` / `repeat`）、`Files.readString/writeString`、**单文件源码直接运行**（`java Hello.java`）、**ZGC 实验**、移除 Java EE 模块 | ⭐ 日常必用 |
| **12** | `Collectors.teeing`（一次流做两种归约）、`String.indent/transform` | 偶尔用 |
| **13** | 文本块**预览**、`switch` 表达式引入 `yield` | 被 15 转正 |
| **14** | **`switch` 表达式正式**、`record` 预览、`instanceof` 模式匹配预览、**增强的 NPE 提示** | 17 全部转正 |
| **15** | **文本块正式**、`sealed` 预览、ZGC 正式、移除 Nashorn | 17 全部转正 |
| **16** | **`record` 正式**、**`instanceof` 模式匹配正式**、`Stream.toList()`、强封装 JDK 内部 API | ⭐ 日常必用 |

**三个「从过渡版就值得马上用」的语法糖**：

```java
// ① 集合工厂（Java 9）：一行创建不可变集合 ⭐
List<String> list = List.of("a", "b", "c");        // 不可变（add 会抛异常）
Map<String, Integer> map = Map.of("a", 1, "b", 2); // 最多 10 组，超过用 Map.ofEntries
Set<String> set = Set.of("x", "y");

// ② var（Java 10）：局部变量类型推断 ⭐
var list = new ArrayList<String>();     // 编译器推断出 ArrayList<String>
var map = new HashMap<String, List<User>>();  // 右边太长的泛型，左边用 var 清爽很多
// ⚠️ var 只能用于【局部变量】，不能用于字段、方法参数、返回值

// ③ String 增强（Java 11）⭐
"  ".isBlank();                 // true（判断是否为空白，比 trim().isEmpty() 更准）
"a\nb\nc".lines().count();      // 3（按行切分成 Stream）
"  hi  ".strip();               // "hi"（比 trim 更懂 Unicode 空白）
"ab".repeat(3);                 // "ababab"
```

> ⚠️ **`List.of()` 的坑**：它返回的是**不可变集合**，`add` / `remove` / `set` 都会抛 `UnsupportedOperationException`；而且**不接受 null 元素**（`List.of(null)` 直接 NPE）。
> ✅ 需要可变就用 `new ArrayList<>(List.of(...))`。

**HttpClient（Java 11）——现代 HTTP 调用**：

```java
// ① 创建客户端（推荐复用，不要每次 new）
HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(5))
    .build();

// ② 构造请求
HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://api.example.com/users/1"))
    .header("Accept", "application/json")
    .GET()
    .build();

// ③ 同步发送
HttpResponse<String> resp = client.send(request, HttpResponse.BodyHandlers.ofString());
System.out.println(resp.statusCode() + " " + resp.body());

// ④ 异步发送（返回 CompletableFuture）
client.sendAsync(request, HttpResponse.BodyHandlers.ofString())
      .thenApply(HttpResponse::body)
      .thenAccept(System.out::println);
```

> 💡 **`HttpClient` 支持 HTTP/2、连接池、异步、WebSocket**，是 `HttpURLConnection` 的现代替代。不过实际项目里通常还是用 **Feign / RestTemplate / WebClient / Hutool HttpUtil**（见 [[14_微服务 SpringCloud 与 Dubbo]]）。

## 三、Java 17 特性（2021 LTS）——语法舒适化

> 17 的核心价值：**把 9~16 里那些「预览」了多年的好特性全部转正**，并且是 **Spring Boot 3 / Spring Framework 6 的最低要求**。

### 3.1 文本块（Text Blocks）：多行字符串不再拼接

**以前写 SQL / JSON**：

```java
// ❌ 拼接地狱：换行要 \n，引号要转义，缩进全靠手调
String sql = "SELECT id, name, age\n" +
             "FROM user\n" +
             "WHERE age > 18\n" +
             "  AND city = '北京'\n" +
             "ORDER BY age DESC";
```

**现在**：

```java
// ✅ 文本块：三个双引号开头，原样书写
String sql = """
        SELECT id, name, age
        FROM user
        WHERE age > 18
          AND city = '北京'
        ORDER BY age DESC
        """;
```

**文本块的三个关键规则**：

| 规则 | 说明 |
|---|---|
| **起始 `"""` 后必须换行** | `"""abc` 是语法错误 |
| **自动去除「公共缩进」** | 以所有行中**缩进最少的那一行**为基准，整体左移（所以上面 `SELECT` 前面没有多余空格） |
| **结尾 `"""` 的位置决定是否保留末尾换行** | `"""` 与内容同行 → 不保留末尾换行；`"""` 独占一行 → 保留 |

**两个实用技巧**：

```java
// ① 用 \ 取消换行（长字符串想换行书写但不要换行符）
String longLine = """
        这是一段很长的文字，\
        但我希望它们连成一行""";
// 结果："这是一段很长的文字，但我希望它们连成一行"

// ② 用 \s 保留行尾空格（默认行尾空格会被去掉）
String s = """
        abc   \s
        def""";
```

> 💡 **最适合用文本块的场景**：**SQL、JSON、HTML、多行日志模板、测试数据**。

### 3.2 `record`：一行搞定不可变数据类 ⭐

**以前写一个 DTO**（或 Lombok 之前的写法）：

```java
// ❌ 传统写法：60 行样板代码
public class UserDTO {
    private final Long id;
    private final String name;
    private final Integer age;

    public UserDTO(Long id, String name, Integer age) {
        this.id = id; this.name = name; this.age = age;
    }
    public Long getId() { return id; }
    public String getName() { return name; }
    public Integer getAge() { return age; }

    @Override public boolean equals(Object o) { /* ...10 行... */ }
    @Override public int hashCode() { /* ...5 行... */ }
    @Override public String toString() { /* ...5 行... */ }
}
```

**现在**：

```java
// ✅ record 一行搞定
public record UserDTO(Long id, String name, Integer age) {}
```

**编译器自动生成的 5 样东西**：构造器、访问器（`id()` 而非 `getId()`）、`equals`、`hashCode`、`toString`。

**`record` 的本质与限制**：

| 特性 | 说明 |
|---|---|
| 是**不可变**的 | 所有字段隐式 `private final`，**没有 setter** |
| 隐式继承 `java.lang.Record` | 所以**不能继承其他类**（但可以实现接口） |
| 可以定义额外方法 | 但不能定义额外**实例字段** |
| 可以自定义构造器 | **紧凑构造器**用于参数校验 |

**紧凑构造器（做参数校验）**：

```java
public record UserDTO(Long id, String name, Integer age) {
    // 紧凑构造器：不写参数列表，校验逻辑写在这里
    public UserDTO {
        if (age != null && age < 0) {
            throw new IllegalArgumentException("年龄不能为负");
        }
        // 赋值由编译器自动完成（不用写 this.age = age）
    }

    // 可以加额外方法
    public boolean isAdult() {
        return age != null && age >= 18;
    }

    // 静态工厂方法
    public static UserDTO of(String name) {
        return new UserDTO(null, name, null);
    }
}
```

**`record` 最常用的四个场景**：

| 场景 | 示例 |
|---|---|
| **DTO / VO**（接口出入参） | `record UserVO(Long id, String name) {}` |
| **多返回值** | `record Result(int code, String msg) {}` 替代 `Map` 或自定义类 |
| **复合 Map 的 key** | `record Point(int x, int y) {}` —— equals/hashCode 自动生成，可安全做 key |
| **模式匹配的解构**（配合 Java 21） | `if (obj instanceof Point(int x, int y)) { ... }` |

> ⚠️ **`record` 的四个坑**：
> 1. **访问器是 `name()` 不是 `getName()`** → **Jackson 序列化默认认不出**（Spring Boot 3 用的 Jackson 2.15+ 已支持，但老版本要加 `@JsonProperty` 或用 `-parameters` 编译）；
> 2. **JPA 实体不能用 record**（Hibernate 需要无参构造 + 可变字段）；
> 3. **不能继承**，也不能被继承（是 final 的）；
> 4. **字段仍然可以被「反射」改**（`final` 不是绝对安全），只是没有公开的修改入口。

### 3.3 `sealed` 密封类：精确控制「谁能继承我」

**问题**：`public class Animal` 谁都能继承，你无法穷举所有子类，也就无法写出「完备」的判断逻辑。

```java
// ✅ sealed：明确列出允许继承的子类
public sealed interface Shape permits Circle, Rectangle, Triangle {}

// 子类必须是 final / sealed / non-sealed 三者之一
public final class Circle implements Shape {}          // final：不能再被继承
public final class Rectangle implements Shape {}
public final class Triangle implements Shape {}
```

**三个关键字的关系**：

| 关键字 | 含义 |
|---|---|
| `sealed` | **我允许指定的类继承我**（`permits` 列出白名单） |
| `final` | **到此为止**，不能再被继承 |
| `non-sealed` | **重新开放**，我的子类可以被任意继承 |
| `permits` | 白名单（**如果子类和父类在同一文件里，可以省略**） |

**为什么 `sealed` 重要？** —— 它是**模式匹配「穷举检查」的前提**：

```java
// 因为 Shape 的子类只有三个（编译器知道），所以 switch 可以检查「是否覆盖全部」
double area = switch (shape) {
    case Circle c    -> Math.PI * c.radius() * c.radius();
    case Rectangle r -> r.width() * r.height();
    case Triangle t  -> t.base() * t.height() / 2;
    // 不需要 default！因为编译器能证明三种情况已覆盖
};
```

> 💡 **类比**：`sealed` 就像**家族信托的受益人名单**——只有名单上的人能继承，其他人一律不行。这样「处理这笔遗产」的逻辑就能**穷举所有可能**，不会漏。

### 3.4 `switch` 表达式（正式）：从「语句」变成「表达式」

**老 `switch` 的三大痛点**：会穿透（忘写 `break`）、不能返回值、不能穷举检查。

```java
// ❌ 老写法：必须写 break，忘了就穿透；还得先声明变量
String type;
switch (day) {
    case MONDAY:
    case TUESDAY:
        type = "工作日"; break;      // ⚠️ 忘写 break 就会继续往下执行
    case SATURDAY:
    case SUNDAY:
        type = "周末"; break;
    default:
        type = "未知";
}

// ✅ 新写法：箭头语法 + 直接返回值
String type = switch (day) {
    case MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY -> "工作日";   // 多个值用逗号
    case SATURDAY, SUNDAY -> "周末";
    default -> "未知";
};
```

**需要写多行逻辑时用 `yield`**：

```java
int numLetters = switch (day) {
    case MONDAY, FRIDAY, SUNDAY -> 6;
    case TUESDAY -> 7;
    case THURSDAY, SATURDAY -> {
        System.out.println("处理 " + day);   // 多行逻辑
        yield 8;                             // ⭐ 用 yield 返回值（不是 return）
    }
    default -> throw new IllegalArgumentException("未知: " + day);
};
```

| 对比项 | 老 `switch` | 新 `switch` 表达式 |
|---|---|---|
| 穿透 | 会（要写 break） | **不会**（箭头语法天然不穿透） |
| 返回值 | 不能 | **能**（直接赋值 / `yield`） |
| 穷举检查 | 无 | **对 enum / sealed 会检查是否覆盖全部** |
| 多值 | 要写多个 `case` | `case A, B, C ->` |

> ⚠️ **`switch` 表达式的三条规则**：
> 1. **必须「穷举」**：要么覆盖所有可能，要么写 `default`，否则编译报错；
> 2. **`case` 的值必须可穷举**：int / String / enum / sealed 类型；
> 3. **分支里返回值用 `yield`**，不是 `return`。

### 3.5 `instanceof` 模式匹配（正式）：不用再强转

```java
// ❌ 老写法：判断 + 强转 + 起新名字，三行才能用
if (obj instanceof User) {
    User user = (User) obj;         // 强转（编译器明明已经知道类型了）
    System.out.println(user.getName());
}

// ✅ 新写法：判断的同时完成「绑定变量」
if (obj instanceof User user) {     // ⭐ 类型判断 + 声明变量，一步到位
    System.out.println(user.getName());   // 直接就能用，作用域自动限定在 if 内
}
```

**还能和 `&&` 组合做「先判空再判类型」**：

```java
if (obj instanceof User user && user.getAge() > 18) {
    // user 在这里依然有效（Java 的「流敏感分析」保证前面已判过类型）
    System.out.println(user.getName());
}
```

> 💡 **为什么这是个「大」特性**：它让代码从「**防御式三行**」变成「**一行表达意图**」。结合 Java 21 的 `record` 模式匹配，还能直接**解构**（见 4.4）。

### 3.6 增强的 NPE 提示（JEP 358）：帮你指出「到底哪个是 null」

**以前**：

```java
// 报错只有一行，完全不知道是 a、b 还是 c 为 null
Exception in thread "main" java.lang.NullPointerException
    at com.demo.Main.main(Main.java:10)
```

**现在（Java 14+，默认开启）**：

```java
// ⭐ 直接告诉你「哪个变量/方法调用的结果是 null」
Exception in thread "main" java.lang.NullPointerException:
        Cannot invoke "com.demo.Address.getCity()" because the return value of "com.demo.User.getAddress()" is null
    at com.demo.Main.main(Main.java:10)
```

> ✅ **这是升级到 17 后「体感最爽」的变化之一**——省掉了大量「打日志猜哪个是 null」的时间。
> 💡 需要更详细的帮助信息可以加 JVM 参数 `-XX:+ShowCodeDetailsInExceptionMessages`（17 默认已开）。

### 3.7 其他 17 值得知道的改进

| 特性 | 说明 |
|---|---|
| **`Stream.toList()`** | `.collect(Collectors.toList())` 的简写 → `.toList()`（返回**不可变** List） |
| **`RandomGenerator` 接口** | 统一各种随机数生成器的接口，支持 `RandomGeneratorFactory` 按名字创建 |
| **强封装 JDK 内部 API** | 默认禁止反射访问 `sun.*` 等内部类（很多老库因此报错，见 6.3） |
| **弃用 `SecurityManager`** | 标记为「待移除」（JEP 411） |
| **弃用「最终确定」`finalize()`** | 标记为「待移除」——**它一直不靠谱，别再用了**（用 `try-with-resources` / `Cleaner`） |
| **始终严格的浮点语义** | 恢复「所有平台浮点结果完全一致」（JEP 306） |
| **移除 RMI Activation / 实验性 AOT、JIT** | 清理历史包袱 |
| **macOS AArch64（M 系列芯片）支持** | 原生支持 Apple Silicon |

### 3.8 Java 17 踩坑清单

| 坑 | 说明 | 正确做法 |
|---|---|---|
| **`record` 的 `name()` 序列化不出来** | Jackson 老版本只认 `getName()` | 升 Jackson 2.15+ / 加 `@JsonProperty` / 编译加 `-parameters` |
| **JPA 实体用 `record`** | Hibernate 需要无参构造 + 可变字段 | 实体用普通类，DTO 用 `record` |
| **`sealed` 子类忘记写 `final`/`sealed`/`non-sealed`** | 编译报错 | 三者必选其一 |
| **`switch` 表达式漏了分支** | 编译报错（这是好事，逼你穷举） | 补全分支或加 `default` |
| **`switch` 分支里写 `return`** | 编译错误 | 用 `yield` |
| **`Stream.toList()` 返回不可变** | `add` 抛异常 | 需要可变用 `collect(Collectors.toList())` |
| **强封装内部 API 导致老库报错** | `Unable to make field ... accessible` | 升级库，或临时加 `--add-opens`（**不推荐长期用**） |
| **文本块首行 `"""` 后没换行** | 语法错误 | `"""` 后必须换行 |
| **文本块缩进不符合预期** | 公共缩进按「最少缩进行」算 | 把结尾 `"""` 的缩进对齐到期望基准 |

## 四、Java 21 特性（2023 LTS）——并发革命

> Java 21 是继 17 之后的下一个 LTS。如果说 8 是「函数式革命」、17 是「语法舒适化」，那 **21 的核心就一句话：把「高并发」这件事从"拼线程池调参"变成"按直觉写代码"**。
>
> 21 里最值得学的只有一件事：**虚拟线程**。其余特性（记录模式、switch 模式匹配）是 17 的收尾，把「模式匹配」这套语法补齐。

### 4.1 虚拟线程（Virtual Threads）⭐⭐⭐

#### 先搞懂：为什么需要它

传统 Java 线程（叫**平台线程**，Platform Thread）是 **1:1 绑定操作系统内核线程**的：

```
Java 的 Thread  ←→  操作系统内核线程   （1 个 Java 线程 = 1 个内核线程）
```

这带来三个硬伤：

| 问题 | 具体表现 |
| --- | --- |
| **创建贵** | 每个线程默认栈约 **1 MB**，开 1 万个就吃掉 10 GB 内存 |
| **切换贵** | 线程切换要陷入内核态，几千个线程切换时 CPU 大量时间花在「换人」上 |
| **数量有上限** | 一台机器通常几千个线程就到顶了，再开就 OOM 或调度爆炸 |

**生活类比**：平台线程就像**公司里的正式员工**——招聘成本高（要工位、要电脑、要签合同），人数有编制上限。你想接 1 万个「等客户回消息」的活，不可能真招 1 万人干等着。

而**虚拟线程**（Virtual Thread）是 **JVM 自己管理的"轻量线程"**，M:N 映射：

```
1 万个虚拟线程  →  少量平台线程（载体线程，Carrier Thread）  →  内核线程
```

**生活类比**：虚拟线程就像**客服外包**——公司只留 8 个正式工位（载体线程），但可以同时"挂" 1 万个会话。谁在等客户打字（阻塞），就把他"挂起"，工位让给下一个人用。**等客户打字的时间不占工位**，这才是关键。

#### 一个数字感受差距

| 指标 | 平台线程 | 虚拟线程 |
| --- | --- | --- |
| 初始栈内存 | ~1 MB | **几百字节 ~ 几 KB**（存在堆上，按需增长） |
| 创建 100 万个耗时 | 几分钟 + OOM | **几秒** |
| 创建成本 | 高（系统调用） | 低（就是个 Java 对象） |
| 谁调度 | 操作系统 | **JVM** |
| 阻塞时 | 占用内核线程 | **让出载体线程**（自动挂起） |
| 适合任务 | CPU 密集 / 少量长任务 | **IO 密集型、高并发** |

#### 怎么写：三种姿势

**姿势一：直接创建**

```java
// Thread.ofVirtual() —— 得到一个"虚拟线程构建器"
Thread vt = Thread.ofVirtual()
        .name("my-virtual-thread")   // 起个名，方便排查
        .start(() -> {
            // 这个 Runnable 就跑在虚拟线程上
            System.out.println("跑在虚拟线程上：" + Thread.currentThread());
        });

vt.join();   // 等它跑完（跟普通线程用法一样）
```

**姿势二：一行提交任务（最常用）✅**

```java
// 关键点：newVirtualThreadPerTaskExecutor()
// —— 每提交一个任务，就新建一个虚拟线程（注意：不是从池里取！）
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {

    // 提交 10 万个任务，每个都跑在自己的虚拟线程上
    for (int i = 0; i < 100_000; i++) {
        final int id = i;
        executor.submit(() -> {
            // 假设这里是"调一次下游接口"这种 IO 操作
            Thread.sleep(1000);      // 阻塞 1 秒 —— 虚拟线程会在这里自动让出载体线程
            return "任务 " + id + " 完成";
        });
    }

}   // try-with-resources 退出时会 close()，自动等待所有任务结束
```

> ⚠️ **注意 `newVirtualThreadPerTaskExecutor()` 的名字**：它是"每个任务一个新线程"，**内部不做池化**。这不是缺陷，而是设计——虚拟线程创建太便宜了，不需要池化。

**姿势三：给现有代码"无痛提速"**

如果你已经有一个用 `newFixedThreadPool(200)` 的 IO 密集服务，**只改一行**：

```java
// ❌ 改造前：200 个平台线程，第 201 个请求就得排队
ExecutorService pool = Executors.newFixedThreadPool(200);

// ✅ 改造后：每个请求一个虚拟线程，能同时扛几十万
ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor();
```

只要你的代码是「**一个请求一个线程**」的同步写法，换成虚拟线程后，吞吐量能上一个数量级，**而业务代码一行都不用改**。这就是虚拟线程最大的价值——**不用再学响应式编程（WebFlux/Reactor）那套回调地狱，用同步写法也能扛高并发**。

#### ⚠️ 坑一：pinning（钉住）——虚拟线程的头号陷阱

虚拟线程在**大部分阻塞点**（`Thread.sleep`、网络 IO、`ReentrantLock`、`BlockingQueue`）都会自动让出载体线程。**但有例外**：

> **当虚拟线程在 `synchronized` 块里阻塞时，它会把载体线程"钉住"（pin），此时载体线程无法去执行别的虚拟线程。**

```java
// ❌ 危险写法：synchronized 里做 IO，会把载体线程钉死
public synchronized String callRemote() {
    return httpClient.send(...);   // 这里阻塞 → 载体线程被钉住，别的虚拟线程用不了它
}

// ✅ 推荐写法：用 ReentrantLock 替代 synchronized
private final ReentrantLock lock = new ReentrantLock();

public String callRemote() {
    lock.lock();                   // ReentrantLock 阻塞时，虚拟线程能正常让出载体线程
    try {
        return httpClient.send(...);
    } finally {
        lock.unlock();
    }
}
```

**怎么发现 pinning？** 加 JVM 参数：

```bash
-Djdk.tracePinnedThreads=full      # 有虚拟线程被钉住时，打印完整堆栈
```

> 💡 **口诀**：**写虚拟线程友好的代码，就用 `ReentrantLock` 别用 `synchronized`；用 `ConcurrentHashMap` 等 JUC 类，别自己写同步块。**
>
> （注：JDK 24 起 `synchronized` 的 pinning 问题已被修复，但 21 上必须注意。）

#### ⚠️ 坑二：虚拟线程不适合 CPU 密集任务

虚拟线程解决的是「**线程大部分时间在等 IO**」的问题。如果任务是纯计算（比如大数运算、图像处理、加解密），虚拟线程**没有任何优势**——因为载体线程数量就那么多（默认 = CPU 核数），算力不会因为你开 10 万个虚拟线程而变多。

| 任务类型 | 推荐 |
| --- | --- |
| **IO 密集**（调接口、查库、读文件、等消息） | ✅ 虚拟线程，越多越好 |
| **CPU 密集**（计算、编解码、压缩） | ❌ 用平台线程池，大小 ≈ CPU 核数（甚至用 ForkJoinPool） |
| **混合型** | 拆开：IO 部分用虚拟线程，计算部分丢给平台线程池 |

#### ⚠️ 坑三：不要池化虚拟线程

```java
// ❌ 错误：想"复用"虚拟线程
ExecutorService wrong = Executors.newFixedThreadPool(1000, Thread.ofVirtual().factory());

// ✅ 正确：每个任务一个新虚拟线程
ExecutorService right = Executors.newVirtualThreadPerTaskExecutor();
```

**为什么不能池化？** 池化的目的是「复用昂贵资源」。虚拟线程**不昂贵**，池化反而带来三个坏处：
1. 池化会限制并发上限（池多大就只能跑多少），白白浪费了虚拟线程"可以无限多"的优势
2. 池化的线程会被**复用**，可能残留 `ThreadLocal` 脏数据
3. 池化逻辑本身是额外的复杂度

#### ⚠️ 坑四：`ThreadLocal` 在虚拟线程下的新问题

每个虚拟线程都有自己的 `ThreadLocal` 副本。开 100 万个虚拟线程，如果每个都往 `ThreadLocal` 里塞一个大对象，内存直接爆炸。

```java
// ❌ 危险：ThreadLocal 里放重对象 + 海量虚拟线程 = OOM
private static final ThreadLocal<BigObject> CACHE = ThreadLocal.withInitial(BigObject::new);

// ✅ Java 21 的新选择：ScopedValue（预览特性）
// 作用域结束自动释放，且对虚拟线程友好、可继承、不可变
```

> 实践建议：**虚拟线程 + `ThreadLocal` 要克制**，尤其是缓存类数据。能用参数传递就别放 `ThreadLocal`。

#### 虚拟线程小结

| 一句话 | 内容 |
| --- | --- |
| **是什么** | JVM 调度的轻量线程，M:N 映射到平台线程 |
| **解决什么** | 高并发 IO 场景下「线程太贵、数量有上限」的问题 |
| **最大价值** | 同步写法也能扛高并发，**不用改造成响应式** |
| **怎么用** | `Executors.newVirtualThreadPerTaskExecutor()` 一行搞定 |
| **别用来干** | CPU 密集任务、池化复用 |
| **注意什么** | `synchronized` 里的 pinning、`ThreadLocal` 内存 |

### 4.2 结构化并发（Structured Concurrency）——预览

**要解决的问题**：你调 3 个下游接口，用 `CompletableFuture` 并发发起。如果其中一个失败了，另外两个怎么取消？如果主线程中断了，子任务谁来收尾？——**并发任务的生命周期管不住**。

**生活类比**：结构化并发就像**旅行团**——游客（子任务）必须跟着团（作用域），团解散时所有游客必须归队。不允许有人"脱团"在后台乱跑。

```java
// ⚠️ Java 21 中是预览特性，编译运行需加 --enable-preview
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {

    // 三个子任务并发跑，各自在自己的虚拟线程上
    Subtask<String> user  = scope.fork(() -> userService.getUser(id));
    Subtask<Order>  order = scope.fork(() -> orderService.getOrder(id));
    Subtask<Stock>  stock = scope.fork(() -> stockService.getStock(id));

    scope.join();            // 等所有子任务结束
    scope.throwIfFailed();   // 任何一个失败 → 抛异常（其余自动取消）

    // 三个都成功了，安全取值
    return new Detail(user.get(), order.get(), stock.get());
}
// try 块结束 → 作用域关闭，保证所有子任务都已结束（不会有线程泄漏）
```

两种现成的策略：

| 策略 | 行为 | 适用场景 |
| --- | --- | --- |
| `ShutdownOnFailure` | **任一失败就全部取消** | 需要所有结果都成功（下单要查用户+库存+价格） |
| `ShutdownOnSuccess` | **任一成功就取消其余** | 只要最快的一个结果（多机房探测、竞速查询） |

> 💡 结构化并发目前是**预览特性**，生产环境要慎重。但**思想**很重要：**并发任务应该有清晰的作用域边界，不能"发射后不管"**。

### 4.3 记录模式（Record Patterns）——把 record 拆开

17 的 `record` 让你「一行定义数据类」；21 的**记录模式**让你「一行把数据类拆开」。

```java
// 先定义一个坐标
record Point(int x, int y) {}

// ❌ 17 的写法：拿到 Point 后还要手动调 x() y()
if (obj instanceof Point p) {
    int x = p.x();     // 手动取值
    int y = p.y();
    System.out.println("坐标：" + x + ", " + y);
}

// ✅ 21 的写法：直接在 instanceof 里"解构"
if (obj instanceof Point(int x, int y)) {     // 一步拆开
    System.out.println("坐标：" + x + ", " + y);
}
```

**支持嵌套解构**——这才是它真正好用的地方：

```java
record Point(int x, int y) {}
record Line(Point start, Point end) {}

// 嵌套解构：直接从 Line 里把两个坐标的四个值全拆出来
if (obj instanceof Line(Point(int x1, int y1), Point(int x2, int y2))) {
    System.out.printf("线段从 (%d,%d) 到 (%d,%d)%n", x1, y1, x2, y2);
}
```

配合泛型还能做类型安全的容器拆解：

```java
record Box<T>(T content) {}

// 拆 Box 的同时，顺便用泛型模式判断 content 的类型
if (obj instanceof Box<String>(String s)) {
    System.out.println("盒子里是字符串：" + s);
}
```

### 4.4 `switch` 模式匹配（Pattern Matching for switch）——正式版

17 的 `switch` 表达式支持了 `->` 和 `yield`；21 把它和**模式匹配**结合，`switch` 从「只能匹配常量」升级成「**能匹配类型、能解构、能加条件**」。

#### 基础：按类型分支，不用再写一串 `if instanceof`

```java
// ❌ 传统写法：一堆 if-else instanceof
static double area(Object shape) {
    if (shape instanceof Circle c) {
        return Math.PI * c.r() * c.r();
    } else if (shape instanceof Rectangle r) {
        return r.w() * r.h();
    } else if (shape == null) {
        return 0;
    } else {
        throw new IllegalArgumentException("未知形状");
    }
}

// ✅ 21 写法：switch 模式匹配
static double area(Object shape) {
    return switch (shape) {
        case Circle c    -> Math.PI * c.r() * c.r();   // 匹配类型并绑定变量 c
        case Rectangle r -> r.w() * r.h();
        case null        -> 0;                          // 显式处理 null（以前会直接 NPE）
        default          -> throw new IllegalArgumentException("未知形状");
    };
}
```

#### 进阶一：加「守卫条件」`when`

```java
return switch (shape) {
    // 只有"半径大于 0 的圆"才走这个分支
    case Circle c when c.r() > 0 -> Math.PI * c.r() * c.r();
    // 半径为 0 的圆走这里
    case Circle c                -> 0;
    case Rectangle r             -> r.w() * r.h();
    case null, default           -> 0;    // null 和 default 可以合并写
};
```

#### 进阶二：和记录模式联动，一步解构

```java
return switch (shape) {
    // 直接解构出坐标和半径，变量随取随用
    case Circle(Point(int cx, int cy), int r) -> Math.PI * r * r;
    case Rectangle(Point p1, Point p2)        -> calcArea(p1, p2);
    default -> 0;
};
```

#### 关键规则

| 规则 | 说明 |
| --- | --- |
| **穷尽性检查** | 如果 `switch` 是表达式（要返回值），**必须覆盖所有情况**，否则编译报错——这是安全网 |
| **`null` 要显式处理** | 老 `switch` 遇到 null 直接 NPE；新模式匹配里 `case null` 才走，不写就可能 NPE |
| **`default` 可以省** | 如果穷尽了所有类型（比如 sealed 类的所有子类），可以不写 `default` |
| **顺序有意义** | 从上往下匹配，**子类型要写在父类型前面**，否则子类型永远匹配不到 |

> ⚠️ **顺序坑**：`case Object o` 写在前面，后面的 `case String s` 就成了死代码。编译器会报错提醒你，但设计分支顺序时要有意识：**具体在前、笼统在后**。

#### 和 17 的 `sealed` 是天作之合

```java
sealed interface Shape permits Circle, Rectangle, Triangle {}   // 17：限定子类
record Circle(double r)          implements Shape {}
record Rectangle(double w, double h) implements Shape {}
record Triangle(double b, double h)  implements Shape {}

// 21：因为编译器知道 Shape 只有这三种，穷尽检查能 100% 生效
double area(Shape s) {
    return switch (s) {
        case Circle c    -> Math.PI * c.r() * c.r();
        case Rectangle r -> r.w() * r.h();
        case Triangle t  -> 0.5 * t.b() * t.h();
        // 不需要 default —— 编译器知道已经穷尽
    };
}
```

> 💡 **`sealed` + `record` + `switch` 模式匹配** 三件套合起来，Java 终于有了接近 **Rust / Kotlin 的代数数据类型（ADT）表达能力**。这是 17 + 21 一起才完整的能力。

### 4.5 分代 ZGC（Generational ZGC）

**背景**：ZGC 是低延迟垃圾回收器，STW（Stop-The-World，暂停用户线程）时间在**亚毫秒级**。但早期 ZGC 不分代——所有对象混在一起回收，**效率不如分代**。

**21 的改进**：ZGC 支持**分代**（年轻代 / 老年代分开回收），思路和 G1 一样——**大多数对象朝生夕死，优先扫年轻代，收益最高**。

```bash
# 开启分代 ZGC（21 上需要显式加参数）
-XX:+UseZGC -XX:+ZGenerational
```

| 回收器 | 特点 | 适用 |
| --- | --- | --- |
| **G1** | 默认，平衡型 | 大多数场景 |
| **ZGC（分代）** | 超低延迟（<1ms），内存占用略高 | 大堆（几十 GB+）、延迟敏感服务 |
| **Shenandoah** | 低延迟，类似 ZGC | 低延迟场景 |
| **Parallel** | 高吞吐，STW 较长 | 批处理、离线任务 |

> 选型口诀：**默认 G1；延迟敏感 + 大堆 → 分代 ZGC；吞吐优先的离线任务 → Parallel。**

### 4.6 `SequencedCollection`：给集合补上「首尾操作」

Java 集合一直有个尴尬：`List` 有 `get(0)` / `get(size()-1)`，但 `Deque` / `LinkedHashSet` 各有各的 API，**没有统一接口**。

21 引入了 `SequencedCollection` / `SequencedSet` / `SequencedMap` 接口：

```java
// 统一的"首尾"API，List / Deque / LinkedHashSet / LinkedHashMap 都实现了
List<String> list = new ArrayList<>(List.of("A", "B", "C"));

list.getFirst();      // "A"   —— 替代 list.get(0)
list.getLast();       // "C"   —— 替代 list.get(list.size() - 1)
list.addFirst("X");   // 头插
list.addLast("Y");    // 尾插
list.removeFirst();   // 删头
list.reversed();      // 返回一个"反向视图"（不复制，只翻转视角）⭐
```

`reversed()` 是个很实用的改进——**返回的是视图不是副本**，所以：

```java
List<String> view = list.reversed();
view.add("Z");        // 这个修改会反映到原 list 上（因为是同一个底层数据）
```

> ⚠️ 别把 `reversed()` 当 `Collections.reverse()`——前者返回视图**不改原集合**，后者是原地翻转**改原集合**。

### 4.8 Java 21 踩坑清单

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **`synchronized` 里阻塞导致 pinning** | 虚拟线程性能反而下降 | 改用 `ReentrantLock`；用 `-Djdk.tracePinnedThreads=full` 排查 |
| **用虚拟线程跑 CPU 密集任务** | 吞吐没提升甚至更差 | CPU 密集用平台线程池 |
| **池化虚拟线程** | 并发上不去，还可能有脏数据 | 用 `newVirtualThreadPerTaskExecutor()`，别池化 |
| **`ThreadLocal` 存大对象** | 海量虚拟线程 → OOM | 改用 `ScopedValue`，或别用 `ThreadLocal` 缓存 |
| **`switch` 模式匹配没写 `case null`** | 传 null 时 NPE | 显式加 `case null ->` 或 `case null, default ->` |
| **`switch` 分支顺序错误** | 子类型被父类型"吃掉" | 具体的写前面，笼统的写后面 |
| **`switch` 表达式不穷尽** | 编译报错 | 补齐分支或加 `default` |
| **`reversed()` 误当 `Collections.reverse()`** | 原集合被改/没被改，与预期不符 | 记住：`reversed()` 返回视图，不改原集合 |
| **生产环境用了预览特性** | 升级 JDK 后编译失败 | 预览特性只在实验代码里用 |
| **`finalize()` 依赖** | 21 已弃用，未来删除 | 改用 `try-with-resources` / `Cleaner` |
| **误以为换 21 就能提速** | 同步代码没改，性能没变 | 虚拟线程要**真的用起来**（把线程池换掉）才有效果 |

| **JVM 内存** | PermGen → Metaspace | 无重大变化 | 无重大变化 |
| **支持状态** | 商业支持已到期（2019/2030 视厂商） | 支持到 2029+ | 支持到 2031+ |
| **现在还用吗** | ⚠️ 存量多，新项目不建议 | ✅ 稳，很多公司的主力 | ✅ 新项目首选 |

### 5.2 三个版本「同一个需求」的写法对比

以「遍历订单，筛选金额大于 100 的，取客户名，去重，排序」为例：

```java
// ========== Java 8 之前（匿名内部类）==========
List<String> names = new ArrayList<>();
Set<String> seen = new HashSet<>();
for (Order o : orders) {
    if (o.getAmount() > 100) {
        if (seen.add(o.getCustomerName())) {
            names.add(o.getCustomerName());
        }
    }
}
Collections.sort(names);

// ========== Java 8（Stream 链式）==========
List<String> names = orders.stream()
        .filter(o -> o.getAmount() > 100)   // 过滤
        .map(Order::getCustomerName)        // 转换
        .distinct()                          // 去重
        .sorted()                            // 排序
        .collect(Collectors.toList());

// ========== Java 17（+ record 定义 Order）==========
record Order(String customerName, double amount) {}   // 数据类一行搞定

List<String> names = orders.stream()
        .filter(o -> o.amount() > 100)       // record 的访问器是 amount() 不是 getAmount()
        .map(Order::customerName)
        .distinct()
        .sorted()
        .toList();                            // 17 新增：直接 toList()

// ========== Java 21（+ 虚拟线程并发处理）==========
// 如果是"每个订单要调一次接口"的 IO 场景：
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = orders.stream()
            .filter(o -> o.amount() > 100)
            .map(o -> executor.submit(() -> remoteService.getName(o)))  // 并发调接口
            .toList();

    List<String> names = futures.stream()
            .map(f -> {
                try { return f.get(); }
                catch (Exception e) { throw new RuntimeException(e); }
            })
            .distinct()
            .sorted()
            .toList();
}
```

### 5.3 新项目该选哪个版本？

```
新项目？
├─ 要上生产 → Java 21（LTS，虚拟线程 + 模式匹配，支持到 2031+）
├─ 团队保守 / 依赖库还没适配 21 → Java 17（LTS，稳，够用）
└─ 维护老项目 → 保持 8，但**制定升级计划**（8 的免费支持早已结束，有安全风险）

Spring Boot 版本对应：
- Spring Boot 2.x  → 最低 Java 8
- Spring Boot 3.x  → **最低 Java 17**（这是很多公司升级 Java 的直接动因）
```

> 💡 **最实际的建议**：**新项目直接 Java 21**。因为 Spring Boot 3.x 已经强制要求 17+，而 17 → 21 的迁移成本**极低**（几乎无破坏性变更），却能白拿虚拟线程这个大杀器。

## 六、版本升级与迁移实战

### 6.1 从 Java 8 升到 17 / 21 的「五步法」

| 步骤 | 做什么 | 工具 / 命令 |
| --- | --- | --- |
| **1. 体检** | 扫描代码里用了哪些「8 之后被移除 / 弃用」的 API | `jdeprscan --release 17 myapp.jar` |
| **2. 依赖体检** | 检查第三方库有没有支持 17 的版本 | `mvn versions:display-dependency-updates`、`dependency:tree` |
| **3. 换编译目标** | 改 `pom.xml` 的 `maven.compiler.release` | `<maven.compiler.release>17</maven.compiler.release>` |
| **4. 逐个模块编译** | 先编译、后运行，把编译错误一次清完 | `mvn clean compile` |
| **5. 跑测试 + 压测** | 单元测试、集成测试、性能对比 | `mvn verify`、JMeter |

### 6.2 从 8 升到 17 最常见的 8 类编译错误

| 错误 | 原因 | 解法 |
| --- | --- | --- |
| `package javax.xml.bind does not exist` | JAXB 在 Java 11 被移出 JDK | 加 `jakarta.xml.bind-api` + `jaxb-impl` 依赖 |
| `package javax.annotation does not exist` | `@PostConstruct` 等注解被移除 | 加 `jakarta.annotation-api` |
| `Unable to make field accessible` | 强封装 JDK 内部 API（JEP 403） | 升级库；临时用 `--add-opens`（不推荐长期） |
| `Unsupported class file major version 61` | 某个工具（如老 Lombok）不认 17 的字节码 | 升级该工具 |
| `Illegal reflective access` 警告 | 反射访问内部 API | 升级库，或加 `--add-exports` |
| `Symbol is declared in module ... which does not export` | JPMS 模块化限制 | 加 `--add-exports` / `--add-opens` |
| **Lombok 版本太老** | 老版本 Lombok 不支持 17 | 升到 **1.18.20+** |
| **`sun.misc.Unsafe` 相关报错** | Unsafe 内部 API 受限 | 升级库；或用 `--add-opens java.base/sun.misc=ALL-UNNAMED` |

### 6.3 依赖库版本对照（升级时必查）

| 库 | Java 17 最低版本 | Java 21 最低版本 |
| --- | --- | --- |
| Spring Boot | **3.0+**（3.x 全线要 17） | 3.2+ |
| Spring Framework | 6.0+ | 6.1+ |
| Lombok | **1.18.20+** | 1.18.30+ |
| MyBatis | 3.5.9+ | 3.5.13+ |
| Hutool | 5.8+ | 5.8.20+ |
| Jackson | 2.13+ | 2.15+ |
| Netty | 4.1.68+ | 4.1.100+ |
| Guava | 31+ | 32+ |

> ⚠️ **升级顺序**：**先升依赖库 → 再升 JDK**。反过来的话，你会在编译阶段就被一堆库的不兼容报错淹没，分不清是"我的代码问题"还是"库的问题"。

### 6.4 从 17 升到 21 要改什么？

**好消息：几乎不用改。** 17 → 21 没有破坏性变更，主要注意三点：

| 注意点 | 说明 |
| --- | --- |
| **`finalize()` 弃用警告** | 21 会打印弃用警告，逐步替换为 `try-with-resources` |
| **`Thread.stop()` 等弃用** | 编译警告，替换为 `interrupt()` + 标志位 |
| **想用虚拟线程要主动改** | 升级 JDK 不会自动提速，要**把线程池换掉**才有效果 |

```java
// 17 → 21 后，想让 IO 密集型服务提速，只需改这一处：
// ExecutorService pool = Executors.newFixedThreadPool(200);
ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor();
```

> 💡 **提醒**：Java 21 里的**预览特性**（结构化并发、`ScopedValue`、字符串模板）需要 `--enable-preview`，且**每次 JDK 小版本升级都要重新编译**。生产代码别碰。

## 七、动手路线（五阶段）

> 别指望一次看完就记住。**按下面的路线走，每一阶段都能立刻用上。**

| 阶段 | 目标 | 具体动作 | 验收标准 |
| --- | --- | --- | --- |
| **阶段一：8 的基本功（1 周）** | 把 Lambda 和 Stream 用顺 | ① 把项目里 5 个 for 循环改写成 Stream<br>② 用 `Collectors.groupingBy` 做一次分组统计<br>③ 用 `Optional` 消除 3 处 `if (x != null)` | 看到 `List<Order>` 能条件反射想到 `stream().filter().map().collect()` |
| **阶段二：8 的进阶（1 周）** | 理解函数式接口和异步 | ① 自己写一个函数式接口 + Lambda 实现<br>② 用 `CompletableFuture` 并发调 3 个接口并合并结果<br>③ 用 `java.time` 替换掉项目里的 `SimpleDateFormat` | 能说清 `Function` / `Consumer` / `Supplier` / `Predicate` 的区别 |
| **阶段三：17 的语法升级（3 天）** | 用上新语法 | ① 把 3 个 DTO 改成 `record`<br>② 把长 SQL 字符串改成文本块<br>③ 把 `if-else instanceof` 改成 `switch` 表达式<br>④ 用 `sealed` 定义一个只允许三种实现的接口 | 代码行数明显下降，IDE 无警告 |
| **阶段四：21 的并发革命（1 周）** | 真正用上虚拟线程 | ① 找一个 IO 密集的接口，把线程池换成 `newVirtualThreadPerTaskExecutor()`<br>② 压测对比改造前后的 QPS / RT<br>③ 用 `-Djdk.tracePinnedThreads=full` 检查有没有 pinning<br>④ 把 `synchronized` 热点改成 `ReentrantLock` | 压测显示吞吐量提升，且无 pinning 告警 |
| **阶段五：模式匹配收尾（3 天）** | 吃透 21 的语法糖 | ① 用记录模式解构一个嵌套 record<br>② 用 `switch` 模式匹配 + `when` 守卫重写一段复杂的类型分发逻辑<br>③ 用 `reversed()` 优化一处集合倒序 | 能把「`sealed` + `record` + `switch`」三件套组合用起来 |

**推荐练习项目**：把「订单查询接口」改造一遍——
- 用 `record` 定义 DTO
- 用 Stream 做过滤统计
- 用虚拟线程并发调用户服务 / 库存服务
- 用 `switch` 模式匹配处理不同的订单状态
- 全程用文本块写 SQL

一个项目下来，8 / 17 / 21 的核心特性就都摸过了。

## 八、一句话总结

> **Java 8 教你「用函数式思维处理集合」；Java 17 教你「用更少的代码表达同样的意思」；Java 21 教你「用同步的写法扛住高并发」。**
>
> 三个版本不是替代关系，而是**层层叠加**：21 里 Lambda、Stream、`record`、文本块全都还在用，只是你多了更多选择。
>
> **实践优先级**：Stream + Lambda（天天用）> 虚拟线程（IO 密集场景的降维打击）> `record` + 文本块（省代码）> `switch` 模式匹配（复杂分支分发）> 其余按需。

### 三个最容易踩的认知误区

| 误区 | 真相 |
| --- | --- |
| ❌「升到 21 项目就自动变快」 | 虚拟线程要**主动把线程池换掉**才生效；CPU 密集任务甚至可能变慢 |
| ❌「`record` 能完全替代 Lombok / 实体类」 | `record` 不可变、不能继承、不支持 JPA 无参构造，**只适合 DTO / 值对象** |
| ❌「Stream 一定比 for 循环快」 | Stream 有惰性求值和包装开销，**简单循环反而更快**；用 Stream 是为了**可读性**，不是为了性能 |
