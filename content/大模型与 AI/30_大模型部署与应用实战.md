# 大模型部署与应用实战（Qwen + vLLM + Dify + OneAPI，从部署到应用全流程）

> **一句话概括**：大模型应用 = 模型（Qwen）+ 推理引擎（vLLM）+ 统一网关（OneAPI）+ 应用编排（Dify）。模型负责「想」，推理引擎负责「跑得快」，网关负责「统一管理和计费」，Dify 负责「把模型变成可用的应用」。四者配合，就能从 0 到 1 搭建一套企业级大模型应用平台。
>
> **适合谁**：想本地部署大模型但不知道从哪开始、听说过 vLLM/Dify/OneAPI 但说不清各自的作用、想把大模型集成到业务系统里但不知道架构怎么设计的人。
>
> 📖 **相关专篇**：Java 代码里怎么调大模型（ChatClient / RAG / Tool Calling / MCP）见 [[34_Spring AI 实战]]。

---

## 零、先建立印象：把大模型应用想象成「餐厅运营」

| 餐厅 | 大模型应用 |
|---|---|
| **厨师（大脑）** | 大模型（Qwen）—— 负责「思考」和「生成」 |
| **厨房设备（效率）** | vLLM —— 让厨师「炒菜更快」，同时炒多道菜（连续批处理） |
| **前台收银（统一管理）** | OneAPI —— 统一管理多个「厨师」，接单、计费、限流 |
| **菜单和套餐（应用编排）** | Dify —— 把「厨师的能力」包装成具体的「菜品」（对话、知识库、工作流） |
| **顾客（用户）** | 业务系统 / 终端用户 —— 通过 API 或界面使用 |

**为什么需要这四层？**
```
只有模型（Qwen）：能跑，但性能差、不好管理、不好集成
+ vLLM：推理快了，但还是裸 API，没有应用层
+ OneAPI：统一管理了，但还是需要自己写应用代码
+ Dify：可视化编排应用，非技术人员也能搭建大模型应用
```

## 一、模型层：Qwen 通义千问

### 1.1 为什么选 Qwen？

| 对比项 | Qwen（通义千问） | Llama | ChatGLM |
|---|---|---|---|
| **开源协议** | Apache 2.0（商用友好） | Llama 协议（商用有限制） | Apache 2.0 |
| **中文能力** | 强（阿里训练，中文优化） | 中（英文为主） | 强 |
| **模型尺寸** | 0.5B ~ 72B，选择多 | 7B ~ 70B | 6B ~ 130B |
| **生态** | 活跃，阿里持续更新 | 最活跃，社区最大 | 较活跃 |
| **推理性能** | 好 | 好 | 中 |

> 💡 **选型建议**：中文场景、商用、想要灵活选择模型尺寸 → 选 Qwen。Qwen2.5 系列是目前（2024年底）开源模型中中文能力最强的之一，7B 模型在 16GB 显存的显卡上就能流畅运行。

### 1.2 Qwen 模型选择

| 模型 | 参数量 | 最低显存 | 适用场景 |
|---|---|---|---|
| Qwen2.5-0.5B | 5亿 | 2GB | 边缘设备、简单任务、学习测试 |
| Qwen2.5-1.5B | 15亿 | 4GB | 简单对话、分类、摘要 |
| Qwen2.5-3B | 30亿 | 8GB | 中等复杂度任务、消费级显卡 |
| **Qwen2.5-7B** | **70亿** | **16GB** | **通用场景，性价比最高（推荐）** |
| Qwen2.5-14B | 140亿 | 32GB | 复杂推理、代码生成 |
| Qwen2.5-32B | 320亿 | 64GB | 专业场景、接近 GPT-3.5 |
| Qwen2.5-72B | 720亿 | 140GB+ | 企业级、接近 GPT-4 |

**量化版本（显存不够时用）：**
```
FP16：原始精度，显存需求最大
INT8：量化到 8 位，显存减半，精度损失小
INT4：量化到 4 位，显存减 3/4，精度有一定损失
GPTQ/AWQ：更先进的量化算法，精度损失更小
```

> 💡 **实战建议**：7B 模型用 INT4 量化，8GB 显存就能跑（RTX 3060/3070/4060 都可以），适合个人开发和测试。生产环境用 FP16 或 INT8，保证精度。

## 二、推理引擎层：vLLM

### 2.1 为什么需要 vLLM？

```
直接用 HuggingFace Transformers 推理：
- 慢：一次只能处理一个请求（串行）
- 显存浪费：KV Cache 占大量显存但利用率低
- 不支持动态批处理：请求来了要等上一个处理完

vLLM 解决了这些问题：
- PagedAttention：像操作系统虚拟内存一样管理 KV Cache，显存利用率从 20% 提升到 90%+
- 连续批处理（Continuous Batching）：请求来了立刻加入批次，不用等，吞吐量提升 10-100 倍
- 支持张量并行：多卡推理，大模型也能跑
```

### 2.2 vLLM 快速部署

```bash
# 1. 安装 vLLM
pip install vllm

# 2. 启动 OpenAI 兼容 API 服务（最简单的方式）
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct \
  --served-model-name qwen2.5-7b \
  --host 0.0.0.0 \
  --port 8000 \
  --tensor-parallel-size 1 \      # 单卡
  --gpu-memory-utilization 0.85 \ # 显存利用率 85%
  --max-model-len 8192            # 最大上下文长度

# 3. 多卡推理（比如 2 张卡）
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-14B-Instruct \
  --tensor-parallel-size 2 \
  --port 8000

# 4. 用 INT4 量化（显存不够时）
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct-AWQ \
  --quantization awq \
  --port 8000

# 5. 测试 API
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5-7b",
    "messages": [{"role": "user", "content": "你好，请介绍一下你自己"}],
    "temperature": 0.7,
    "max_tokens": 512
  }'
```

### 2.3 Docker 部署（推荐，生产环境）

```bash
# 拉取镜像
docker pull vllm/vllm-openai:latest

# 启动容器
docker run -d \
  --name vllm-qwen \
  --gpus all \
  --shm-size 16g \
  -p 8000:8000 \
  -v /data/models:/models \
  vllm/vllm-openai:latest \
  --model /models/Qwen2.5-7B-Instruct \
  --served-model-name qwen2.5-7b \
  --host 0.0.0.0 \
  --port 8000 \
  --gpu-memory-utilization 0.85
```

### 2.4 vLLM 关键参数

| 参数 | 说明 | 建议值 |
|---|---|---|
| `--model` | 模型路径或 HuggingFace 模型名 | 必填 |
| `--served-model-name` | API 中显示的模型名 | 自定义，方便管理 |
| `--tensor-parallel-size` | 张量并行（多卡） | 单卡填 1，多卡填卡数 |
| `--gpu-memory-utilization` | 显存利用率 | 0.85（留 15% 余量） |
| `--max-model-len` | 最大上下文长度 | 8192 / 16384 / 32768 |
| `--max-num-seqs` | 最大并发序列数 | 256（默认） |
| `--quantization` | 量化方式 | awq / gptq / fp8 |
| `--dtype` | 数据类型 | float16 / bfloat16 |
| `--enable-prefix-caching` | 前缀缓存（相同前缀复用） | 开启，提升重复请求性能 |

## 三、统一网关层：OneAPI

### 3.1 为什么需要 OneAPI？

```
问题：
1. 有多个模型（Qwen-7B、Qwen-14B、GPT-4、Claude），每个有不同的 API 地址和 Key
2. 业务系统要对接多个模型，代码复杂
3. 想统一管理用量、计费、限流
4. 想给不同用户分配不同的模型权限和额度

OneAPI 解决：
- 统一 API 入口：所有模型走同一个地址，OpenAI 兼容格式
- 多模型管理：支持 OpenAI、Azure、Claude、Gemini、自定义模型（vLLM）等
- 渠道管理：每个模型一个渠道，支持负载均衡、故障转移
- 用户和令牌：多用户、多 API Key，每个 Key 有额度和过期时间
- 用量统计：实时统计每个用户、每个模型的调用量和费用
- 限流：按用户、按模型限流
```

### 3.2 OneAPI 快速部署

```bash
# Docker 部署（推荐）
docker run -d \
  --name one-api \
  -p 3000:3000 \
  -v /data/one-api:/data \
  --restart always \
  justsong/one-api:latest

# 访问：http://localhost:3000
# 默认管理员账号：root / 123456（首次登录后修改密码）
```

### 3.3 配置 vLLM 作为渠道

```
1. 登录 OneAPI 管理后台
2. 渠道 → 添加新渠道
3. 类型：自定义渠道
4. 名称：Qwen2.5-7B-vLLM
5. 模型：qwen2.5-7b（和 vLLM 的 --served-model-name 一致）
6. 地址：http://<vllm-ip>:8000/v1
7. 密钥：随便填（vLLM 默认不需要密钥）
8. 权重：1（负载均衡用）
9. 保存
```

### 3.4 创建用户和令牌

```
1. 用户 → 添加用户
2. 设置用户名、密码、额度（比如 1000000 令牌 = 100 万 token）
3. 令牌 → 添加令牌
4. 选择用户、设置名称、过期时间、额度
5. 复制生成的 API Key（sk-xxxx）
```

### 3.5 业务系统调用

```python
# Python 示例（OpenAI 兼容格式）
from openai import OpenAI

client = OpenAI(
    api_key="sk-xxxx",  # OneAPI 生成的令牌
    base_url="http://one-api-host:3000/v1"
)

response = client.chat.completions.create(
    model="qwen2.5-7b",
    messages=[{"role": "user", "content": "你好"}],
    temperature=0.7,
    max_tokens=512
)
print(response.choices[0].message.content)
```

```java
// Java 示例（Spring Boot + OpenAI 客户端）
// 只需要改 baseUrl 和 apiKey，其他和调用 OpenAI 完全一样
OpenAiClient client = OpenAiClient.builder()
    .baseUrl("http://one-api-host:3000/v1")
    .apiKey("sk-xxxx")
    .build();

ChatCompletionRequest request = ChatCompletionRequest.builder()
    .model("qwen2.5-7b")
    .messages(List.of(new ChatMessage("user", "你好")))
    .temperature(0.7)
    .maxTokens(512)
    .build();

ChatCompletionResponse response = client.createChatCompletion(request);
```

> 💡 **关键价值**：业务系统只需要对接 OneAPI，不用关心底层是 vLLM 还是 OpenAI 还是其他模型。想换模型？只改 `model` 参数就行，代码不用动。

## 四、应用编排层：Dify

### 4.1 为什么需要 Dify？

```
OneAPI 提供了统一的 API，但要做一个完整的大模型应用，还需要：
- 提示词管理（Prompt）：不同场景不同提示词，版本管理
- 知识库（RAG）：上传文档，让模型基于文档回答
- 工作流：多步骤编排（检索 → 推理 → 格式化 → 输出）
- 对话管理：历史对话、上下文管理
- 前端界面：用户直接用的聊天界面
- API 发布：把应用发布成 API 给业务系统调用

Dify 全部提供，可视化操作，非技术人员也能搭建大模型应用。
```

### 4.4 Dify 核心功能

#### 4.4.1 对话型应用（Chatbot）

```
1. 工作室 → 创建应用 → 对话型应用
2. 选择模型：qwen2.5-7b
3. 编写系统提示词（Prompt）：
   "你是一个专业的Java技术顾问，擅长Spring Boot、微服务、分布式系统。
    请用通俗易懂的语言回答用户的问题，包含代码示例。"
4. 配置参数：temperature=0.7、max_tokens=2048
5. 发布 → 可以直接用 Dify 提供的聊天界面，也可以用 API 调用
```

#### 4.4.2 知识库（RAG - Retrieval Augmented Generation）

```
场景：让模型基于你的私有文档回答问题（比如公司内部文档、产品手册）

步骤：
1. 知识库 → 创建知识库
2. 上传文档（PDF、Word、Markdown、TXT、网页等）
3. 分段设置：
   - 分段方式：自动分段 / 自定义分段
   - 分段长度：1000 tokens
   - 分段重叠：100 tokens（保证上下文连贯）
4. 索引方式：高质量（Embedding 向量化，语义检索）/ 经济（关键词检索）
5. 等待索引完成
6. 在应用中关联知识库 → 配置检索参数（Top K、相似度阈值）
```

**RAG 工作原理：**
```
用户提问 → 检索知识库（找到相关片段）→ 把片段拼到 Prompt 里 → 模型基于片段回答
```

> 💡 **RAG vs 微调（Fine-tuning）**：
> - RAG：外挂知识库，数据更新方便，适合知识密集型场景
> - 微调：把知识「教」给模型，适合风格/格式/特定任务学习
> - 大多数场景用 RAG 就够了，成本低、更新快

#### 4.4.3 工作流（Workflow）

```
场景：复杂任务需要多步骤处理（比如：用户提问 → 检索知识库 → 判断是否需要搜索 → 调用搜索 → 汇总回答）

Dify 工作流节点：
- 开始节点：用户输入
- LLM 节点：调用大模型
- 知识检索节点：检索知识库
- HTTP 请求节点：调用外部 API
- 代码节点：写 Python/JS 代码处理数据
- 条件分支节点：if-else 判断
- 迭代节点：循环处理列表
- 变量聚合节点：合并多个分支的结果
- 结束节点：输出结果
```

#### 4.4.4 API 发布

```
每个应用都可以发布成 API：
- 对话 API：/v1/chat-messages
- 工作流 API：/v1/workflows/run
- 文档知识库 API：上传、管理文档

业务系统调用 Dify API：
POST http://dify-host/v1/chat-messages
Header: Authorization: Bearer app-xxxx
Body: {
  "query": "什么是分布式锁？",
  "user": "user-123",
  "response_mode": "streaming"  // 流式输出
}
```

## 六、Java 后端集成大模型实战

### 6.1 Spring Boot 集成（通过 OneAPI）

```xml
<!-- Maven 依赖 -->
<dependency>
    <groupId>com.theokanning.openai-gpt3-java</groupId>
    <artifactId>service</artifactId>
    <version>0.18.2</version>
</dependency>
```

```java
@Configuration
public class AiConfig {
    @Value("${ai.base-url}")
    private String baseUrl;  // http://one-api-host:3000/v1
    @Value("${ai.api-key}")
    private String apiKey;   // sk-xxxx

    @Bean
    public OpenAiService openAiService() {
        return new OpenAiService(apiKey, Duration.ofSeconds(60));
    }
}

@Service
public class AiService {
    @Autowired
    private OpenAiService openAiService;

    @Value("${ai.model:qwen2.5-7b}")
    private String model;

    public String chat(String question) {
        ChatCompletionRequest request = ChatCompletionRequest.builder()
            .model(model)
            .messages(List.of(
                new ChatMessage("system", "你是一个专业的Java技术顾问"),
                new ChatMessage("user", question)
            ))
            .temperature(0.7)
            .maxTokens(2048)
            .build();

        ChatCompletionResult result = openAiService.createChatCompletion(request);
        return result.getChoices().get(0).getMessage().getContent();
    }

    // 流式输出（SSE）
    public void chatStream(String question, SseEmitter emitter) {
        ChatCompletionRequest request = ChatCompletionRequest.builder()
            .model(model)
            .messages(List.of(new ChatMessage("user", question)))
            .stream(true)
            .build();

        openAiService.streamChatCompletion(request)
            .blockingForEach(chunk -> {
                String content = chunk.getChoices().get(0).getMessage().getContent();
                if (content != null) {
                    emitter.send(SseEmitter.event().data(content));
                }
            });
        emitter.complete();
    }
}
```

### 6.2 调用 Dify 工作流 API

```java
@Service
public class DifyService {
    @Value("${dify.base-url}")
    private String baseUrl;  // http://dify-host/v1
    @Value("${dify.api-key}")
    private String apiKey;   // app-xxxx

    public String runWorkflow(String query, String userId) {
        RestTemplate restTemplate = new RestTemplate();
        HttpHeaders headers = new HttpHeaders();
        headers.set("Authorization", "Bearer " + apiKey);
        headers.setContentType(MediaType.APPLICATION_JSON);

        Map<String, Object> body = new HashMap<>();
        body.put("inputs", Map.of("query", query));
        body.put("user", userId);
        body.put("response_mode", "blocking");

        HttpEntity<Map<String, Object>> entity = new HttpEntity<>(body, headers);
        ResponseEntity<String> response = restTemplate.postForEntity(
            baseUrl + "/workflows/run", entity, String.class);
        return response.getBody();
    }
}
```

## 七、面试口述总结

> **大模型应用的整体架构是什么？**
> 四层架构：模型层（Qwen）+ 推理引擎层（vLLM）+ 统一网关层（OneAPI）+ 应用编排层（Dify）。模型负责生成，vLLM 负责高性能推理，OneAPI 统一管理多模型和计费，Dify 负责把模型包装成可用的应用（对话、知识库、工作流）。
>
> **为什么用 vLLM 而不是直接用 Transformers？**
> vLLM 的 PagedAttention 技术像操作系统虚拟内存一样管理 KV Cache，显存利用率从 20% 提升到 90%+；连续批处理让请求来了立刻加入批次，不用等，吞吐量提升 10-100 倍。直接用 Transformers 是串行推理，性能差很多。
>
> **OneAPI 的作用是什么？**
> 统一 API 入口，所有模型走同一个地址，OpenAI 兼容格式。支持多模型管理、渠道负载均衡、用户令牌管理、用量统计、限流计费。业务系统只需要对接 OneAPI，不用关心底层是哪个模型，换模型只改 model 参数。
>
> **Dify 和 OneAPI 的区别？**
> OneAPI 是「模型网关」，管模型、管计费、管 API。Dify 是「应用平台」，在模型之上做应用编排——提示词管理、知识库 RAG、工作流、对话界面、API 发布。OneAPI 管「模型」，Dify 管「应用」。
>
> **RAG 和微调的区别？**
> RAG 是外挂知识库，检索相关文档片段拼到 Prompt 里，模型基于片段回答。数据更新方便，成本低，适合知识密集型场景。微调是把知识「教」给模型，改变模型参数，适合风格/格式/特定任务学习。大多数场景用 RAG 就够了。
>
> **7B 模型需要什么配置？**
> FP16 精度需要 16GB 显存（RTX 3090/4090），INT4 量化 8GB 显存就能跑（RTX 3060/4060）。个人开发测试用 INT4，生产环境用 FP16 或 INT8 保证精度。
