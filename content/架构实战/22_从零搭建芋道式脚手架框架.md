# 从零搭建芋道式脚手架框架（原理 → 应用 → 进阶）

> **一句话概括**：芋道/若依这类框架，就是**把每个后台系统都要重复写的那 80% 代码提前写好**，你只写剩下 20% 的业务差异。
>
> **本文怎么读**：每个概念我都先用「大白话 + 生活类比」讲一遍，再给专业说法和代码。代码块的注释是重点，照着抄就能跑。**看不懂就跳过代码先看文字**，三段式（原理 → 应用 → 进阶）可以分开读。
>
> **适合谁**：会写 Spring Boot 增删改查，但没从零搭过框架、看芋道源码一头雾水的人。

---

## 零、先建立整体印象：把它想象成"开一家连锁餐厅"

如果直接堆术语（starter、拦截器、多租户、数据权限），很容易劝退。先用一个贯穿全文的类比：

| 现实世界 | 对应到框架 | 一句话解释 |
|---|---|---|
| **中央厨房** | Common 公共层 | 所有门店共用的底料、工具，一次做好处处复用 |
| **门店前厅** | Controller | 负责接待客人、传菜、把结果端出去 |
| **后厨灶台** | Service | 真正做菜的地方，配菜、调味、装盘 |
| **备菜间** | Manager 层 | 洗好切好的半成品，多个灶台都能拿去用 |
| **仓库** | Mapper / 数据库 | 取食材、存食材 |
| **门卫/前台** | Gateway 网关 | 检查你是不是这儿的人、能进哪个区 |
| **工牌** | JWT（令牌） | 证明"我是谁"的凭证，进门要刷卡 |
| **门禁权限表** | RBAC 权限 | 你是经理还是服务员，能进的区域不一样 |
| **能看哪些账** | 数据权限 | 店长看全店流水，店员只能看自己的单 |
| **同一栋楼里的多家公司** | 多租户 | 门牌号不同，互相看不到对方的东西 |

**记住这个类比，后面每一节都能对号入座。**

## 一、原理篇：它到底是个啥，凭什么值钱

### 1.1 先分清三个容易混的概念

新人最容易把这三个搞混，一张表说清：

| 类型 | 例子 | 大白话 | 你要写多少代码 |
|---|---|---|---|
| **中间件** | Redis / Kafka / Minio | 别人做好的"工具"，你拿来用就行 | 只写怎么用 |
| **业务框架** | Spring Boot / Spring Cloud | 给你一个"空房子"，装修自己来 | 业务代码全写 |
| **脚手架框架** | 芋道 / 若依 / Jeecg | 给你"精装修的样板间"，摆家具就行 | **只写差异部分** |

**脚手架框架提前帮你写好了这些**（每个后台系统都需要，但每个都长得一样）：
登录登出、用户管理、角色、菜单、按钮权限、部门、字典、操作日志、登录日志、定时任务、文件上传、代码生成。

> **芋道和若依什么关系？**
> 芋道 ≈ 若依的"精修增强版 + 微服务版"，模块切得更细、通用能力拆得更彻底。
> **态度**：别神化它，也别鄙视它。它是提效工具不是技术天花板。正确的姿势是——**用它的骨架，但里面每一行通用代码你都知道怎么自己写出来**。

### 1.2 整体分层：为什么比三层多一个 Manager

```
浏览器（前端页面）
   ↓ 发 HTTP 请求
网关 Gateway    ← 门卫：验工牌(JWT)、查权限、限流、指路
   ↓
Controller     ← 前厅：接参数、校验、喊后厨、把结果端出去
   ↓
Service        ← 后厨：写业务逻辑、开事务、调备菜间和仓库
   ↓
Manager        ← 备菜间（芋道特色）：可复用的半成品、第三方调用
   ↓
Mapper         ← 仓库：取数据存数据，MyBatis-Plus
   ↓
MySQL / 达梦 / Redis / Minio / Flowable
```

**为什么要多一个 Manager 层？**（面试高频题，也是芋道最核心的设计）

讲个真实场景就懂了：
- `UserService`（用户服务）需要查用户属于哪个部门 → 调 `DeptService`
- `DeptService`（部门服务）需要查部门下有哪些人 → 又要调 `UserService`
- **结果**：A 依赖 B，B 又依赖 A → Spring 启动时报**循环依赖**，直接起不来

**怎么破？** 把它们都需要的能力抽出来，放到下一层：

```
UserService  ─┐
              ├──> UserManager / DeptManager / FileManager
DeptService  ─┘
```

依赖从"互相依赖"变成"都往下依赖"，问题消失。

**Manager 层的两个职责**（记住这两句就够了）：
1. **装可复用的原子能力** —— 多个 Service 都要用的查询、校验，放这里
2. **封装第三方调用** —— Minio 上传、Redis 缓存、发短信，Service 只管"我要存文件"，不用知道存到 Minio 还是阿里云 OSS

> 类比：Service 是"做这道菜"，Manager 是"洗菜切菜这些谁都能用的准备活"。
> **好处**：哪天把 Minio 换成 OSS，只改 Manager 一处，Service 一行不动。

### 1.3 技术选型：每个组件为什么选它

| 干什么用 | 选什么 | 为什么是它（人话版） |
|---|---|---|
| 服务注册 + 配置中心 | **Nacos** | 一个顶两个（注册+配配置），比 Zookeeper 好用太多 |
| 网关 | **Spring Cloud Gateway** | 新一代，性能好，比老旧的 Zuul 强 |
| 服务间调用 | **OpenFeign**（或 Dubbo） | 像调本地方法一样调远程接口，写着舒服 |
| 登录认证 | **Spring Security + JWT** | 业界标准，功能全；想简单就换 Sa-Token |
| 操作数据库 | **MyBatis-Plus** | 单表增删改查的代码都不用写了，省掉 60% SQL |
| 缓存 | **Redis + Caffeine** | Redis 是"公共冰箱"，Caffeine 是"手边的小冰盒"，近处拿更快 |
| 分布式锁 | **Redisson** | 自动续期，比自己写 setnx 稳得多，不怕死锁 |
| 存文件 | **Minio** | 自己搭建的"阿里云 OSS"，接口兼容，随时能换 |
| 工作流审批 | **Flowable** | 请假、合同审批这类流程引擎 |
| 限流熔断 | **Sentinel** | 流量太大时自动挡住，防止系统被打垮 |

> 每一项的详细原理都在对应的笔记里，本文末尾「关联」区有索引。

### 1.4 五个"灵魂设计"（这才是它真正值钱的地方）

**把框架玩明白，关键不在于堆了多少组件，而在于这五个横切能力。** 大白话逐个讲：

#### ① 统一返回 + 全局异常：接口返回值只有一个格式
**痛点**：没有它之前，每个接口返回格式五花八门，前端对接想骂人；每个方法都要 `try-catch`，满是重复代码。

**做法**：所有接口统一返回 `{code, data, msg}`；出错时你只管 `throw` 抛异常，有个"总管家"自动把它转成错误响应。

```java
// 业务代码干净到这种程度：
public Long createUser(UserSaveReqVO req) {
    if (userMapper.existsByName(req.getName())) {
        throw new ServiceException("用户名已存在");   // 抛出去就完事了，不用管怎么返回
    }
    // ...正常逻辑
}
```

#### ② 注解化能力：想要什么功能，加一行注解
```java
@OperateLog(...)     // 自动记录"谁改了什么"
@Idempotent(...)     // 自动防重复提交
@RateLimiter(...)    // 自动限流
@DataPermission(...) // 自动加数据范围
@Dict(...)           // 自动把 1 翻译成"男"
```
**类比**：像给房间装开关，按一下灯就亮。你不用关心电线怎么走（AOP 切面已经帮你接好了）。

#### ③ 数据权限：自动改 SQL（最难也最值钱）
**痛点**：店长要看全店数据，店员只能看自己的。难道每个查询都手写一遍 `WHERE 部门 IN (...)`？那得写吐。

**做法**：你只写干净的业务 SQL，框架在**执行前偷偷帮你加上范围条件**：
```sql
-- 你写的：        SELECT * FROM 订单表 WHERE 状态 = 已完成
-- 框架自动改成：  SELECT * FROM 订单表 WHERE 状态 = 已完成 AND 部门ID IN (10,11,12)
```
**业务代码零侵入**，这是最体现功力的一块，第 2.6 节手把手实现。

#### ④ 多租户：一套系统服务多家公司（SaaS）
**痛点**：你的系统卖给 A 公司和 B 公司，A 绝对不能看到 B 的数据。

**做法**：所有表加一个 `tenant_id`（租户号），框架**自动**在每条 SQL 后面拼上 `AND tenant_id = 自己的租户号`。你写 SQL 时完全不用管这个字段。

#### ⑤ 代码生成器：CRUD 从 2 小时压到 30 秒
建好数据库表 → 点一下 → 自动生成 Controller/Service/Mapper/实体类/前端页面/菜单 SQL。

> **这五点的共同思想**（背下来）：**约定优于配置 + 横切关注点下沉**。
> 人话：**大家都这么干，那就别让每个人重复写了，统一抽到底层去。**
> 理解了这一句，你搭的就不是"又一个若依"，而是**你自己的框架**。

## 二、应用篇：9 步搭出来，代码照着抄

### 2.1 第 1 步：搭 Maven 多模块骨架（搭隔断）

**大白话**：一个大项目切成几个小房间，各管各的，别全堆一块儿。

```
yudao-demo/
├── pom.xml                  ← 总管家：统一管所有 jar 包的版本号
├── yudao-common/            ← 公共层：工具类、统一返回、异常处理
├── yudao-module-system/     ← 系统模块：用户、角色、菜单、字典、部门
├── yudao-module-infra/      ← 基础设施：文件、定时任务、日志、代码生成
├── yudao-server/            ← 启动入口：把所有模块打包成一个可运行的 jar
└── yudao-gateway/           ← 网关（只有微服务版才需要）
```

**父 pom 的关键点**：只管版本号，不管引入。
```xml
<dependencyManagement>
  <dependencies>
    <!-- 引入 Spring Boot 官方的版本清单（BOM）。
         好处：以后写 <dependency> 时不用再写 <version>，
         所有版本由官方统一调好，绝不会出现 jar 包打架 -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>${spring.boot.version}</version>
      <type>pom</type>
      <scope>import</scope>      <!-- import = 把别人的清单搬过来用 -->
    </dependency>
    <!-- 同理再引入 Spring Cloud Alibaba 的清单 -->
  </dependencies>
</dependencyManagement>
```

> ⚠️ **新手最常见的错**：在父 pom 里直接写 `<dependencies>` 把 jar 塞给所有子模块。
> 结果：不需要 Redis 的模块也被迫引入 Redis。**用 `dependencyManagement` 只声明版本，谁用谁自己引。**
>
> 💡 **建议**：单体起步，按业务切模块。等团队变大、某个模块需要单独部署了，再拆微服务。**一上来就搞微服务 = 自找麻烦**（调试难、部署难、问题多）。

### 2.2 第 2 步：Common 公共层（统一返回 + 异常兜底）

**大白话**：定两个规矩 —— ① 所有接口返回的格式必须长一样；② 出错不用你自己处理，有人兜着。

#### ① 统一返回体
```java
@Data
public class CommonResult<T> implements Serializable {
    private Integer code;   // 状态码：0=成功，其他=各种失败（前端靠它判断）
    private T data;         // 真正的数据（成功时才有用）
    private String msg;     // 提示语：给用户看的，比如"用户名已存在"

    // 成功时用这个
    public static <T> CommonResult<T> success(T data) {
        CommonResult<T> r = new CommonResult<>();
        r.code = 0;
        r.data = data;
        r.msg = "成功";
        return r;
    }
    // 失败时用这个
    public static <T> CommonResult<T> error(Integer code, String msg) {
        CommonResult<T> r = new CommonResult<>();
        r.code = code;
        r.msg = msg;
        return r;
    }
}
```
**前端收到的永远是这个格式**，对接时不用猜：
```json
{ "code": 0, "data": { "id": 1, "name": "张三" }, "msg": "成功" }
```

#### ② 全局异常兜底（重点！）
```java
/**
 * @RestControllerAdvice = 全局"接锅侠"
 * 任何 Controller 抛出的异常，都会被这里接住，转成统一格式返回。
 * 业务代码从此告别 try-catch。
 */
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 1. 业务异常：我们自己主动抛的，比如"余额不足"、"用户名已存在"
    @ExceptionHandler(ServiceException.class)
    public CommonResult<?> handleServiceException(ServiceException ex) {
        return CommonResult.error(ex.getCode(), ex.getMessage());
    }

    // 2. 参数校验失败：比如 @NotBlank 标注的字段传了空值
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public CommonResult<?> handleValidException(MethodArgumentNotValidException ex) {
        // 从一堆校验结果里，取出第一条错误信息就够了
        String msg = ex.getBindingResult().getFieldError().getDefaultMessage();
        return CommonResult.error(400, "参数不对：" + msg);
    }

    // 3. 其他所有没预料到的异常（空指针、数据库挂了...）
    @ExceptionHandler(Exception.class)
    public CommonResult<?> handleUnknownException(Exception ex) {
        log.error("[系统异常]", ex);                    // 详细堆栈只写进日志
        return CommonResult.error(500, "服务器开小差了"); // 对外只说人话
    }
}
```
> 🔒 **安全提醒**：第 3 个方法里**绝对不要把异常堆栈直接返回给前端**，会把数据库表结构、文件路径全暴露出去。只写日志，对外给一句友好提示。

#### ③ 自定义业务异常
```java
/** 业务异常：想报错就 throw 它，比如 throw new ServiceException("库存不足") */
public class ServiceException extends RuntimeException {
    private Integer code;   // 错误码，前端可以按不同 code 走不同逻辑
}
```

#### ④ 必备工具类
`ServletUtils`（拿 request/response）、`JsonUtils`（JSON 转换）、`DateUtils`（时间处理）、`BeanUtils`（对象属性拷贝）、`IpUtils`（拿真实 IP）、`AssertUtils`（不满足条件就抛异常）。

> 💡 **关键点**：`code` 一定用**错误码常量**，别在代码里到处写 `400`、`500` 这种魔法数字。
> 原因：以后要改错误码对应文案时，改一个常量就行，不用满项目搜索替换。

### 2.3 第 3 步：接入 MyBatis-Plus（让 CRUD 不再手写）

**大白话**：MyBatis-Plus 帮你把"增删改查"这些重复 SQL 全写好了，你继承一下就有。

#### ① 配置文件
```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/yudao?useSSL=false&serverTimezone=Asia/Shanghai
    username: root
    password: root
    # 换成达梦数据库见 [[09_达梦 DM 数据库]]

mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true   # 自动把 create_time 转成 createTime
  global-config:
    db-config:
      logic-delete-field: deleted        # 删除 = 打个标记，不是真删数据
      logic-delete-value: 1              # 1 表示已删除
      logic-not-delete-value: 0          # 0 表示没删
      id-type: ASSIGN_ID                 # ID 用雪花算法自动生成（分布式不重复）
```

#### ② 插件配置（重点，注意顺序）
```java
@Configuration
public class MybatisConfig {

    /**
     * MyBatis-Plus 的"插件链"——每个插件都是一个"拦截器"，
     * 会在 SQL 执行前后动手脚。顺序很重要！
     */
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();

        // 分页插件：让你传页码就能返回分页结果，不用手写 LIMIT
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));

        // 乐观锁插件：防止两个人同时改同一条数据互相覆盖（配合 @Version 注解）
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());

        // 多租户插件：自动给每条 SQL 拼上 tenant_id（进阶篇细讲）
        // interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(tenantHandler));

        return interceptor;
    }

    // 自动填充：插入数据时自动填上创建时间/创建人，更新时自动填更新时间
    @Bean
    public MetaObjectHandler metaObjectHandler() {
        return new MetaObjectHandler() {
            @Override
            public void insertFill(MetaObject metaObject) {
                this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
                this.strictInsertFill(metaObject, "creator", String.class, getCurrentUsername());
            }
            @Override
            public void updateFill(MetaObject metaObject) {
                this.strictUpdateFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
                this.strictUpdateFill(metaObject, "updater", String.class, getCurrentUsername());
            }
        };
    }
}
```

#### ③ 公共实体基类（所有表都有的字段抽出来）
```java
@Data
public class BaseDO {
    @TableId(type = IdType.ASSIGN_ID)              // 雪花算法自动生成 ID，不用数据库自增
    private Long id;

    @TableField(fill = FieldFill.INSERT)           // 插入时自动填（配合上面的 MetaObjectHandler）
    private LocalDateTime createTime;

    @TableField(fill = FieldFill.INSERT_UPDATE)    // 插入和更新时都自动填
    private LocalDateTime updateTime;

    @TableField(fill = FieldFill.INSERT)
    private String creator;                        // 创建人

    @TableField(fill = FieldFill.UPDATE)
    private String updater;                        // 修改人

    @TableLogic                                    // 逻辑删除标记：删除时自动改成 UPDATE deleted=1
    private Boolean deleted;
}
```
**以后每个实体类继承它就自动有这些字段**，不用每张表重复写：
```java
@Data
@TableName("sys_notice")
public class NoticeDO extends BaseDO {
    private String title;      // 只需要写业务字段
    private String content;
}
```

> 分页、条件构造器（Wrapper）、乐观锁的详细用法见 [[06_MyBatis 与 MyBatis-Plus]]。

### 2.4 第 4 步：登录认证（验明身份）

**大白话**：解决"你是谁"的问题。用户登录一次，拿到一张"工牌"（token），之后每次请求都带上它。

#### 两种方案选一个就行
| 方案 | 大白话特点 | 什么时候选 |
|---|---|---|
| **Spring Security + JWT** | 业界标准，功能全，但配置有点啰嗦 | 要接第三方登录（微信/钉钉）、要标准 OAuth2 |
| **Sa-Token** | 国产轻量，一个注解搞定，中文文档好 | 纯内部后台系统，团队追求快速上手 |

芋道两个都支持，默认是 Spring Security。下面用 Spring Boot 3 / Security 6 的写法：

```java
@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
          // ① 关掉 Session：我们用 JWT 令牌，不需要服务器记状态
          //    （Session 是"服务器记小本本"，JWT 是"你自己带着工牌"）
          .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))

          // ② 关掉 CSRF 防护：前后端分离 + 令牌放请求头里，用不上这个
          .csrf(AbstractHttpConfigurer::disable)

          // ③ 配置哪些路径不用登录就能访问
          .authorizeHttpRequests(a -> a
              .requestMatchers("/admin-api/system/auth/login").permitAll()  // 登录接口放行
              .requestMatchers("/actuator/**").permitAll()                  // 健康检查放行
              .anyRequest().authenticated())                                // 其他全要登录

          // ④ 插一个自己的过滤器：在正式校验前，先把请求头里的 token 解析出来
          .addFilterBefore(jwtAuthenticationTokenFilter,
                           UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}
```

#### JWT 过滤器：整个认证的核心，其实就三行逻辑
```java
/**
 * 每个请求进来都要过这一关。
 * 它的活儿：从请求头拿出令牌 → 解析出"这是谁" → 记到上下文中，后面业务随时能取。
 */
public class JwtAuthenticationTokenFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        // ① 拿令牌：从请求头 Authorization: Bearer xxxxx 里取
        String token = request.getHeader("Authorization");

        if (token != null && token.startsWith("Bearer ")) {
            token = token.substring(7);   // 去掉 "Bearer " 这 7 个字符

            // ② 解析令牌：验证签名有没有被篡改、有没有过期，解出用户信息
            LoginUser loginUser = jwtUtils.parseToken(token);

            if (loginUser != null) {
                // ③ 存到上下文：相当于在本次请求范围内贴了个标签
                //    后面任何地方都能用 SecurityFrameworkUtils.getLoginUser() 拿到"当前是谁"
                SecurityContextHolder.getContext().setAuthentication(
                    new UsernamePasswordAuthenticationToken(
                        loginUser, null, loginUser.getAuthorities()));
            }
        }
        chain.doFilter(request, response);   // 放行，继续执行后面的逻辑
    }
}
```
**从此业务代码里随时能知道"当前登录的是谁"**：
```java
LoginUser user = SecurityFrameworkUtils.getLoginUser();
Long userId = user.getId();      // 当前用户 ID
```

#### 完整登录流程（背下来）
```
1. 校验验证码（从 Redis 里比对，防止机器暴力破解）
2. 根据用户名查数据库，拿到用户信息
3. 用 BCrypt 比对密码（BCrypt 是单向加密，数据库里存的不是明文，连管理员都看不到你的密码）
4. 校验通过 → 生成 JWT 令牌
5. 把用户权限列表存进 Redis（key = login:token:{uuid}），下次不用查库
6. 把令牌返回给前端，前端存起来，之后每个请求都带上
```

> 认证/授权的区别、OAuth2 授权码流程、JWT 怎么做到"登出即失效"，
> 见 [[20_Spring Security 与 OAuth2-JWT 安全认证]]。

### 2.5 第 5 步：授权 RBAC 权限模型（你能干什么）

**大白话**：解决"你能干什么"。认证是"你是谁"，授权是"你能进哪个门"。

#### 五张表搞定（这是业界标准模型，务必背下来）
```
sys_user         用户表    —— 谁
sys_role         角色表    —— 有什么身份（比如：管理员、财务、普通员工）
sys_menu         菜单表    —— 有哪些功能（type 区分：目录 / 菜单 / 按钮）
sys_user_role    用户-角色 —— 谁是什么身份（一个人可以有多个身份）
sys_role_menu    角色-菜单 —— 什么身份能用什么功能
```
**关系一目了然**：
```
张三 ──(用户-角色)──> 财务专员 ──(角色-菜单)──> [查看报表] [导出报表] [审核]
                                              ↑
                              这些就是"权限标识"，比如 report:finance:export
```

#### 后端校验：在接口上加一行注解
```java
@GetMapping("/user/page")
@PreAuthorize("@ss.hasPermission('system:user:query')")   // 有这个权限才放行
public CommonResult<PageResult<UserRespVO>> page(UserPageReqVO req) { ... }
```
```java
/**
 * @PreAuthorize 里 "@ss.xxx" 的意思是：调用名为 ss 的 Bean 的 xxx 方法，返回 true 才放行。
 */
@Component("ss")    // 这个 "ss" 就是上面 @ss 引用的名字
public class PermissionServiceImpl {

    public boolean hasPermission(String permission) {
        LoginUser user = SecurityFrameworkUtils.getLoginUser();  // 当前登录用户

        if (user.isSuperAdmin()) {
            return true;    // 超级管理员：所有权限都有，直接放行
        }
        // 普通用户：看他登录时缓存到 Redis 的权限列表里，有没有这个标识
        return user.getPermissions().contains(permission);
    }
}
```

#### 前端控制：按钮该不该显示
登录时把权限标识列表返回给前端，前端用指令控制显隐：
```html
<!-- 没有 system:user:delete 权限的人，这个按钮根本不显示 -->
<el-button v-hasPermi="['system:user:delete']">删除</el-button>
```

> ⚠️ **极其重要的安全提醒**：**前端隐藏按钮只是让用户看着舒服，不是真正的安全！**
> 懂行的人直接抓包改请求，照样能调你的接口。**真正的权限校验必须在后端接口上做**，这是最常见的越权漏洞来源，也是面试必问点。

#### 菜单动态路由
后端根据用户的角色，返回**树形菜单**（包含页面路径、图标、排序），前端拿着它动态注册路由。
**所以：不同角色的人登录进去，看到的左侧菜单栏是不一样的。**

### 2.6 第 6 步：数据权限（最难的一块，慢点看）

#### 先搞懂要解决什么问题
| 角色 | 打开"销售订单"页面应该看到 |
|---|---|
| 老板 | 全公司所有订单 |
| 华东区经理 | 华东区 + 下面城市的所有订单 |
| 普通销售 | 只有自己开的那几单 |

**笨办法**：每个查询都手写一遍 `WHERE 部门 IN (...)` → 几十个接口要写几十遍，改需求时改到崩溃。

**聪明办法**：**你只写干净的业务 SQL，框架在 SQL 真正执行到数据库之前，偷偷帮你加上范围限制。**

#### 实现三步走

**第 1 步：定义一个注解，用来"声明"这个接口需要什么数据范围**
```java
/**
 * 加在方法上，声明"这个查询要按什么范围过滤数据"
 */
@Target({METHOD, TYPE})
public @interface DataPermission {
    // 能看多大范围（可选值见下）
    DataScopeEnum value() default DataScopeEnum.DEPT_AND_CHILD;

    String deptAlias() default "dept_id";     // 表里的"部门"字段叫什么
    String userAlias() default "create_by";   // 表里的"创建人"字段叫什么
}
```
可选的数据范围（用自然语言理解）：
```
ALL            全部数据，想看啥看啥（老板）
DEPT_CUSTOM    自定义几个部门，比如"华东区 + 华南区"
DEPT_ONLY      只能看自己所在部门
DEPT_AND_CHILD 自己部门 + 所有下属部门（部门经理）
SELF           只能看自己创建的（普通员工）
```

**第 2 步：AOP 切面 —— 把注解上的规则先"记下来"**
```java
/**
 * 方法执行前：把注解信息塞进"当前线程的便签纸"（ThreadLocal）
 * ThreadLocal = 每个线程独有的小本本，只有这个线程能看，互不干扰
 */
@Around("@annotation(dataPermission)")     // 拦截所有加了 @DataPermission 的方法
public Object around(ProceedingJoinPoint jp, DataPermission dataPermission) {
    DataPermissionContextHolder.add(dataPermission);   // 记到便签纸上
    try {
        return jp.proceed();          // 执行真正的业务方法（里面会查数据库）
    } finally {
        DataPermissionContextHolder.clear();   // 用完必须擦掉！否则下一个请求会读到脏数据
    }
}
```

**第 3 步：MyBatis 拦截器 —— 真正去改 SQL**
```java
/**
 * 这个拦截器会在每条 SQL 送到数据库之前被调用。
 * 它的活儿：看看便签纸上有没有"数据范围"要求，有的话就往 SQL 里拼条件。
 */
@Intercepts(@Signature(type = StatementHandler.class, method = "prepare",
                       args = {Connection.class, Integer.class}))
public class DataPermissionInterceptor implements Interceptor {

    @Override
    public Object intercept(Invocation invocation) throws Throwable {

        // ① 先看便签纸：这次查询有没有数据范围要求？
        DataPermission dp = DataPermissionContextHolder.get();
        if (dp == null) {
            return invocation.proceed();   // 没有要求 → 原样放行，不改 SQL
        }

        // ② 拿到程序员写的原始 SQL
        String originSql = getSql(invocation);

        // ③ 用 JSqlParser（一个能"读懂"SQL 的工具）解析，然后追加 WHERE 条件
        String newSql = buildDataScopeSql(originSql, dp, currentUser);

        // ④ 把改好的 SQL 塞回去，让数据库执行这条改过的 SQL
        setSql(invocation, newSql);

        return invocation.proceed();
    }
}
```

**最终效果**（对照着看最直观）：
```sql
-- 程序员写的（干净、只关心业务）：
SELECT * FROM sys_user WHERE status = 1

-- 部门经理登录后，实际执行的：
SELECT * FROM sys_user WHERE status = 1 AND dept_id IN (10, 11, 12)

-- 普通员工登录后，实际执行的：
SELECT * FROM sys_user WHERE status = 1 AND create_by = 10086
```

> **这就是"零侵入"**：业务代码里一个数据权限的字眼都没有，但权限已经生效了。
> 面试时能把这条链路（注解 → AOP 存 ThreadLocal → 拦截器改 SQL）讲清楚，非常加分。

#### 五个必踩的坑（血泪经验）
1. **ThreadLocal 用完必须 clear** —— 尤其是用了线程池的场景，线程是复用的！不清理的话，A 用户可能看到 B 用户的数据范围，**这是严重的数据泄露事故**。上面的 `finally` 块就是干这个的。
2. **拦截器顺序有讲究** —— 数据权限必须在分页统计总数**之前**生效，否则"总数 100 条"但列表只有 10 条，对不上。
3. **复杂 SQL 容易改错** —— 子查询、UNION、多表联查时，自动改写可能出错，记得给表起别名。
4. **和数据缓存冲突** —— 同样一条 SQL，不同用户结果不同！所以**缓存的 key 里必须带上用户 ID**，否则张三会看到李四的数据。
5. **别用 `${}` 拼接参数** —— 有 SQL 注入风险，一律用 `#{}（详见 [[06_MyBatis 与 MyBatis-Plus]]）。

### 2.7 第 7 步：可插拔的便利能力（加个注解就生效）

**大白话**：这一步决定了你的框架"好不好用"。套路都是一样的 —— **一个注解 + 一个切面 + 一个 Redis 工具**。

#### ① 分布式锁：防止多人同时改同一份数据
```java
// 用法：秒杀扣库存时，同一个商品必须排队，不能同时扣
@RedisLock(value = "'seckill:' + #req.productId", waitTime = 3)
public void deductStock(SeckillReq req) { ... }
```
**大白话**：给这把操作加把锁，同一个商品 ID 只能一个人操作，其他人排队等（最多等 3 秒，等不到就报错）。
**为什么用 Redisson**：它有个"看门狗"机制，业务没执行完会自动给锁续期，不会莫名其妙锁过期。比自己手写 `setnx` 稳得多。

#### ② 幂等：防止重复提交
```java
@Idempotent(timeout = 5, message = "请勿重复提交")
public Long createOrder(OrderReq req) { ... }
```
**大白话**：用户手抖点了两下"提交"，只能成功一次。
**原理**：用"方法名 + 参数 + 用户ID"算个指纹当 key，5 秒内这个指纹只放行一次。

#### ③ 限流：防止被刷
```java
@RateLimiter(count = 10, time = 60, message = "操作过于频繁")
```
**大白话**：60 秒内最多操作 10 次，超了就拒绝。
**和网关限流的区别**：网关是"小区大门口限流"，防整体洪峰；这个是"某个具体接口限流"，防单点被刷。

#### ④ 操作日志：谁在什么时候干了什么
```java
@OperateLog(module = "用户管理", operation = "新增用户")
public Long createUser(UserSaveReqVO req) { ... }
```
自动记录：操作人、IP 地址、耗时、请求参数、返回结果、是否报错。
> ⚠️ **一定要异步入库**（丢给线程池去写），否则会拖慢主流程。
> ⚠️ **一定要定期归档清理**，日志表涨得飞快，我见过半年涨到几千万行把数据库拖垮的生产事故。

#### ⑤ 字典翻译：自动把 1 变成"男"
```java
@Dict(type = "sys_user_sex")    // 返回给前端时，1 自动变成 "男"，0 变成 "女"
private Integer sex;
```
**大白话**：数据库存 1/0（省空间），前端要显示"男/女"（给人看），这个转换框架自动做。
> 注意：字典数据要缓存起来，且**改动字典时要清缓存**，否则改了后台不生效。

#### ⑥ 参数校验：不用写 if 判断
```java
@Data
public class UserSaveReqVO {
    @NotBlank(message = "用户名不能为空")
    private String username;

    @Email(message = "邮箱格式不对")
    private String email;
}

// Controller 里加个 @Valid 就自动校验了
public CommonResult<Long> create(@Valid @RequestBody UserSaveReqVO req) { ... }
```
校验失败会自动抛异常，被 2.2 步的全局异常处理器接住，返回 `"用户名不能为空"`。

> **这一节的核心思想**：**业务代码只加一行注解，脏活累活框架全兜了**。这就是"脚手架"的价值所在。

### 2.8 第 8 步：代码生成器（提效 10 倍）

**大白话**：你建好数据库表，它照着你平时手写 CRUD 的套路，把整套代码"打印"出来。

#### 流程四步
```
读表结构 → 组装数据 → 套模板渲染 → 写成文件
```

**第 1 步：读取表结构**（数据库自己就存着这些信息）
```sql
-- 查 information_schema（数据库的"户口本"，记着所有表的字段信息）
SELECT column_name,        -- 字段名
       data_type,          -- 类型（varchar / int ...）
       column_comment,     -- 字段注释（所以建表时一定要写注释！）
       is_nullable,        -- 能不能为空
       column_key          -- 是不是主键
FROM information_schema.COLUMNS
WHERE table_schema = 'yudao' AND table_name = 'sys_notice';
```

**第 2、3 步：塞进模板引擎渲染**
```java
// Velocity 是一款模板引擎：模板 + 数据 = 最终文本
VelocityContext ctx = new VelocityContext();
ctx.put("tableName", "sys_notice");   // 表名
ctx.put("className", "Notice");       // 类名：去掉 sys_ 前缀，再转驼峰
ctx.put("columns", columns);          // 字段列表

// 遍历所有模板，每个模板生成一份文件
for (Template tpl : templates) {
    StringWriter sw = new StringWriter();
    tpl.merge(ctx, sw);                              // 把数据填进模板的 ${} 占位符
    writeFile(genPath + resolveFileName(tpl), sw.toString());  // 写成文件
}
```
**类比**：就像 Word 的"邮件合并"—— 模板是通知书，数据是收件人名单，一键生成几百份。

**第 4 步：生成哪些文件**（每个都对应你平时手写的那一份）
```
controller/NoticeController.java     ← 接口层
service/NoticeService.java           ← 接口
service/NoticeServiceImpl.java       ← 业务实现
manager/NoticeManager.java           ← 备菜间（还记得 1.2 讲的吗）
mapper/NoticeMapper.java             ← 数据访问
dataobject/NoticeDO.java             ← 实体类
vo/NoticeSaveReqVO.java              ← 新增/修改请求参数
vo/NoticeRespVO.java                 ← 返回结果
vo/NoticePageReqVO.java              ← 分页查询参数
sql/sys_notice.sql                   ← 菜单 SQL（自动把菜单和按钮权限插进数据库）
views/notice/notice.vue              ← 前端页面（表格 + 表单 + 分页，全齐了）
```

```java
@RestController
```

### 2.9 第 9 步：微服务化（单体跑通了再拆）

#### 什么时候才该拆？
```
单体（一个 jar 包搞定全部）
   ↓ 出现以下情况才考虑拆：
   • 团队超过 10 个人，改同一份代码天天冲突
   • 某个模块需要独立扩容（比如文件服务压力大，想单独加机器）
   • 一个模块发布要拖着整个系统重启
   ↓
微服务：Gateway + Nacos + OpenFeign + Sentinel + Seata
```

#### 拆成什么样
```
yudao-gateway        门卫：验令牌、查权限、限流、指路
yudao-module-system  用户/角色/菜单/权限（所有人都依赖它，对外提供远程接口）
yudao-module-infra   文件/定时任务/日志
yudao-module-bpm     工作流审批
```

#### 服务之间怎么调用
```java
/**
 * Feign = 声明式远程调用
 * 大白话：写个接口，加个注解，调用的时候就像调本地方法一样简单，
 *        底层帮你发 HTTP 请求、做负载均衡。
 */
@FeignClient(name = "system-server",                 // 要调哪个服务
             fallbackFactory = UserApiFallback.class) // 对方挂了怎么办
public interface UserApi {
    @GetMapping("/rpc/user/get")
    CommonResult<UserDTO> getUser(@RequestParam("id") Long id);
}

// 调用方：就像调本地方法
UserDTO user = userApi.getUser(id).getData();
```

#### 网关怎么指路
```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: system-server
          uri: lb://system-server        # lb = load balance，从 Nacos 找服务并负载均衡
          predicates:
            - Path=/admin-api/system/**  # 这类路径的请求转给 system 服务
          filters:
            - StripPrefix=1              # 转发时去掉第一级路径
```

#### 拆分四条铁律（记住能少踩无数坑）
1. **先拆共用能力，再拆业务** —— 用户、权限、字典、文件这些谁都要用的，先下沉成公共服务。
2. **数据库必须一起拆开** —— 服务拆了但共用一张库，那叫"分布式单体"，比单体还糟糕（改表结构要所有人一起改）。
3. **别在循环里调远程接口** —— 查 100 条订单，循环里调 100 次用户服务 = 100 次网络请求，慢到爆。要改成"批量查询接口"一次性查回（这就是著名的 N+1 问题）。
4. **必须配降级方案** —— 对方服务挂了，你的服务不能跟着崩。要有 `fallback`（降级返回默认值）+ 熔断（连续失败就暂时不调了）。

## 三、进阶篇：硬骨头 + 面试怎么说

### 3.1 把通用能力打包成 Starter（框架化的关键一步）

**大白话**：前面写的那些通用代码（统一返回、锁、日志…），别每个项目复制粘贴，打包成一个 jar，新项目引个依赖就全都有了。

芋道就是这么组织的：`yudao-spring-boot-starter-web`、`-security`、`-mybatis`、`-redis`、`-excel`。

**怎么做？两步：**

```java
// ① 写个自动配置类
@AutoConfiguration                          // 声明：我是一个自动配置类
@ConditionalOnClass(RedisTemplate.class)    // 条件：项目里引入了 Redis 才生效
@EnableConfigurationProperties(YudaoRedisProperties.class)  // 允许用 yml 配置参数
public class YudaoRedisAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean   // 条件：如果用户自己没定义这个 Bean，才用我这个
    public RedisCacheManager cacheManager(...) { ... }
}
```
```properties
# ② 在固定位置写个"清单文件"，告诉 Spring Boot 来加载我
# 文件路径：resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
# 文件内容就是类的全限定名：
cn.iocoder.yudao.framework.redis.config.YudaoRedisAutoConfiguration
```

**原理一句话**（面试必背）：
> Spring Boot 启动时会扫描所有 jar 包里的这个清单文件 → 按 `@Conditional` 条件筛选（有没有这个依赖、用户有没有自己定义）→ 把符合条件的 Bean 装配进容器。

**为什么叫"可插拔"**：因为有了 `@ConditionalOnMissingBean`，**用户自己定义一个同名的 Bean 就能覆盖框架默认的**。想要默认行为就别管，想定制就自己写一个。

> 这背后的自动配置原理详见 [[05_SpringBoot 核心]]，这是 Spring Boot 最核心的设计思想。

### 3.2 多租户：一套系统服务多家公司

**大白话**：你做的系统要同时卖给 A 公司和 B 公司，两边数据绝对不能串。

#### 三种方案怎么选
| 方案 | 大白话 | 成本 | 什么时候用 |
|---|---|---|---|
| **独立数据库** | 一家公司一个数据库，彻底隔离 | 最贵，运维会累死 | 金融、医疗这类大客户，数据必须物理隔离 |
| **独立 Schema** | 同一个库，但每家一套表 | 中等 | 中型客户 |
| **共享表 + tenant_id** | 大家共用表，每行数据打个"属于哪家"的标记 | 最便宜 | **绝大多数 SaaS 都这么干**（芋道默认） |

#### 共享表方案怎么实现（自动拼条件）
```java
@Bean
public TenantLineInnerInterceptor tenantInterceptor() {
    return new TenantLineInnerInterceptor(new TenantLineHandler() {

        // 当前用户的租户号是多少（从 ThreadLocal 便签纸上取）
        public Expression getTenantId() {
            return new LongValue(TenantContextHolder.getTenantId());
        }

        // 标记租户的字段名
        public String getTenantIdColumn() {
            return "tenant_id";
        }

        // 哪些表不需要隔离（比如字典表、租户表本身，是全局共用的）
        public boolean ignoreTable(String tableName) {
            return IGNORE_TABLES.contains(tableName);
        }
    });
}
```
**效果**：你写 `SELECT * FROM 订单`，实际执行的是 `SELECT * FROM 订单 WHERE tenant_id = 1001`（1001 是当前用户所属公司）。

#### 三个隐蔽的坑
1. **唯一索引必须带上 tenant_id** —— 否则 A 公司建了个叫"财务部"的部门，B 公司就建不了同名部门了（索引冲突）。正确做法：`UNIQUE(tenant_id, name)`。
2. **定时任务要临时关掉租户过滤** —— 比如"每天凌晨统计所有公司的数据"，这时候要 `TenantContextHolder.clear()`，否则只能统计到一个公司的。
3. **线程池里拿不到租户号**（最隐蔽的 bug）—— ThreadLocal 不会自动传给子线程。异步任务、线程池里执行的代码，租户号是空的，会导致 SQL 拼错。**要么手动传参，要么用 TTL（阿里开源的 TransmittableThreadLocal）包装线程池。**

### 3.3 分布式事务：别一上来就上 Seata

**大白话**：一个操作要同时改两个数据库（或两个服务），怎么保证要么都成功、要么都失败？

| 场景 | 方案 | 说明 |
|---|---|---|
| 同一个数据库 | `@Transactional` | Spring 自带的就够用，**别过度设计** |
| 跨服务 | **最终一致** | 允许短暂不一致，靠补偿任务慢慢对齐。性能好，推荐 |
| 非要强一致 | **Seata AT** | 性能损耗 30%+，热点数据还会锁竞争 |

**最终一致怎么做**（最实用）：
```
1. 订单服务：创建订单（本地事务，一定成功）
2. 同时往"消息表"插一条"待扣库存"的记录（同一个本地事务）
3. 后台任务定时扫描消息表，去调用库存服务扣库存
4. 扣成功 → 标记完成；扣失败 → 重试 N 次，还失败就告警人工介入
```

> 💡 **判断口诀**：**能用"事后补偿"解决的，就别上分布式事务。**
> 只有信贷、资金、支付这类"一分钱都不能错"的场景，才值得上 Seata。

### 3.4 上线前安全检查清单（逐条对照）

- **水平越权** —— 改个 `userId` 参数就能看别人的数据？→ 所有查询都要带数据范围或归属校验（见 2.6）
- **垂直越权** —— 普通用户直接调管理员接口能通？→ 后端每个接口都要有 `@PreAuthorize`，**不能只靠前端隐藏按钮**
- **SQL 注入** —— MyBatis 里用 `#{} 别用 `${}`；排序字段（ORDER BY）要做白名单校验
- **XSS 攻击** —— 用户输入的富文本内容，输出前要转义；Vue 里慎用 `v-html`
- **敏感信息泄露** —— 日志里的手机号/身份证/银行卡要打码；返回给前端的对象里别带 `password` 字段
- **文件上传** —— 别信前端传的 content-type（可以伪造），要校验真实文件类型、大小；Minio 密钥绝不能下发到前端
- **接口幂等** —— 支付、下单、审批这类接口，用户点两下不能产生两条记录
- **配置安全** —— `application.yml` 里别写明文密码，用 Nacos 配置中心 + 环境变量

### 3.5 面试怎么讲这个项目（加分模板）

> ❌ **减分说法**："我们公司用了芋道框架，我在上面写了增删改查。"（等于说"我只是在别人的地基上搬砖"）
>
> ✅ **加分说法**：
> "我在公司基于芋道搭建了内部脚手架，**不是直接用，而是做了改造**：
> 1. 把通用能力抽成 5 个 starter（web/security/mybatis/redis/excel），新项目引依赖即用，**项目接入时间从 2 天缩到 2 小时**；
> 2. 用 MyBatis 拦截器 + JSqlParser 实现数据权限，业务 SQL 零侵入，覆盖了 40 多个查询接口；
> 3. 过程中发现数据权限的 ThreadLocal 在线程池场景会串权限，我用 TTL 传递 + finally 强制清理解决了；
> 4. 大屏项目 IoT 消息积压，我用本地缓存 + 线程池削峰解决（见 [[15_高并发高可用设计]]）。"

**核心原则**：**讲改造 > 讲使用**。能说清"我改了什么、为什么改、踩了什么坑、效果提升了多少"，才是真的用过。

### 3.6 常见坑速查表（出问题先来这儿找）

| 现象 | 最可能的原因 | 怎么解决 |
|---|---|---|
| 数据权限偶尔失效、看到别人的数据 | ThreadLocal 没清理，或线程池里传丢了 | `finally` 里强制清理 + 用 TTL 包装线程池 |
| 分页显示总数 100 条，但列表只有 10 条 | 分页插件和数据权限拦截器的顺序错了 | 数据权限拦截器要**先于**分页生效 |
| 给角色改了权限，但不生效 | 权限缓存在 Redis 里没清 | 改权限时删掉对应的 Redis key，或缩短过期时间 |
| 字典改了，页面上还是老的 | 字典缓存是脏的 | 改字典时清缓存；系统启动时预热 |
| 操作日志表把数据库撑爆了 | 没有归档清理策略 | 定时归档到历史表，或按月分表 |
| 接口很慢，CPU 却不高 | 循环里调用了远程接口（N+1 问题） | 改成批量查询接口，一次查回 |
| 启动报错"循环依赖" | 两个 Service 互相注入 | 抽到 Manager 层（见 1.2） |
| 逻辑删除的数据还能查出来 | 手写 SQL 忘了加 `deleted = 0` | 统一用 MP 的条件构造器；手写 SQL 时显式加上 |
| 分布式部署后雪花 ID 重复 | 多台机器用了相同的 workerId | 每台机器配不同的 workerId，或改用 Redis 发号 |

### 3.7 动手学习路线（照着做就能学会）

1. **跑通** —— 把 yudao-cloud 拉下来本地跑起来（用 Docker 一键起 MySQL/Redis/Nacos，见 [[17_Docker容器排错]]）
2. **拆** —— 删掉一个模块（比如工作流模块），看看启动报什么错、缺什么依赖，借此理解模块之间的边界
3. **仿** —— 照着本文 9 步，从一个空的 Maven 工程手写个 mini 版。**能做到第 2.6 步的数据权限，就算出师了**
4. **改** —— 给它加一个自己的 starter（比如 `@TenantLog` 租户操作日志）
5. **讲** —— 把 3.5 的话术对着镜子讲一遍。**讲不顺，说明还没真懂**
