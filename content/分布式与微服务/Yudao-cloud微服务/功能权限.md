# 功能权限（RBAC + Token + 权限注解）

> **一句话概括**：用 **RBAC 模型**（用户 → 角色 → 菜单/按钮）控制"你能不能按这个按钮"，用 **`@PreAuthorize("@ss.hasPermission('system:user:list')")`** 一个注解实现接口级鉴权。

---

## 零、先建立整体印象：公司的门禁卡

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

一家公司里，不同的人能去的地方不一样：

| 人 | 能进的地方 |
|---|---|
| 实习生 | 工位、茶水间 |
| 部门经理 | + 会议室、本部门档案柜 |
| 老板 | 所有地方（含财务室） |

如果给**每个人**单独配权限，500 个员工要配 500 次，新来一个配一次 —— 累死。

聪明做法：先定义**角色**（实习生/经理/老板），把**权限挂在角色上**，再把**角色发给员工**。

```
员工（User）──属于──→ 角色（Role）──拥有──→ 权限（菜单/按钮）
```

这就是 **RBAC（Role-Based Access Control，基于角色的访问控制）**。

新人入职？给他发个"实习生"工牌就行，不用一条条配权限。**这就是 RBAC 的全部价值**。

## 一、原理篇

### 1.1 RBAC 模型

```
    ┌────────┐         ┌────────┐        ┌──────────────┐
    │  用户   │  多对多  │  角色   │  多对多 │  菜单 / 按钮   │
    │  User  │◄───────►│  Role  │◄──────►│    Menu      │
    └────────┘         └────────┘        └──────────────┘
                                                │
                                          ┌─────┴─────┐
                                          │ 权限标识    │
                                          │system:user:list│
                                          └───────────┘
```

**权限标识格式**（推荐）：`${系统}:${模块}:${操作}`

例如 `system:admin:add` = system 系统的 admin 模块的 add 添加操作。

### 1.2 Token 认证机制 ⭐

#### 为什么不用 Spring Security 内置的表单登录？

> **官方原话**："Spring Security 的登录拓展起来不方便，例如说验证码、三方登录等等。"

表单登录是"能用但不好改"，企业项目需要验证码、短信登录、微信登录、SSO……自己实现更灵活。

#### 为什么不用 JWT？（重要）⭐

> **官方原话**：
> > "JWT 是无状态的，**无法实现 Token 的作废**，例如说用户登出系统、修改密码等等场景。"

这是**很多人的误区** —— 觉得 JWT 高级就用 JWT。但 JWT 一旦签发，在过期前**无法主动失效**。

| 场景 | JWT | 数据库/Redis Token |
|---|---|---|
| 用户点"退出登录" | ❌ Token 仍然有效（除非前端删掉） | ✅ 服务端删除即失效 |
| 用户修改密码后踢掉旧设备 | ❌ 做不到 | ✅ 删除该用户所有 Token |
| 管理员封禁某用户 | ❌ 做不到 | ✅ 立即生效 |
| 服务端压力 | ✅ 无（不用查库） | ⚠️ 要查（但 Redis 缓存后很快） |

**芋道的方案**：Token 存数据库（`system_oauth2_access_token` 表的 `id` 字段），并**缓存到 Redis**（`oauth2_access_token:%s`）—— 兼顾了可控性和性能。

> 💡 **一句话**：**需要"踢人下线"能力的系统，别用纯 JWT。** 这是架构选型的重要判断点。

#### Token 有效期

在 `system_oauth2_client` 表（`client_id = default`）配置：

| 字段 | 默认 | 含义 |
|---|---|---|
| `access_token_validity_seconds` | 1800 秒（**30 分钟**） | 访问令牌有效期 |
| `refresh_token_validity_seconds` | 2592000 秒（**30 天**） | 刷新令牌有效期 |

#### 请求格式

```http
Authorization: Bearer d2a3cdbc6c53470db67a582bd115103f
```

#### 开发调试神器：Token 模拟机制

```yaml
yudao:
  security:
    mock-enable: true     # 开启模拟
    mock-secret: test     # 前缀
```

```http
Authorization: Bearer test1     # = 模拟 userId=1 的用户
```

> 💡 调 Swagger / Postman 时不用每次先登录拿 Token，直接用 `test1`、`test2` 切换用户。**极大提升调试效率**。

## 二、应用篇

### 2.1 `@PreAuthorize` 权限注解 ⭐

#### 基于【权限标识】

```java
// 需要 system:user:list 权限
@PreAuthorize("@ss.hasPermission('system:user:list')")

// 有 add 或 edit 任一权限即可
@PreAuthorize("@ss.hasAnyPermissions('system:user:add,system:user:edit')")
```

#### 基于【角色标识】

```java
// 属于 user 角色
@PreAuthorize("@ss.hasRole('user')")

// 属于 user 或 admin 之一
@PreAuthorize("@ss.hasAnyRoles('user,admin')")
```

#### 完整示例

```java
@GetMapping("/page")
@Operation(summary = "获得用户分页")
@PreAuthorize("@ss.hasPermission('system:user:list')")   // 👈 一行搞定鉴权
public CommonResult<PageResult<UserRespVO>> getUserPage(@Valid UserPageReqVO pageVO) {
    return success(userService.getUserPage(pageVO));
}
```

#### 实现原理（面试会问）

```
@PreAuthorize("@ss.hasPermission('system:user:list')")
              │
              ├─ @ 符号 = 引用 Spring 容器里的 Bean
              ├─ ss = Bean 的名字，对应 PermissionServiceImpl 类
              └─ hasPermission(...) = 调用该 Bean 的方法，返回 true/false
```

返回 `false` → Spring Security 抛出权限不足异常 → 全局异常处理器返回 403。

### 2.2 `@PreAuthenticated` 认证注解（芋道自定义）

`@PreAuthorize` 管的是**权限**（你能不能做这个操作），`@PreAuthenticated` 管的是**认证**（你登录了没有）。

```java
@PostMapping("/update-password")
@PreAuthenticated        // 👈 声明：必须登录才能访问
public CommonResult<Boolean> updatePassword(@RequestBody @Valid AppAuthUpdatePasswordReqVO reqVO) {
    // ...
}
```

> 💡 **使用场景**：用户 App 的 `/app-api/**` 接口**默认无需登录**（方便浏览商品），需要登录的接口就加这个注解。

### 2.3 三种方式配置"匿名访问"

**默认规则**：
- `/admin-api/**`（管理后台）→ **必须登录**
- `/app-api/**`（用户 App）→ **无需登录**

想放开某些接口，有三种方式：

#### 方式一：`AuthorizeRequestsCustomizer`（模块级）

```java
@Configuration(value = "infraSecurityConfiguration")
public class SecurityConfiguration {

    @Bean("infraAuthorizeRequestsCustomizer")
    public AuthorizeRequestsCustomizer authorizeRequestsCustomizer() {
        return registry -> {
            // Swagger 接口文档
            registry.requestMatchers("/swagger-ui.html").permitAll()
                    .requestMatchers("/v3/api-docs/**").permitAll();
            // Spring Boot Actuator
            registry.requestMatchers("/actuator/**").permitAll();
            // Druid 监控
            registry.requestMatchers("/druid/**").permitAll();
            // 文件读取
            registry.requestMatchers(buildAdminApi("/infra/file/*/get/**")).permitAll();
        };
    }
}
```

#### 方式二：`@PermitAll` 注解（接口级，最省事）

```java
@GetMapping("/{configId}/get/{path}")
@PermitAll                    // 👈 允许匿名访问
public void getFileContent(HttpServletResponse response, ...) { ... }
```

#### 方式三：配置文件

```yaml
yudao:
  security:
    permit-all-urls:
      - /admin-ui/**
      - /admin-api/xxx/yyy
```

> ⚠️ **`permitAll()` vs `anonymous()` 的区别**（官方特别提示）：
> - `permitAll()`：**所有人**都能访问，带不带 Token 都行
> - `anonymous()`：**只有匿名用户**能访问，**带 Token 访问反而报错**
>
> 绝大多数场景用 `permitAll()`。

## 三、进阶篇

### 3.1 Spring Boot 2 vs 3 的 Security 配置差异 ⭐

芋道同时支持两个版本，配置写法不同：

| | Spring Boot 2.x（JDK 8） | Spring Boot 3.x（JDK 21） |
|---|---|---|
| 匹配方法 | `antMatchers(...)` | **`requestMatchers(...)`** |
| 放行方法 | `.anonymous()` | `.permitAll()` |
| 配置类 | `ExpressionUrlAuthorizationConfigurer...ExpressionInterceptUrlRegistry` | `AuthorizeHttpRequestsConfigurer...AuthorizationManagerRequestMatcherRegistry` |

```java
// ❌ Spring Boot 2.x 老写法
registry.antMatchers("/druid/**").anonymous();

// ✅ Spring Boot 3.x 新写法
registry.requestMatchers("/druid/**").permitAll();
```

> ⚠️ 芋道最新版基于 Spring Boot 3.2，**必须用 `requestMatchers`**。从老博客复制代码时注意。

### 3.2 权限校验的完整链路

```
① 前端请求带 Token
        │
        ▼
② TokenAuthenticationFilter 过滤器
   解析 Token → 查 Redis → 得到 LoginUser
        │
        ▼
③ 存入 SecurityContext（当前线程）
        │
        ▼
④ 进入 Controller 方法前，@PreAuthorize 拦截
   调用 PermissionServiceImpl.hasPermission(...)
        │
        ▼
⑤ 查该用户的角色 → 查角色的菜单权限 → 比对
        │
   ┌────┴────┐
   │ 有权限   │ 无权限 → 抛异常 → 403
   ▼
⑥ 执行业务方法
```

### 3.3 前端权限控制

后端管"接口能不能调"，前端还要管"**按钮要不要显示**"：

```vue
<!-- 方式一：指令 -->
<el-button v-hasPermi="['system:user:create']">新增</el-button>

<!-- 方式二：v-if 判断 -->
<el-button v-if="checkPermi(['system:user:create'])">新增</el-button>
```

> ⚠️ **前端权限只是"体验优化"，不是安全！** 用户可以直接调接口绕过前端。**后端 `@PreAuthorize` 才是真正的安全边界**。

### 3.4 生产坑位

| 坑 | 现象 | 解决 |
|---|---|---|
| **`@PreAuthorize` 不生效** | 没开 `@EnableMethodSecurity` | 芋道已配置；自己项目要加 |
| **同类内部调用不鉴权** | AOP 代理问题（同 `@Async`） | 移到别的类 / 注入自己 |
| **权限标识写错** | 一直报 403，查不出原因 | 检查 `system_menu.permission` 字段 |
| **Token 过期** | 突然所有接口 401 | 用 refresh_token 续期 |
| **忘记配匿名** | 登录接口本身也要登录，死循环 | 登录/验证码接口必须 `@PermitAll` |
| **权限缓存不刷新** | 改了角色权限，用户还是老权限 | 见 [[本地缓存]] 的广播刷新机制 |

## 四、一句话总结

| 问题 | 答案 |
|---|---|
| 权限模型 | **RBAC**：用户 → 角色 → 菜单/按钮 |
| 权限标识格式 | `${系统}:${模块}:${操作}`，如 `system:user:list` |
| 鉴权注解 | `@PreAuthorize("@ss.hasPermission('xxx')")` |
| 登录注解 | `@PreAuthenticated`（App 端接口用） |
| **为什么不用 JWT** | **无法主动作废**（登出、改密码、封号都做不到） |
| Token 有效期 | 访问令牌 30 分钟，刷新令牌 30 天 |
| 匿名访问 | `@PermitAll` / `AuthorizeRequestsCustomizer` / 配置文件 |
