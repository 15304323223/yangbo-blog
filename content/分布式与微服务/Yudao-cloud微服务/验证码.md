# 验证码

> **一句话概括**：芋道用 **AJ-Captcha** 实现**行为验证码**（滑动拼图 / 文字点选），比传统"输入扭曲字符"体验更好、更防机器。登录时前端弹验证码 → 用户滑一下 → 前端把结果随表单一起提交 → **后端必须做二次校验**（这步最容易被漏）。

**适合谁读**：要接入登录验证码、要做防刷的人。
**怎么读**：本篇比较短，「零」理解为什么用行为验证码，「一」的**二次校验**是安全核心，「三」是开关配置。

---

## 零、先建立整体印象：两种验证码的区别

### 传统字符型验证码（老式）

```
① 展示一张扭曲、带噪点的图片："A 7 f K"
② 用户眯着眼辨认，手动键盘输入
③ 后端比对字符串
```

**问题**：
- 😫 **用户体验差**：看半天还输错，尤其数字 0/O、1/l 分不清
- 🤖 **已经不难为机器了**：OCR + 打码平台轻松破解
- ♿ **无障碍差**：视障用户基本没法用

### 行为验证码（芋道采用 ✅）

```
① 展示一张图 + 一个缺口（滑动拼图），或者"请依次点击：苹 果 香 蕉"（文字点选）
② 用户用鼠标【拖】或【点】—— 不需要键盘输入
③ 后端比对：位置对不对 + 轨迹是不是人
```

> 官方解释为什么用它：*"相比传统字符型的'展示-填写-比对'流程，行为验证码是'展示-操作-比对'，用户只需要用鼠标产生指定的行为轨迹，不需要键盘手动输入，用户体验更好，更加难以被机器识别，更加安全可靠。"*

💡 **"行为轨迹"是关键**：机器可以轻松把滑块拖到正确位置，但**拖动的轨迹**（加速度、抖动、中间的犹豫）很难模拟成人。AJ-Captcha 会分析这条轨迹。

**两种类型**：
- **滑动拼图**（`blockPuzzle`）：把拼图拖到缺口里
- **文字点选**（`clickWord`）：按顺序点击图中的字

## 一、交互流程（5 步）⭐

```
┌──────┐                    ┌──────┐                  ┌──────────┐
│ 前端 │                    │ 后端 │                  │ 验证码服务 │
└──┬───┘                    └──┬───┘                  └────┬─────┘
   │ ① 用户访问登录页，请求显示验证码                     │
   │──────────────────────────>│                          │
   │                           │──── 生成底图+缺口 ──────>│
   │<──────────────────────────│<─────────────────────────│
   │                                                      │
   │ ② 用户拖动滑块完成拼图                                │
   │                                                      │
   │ ③ 提交登录表单（带上验证码的输出结果 captchaVerification）│
   │──────────────────────────>│                          │
   │                           │ ④ 后端【二次校验】⭐      │
   │                           │──── verification() ─────>│
   │                           │<──── 通过 / 失败 ────────│
   │ ⑤ 返回登录结果             │                          │
   │<──────────────────────────│                          │
```

### ⚠️ 第 ④ 步是安全核心

**千万不能只靠前端校验！**

```java
// ❌ 错误：前端拿到"验证通过"就信了，直接放行登录
// 攻击者可以抓包，把 captchaVerification 改成任意值，或者干脆不传

// ✅ 正确：后端必须自己调一次 verification 做二次校验
@PostMapping("/login")
public CommonResult<AuthLoginRespVO> login(@RequestBody @Valid AuthLoginReqVO reqVO) {
    // 二次校验验证码
    // 失败会抛异常，被全局异常处理器转成 400
    captchaService.verification(reqVO.getCaptchaVerification());

    // 校验通过，才继续走登录逻辑
    return success(authService.login(reqVO, ...));
}
```

💡 **为什么必须后端二次校验？**

前端的校验结果**可以被篡改**。攻击者用 Burp Suite 抓包，把 `captchaVerification` 改成 `"passed"` —— 如果后端不校验，验证码就形同虚设。

**后端二次校验的本质**：用只有服务端知道的密钥，重新验证前端传来的那段加密串是不是真的。

## 二、配置说明

### 2.1 Maven 依赖

```xml
<dependency>
    <groupId>cn.iocoder.boot</groupId>
    <artifactId>yudao-spring-boot-starter-captcha</artifactId>
</dependency>
```

⚠️ **注意**：用的是 **captcha-plus**，不是原版 AJ-Captcha。

> 官方：*"由于 AJ-Captcha 对 Spring Boot 3.X 版本的支持还不完善，所以使用 captcha-plus 替代，它是基于 AJ-Captcha 进行增强。"*

💡 芋道 Boot 3 版本（Spring Boot 3.2.0）用原版 AJ-Captcha 会报错，captcha-plus 是社区/芋道的兼容增强版。

### 2.2 application.yaml 配置（带注释版）

```yaml
aj:
  captcha:
    # 滑动验证底图路径，不配置使用默认图片
    # classpath: 开头表示取 resource 目录下路径
    jigsaw: classpath:images/jigsaw

    # 文字点选底图路径
    pic-click: classpath:images/pic-click

    # 缓存类型：local / redis
    # ⚠️ 集群部署必须设成 redis，否则请求打到别的机器就校验失败
    cache-type: redis

    # local 缓存的阈值，达到这个值清除缓存
    cache-number: 1000

    # local 定时清除过期缓存（秒），0 表示不执行
    timing-clear: 180

    # 验证码类型
    #   blockPuzzle = 滑块拼图
    #   clickWord   = 文字点选
    #   default     = 两种都实例化（前端自己选）
    type: blockPuzzle

    # 右下角水印文字
    # Linux 上中文可能需要转 Unicode（用 https://tool.chinaz.com/tools/unicode.aspx）
    water-mark: 芋道源码

    # 滑动干扰项：0 / 1 / 2
    interference-options: 0

    # ========== 防刷限流 ==========
    req-frequency-limit-enable: false  # 是否开启接口请求次数限制

    req-get-lock-limit: 5              # 验证失败 5 次，get 接口锁定
    req-get-lock-seconds: 10           # 锁定时间间隔（秒）
    req-get-minute-limit: 30           # get 接口一分钟内请求数限制
    req-check-minute-limit: 60         # check 接口一分钟内请求数限制
    req-verify-minute-limit: 60        # verify 接口一分钟内请求数限制
```

### 2.3 换图片

想换成自己公司的图片？修改 `resources/images` 目录即可：

```
resources/
  └── images/
      ├── jigsaw/        ← 滑动拼图的底图
      └── pic-click/     ← 文字点选的底图
```

💡 **建议**：放自己公司的产品图/风景图，既统一品牌又有一定防爬效果（攻击者的训练集里没有你的图）。

### 2.4 参考代码

- 后端：`CaptchaController`（获取/校验验证码的接口）、`AuthController`（登录时调用校验）
- 前端 Vue3：`src/components/Verifition`、`LoginForm.vue`

## 三、怎么关闭验证码

本地开发时，每次登录都要拖滑块很烦。**关掉它**：

### 后端

```yaml
# application-local.yaml
yudao:
  captcha:
    enabled: false        # ← 关掉
```

### 前端

**Vue3 版（yudao-ui-admin-vue3）**：

```bash
# .env.local（或对应环境的 .env 文件）
VITE_APP_CAPTCHA_ENABLE=false
```

**Vue2 版（yudao-ui-admin-vue2）**：

```bash
VUE_APP_DOC_ENABLE=false
```

> 官方吐槽（很实在）：*"如果你不知道环境对应的 .env 配置文件是哪个，就全部改成 false 吧！"*

⚠️ **安全提醒**：**生产环境必须开着**。关验证码 = 别人可以写脚本无限次尝试密码（撞库）。实在嫌烦，至少配合 [[请求限流 RateLimiter]] 限制登录接口的调用频率。

## 四、前端接入（3 行代码）

### Vue3

```vue
<template>
  <Verify
    ref="verify"
    mode="pop"                              <!-- pop = 弹出；fixed = 嵌入 -->
    :captchaType="captchaType"              <!-- blockPuzzle / clickWord -->
    :imgSize="{ width: '400px', height: '200px' }"
    @success="handleLogin"                  <!-- 验证成功后才执行登录 -->
  />
</template>
```

### Vue2

```vue
<Verify
  ref="verify"
  :captcha-type="'blockPuzzle'"
  :img-size="{width:'400px',height:'200px'}"
  @success="handleLogin"
/>
```

### uni-app（用户 App）

```vue
<Verify
  @success="pwdLogin"
  :mode="'pop'"
  :captchaType="'blockPuzzle'"
  :imgSize="{ width: '330px', height: '155px' }"
  ref="verify"
/>
```

**关键点**：`@success="handleLogin"` —— **验证成功后才调登录接口**。验证失败/没验证，登录按钮不触发。

## 五、踩坑清单

| # | 坑 | 症状 | 解法 |
|---|---|---|---|
| 1 | **后端没做二次校验** | 验证码形同虚设，可被绕过 | 必须调 `captchaService.verification()` |
| 2 | **集群部署 `cache-type: local`** | 有时能过有时不能（请求打到不同机器） | 改成 `redis` |
| 3 | 后端关了前端没关（或反之） | 登录一直失败 / 验证码不出来 | 两边都要改，保持一致 |
| 4 | Linux 上水印乱码 | 水印显示成问号 | 中文转 Unicode 写进配置 |
| 5 | 用了原版 AJ-Captcha | Spring Boot 3 下启动报错 | 用 `captcha-plus` |
| 6 | 生产环境关了验证码 | 被撞库刷密码 | 生产必须开 |
| 7 | 图片目录路径写错 | 验证码出不来 | 确认 `resources/images` 下真有图片 |
| 8 | 开了限流但阈值太低 | 正常用户也被锁 | 调 `req-*-minute-limit` |

### 💡 集群部署的坑（坑 2 展开）

```
用户请求 → Nginx → 服务器 A（生成验证码，存 local 缓存）
用户提交 → Nginx → 服务器 B（查 local 缓存 → 找不到！）

结果：验证码永远校验失败 ❌
```

**解法**：`cache-type: redis`，所有服务器共享一份缓存。

这和 [[Redis 缓存]]、[[分布式锁]] 的道理一样 —— **凡是要跨进程共享的状态，都得放 Redis。**

## 六、进阶：验证码不是万能的

⚠️ **行为验证码也会被破解**。市面上有专门的"打码平台"，用真人或者训练好的模型来过滑块。

**完整的登录防护应该是多层的**：

| 层级 | 措施 | 相关笔记 |
|---|---|---|
| 1 | **验证码**（挡住低级脚本） | 本篇 |
| 2 | **接口限流**（限制同一 IP/账号的尝试频率） | [[请求限流 RateLimiter]] |
| 3 | **账号锁定**（连续错 N 次锁 10 分钟） | 业务代码 |
| 4 | **登录日志 + 告警**（异地登录提醒） | [[操作日志、访问日志、异常日志]] |
| 5 | **双因子认证**（短信/邮箱验证码） | [[用户体系]] |

💡 **经验之谈**：验证码的主要作用是**提高攻击成本**，不是**杜绝攻击**。让攻击者觉得"搞你不如搞别人"就够了。

---

## 七、一句话总结

**验证码用行为验证码（滑动拼图/文字点选），体验好且难破解。接入只要三步：引入 `yudao-spring-boot-starter-captcha`、配 `aj.captcha`、前端塞个 `<Verify>` 组件。两个必记要点：① 后端必须做二次校验（`captchaService.verification()`），否则等于没验证；② 集群部署时 `cache-type` 必须设成 `redis`。**
