# 多数据源（读写分离）、事务

> **一句话概括**：一个项目连多个数据库 —— 主库写、从库读（读写分离），或者按业务分库。芋道用 **Dynamic Datasource** 实现，一个 `@DS` 注解切换数据源。事务分三种：`@Transactional`（单库）、`@DSTransactional`（多库）、Seata（跨服务）。

---

## 零、先建立整体印象：一家餐厅的两个仓库

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

餐厅原来只有一个仓库，进货和出货都在这里。生意好了以后，一个仓库忙不过来 —— 送货的车和取货的车挤在一起。

老板想了个办法：

- **主仓库（Master）**：只负责**进货**（写操作）
- **分仓库（Slave）**：只负责**出货**（读操作），从主仓库同步数据

这就是**读写分离**。

为什么有用？因为**读操作远比写操作多**（一个电商网站，看商品的人比下单的人多 100 倍）。把读压力分出去，主库就轻松了。

```
         ┌──────────────┐
         │   应用服务器   │
         └──────┬───────┘
        写请求 ↓   ↓ 读请求
    ┌────────────┐  ┌────────────┐
    │  主库 Master │──→│ 从库 Slave │
    │  （写）      │同步│  （读）     │
    └────────────┘  └────────────┘
```

## 一、原理篇

### 1.1 数据连接池：Druid

芋道用阿里 **Druid** 作为连接池，而不只是 Spring Boot 默认的 HikariCP。

| | HikariCP | Druid |
|---|---|---|
| 性能 | ⚡ 略快 | 稍慢（但差距极小） |
| 监控 | ❌ 无 | ✅ **自带监控界面**（SQL 监控、慢 SQL、连接池状态） |
| 防火墙 | ❌ | ✅ SQL 防注入 |
| 适合 | 纯性能追求 | **需要可观测性的生产环境** |

> 💡 **Druid 最大的价值是监控界面** —— 能直接看到"哪条 SQL 执行最慢""哪个 SQL 调用次数最多"。排查性能问题时的神器。

### 1.2 多数据源：Dynamic Datasource

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>dynamic-datasource-spring-boot-starter</artifactId>
</dependency>
```

配置（一主一从）：

```yaml
spring:
  datasource:
    dynamic:
      primary: master    # 默认数据源
      datasource:
        master:          # 主库（写）
          url: jdbc:mysql://127.0.0.1:3306/ruoyi-vue-pro?...
          username: root
          password: 123456
        slave:           # 从库（读）
          url: jdbc:mysql://127.0.0.1:3307/ruoyi-vue-pro?...
          username: root
          password: 123456
      druid:             # Druid 连接池配置
        initial-size: 5
        min-idle: 10
        max-active: 20
```

## 二、应用篇：数据源切换

### 2.1 三个切换注解

| 注解 | 作用 | 使用场景 |
|---|---|---|
| `@Master` | 用主库 | **写操作**（默认就是主库，一般不用加） |
| `@Slave` | 用从库 | **读操作**（查询列表、详情） |
| `@DS("xxx")` | 用指定名字的数据源 | 多业务库场景 |

```java
@Service
public class UserServiceImpl {

    // 写操作：默认走主库，不用加注解
    public Long createUser(UserSaveReqVO reqVO) {
        userMapper.insert(user);
    }

    // 读操作：走从库，减轻主库压力
    @Slave
    public List<UserDO> getUserList() {
        return userMapper.selectList();
    }

    // 指定其他业务库（比如报表库）
    @DS("report")
    public List<ReportDO> getReportData() {
        return reportMapper.selectList();
    }
}
```

### 2.2 Druid 监控界面

**访问地址**：`http://127.0.0.1:48080/druid/index.html`

**能看到什么**：
- 数据源基本信息
- **SQL 监控**（执行次数、耗时、最慢、错误数）⭐
- SQL 防火墙
- Web 应用 / URI 监控
- Session 监控

也可以通过前端菜单【基础设施 → MySQL 监控】查看（本质是 iframe 内嵌 `/druid/index.html`）。

> ⚠️ **生产必须开启登录认证**！官方专门提醒：
> ```yaml
> spring:
>   datasource:
>     druid:
>       stat-view-servlet:
>         login-username: admin
>         login-password: your-password
> ```
> 否则任何人都能看到你数据库的 SQL 执行情况，是**严重安全漏洞**。

## 三、进阶篇：三种事务方案 ⭐

这是本篇的核心。事务方案按"几台机器 × 几个数据源"分三种：

| 场景 | 方案 | 说明 |
|---|---|---|
| **单机 + 单数据源** | `@Transactional` | Spring 原生事务，最常用 |
| **单机 + 多数据源** | `@DSTransactional` | Dynamic Datasource 提供 |
| **多机（微服务）** | **Seata** | 分布式事务框架 |

### 3.1 `@Transactional`（单库，90% 场景）

```java
@Transactional(rollbackFor = Exception.class)
public Long createUser(UserSaveReqVO reqVO) {
    userMapper.insert(user);
    userProfileMapper.insert(profile);   // 同一个库，一起回滚
    return user.getId();
}
```

> ⚠️ **坑**：`@Transactional` 开启后，**数据源就被绑定了**，中间无法切换。所以多数据源场景不能用它。

### 3.2 `@DSTransactional`（多库，单机）

```java
public class AService {

    @Resource private BService bService;
    @Resource private CService cService;

    @DS("a")                    // 注意：如果 a 是默认数据源，可以不加
    @DSTransactional            // 👈 多数据源事务
    public void create() {
        bService.createB();     // 操作 b 数据源
        cService.createC();     // 操作 c 数据源
    }
}

public class BService {
    @DS("b")
    public void createB() { bMapper.insert(...); }
}

public class CService {
    @DS("c")
    public void createC() { cMapper.insert(...); }
}
```

**官方 Q&A（两个高频疑问）**：

| 问题 | 官方答案 |
|---|---|
| **Q1**：c 数据源操作发生异常，a、b 会回滚吗？ | ✅ **会的**。因为 `@DSTransactional` 是**最外层方法结束后才统一提交**，此时还没提交，所以不需要"回滚"，直接不提交即可 |
| **Q2**：b、c 方法上也加 `@DSTransactional` 会有影响吗？ | ✅ **不会**，放心加（事务会传播到外层） |

> ⚠️ **官方明确提示**：`@DSTransactional` 提供的是**"相对可靠"**的一致性，**不是绝对的**。因为最终提交时如果某个数据源提交失败，仍可能不一致。
> 需要强一致 → 用 Seata。

### 3.3 Seata 分布式事务（多机）

微服务场景下，A 服务调 B 服务、C 服务，各自操作各自的数据库 —— 这就是**分布式事务**。

芋道推荐用 **Seata**（AT 模式对业务代码几乎无侵入）。

> 💡 详见 [[14_微服务 SpringCloud 与 Dubbo]]。官方原话："不过如果你是单机项目，则可以不用关注这一点。"

### 3.4 三种方案对比速查

| | `@Transactional` | `@DSTransactional` | Seata |
|---|---|---|---|
| 机器数 | 单机 | 单机 | **多机** |
| 数据源 | 单 | **多** | 单/多 |
| 一致性 | 强 | **相对可靠**（非绝对） | 强 |
| 性能 | 高 | 中 | 低（有全局锁、undo log） |
| 复杂度 | 低 | 低 | 高（要部署 Seata Server） |

### 3.5 分库分表

官方建议：用 **ShardingSphere 的 Sharding-JDBC** 完成分库分表。

> 💡 分库分表和读写分离的区别：
> - **读写分离**：数据一样，只是读写分开（解决**读压力**）
> - **分库分表**：数据拆开存（解决**数据量太大**，单表千万级）

## 四、一句话总结

| 问题 | 答案 |
|---|---|
| 为什么读写分离 | 读比写多得多，把读压力分给从库 |
| 连接池为什么用 Druid | 自带**监控界面**，能看到慢 SQL |
| 怎么切换数据源 | `@Slave`（读）/ `@Master`（写）/ `@DS("名字")`（指定） |
| 三种事务怎么选 | 单库 `@Transactional` / 多库 `@DSTransactional` / 跨服务 Seata |
| 生产必做 | **Druid 监控界面开启登录认证** |
| 分库分表 | 用 Sharding-JDBC |
