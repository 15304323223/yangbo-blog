# 代码生成（树表）

> **一句话概括**：树表 = 单表 + 一个 `parent_id` 字段 + 生成器里把【生成模版】改成**【树表】**并指定父子字段。生成出来的列表是**可展开的树形表格**，还自带"上级节点选择"的下拉。

**前置阅读**：[[代码生成【单表】]] —— 本篇只讲差异部分，重复内容不赘述。

---

## 零、先建立整体印象：什么是树表？

**普通单表**：一堆平铺的记录，彼此没关系。

```
用户组 A
用户组 B
用户组 C
```

**树表**：记录之间有**父子关系**，形成层级。

```
总经办
├── 技术部
│   ├── 后端组
│   └── 前端组
└── 市场部
    ├── 品牌组
    └── 渠道组
```

**典型场景**：

| 场景 | 说明 |
|---|---|
| 部门 | 公司 → 事业部 → 部门 → 小组 |
| 商品分类 | 服饰 → 男装 → 上衣 → T恤 |
| 菜单 | 系统管理 → 用户管理 → 用户列表 |
| 地区 | 省 → 市 → 区 |
| 组织架构 | 集团 → 子公司 → 分公司 |

## 一、第 1 步：设计表结构

以"分类"为例：

```sql
CREATE TABLE `system_category` (
  `id`          bigint      NOT NULL AUTO_INCREMENT COMMENT '编号',
  `name`        varchar(100) NOT NULL DEFAULT ''     COMMENT '名字',
  `parent_id`   bigint      NOT NULL                COMMENT '父级编号',   -- ⭐ 关键字段
  `creator`     varchar(64) DEFAULT ''              COMMENT '创建者',
  `create_time` datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updater`     varchar(64) DEFAULT ''              COMMENT '更新者',
  `update_time` datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `deleted`     bit(1)      NOT NULL DEFAULT b'0'   COMMENT '是否删除',
  `tenant_id`   bigint      NOT NULL DEFAULT '0'    COMMENT '租户编号',
  PRIMARY KEY (`id`) USING BTREE
) ENGINE=InnoDB COMMENT='分类表';
```

### 和普通单表的唯一区别：`parent_id` ⭐

```
parent_id 字段，用于标识父级分类的编号。
如果是顶级分类，则 parent_id 为 0。
```

**约定**：
- 顶级节点的 `parent_id = 0`
- 子节点的 `parent_id = 父节点的 id`

⚠️ **为什么用 `0` 而不是 `NULL`？**
1. `NULL` 不能进索引、不能比较，查询很麻烦
2. `parent_id = 0` 可以直接用 `WHERE parent_id = ?` 查
3. 芋道、若依、大多数国内系统的约定

其他字段（5 个系统字段 + tenant_id）和单表完全一样，见 [[代码生成【单表】]]。

## 二、第 2 步：代码生成

### 2.1 导入表

[基础设施 → 代码生成] → **[基于 DB 导入]** → 勾选 `system_category` → [确认]

（和单表一模一样）

### 2.2 编辑配置 ⭐ 关键差异在这

点击 `system_category` 行的 **[编辑]**，做 3 件事：

**① 【生成模版】改成【树表】** 🔥

> 官方标了火焰符号：*"最最关键的步骤！"*

**② 【树表信息】指定两个字段**

| 配置项 | 本例的值 | 作用 |
|---|---|---|
| **父编号字段** | `parent_id` | 哪个字段存父节点 id |
| **树名称字段** | `name` | 哪个字段作为节点的显示名 |

**③ 【生成信息】照常填**

- 上级菜单：选【系统管理】
- 前端类型：按你的前端项目选（如 Vue3 Element Plus 标准模版）

点 **[提交]**。

### 2.3 预览 + 生成

点 **[预览]** 检查 → 点 **[生成]** 下载。

## 三、生成了什么不一样的东西？

和单表相比，树表多生成了这些：

### 3.1 后端

**① 分页 VO 里多了 parentId**

```java
@Data
public class CategoryPageReqVO extends PageParam {
    private String name;
    private Integer status;
    private Long parentId;      // ← 支持按父节点过滤
}
```

**② Controller 多了"获取精简列表"接口**

用于前端的"上级分类"下拉框：

```java
@GetMapping("/list-all-simple")
@Operation(summary = "获取分类精简信息列表")
public CommonResult<List<CategorySimpleRespVO>> getCategoryList() {
    // 返回全部分类（树形或扁平，取决于实现）
}
```

**③ Service 里有构建树的逻辑**

```java
@Override
public List<CategoryDO> getCategoryList(CategoryListReqVO reqVO) {
    // 查出全部，再在内存里组装成树
    return buildTree(categoryMapper.selectList(reqVO));
}
```

💡 **关键设计**：**一次性查出全部数据，在 Java 内存里组装成树**，而不是递归查数据库。

**为什么？** 递归查 = N+1 问题。分类表通常就几百行，一次查完在内存里组装，快得多。

### 3.2 前端

树形表格用 Element Plus 的 `el-table` + `row-key` + `tree-props`：

```vue
<el-table
  v-loading="loading"
  :data="list"
  row-key="id"
  :tree-props="{ children: 'children', hasChildren: 'hasChildren' }"
  default-expand-all
>
  <el-table-column label="分类名" prop="name" />
  ...
</el-table>
```

表单里的"上级分类"用 `el-tree-select`：

```vue
<el-tree-select
  v-model="formData.parentId"
  :data="categoryTree"
  :props="{ label: 'name', children: 'children' }"
  check-strictly
  placeholder="请选择上级分类"
/>
```

## 四、树表的几个经典坑 ⚠️

### 坑 1：删除父节点时，子节点变成"孤儿"

**症状**：删了"技术部"，它下面的"后端组"还在数据库里，`parent_id` 指向一个不存在的 id，前端永远显示不出来（因为找不到爸爸就挂不到树上）。

**解法**（二选一）：

```java
// 方案 A：不允许删（推荐）
@Override
public void deleteCategory(Long id) {
    // 校验是否有子节点
    if (categoryMapper.selectCountByParentId(id) > 0) {
        throw exception(CATEGORY_EXISTS_CHILDREN);   // "存在子分类，不允许删除"
    }
    categoryMapper.deleteById(id);
}

// 方案 B：级联删除（危险，谨慎）
// 递归删除所有子孙节点
```

### 坑 2：选上级节点时选到了自己或自己的子孙 → 环

**症状**：把"技术部"的上级改成"后端组"（它自己的子节点）→ 树变成环 → 页面死循环、接口超时。

**解法**：前端的 `el-tree-select` 要把自己和自己的子孙禁用掉。

```java
// 后端传一个"不可选的 id 列表"给前端
public CommonResult<Set<Long>> getDisabledIds(Long id) {
    // 查出 id 的所有子孙（包括自己）
    return success(getAllDescendantIds(id));
}
```

### 坑 3：递归组装树导致栈溢出

**症状**：层级特别深（比如 1000 层）时 `StackOverflowError`。

**解法**：用**迭代**代替递归，或者限制最大层级。

```java
// ❌ 递归（层级深会爆栈）
private void buildTree(CategoryDO node) {
    node.setChildren(getChildren(node.getId()));
    node.getChildren().forEach(this::buildTree);
}

// ✅ 迭代：先转 Map，再挂父子
public List<CategoryDO> buildTree(List<CategoryDO> list) {
    Map<Long, CategoryDO> map = convertMap(list, CategoryDO::getId);
    List<CategoryDO> roots = new ArrayList<>();
    for (CategoryDO node : list) {
        CategoryDO parent = map.get(node.getParentId());
        if (parent == null || node.getParentId() == 0) {
            roots.add(node);                    // 顶级节点
        } else {
            parent.getChildren().add(node);     // 挂到父节点下
        }
    }
    return roots;
}
```

💡 **这个写法是 O(n)，只遍历两遍，比递归快得多，也不会爆栈。**

### 坑 4：数据量大时一次查全部会卡

**症状**：分类有 10 万条，一次性查出来组装树 → 接口几秒才返回。

**解法**：
- **懒加载**：前端点开哪层才查哪层（`el-table` 的 `lazy` + `load`）
- **或者**：树表通常数据量不大，真到 10 万条要考虑是不是设计错了

### 坑 5：`parent_id = 0` 的约定被打破

**症状**：有的数据 `parent_id` 是 `NULL` 或 `-1`，组装树时挂不上。

**解法**：建表时设 `DEFAULT '0'`，并在 Service 里兜底：

```java
if (node.getParentId() == null) {
    node.setParentId(0L);
}
```

## 五、树表 vs 单表：生成配置对比

| 配置项 | 单表 | 树表 |
|---|---|---|
| 生成模版 | 单表 | **树表** |
| 父编号字段 | 无 | **必填**（如 `parent_id`） |
| 树名称字段 | 无 | **必填**（如 `name`） |
| 表结构 | 普通字段 | **多一个 `parent_id`** |
| 前端列表 | 平铺表格 | **可展开树形表格** |
| 前端表单 | 普通输入 | **多一个"上级"树形下拉** |
| 后端接口 | 5 个 CRUD | **多一个"精简列表"接口** |

---

## 六、一句话总结

**树表 = 单表 + `parent_id` 字段（顶级为 0）+ 生成器里【生成模版】选【树表】并指定"父编号字段"和"树名称字段"。三个必防的坑：删父节点前先检查有没有子节点、选上级时禁止选自己和子孙（防环）、组装树用 Map 迭代而不是递归（防爆栈）。**
