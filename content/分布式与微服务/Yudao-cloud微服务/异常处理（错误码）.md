# 异常处理（错误码）

> **一句话概括**：芋道的异常处理就三件事 —— **成功返回 `CommonResult.success(data)`，失败 `throw ServiceException`，错误码全局唯一且能在后台改文案**。用抛异常而不是返回错误对象，是因为 **Spring 事务靠异常回滚**。

**适合谁读**：所有写接口的人。这是最基础也最容易写错的一块。
**怎么读**：「零」理解为什么不用 HTTP 状态码，「一」学统一响应，「三」的错误码分段规则要记牢。

---

## 零、先建立整体印象：快递单的"签收状态"

你寄快递，物流信息长这样：

```
✅ 已签收
   包裹：xxx

❌ 派送失败
   原因：收件人电话无人接听
```

对应到接口返回：

```json
// 成功
{
  "code": 0,
  "data": { "id": 1, "username": "yudaoyuanma" }
}

// 失败
{
  "code": 233666,
  "message": "商品库存不足"
}
```

**只有 3 个字段**：`code`（状态码）、`data`（成功数据）、`message`（错误提示）。

### 为什么不用 HTTP 状态码？

RESTful 规范推荐用 HTTP 状态码（200/400/404/500）。**芋道不用**，官方给了两个理由：

**① 业务错误太多，HTTP 状态码映射不了**

> *"例如说，活动还未开始、订单已取消等等"*

💡 你想想：`活动还未开始` 该用哪个状态码？400？409？422？**HTTP 那几十个状态码根本装不下业务的千奇百怪。** 而用数字错误码，你可以定义无限个。

**② 学习成本高**

> *"开发者对 HTTP 响应状态码不是很了解。例如说，可能只知道 200、403、404、500 几种常见的"*

💡 现实：大部分人对 402（Payment Required）、418（I'm a teapot）、451 完全没概念。

### 那 HTTP 状态码还用吗？

**用，但只用在系统层面。** 芋道的系统错误码段 `0-999` 就是和 HTTP 状态码对应的（见「三」）。

## 一、统一响应：CommonResult

### 1.1 基本用法

```java
@RestController
@RequestMapping("/system/user")
public class UserController {

    @GetMapping("/get")
    @Operation(summary = "获得用户")
    public CommonResult<UserRespVO> getUser(@RequestParam("id") Long id) {
        UserDO user = userService.getUser(id);
        return success(BeanUtils.toBean(user, UserRespVO.class));  // ← success() 静态方法
    }
}
```

✅ **`success()` 是 `CommonResult` 的静态方法**，芋道的 Controller 都继承了 `BaseController`（或静态导入），直接调就行。

### 1.2 `data` 字段要用 VO，不要用 Map

> 官方：*"CommonResult 的 data 字段是泛型，建议定义对应的 VO 类，而不是使用 Map 类。"*

```java
// ❌ 不推荐
public CommonResult<Map<String, Object>> getUser() {
    Map<String, Object> map = new HashMap<>();
    map.put("id", 1);
    map.put("name", "张三");
    return success(map);
}

// ✅ 推荐
public CommonResult<UserRespVO> getUser() {
    return success(BeanUtils.toBean(user, UserRespVO.class));
}
```

**为什么？**

| | VO 类 | Map |
|---|---|---|
| Swagger 文档 | ✅ 自动生成字段说明 | ❌ 只有 `Map<String,Object>`，前端抓瞎 |
| 字段改名 | ✅ 编译期报错 | ❌ 运行时才发现 |
| IDE 提示 | ✅ 有 | ❌ 没有 |
| 类型安全 | ✅ | ❌ |

详见 [[VO 对象转换、数据翻译]]。

### 1.3 为什么不用 `@ControllerAdvice` 自动包装？

很多项目用 `@ControllerAdvice` + `ResponseBodyAdvice` 全局拦截，自动把返回值包成 `CommonResult`。这样 Controller 里直接 `return userVO` 就行，很省事。

**芋道不用，两个原因**：

**① 破坏方法定义，Swagger 出错**

> *"这样的方式'破坏'了方法的定义，导致一些隐性的问题。例如说，Swagger 接口定义错误，展示的响应结果不是 CommonResult。"*

💡 因为方法签名写的是 `UserRespVO`，实际返回的是 `CommonResult<UserRespVO>`。Swagger 按签名生成文档 → **文档和真实响应不一致**，前端按文档对接就错了。

**② 有些接口不需要包装**

> *"例如说，第三方支付回调只需要返回 'success' 字符串。"*

💡 微信支付、支付宝的回调接口，人家要求你**必须返回纯字符串 `success`**，包成 JSON 就判定失败。**自动包装会让这些接口没法写**。

## 二、异常处理

### 2.1 Spring MVC 的异常：@ControllerAdvice + @ExceptionHandler

核心类：`GlobalExceptionHandler`

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    /**
     * 处理业务异常 ServiceException
     */
    @ExceptionHandler(ServiceException.class)
    public CommonResult<?> serviceExceptionHandler(ServiceException ex) {
        log.error("[serviceExceptionHandler]", ex);
        return CommonResult.error(ex.getCode(), ex.getMessage());
    }

    /**
     * 处理参数校验异常
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public CommonResult<?> methodArgumentNotValidExceptionHandler(MethodArgumentNotValidException ex) {
        log.error("[methodArgumentNotValidExceptionHandler]", ex);
        FieldError fieldError = ex.getBindingResult().getFieldError();
        return CommonResult.error(BAD_REQUEST.getCode(),
                String.format("请求参数不正确:%s", fieldError.getDefaultMessage()));
    }

    /**
     * 处理系统异常，兜底
     */
    @ExceptionHandler(Exception.class)
    public CommonResult<?> defaultExceptionHandler(Exception ex) {
        log.error("[defaultExceptionHandler]", ex);
        return CommonResult.error(INTERNAL_SERVER_ERROR.getCode(), INTERNAL_SERVER_ERROR.getMsg());
    }
}
```

**处理链**：

```
Controller 抛异常
   │
   ▼ Spring MVC 捕获，找 @ExceptionHandler
   │
   ├─ ServiceException        → 转成 {code: 业务码, message: 业务提示}
   ├─ 参数校验异常             → 转成 {code: 400, message: "请求参数不正确:xxx"}
   ├─ 权限异常 AccessDenied   → 转成 {code: 403, message: "无权限"}
   └─ 其它 Exception（兜底）  → 转成 {code: 500, message: "系统异常"}
   │
   ▼ 返回 JSON 给前端
```

### 2.2 Filter 的异常：@ExceptionHandler 管不到 ⚠️

**这是个容易踩的坑**：请求到达 Controller **之前**，要先过一串 Filter（比如 Token 认证过滤器、租户过滤器）。**Filter 里抛的异常，`@ExceptionHandler` 捕获不到！**

**为什么？** 因为 `@ExceptionHandler` 是 Spring MVC 的 `DispatcherServlet` 提供的能力，而 **Filter 在 Servlet 之前执行**。

```
HTTP 请求
   │
   ▼ Filter 链  ← 这里抛异常，@ExceptionHandler 管不着 ❌
   │
   ▼ DispatcherServlet（Spring MVC）
   │
   ▼ Controller ← 这里抛异常，@ExceptionHandler 能捕获 ✅
```

**解法**：只能在 Filter 里 **`try-catch` + 手动写响应**：

```java
public class TokenAuthenticationFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                     HttpServletResponse response,
                                     FilterChain chain) throws ServletException, IOException {
        try {
            // 认证逻辑...
            chain.doFilter(request, response);
        } catch (Exception ex) {
            // 只能自己处理，手动写 JSON 响应
            response.setStatus(HttpStatus.UNAUTHORIZED.value());
            response.setContentType(MediaType.APPLICATION_JSON_VALUE);
            response.setCharacterEncoding("UTF-8");
            response.getWriter().write(
                JsonUtils.toJsonString(CommonResult.error(401, "登录已过期，请重新登录"))
            );
        }
    }
}
```

## 三、业务异常：为什么用 throw 而不是 return？

### 3.1 两种方案对比

Service 里遇到业务错误（用户名已存在、库存不足），怎么告诉上层？

**方案一：返回 `CommonResult`**

```java
public CommonResult<Long> createUser(UserSaveReqVO reqVO) {
    if (userMapper.selectByUsername(reqVO.getUsername()) != null) {
        return CommonResult.error(1001000001, "用户名已存在");   // ← return
    }
    // ...
    return CommonResult.success(id);
}
```

**方案二：抛 `ServiceException`**（芋道采用 ✅）

```java
public Long createUser(UserSaveReqVO reqVO) {
    if (userMapper.selectByUsername(reqVO.getUsername()) != null) {
        throw exception(USER_USERNAME_EXISTS);                    // ← throw
    }
    // ...
    return id;
}
```

### 3.2 官方给了两个致命理由 ⭐

**① 事务回滚会非常麻烦** ⭐⭐⭐

> *"因为 Spring @Transactional 声明式事务，是基于异常进行回滚的，如果使用 CommonResult 返回，则事务回滚会非常麻烦"*

💡 **这是最关键的理由**。`@Transactional` 的回滚机制是**捕获到异常才回滚**。

```java
@Transactional
public CommonResult<Long> createUser(...) {
    userMapper.insert(user);              // ① 插入用户
    if (someError) {
        return CommonResult.error(...);   // ② return 了，没有异常
    }
    // 结果：① 的插入【不会回滚】！数据落库了！❌
}
```

而 `throw` 就会正常回滚。**光这一条，方案一就该枪毙。**

**② 调用方要不停判断**

> *"当调用别的方法时，如果别人返回的是 CommonResult 对象，还需要不断的进行判断，写起来挺麻烦的"*

```java
// ❌ 方案一：每个调用都要判断
CommonResult<UserDO> result = userService.getUser(id);
if (!result.isSuccess()) {
    return CommonResult.error(result.getCode(), result.getMsg());
}
UserDO user = result.getData();
// ... 再来一次判断

// ✅ 方案二：不用管，异常自动往上层冒，最后由 GlobalExceptionHandler 统一处理
UserDO user = userService.getUser(id);
```

### 3.3 ServiceException 的定义

```java
@Data
@EqualsAndHashCode(callSuper = true)
public final class ServiceException extends RuntimeException {   // ← 继承 RuntimeException

    private Integer code;            // 错误码
    private String message;          // 错误提示

    public ServiceException(ErrorCode errorCode) {
        this.code = errorCode.getCode();
        this.message = errorCode.getMsg();
    }
}
```

**为什么继承 `RuntimeException`（非受检异常）？**

> *"大多数业务场景下，我们无需处理 ServiceException 业务异常，而是通过 GlobalExceptionHandler 统一处理……如果真的需要处理 ServiceException 时，通过 try catch 的方式进行主动捕获。"*

💡 **说人话**：如果是受检异常（继承 `Exception`），每个方法签名都得写 `throws ServiceException`，调用方必须 try-catch —— **代码会被 `throws` 淹没**。非受检异常可以不声明、不捕获，一路冒到顶层统一处理。

### 3.4 ServiceExceptionUtil：为什么不能直接 new？

```java
// ❌ 不推荐
throw new ServiceException(1001000001, "用户名已存在");

// ✅ 芋道的写法
throw exception(USER_USERNAME_EXISTS);
```

**为什么要用 `ServiceExceptionUtil` 构建？**

> *"错误提示的内容，支持使用管理后台进行动态配置，所以通过 ServiceExceptionUtil 获取内容的配置与格式化。"*

💡 **关键**：错误提示文案是**可以从后台改的**，不是写死在代码里的。所以需要一个工具类去查配置。

**两个重载方法**：

```java
public static ServiceException exception(ErrorCode errorCode);
public static ServiceException exception(ErrorCode errorCode, Object... params);  // 支持占位符
```

**带参数的用法**：

```java
// 错误码：USER_USERNAME_EXISTS = "用户名为 {} 的账号已存在"
throw exception(USER_USERNAME_EXISTS, reqVO.getUsername());
// 最终提示："用户名为 张三 的账号已存在"
```

## 四、错误码：10 位数字的秘密

### 4.1 两类错误码

| 类型 | 码段 | 定义位置 | 例子 |
|---|---|---|---|
| **系统错误码** | `0 - 999` | `GlobalErrorCodeConstants` | `0` 成功、`400` 参数错误、`401` 未登录、`403` 无权限、`500` 系统异常 |
| **业务错误码** | `10 位` | 各模块的 `ErrorCodeConstants` | `1_001_000_001` |

**系统错误码为什么是 0-999？**

> *"和 HTTP 响应状态码对应。虽然说，HTTP 响应状态码作为业务使用表达能力偏弱，但是使用在系统层面还是非常不错的。"*

💡 **HTTP 状态码用在系统层面刚刚好，业务层面才需要扩展。** 这个设计很聪明。

### 4.2 业务错误码的 10 位分段规则 ⭐

芋道的业务错误码是 **10 位数字，分 4 段**，定义在 `ServiceErrorCodeRange`：

```
    1        001        000        001
    │         │          │          │
    │         │          │          └─ ④ 具体错误（3 位）：第 1 个错误
    │         │          └────────── ③ 模块内分类（3 位）：用户模块
    │         └───────────────────── ② 模块编号（3 位）：system 模块
    └─────────────────────────────── ① 系统标识（1 位）：1 = 业务系统
```

**为什么要这么分？**

> *"按照模块分配错误码的区间，避免模块之间的错误码冲突。"*

💡 **好处**：
1. **不会撞车**：system 模块用 `1_001_xxx`，crm 模块用 `1_002_xxx`，各自扩展互不干扰
2. **看码知模块**：看到 `1_002_000_015`，立刻知道是 CRM 模块的错误 → **排查问题快**
3. **可批量管理**：后台能按模块筛选错误码

### 4.3 每个模块定义自己的错误码枚举

以 `yudao-module-system` 为例：

```java
public interface ErrorCodeConstants {

    // ========== 用户模块 1-001-000-000 ==========
    ErrorCode USER_USERNAME_EXISTS = new ErrorCode(1001000001, "用户名为 {} 的账号已存在");
    ErrorCode USER_MOBILE_EXISTS   = new ErrorCode(1001000002, "手机号为 {} 的账号已存在");
    ErrorCode USER_NOT_EXISTS      = new ErrorCode(1001000003, "用户不存在");
    ErrorCode USER_PASSWORD_FAILED = new ErrorCode(1001000004, "用户密码不正确");

    // ========== 角色模块 1-001-001-000 ==========
    ErrorCode ROLE_NOT_EXISTS      = new ErrorCode(1001001001, "角色不存在");
    ErrorCode ROLE_NAME_DUPLICATE  = new ErrorCode(1001001002, "角色名称已存在");

    // ========== 菜单模块 1-001-002-000 ==========
    ErrorCode MENU_NOT_EXISTS      = new ErrorCode(1001002001, "菜单不存在");
}
```

**使用**：

```java
// 静态导入
import static cn.iocoder.yudao.module.system.enums.ErrorCodeConstants.USER_USERNAME_EXISTS;

throw exception(USER_USERNAME_EXISTS, reqVO.getUsername());
```

### 4.4 错误码管理：文案可以在后台改 ⭐

[系统管理 → 错误码管理] 菜单，可以：
- 查看所有错误码
- **修改错误提示文案**（比如把"用户名为 {} 的账号已存在"改成"该用户名已被注册，换一个试试"）

> 官方：*"启动中的项目会每 60 秒，加载最新的错误码配置。所以，我们在修改完错误码的提示后，无需重启项目。"*

💡 **这个设计非常实用**：产品经理觉得文案不好，**你不用改代码、不用发版**，后台改一下，1 分钟后生效。

#### 两种添加方式

**① 手动添加**：点 [新增] 按钮，一个个填。

**② 自动添加**（推荐）：配置扫描

```yaml
yudao:
  error-code:
    constants-class-list:                    # 需要自动扫描的错误码枚举类
      - cn.iocoder.yudao.module.system.enums.ErrorCodeConstants
      - cn.iocoder.yudao.module.infra.enums.ErrorCodeConstants
      - cn.iocoder.yudao.module.crm.enums.ErrorCodeConstants
```

项目启动时自动扫描这些类里的错误码，**自动添加或更新**到数据库。

⚠️ **注意**：自动添加的错误码类型是【自动生成】，**一旦在后台手动 [编辑] 过，就不再支持自动修改**（避免你的手工修改被覆盖）。

实现代码在 `system/framework/errorcode` 包。

## 五、踩坑清单

| # | 坑 | 症状 | 解法 |
|---|---|---|---|
| 1 | **Service 里用 return 返回错误** | 事务不回滚，脏数据落库 | 一律 `throw exception(...)` |
| 2 | ServiceException 抛在 `@Transactional` 方法内部被 try-catch 吞了 | 事务不回滚 | catch 后要么重新抛出，要么 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` |
| 3 | Filter 里的异常没处理 | 前端收到 500 HTML 错误页，不是 JSON | Filter 里手动 try-catch 写响应 |
| 4 | 用了魔法数字 | `throw new ServiceException(666, "xxx")` | 定义到 `ErrorCodeConstants` |
| 5 | 错误码随便编 | 和其他模块冲突 | 按 `ServiceErrorCodeRange` 分配 |
| 6 | `data` 用 Map | Swagger 文档没法看 | 定义 VO 类 |
| 7 | 提示文案写死在代码里 | 改文案要发版 | 用 `exception(ERROR_CODE)` + 后台配置 |
| 8 | 把系统异常信息直接返回给前端 | 泄露堆栈、SQL、路径 | 兜底 handler 只返回"系统异常"，详情记日志 |

### 坑 2 展开：异常被吞导致事务不回滚

```java
// ❌ 错误：异常被吞了，事务正常提交
@Transactional
public void createUser(...) {
    try {
        otherService.doSomething();     // 这里抛了 ServiceException
    } catch (ServiceException e) {
        log.error("出错了", e);          // 只打日志，没重新抛
    }
    // 事务提交！前面的 insert 全部生效 ❌
}

// ✅ 正确：重新抛出
@Transactional
public void createUser(...) {
    try {
        otherService.doSomething();
    } catch (ServiceException e) {
        log.error("出错了", e);
        throw e;                        // ← 必须重新抛
    }
}
```

### 💡 一个进阶技巧：异常要不要记日志？

```java
@ExceptionHandler(ServiceException.class)
public CommonResult<?> serviceExceptionHandler(ServiceException ex) {
    // 业务异常一般不打 error 日志（否则"用户名已存在"这种正常业务会刷屏）
    // 只打 warn 或 debug
    log.warn("[serviceExceptionHandler] code={}, message={}", ex.getCode(), ex.getMessage());
    return CommonResult.error(ex.getCode(), ex.getMessage());
}

@ExceptionHandler(Exception.class)
public CommonResult<?> defaultExceptionHandler(Exception ex) {
    // 系统异常必须打 error + 完整堆栈
    log.error("[defaultExceptionHandler]", ex);
    return CommonResult.error(500, "系统异常");
}
```

⚠️ **经验之谈**：把"用户输入错误"当 error 记，会发现日志 90% 都是噪音，真正的问题反而被淹没了。

## 六、一句话总结

**成功 `return success(vo)`，失败 `throw exception(ERROR_CODE)`（用 throw 是因为 Spring 事务靠异常回滚）。错误码 10 位分 4 段（系统-模块-分类-序号），全局唯一不冲突；文案存在数据库里，后台改完 60 秒内生效、不用发版。注意 Filter 里的异常 `@ExceptionHandler` 管不着，得手动处理。**
