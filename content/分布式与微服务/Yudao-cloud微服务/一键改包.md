# 一键改包（芋道 Yudao 项目改名）

> **一句话概括**：芋道源码里写着它的"身份证"——Maven 坐标叫 `cn.iocoder.yudao`、前端标题叫"芋道管理系统"、配置文件里到处是 `yudao`。`ProjectReactor` 是一个「改名专员」程序，你填好 4 个新名字，它就把全项目 **2825 个文件**里的旧身份一次性换成你的，还顺手把 Java 包目录也搬好。

## 零、先建立整体印象：给一家公司整体改名

全文用这一个类比串起来，先记住它，后面每一节都能对上号。

假设你接手了一家公司，它叫 **「芋道科技」**。现在老板说：从今天起，这家公司姓「张」，叫 **「张三科技」**。

你以为换个招牌就完事了？太天真。公司的"名字"至少藏在 **7 个地方**：

| 现实中的东西 | 对应到芋道项目里 | 具体长什么样 |
| --- | --- | --- |
| 🏢 营业执照上的**公司全称** | Maven `groupId`（组织名） | `cn.iocoder.yudao` |
| 🏷️ 公司**对外简称 / 项目代号** | Maven `artifactId` | `yudao` → 各模块叫 `yudao-module-system` |
| 🪪 员工**工牌上的部门前缀** | Java 根 `package` | `package cn.iocoder.yudao.module.system` |
| 🏬 大楼前台的**招牌** | 前端 `title` | `<title>芋道管理系统</title>` |
| 📇 通讯录、门禁里的**旧名字** | `application.yaml` 配置 | `mapper-locations: classpath*:mapper/**/*.xml` |
| 📦 仓库台账、合同 | SQL 脚本 + Docker/Jenkins 文件 | 建表注释、镜像名 `yudao-server` |
| 🗄️ 档案柜的**层级目录** | Java 包对应的**磁盘目录** | `cn/iocoder/yudao/module/system/` |

**这就是"改个名"麻烦的根源**：它不是改一处，是改 2825 份文件，而且**第 7 项（目录）最难**——因为 Java 的包名就是磁盘上的文件夹层级，`cn.iocoder.yudao` 对应 `cn/iocoder/yudao/` 四级目录，改内容的同时还得**搬文件夹**。

那怎么办？请一个 **「改名专员机器人」= `ProjectReactor`**：

1. **搬家**：把整个项目**复制**一份到新目录（原项目一个字不动，安全）；
2. **扫楼**：递归遍历，找出所有需要改的文件（日志里那个 `需要重写的文件数量：2825`）；
3. **换标**：对每个文件做文本替换，再顺手把包目录重命名。

跑完你就得到一个"已经姓张"的完整项目。全程十几秒。

## 一、原理篇：它到底改了什么

### 1.1 名字的 7 个藏身之处（改漏一个就翻车）

这是全文最该记住的一张表。很多同学改完启动报各种奇怪的错，**99% 是这张表里某一项漏了**。

| # | 藏身处 | 改之前的样子 | 漏改的后果 |
| --- | --- | --- | --- |
| 1 | `pom.xml` 的 `groupId` / `artifactId` | `<groupId>cn.iocoder.yudao</groupId>` | 模块之间互相引用找不到，Maven 直接飘红 |
| 2 | Java 文件的 `package` 声明 | `package cn.iocoder.yudao.module.system;` | 编译不通过；**目录没同步搬**会出现"包名与路径不符" |
| 3 | Java 文件的 `import` 语句 | `import cn.iocoder.yudao.framework.common.pojo.R;` | 编译不通过，满屏红线 |
| 4 | `mapper.xml` 的 `namespace` / `resultType` | `namespace="cn.iocoder.yudao.module.system.dal.mysql..."` | 启动报 `BindingException: Invalid bound statement` |
| 5 | `application.yaml` | `typeAliasesPackage`、`mapper-locations` | Mapper 扫不到 / 别名失效 |
| 6 | 前端 `.vue` / `index.html` | 页面 `title`、接口前缀 | 页面标题还是"芋道"、接口 404 |
| 7 | SQL 脚本 / Dockerfile / Jenkinsfile | 建表注释、`yudao-server` 镜像名 | 数据初始化异常、部署脚本找不到包 |

> 💡 **最容易翻车的是第 2 项和第 4 项**。
> 第 2 项因为要同时改**内容 + 目录**；
> 第 4 项因为 `mapper.xml` 里写的是**全限定类名字符串**，IDE 的"重构改名"功能对字符串里的类名**基本无感**，最容易漏。

### 1.2 ProjectReactor 的执行流程

```
        ┌─────────────────────────────────────────┐
        │  ① 你填写「对照表」                        │
        │     groupIdNew    新公司全称              │
        │     artifactIdNew 新项目代号               │
        │     packageNameNew 新包名                 │
        │     titleNew      新前端标题               │
        │     projectBaseDirNew 新项目目录           │
        └──────────────────┬──────────────────────┘
                           ▼
        ┌─────────────────────────────────────────┐
        │  ② 复制项目 → projectBaseDirNew           │
        │     （原项目只读不动，改砸了也不怕）         │
        └──────────────────┬──────────────────────┘
                           ▼
        ┌─────────────────────────────────────────┐
        │  ③ 递归扫楼：收集所有需要重写的文件          │
        │     日志：需要重写的文件数量：2825           │
        └──────────────────┬──────────────────────┘
                           ▼
        ┌─────────────────────────────────────────┐
        │  ④ 按文件类型分头处理                      │
        │     .java   → 改 package / import        │
        │     .xml    → 改 namespace / resultType  │
        │     .yaml   → 改配置项中的包名             │
        │     .vue/.html → 改 title                │
        │     pom.xml → 改 groupId / artifactId     │
        │     .sql    → 改注释 / 库名               │
        └──────────────────┬──────────────────────┘
                           ▼
        ┌─────────────────────────────────────────┐
        │  ⑤ 搬目录：cn/iocoder/yudao → com/zhangsan│
        │     （包名是目录层级，必须一起搬）           │
        └──────────────────┬──────────────────────┘
                           ▼
                 ✅ 重写完成（5~10 秒）
```

### 1.3 核心源码（简化示意版，逐行注释）

> 📌 下面是**简化后的示意代码**，逻辑与官方 `script/ProjectReactor.java` 一致，但去掉了官方源码里的大量边界处理（比如跳过 `target/`、`.git/`、静态资源等）。目的是让你看懂原理，**真正跑的时候请用项目里自带的那个类**。

```java
/**
 * ProjectReactor —— 芋道项目的「一键改包」工具（简化示意版）
 * 位置：通常在项目根目录 script/ProjectReactor.java
 * 用法：IDEA 里右键 Run 'ProjectReactor.main()' 就行，不用加任何依赖
 */
public class ProjectReactor {

    // ===== ① 旧名字：从当前项目读取，一般不用你改 =====
    private static final String GROUP_ID_OLD     = "cn.iocoder.yudao";    // 旧公司全称（Maven groupId）
    private static final String ARTIFACT_ID_OLD  = "yudao";               // 旧项目代号（Maven artifactId）
    private static final String PACKAGE_NAME_OLD = "cn.iocoder.yudao";    // 旧 Java 根包名
    private static final String TITLE_OLD        = "芋道";                 // 旧前端标题

    // ===== ② 新名字：👇 只有这 5 行需要你动手填 =====
    private static final String GROUP_ID_NEW     = "com.zhangsan";                    // 你的公司域名倒写
    private static final String ARTIFACT_ID_NEW  = "zhangsan-project";                // 你的项目代号
    private static final String PACKAGE_NAME_NEW = "com.zhangsan";                    // 你的根包名（建议和 groupId 一致）
    private static final String TITLE_NEW        = "张三管理系统";                     // 浏览器标签页上显示的名字
    private static final String PROJECT_BASE_DIR_NEW = "/Users/zhangsan/idea/zhangsan-project"; // 新项目生成到哪

    public static void main(String[] args) throws Exception {
        String projectBaseDir = System.getProperty("user.dir");  // 当前项目所在目录

        // ① 搬家：先整份复制到新目录。原项目一个字节都不动 —— 改砸了直接删掉重跑
        copyProject(projectBaseDir, PROJECT_BASE_DIR_NEW);

        // ② 扫楼：递归遍历新目录，挑出「内容里出现过旧名字」的文件
        List<File> files = getReactorFiles(new File(PROJECT_BASE_DIR_NEW));
        log.info("需要重写的文件数量：{}，预计需要 5-10 秒", files.size());

        // ③ 换标：逐个文件做文本替换
        for (File file : files) {
            rewriteFile(file);
        }

        // ④ 搬目录：把 cn/iocoder/yudao/... 重命名成 com/zhangsan/...
        //    这一步是灵魂 —— Java 包名就是磁盘目录层级，只改文件内容不改目录等于没改
        renamePackageDir(PROJECT_BASE_DIR_NEW, PACKAGE_NAME_OLD, PACKAGE_NAME_NEW);

        log.info("重写完成");
    }

    /**
     * 单个文件的替换逻辑：读出来 → 字符串替换 → 写回去
     */
    private static void rewriteFile(File file) {
        String content = FileUtil.readUtf8String(file);              // 读出文件全部内容

        // ⚠️ 替换顺序有讲究：先换「长的」，再换「短的」
        // 如果先换 "yudao" 这个短词，可能会把某些不该动的地方也污染了
        content = content.replace(GROUP_ID_OLD,     GROUP_ID_NEW);    // cn.iocoder.yudao → com.zhangsan
        content = content.replace(ARTIFACT_ID_OLD,  ARTIFACT_ID_NEW); // yudao-module-system → zhangsan-project-module-system
        content = content.replace(TITLE_OLD,        TITLE_NEW);       // 芋道 → 张三管理系统

        FileUtil.writeUtf8String(content, file);                      // 原样写回
    }
}
```

**看懂这 4 步，你就理解了「工程化批量改名」的全部套路**：`复制 → 扫描 → 替换 → 移动`。以后遇到任何"批量改代码"的需求（比如把公司所有项目的某个工具类换掉），都是这个模子。

## 二、方案对比：为什么别手工改

| 方案 | 耗时 | 漏改风险 | 说明 |
| --- | --- | --- | --- |
| ✅ **ProjectReactor 一键改包** | 十几秒 | 极低 | 官方维护，覆盖 2825 个文件 + 目录搬迁。**首选** |
| ⚠️ IDEA 全局替换 `Ctrl+Shift+R` | 十几分钟 | **高** | 只能替换文本内容，**不会帮你搬目录**；`mapper.xml` 里的字符串类名容易漏 |
| ⚠️ IDEA `Refactor → Rename Package` | 几分钟 | 中 | 只管 `.java`，不管 `xml` / `yaml` / `vue` / `sql` |
| ❌ 手工一个个改 | 几天 | 极高 | 2825 个文件，人肉必然漏，且不可逆 |

> 💡 **一句话结论**：这类"机械、量大、有明确对照关系"的活，**一定要写脚本，不要靠人**。
> 这个思路本身比 `ProjectReactor` 这个类更值钱 —— 面试/工作中遇到"批量重构"需求，能想到"先复制一份再批量改，保证原代码可回退"，就已经超过大多数人了。

## 三、应用篇：4 步跑起来

### 第 ① 步：克隆项目（并顺手点个 Star ⭐）

IDEA → `File → New → Project from Version Control`，填：

| 项目形态 | 仓库地址 |
| --- | --- |
| 单体版（ruoyi-vue-pro） | `https://github.com/YunaiV/ruoyi-vue-pro` |
| 微服务版（yudao-cloud） | `https://github.com/YunaiV/yudao-cloud` |

> 💡 官方会要求克隆最新代码并 Star，一方面是支持作者，另一方面**老版本可能没有 `ProjectReactor` 或字段不一样**。

### 第 ② 步：打开 `ProjectReactor` 类，填 4 个属性

在项目里找到 `ProjectReactor`（一般在根目录 `script/` 下），只改这几个字段：

![ProjectReactor 配置位置](../../99_附件_资源文件/Yudao-Cloud/一键改包-ProjectReactor配置.png)

| 字段 | 填什么 | 例子 |
| --- | --- | --- |
| `groupIdNew` | 公司域名倒写 | `com.zhangsan` |
| `artifactIdNew` | 项目代号（英文小写、中划线） | `zhangsan-project` |
| `packageNameNew` | Java 根包名（建议和 groupId 一致） | `com.zhangsan` |
| `titleNew` | 前端显示的标题 | `张三管理系统` |
| `projectBaseDirNew` | 新项目生成到哪个目录（绝对路径） | `/Users/zhangsan/idea/zhangsan-project` |

> ⚠️ **包名必须是合法 Java 标识符**：全小写、不能有中划线、不能数字开头。`com.zhang-san` 是非法的，要用 `com.zhangsan`。

### 第 ④ 步：用 IDEA 打开新目录，重新导入 SQL

> ⚠️ **这一步最容易被忽略，也是最多人翻车的地方：一定要重新执行 SQL 的导入！**

正确做法（别偷懒用旧库）：

```sql
-- 1. 新建一个干净的库，别复用旧的 yudao 库
CREATE DATABASE `zhangsan-project`
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 2. 把项目 sql/ 目录下的脚本按顺序重新导一遍
--    ruoyi-vue-pro: sql/mysql/ruoyi-vue-pro.sql
--    yudao-cloud:   各模块自己的 sql 目录
```

**为什么要重新导库？** 旧库里是官方 demo 数据 + 旧表结构，改包后的项目可能对不上（尤其是表注释、初始化菜单数据里可能带着旧项目名）。新项目配新库，一次到位最省心。

然后参考官方《快速启动》文档，改 `application.yaml` 里的数据库连接，启动即可。

## 四、进阶篇：改完之后才是坑的开始

### 4.1 改完必做的检查清单（逐项打勾 ✅）

改包成功 ≠ 项目能跑。按这个清单过一遍：

- [ ] 全局搜索 `cn.iocoder` —— 应该**搜不到任何结果**（如果还有，说明漏改了）
- [ ] 全局搜索 `yudao` —— 确认剩下的都是你自己允许保留的
- [ ] Maven 面板点 **Reload All Maven Projects**，确认无飘红
- [ ] `mvn clean` 清掉 `target/`，避免旧的编译产物残留
- [ ] IDEA → `File → Invalidate Caches / Restart`（重要！IDEA 会缓存旧的包结构）
- [ ] 检查 `mapper.xml` 里的 `namespace` 是不是新包名
- [ ] 检查 `application.yaml` 的 `typeAliasesPackage` / `mapper-locations`
- [ ] 检查前端 `index.html` 的 `<title>` 和 `.env` 里的 `VITE_APP_TITLE`
- [ ] 新建数据库并重新导入 SQL
- [ ] 启动后登录，随便点几个菜单（能查数据说明 Mapper 绑定没问题）

### 4.2 常见报错速查表

| 报错信息 | 真正的原因 | 怎么修 |
| --- | --- | --- |
| `Invalid bound statement (not found)` | `mapper.xml` 的 `namespace` 或 `resultType` 还是旧包名 | 全局搜 `cn.iocoder`，重点看 `resources/mapper/` 目录 |
| `ClassNotFoundException: cn.iocoder.yudao...` | 某处 `import` / 配置里的类名漏改 | 全局搜 `cn.iocoder` |
| Maven 依赖全线飘红 | 各模块 `pom.xml` 的 `groupId` 不一致 | Reload Maven；检查父 pom 和子模块 pom |
| 编译报"包名与目录不匹配" | **目录没搬** | 确认磁盘上已经没有 `cn/iocoder/` 目录了 |
| 页面标题还是"芋道" | 前端 `title` 没换 | 查 `index.html`、`.env.*`、`vite.config` |
| 登录后接口 404 | 前端 API 前缀 / 网关路由没换 | 查 `VITE_API_URL`（单体）或 Nacos 网关路由（微服务） |
| 启动报 Bean 冲突/扫不到 | `ComponentScan` 的 basePackage 还是旧的 | 查启动类上的 `@SpringBootApplication(scanBasePackages=...)` |

### 4.3 微服务版（yudao-cloud）额外要改的地方

单体版改完就差不多了，**微服务版还有一堆"藏在配置中心里的名字"**，脚本不一定全覆盖，务必手工核对：

| 位置 | 要检查的东西 |
| --- | --- |
| **Nacos 配置中心** | `dataId`（常带项目名）、配置内容里的包名、Feign 扫描路径 |
| **Nacos 服务名** | `spring.application.name`（如 `yudao-server-system`） |
| **Gateway 网关** | 路由规则里的服务名、断言路径前缀 |
| **Seata** | 事务组名（如 `yudao-system-group`） |
| **Sentinel** | 限流规则里的资源名 |
| **XXL-Job / PowerJob** | 执行器 appname |
| **Docker** | `Dockerfile` / `docker-compose.yml` 里的镜像名、容器名 |
| **Jenkins** | `Jenkinsfile` 里的构建产物名、部署路径 |
| **Nginx** | 静态资源路径、反代 upstream 名 |

> 💡 **排查技巧**：改完以后在**整个新项目目录**（包括 `sql/`、`docker/`、`*.yml`）里全局搜一遍 `yudao`，列出来逐个人工判断要不要改。这是最后一道保险。

### 4.4 ⚠️ 最大的坑：改包后怎么跟上官方更新

官方文档原话：

> 友情提示：修改包名后，未来合并最新的代码可能会有一定的成本。

**为什么？** 因为你的 2825 个文件，每一个都和官方不一样了。官方发新版，`git merge` 时 **git 会认为几乎每个文件都被双方修改过** → 全线冲突 → 合并等于重做一遍。

三种应对方案：

| 方案 | 做法 | 适合 |
| --- | --- | --- |
| ✅ **双目录对比法**（推荐） | 保留一份**未改包**的纯净副本。升级时：① 纯净副本 `git pull` 官方最新 → ② 对新代码再跑一遍 `ProjectReactor` → ③ 用 Beyond Compare 对比"新版改包后"和"你的项目"，只合你改过的业务代码 | 长期维护、跟官方迭代 |
| ⚠️ **vendor 分支法** | 建一个 `vendor` 分支永远保持官方原样，业务改动只提交到 `main`。升级时在 `vendor` 合并官方，再 `rebase` 到 `main` | git 熟练、团队协作 |
| 💡 **只改部分**（最省事） | **只改 `artifactId` 和前端 `title`，包名保留 `cn.iocoder.yudao`** | 外包交付、短周期项目 |

> 💡 **十年经验之谈**：
> 如果你的项目**长期跟随官方迭代**，强烈建议走第三种的折中——**不 Java 改包名，只改对外可见的 title 和 artifactId**。
> 包名藏在 2825 个文件里，用户根本看不见；而改了它，你未来每一次升级都要付一次"全线冲突"的税。**不划算**。
> 只有确实需要交付源码、且客户明确要求品牌化时，才做完整改包。

### 4.5 回滚方案

`ProjectReactor` 是**复制后修改**，原项目目录完全没动。所以：

```
改砸了？→ 直接删掉 PROJECT_BASE_DIR_NEW 目录 → 重新填配置 → 再跑一次
```

**这就是"先复制再修改"这个设计最大的价值 —— 永远留着后悔药。** 你自己的任何批量脚本，也应该保持这个习惯。

## 五、一句话总结

| 场景 | 该做什么 |
| --- | --- |
| 拿到芋道源码要交付/品牌化 | 跑 `ProjectReactor`，4 步搞定 |
| 只是自己学习/长期使用 | 只改 `title`，**别改包名**，省掉未来升级的麻烦 |
| 改完启动报错 | 全局搜 `cn.iocoder` 和 `yudao`，99% 是漏改 |
| 想做批量重构 | 记住套路：**复制 → 扫描 → 替换 → 移动**，永远先复制再改 |
