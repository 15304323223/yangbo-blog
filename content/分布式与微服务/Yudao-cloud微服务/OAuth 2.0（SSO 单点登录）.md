# OAuth 2.0（SSO 单点登录）

> **一句话概括**：OAuth 2.0 是"**授权别人访问你的数据，但不给他密码**"的协议。芋道**自研实现**（不用 Spring Authorization Server），支持授权码/密码/客户端/简化四种模式，并内置 SSO 单点登录。

---

## 零、先建立整体印象：酒店房卡

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

你入住酒店，想让**保洁阿姨**进你房间打扫：

| 方式 | 做法 | 问题 |
|---|---|---|
| ❌ 把房门密码告诉她 | 直接给密码 | 她以后随时能进，你还不知道 |
| ✅ 去前台办一张**临时房卡** | 刷卡进门，退房时收回 | 完美 —— 她能进，但**随时可作废**，且不知道你的密码 |

**OAuth 2.0 就是这张"临时房卡"的发放流程。**

再具体点，OAuth 2.0 有 4 种"办卡方式"：

| 模式 | 类比 | 场景 |
|---|---|---|
| **客户端模式** | 酒店**员工**自己有工牌，不代表任何人 | 机器调机器（内部 RPC、开放平台） |
| **密码模式** | 你把**账号密码**给前台，他帮你办卡 | ⚠️ 只能是**自家**的 App |
| **授权码模式** ⭐ | 前台给你一张**凭证条**，你拿它换房卡 | 第三方登录（微信/QQ/钉钉）、SSO |
| **简化模式** | 前台**直接**给你房卡，跳过换卡 | 老式纯前端应用（已不推荐） |

### SSO 单点登录是什么？

**类比**：一个大型科技园区里有 10 栋楼（OA、ERP、CRM……）。以前每进一栋楼都要登记一次。现在**园区大门口刷一次脸**，之后 10 栋楼随便进。

**一次登录，处处通行** —— 这就是 SSO。

## 一、原理篇

### 1.1 四种授权模式怎么选？⭐

> 🎓 **费曼第 2 段 · 一张决策表搞定**

| 问题 | 答案 |
|---|---|
| **令牌的拥有者是机器吗？** | 是 → **客户端模式**（Client Credentials）。如：开放平台、内部 RPC |
| **客户端是自己公司的吗？** | 是 → **密码模式**（Password）。如：自家 App 调自家授权服务 |
| **客户端是第三方的吗？** | 是 → **授权码模式**（Authorization Code）。如：接微信/钉钉登录 |
| **纯前端应用、没有后端？** | → **简化模式**（Implicit）。⚠️ 已不推荐 |

> ⚠️ **密码模式的风险**：客户端能拿到用户的**明文账号密码**。所以**只限自家客户端**，第三方一律用授权码模式。

### 1.2 芋道用了哪些模式？

```
┌─────────────────────────────────────────┐
│ ① 外部授权（红色）：【授权码模式】         │
│    实现 SSO 单点登录，把用户授权给接入方    │
│    接入方可以是内部系统，也可以是第三方     │
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│ ② 内部登录（绿色）：传统账号密码登录        │
│    仍是 /admin-api/system/auth/login     │
│    ⚠️ 没用【密码模式】，官方说为了降低学习成本│
└─────────────────────────────────────────┘
```

> 💡 **一个重要细节**（官方说明）：
> 虽然内部登录没用密码模式，**但复用了 OAuth 2.0 的"访问令牌 + 刷新令牌"机制**，因为这样安全性更好。
> 这就是为什么 [[功能权限]] 里说的 Token 存在 `system_oauth2_access_token` 表里。

### 1.3 为什么芋道自研 OAuth 2.0，不用 Spring Authorization Server？⭐

> **官方给的三大理由**（非常实在，值得学习这个决策思路）：

| 问题 | 说明 |
|---|---|
| **① 学习成本大** | SAS 是新框架，"入门容易精通难"，引入要花 1-2 周深入学习 |
| **② 排查问题难** | 出问题时往往要调试到源码层面，团队只有个别人具备这个能力 |
| **③ 定制成本高** | 想按业务定制，需要对 SAS 源码有不错掌控力 |

> 💡 **官方点睛**：
> > "具备一定规模的互联网公司，基本不会直接采用 Spring Security OAuth 或 Spring Authorization Server，也是采用自研的方式。"

**补充背景**：`Spring Security OAuth` **已废弃**，被 `Spring Authorization Server`（SAS）替代。

| | 用什么 | 适合 |
|---|---|---|
| 中小项目 / 快速上线 | Spring Authorization Server | 标准、省事 |
| 大厂 / 深度定制 | **自研** | 完全可控 |

## 二、应用篇：SSO 实战

### 2.1 实战一：授权码模式实现 SSO（8 步）

**场景**：接入方（另一个系统）想让用户用 ruoyi-vue-pro 的账号登录。

```
① 用户访问接入方首页（未登录）
        │
        ▼
② 点击「跳转」→ 跳到 ruoyi-vue-pro 的 SSO 授权页
        │
        ▼
③（若 ruoyi-vue-pro 也未登录）先登录账号密码
        │
        ▼
④ 回到 SSO 授权页，勾选授权范围（如"访问你的个人信息"）
        │
        ▼
⑤ 点击「同意授权」→ 生成 code 授权码
        │
        ▼
⑥ 重定向回接入方 callback.html，URL 上带 code
        │
        ▼
⑦ 接入方后端拿 code → 调 ruoyi-vue-pro → 换回 accessToken
        │
        ▼
⑧ 接入方拿到 accessToken → 拉取用户昵称等信息 → 完成登录
```

> ❓ **官方答疑**：为什么没跳到 SSO 授权页，而是跳到了登录页？
> **因为你在 ruoyi-vue-pro 也没登录**，所以它先让你登录，登录完再回到 SSO 授权页继续授权流程。

**客户端配置**（【系统管理 → OAuth 2.0 → 应用管理】）：

| 配置项 | 值 |
|---|---|
| 客户端编号 | `yudao-sso-demo-by-code` |
| 客户端密钥 | `test` |
| 授权类型 | `authorization_code`、`refresh_token` |
| 授权范围 | `user.read`、`user.write` |
| 可重定向 URI | `http://127.0.0.1:18080` |

### 2.2 实战二：密码模式实现 SSO（6 步）

**区别**：用户直接在接入方的登录页输账号密码 → 接入方后端拿密码去换 Token。

```
① 访问接入方首页 → 点击「跳转」→ 跳到接入方自己的 login.html
        │
        ▼
② 用户输入账号密码
        │
        ▼
③ 接入方后端拿账号密码 → 调 ruoyi-vue-pro → 换回 accessToken
        │
        ▼
④ 完成登录，跳回首页，拉取用户信息
```

客户端配置的授权类型改为：`password`、`refresh_token`

> ⚠️ **安全提醒**：密码模式只在**接入方完全可信**（自己公司的系统）时使用。

### 2.3 两种模式对比

| | 授权码模式 ⭐ | 密码模式 |
|---|---|---|
| 步骤 | 8 步（多一次跳转换码） | 6 步（更直接） |
| 密码暴露给接入方 | ❌ 不会 | ✅ **会** |
| 安全性 | 高 | 中 |
| 适用 | 第三方、跨系统 | 自家系统 |

## 三、进阶篇

### 3.1 Token 的生命周期管理

| 操作 | 说明 |
|---|---|
| **校验 Token** | 接入方调 ruoyi-vue-pro 校验 accessToken 是否有效 |
| **刷新 Token** | accessToken 过期（30 分钟），用 refreshToken（30 天）换新 |
| **删除 Token** | 用户退出 → 删除 Token，立即失效 |

> 💡 这就是为什么 accessToken 短（30 分钟）、refreshToken 长（30 天）：
> - accessToken 频繁传输，**被盗风险高** → 短期
> - refreshToken 只在刷新时用，**暴露机会少** → 长期

### 3.2 OAuth 2.0 表结构

| 表 | 作用 |
|---|---|
| `system_oauth2_client` | **客户端**（应用）信息：client_id、密钥、授权类型、令牌有效期 |
| `system_oauth2_access_token` | **访问令牌**：Token、用户 ID、过期时间 |
| `system_oauth2_refresh_token` | **刷新令牌** |
| `system_oauth2_code` | **授权码**（授权码模式用，一次性） |
| `system_oauth2_approve` | **授权记录**（用户同意了哪些范围，用于"自动授权"） |

> 💡 `system_oauth2_approve` 表是实现"**下次自动授权，不再弹窗**"的关键 —— 记录用户已经同意过，下次直接跳过确认页。

### 3.3 生产环境 5 个坑

| 坑 | 现象 | 解决 |
|---|---|---|
| **redirect_uri 不匹配** | 报 `invalid_redirect_uri` | 回调地址必须**完全一致**（含 http/https、端口、结尾斜杠） |
| **code 被重复使用** | 报 `invalid_grant` | code **一次性**，用后即焚（防重放攻击） |
| **client_secret 泄露** | 别人冒充你的应用 | 密钥**只存后端**，绝不能写在前端/App 里 |
| **Token 明文传输** | 中间人攻击 | **必须 HTTPS** |
| **没校验授权范围** | 越权访问 | 每次请求都要校验 Token 的 scope |

### 3.4 芋道 OAuth 2.0 的学习价值

> 💡 **官方原话**：
> > "通过学习项目的 OAuth 2.0 实现，可以进一步加深对 OAuth 2.0 的理解，**知其然而知其所以然**！"

芋道自研的实现代码量不大、可读性好，**是学习 OAuth 2.0 原理的优质素材** —— 比啃 SAS 源码轻松得多。

## 四、一句话总结

| 问题 | 答案 |
|---|---|
| OAuth 2.0 解决什么 | 授权别人访问你的数据，**但不给密码** |
| 四种模式怎么选 | 机器→客户端；自家→密码；第三方→**授权码** |
| SSO 是什么 | 一次登录，多个系统通行 |
| 芋道用什么模式 | 外部用**授权码模式**；内部登录仍用账号密码（但复用 Token 机制） |
| 为什么自研 | SAS 学习/排查/定制**成本都太高** |
| 表 | `system_oauth2_client` / `_access_token` / `_refresh_token` / `_code` / `_approve` |
