## 零、先建立整体印象：技术选型 = 给餐厅选家具

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

假设你要开一家餐厅，开业前要干一件事：**买齐所有家具和设备**。

- 大门要装**门禁**（刷卡进门）→ 选什么品牌的门？要不要人脸识别？
- 厨房要有**灶台、抽油烟机、冷柜** → 是买商用的还是家用的？
- 收银要有**POS 机** → 选传统的还是扫码点单的？
- 后厨要有**调度系统**（外卖单来了谁做、谁送）

你不可能自己造一个门禁、一个 POS 机，**全行业已经有人做好了**，你要做的就是**从好用的产品里挑一组能配起来的**。

技术选型干的**就是这件事**：

> 一个项目要选 **Java 语言**（厨房）、**Spring Boot 框架**（灶台）、**MySQL 数据库**（冷柜）、**Redis 缓存**（手边随手拿的调料架）、**消息队列**（外卖传菜窗口）、**Nginx 网关**（大门）、**Vue 前端**（点菜单和餐桌）……每一项都是从当下最主流的开源软件里挑的。

挑的依据就 4 条（按重要性排）：

1. **能不能干活**（功能覆盖需求）
2. **好不好维护**（团队熟不熟、社区活跃度、招人好不好招）
3. **配不配得上**（和其他组件能不能一起跑，比如 Spring Boot 配 MyBatis 而不是配 Hibernate）
4. **将来好不好升级**（生态稳定、版本不要太激进）

芋道项目选的每一项，**基本都是这 4 条原则的当下最优解**。本篇要讲的就是"它选了谁、为什么选它"。

先看这张图，它把芋道（ruoyi-vue-pro 单体版）的整套架构画出来了。**看不懂？没关系，下面的"翻译"对照表一行一行给你解。**

![ruoyi-vue-pro 技术架构图](../../99_附件_资源文件/Yudao-Cloud/技术选型-架构图.png)

### 1.1 把架构图"翻译"成餐厅布局

| 图里的东西 | 餐厅比喻 | 它到底干什么 |
|---|---|---|
| 🖥️ 电脑 / 📱 手机 | 顾客 | 用浏览器/App 来点菜的人 |
| 管理后台 Vue / UniApp | 大堂点菜单 | 员工 / 管理员操作界面 |
| 用户前台 UniApp | 顾客点菜单 | 顾客用的 App 或小程序 |
| **Nginx × 3** | 餐厅大门 + 接待员 | 门口的 3 个接待员，谁闲就让谁接待顾客（**负载均衡**） |
| **Spring Boot × 3** | 后厨 3 个灶台 | 真正干活的厨师，每个灶台做自己拿手的菜（**业务集群**） |
| MySQL | 主冷柜（食材库） | **业务数据**放这里 —— 订单、用户、商品 |
| Redis | 灶台边的随手调料架 | **缓存数据**放这里 —— 5 分钟内还要再用的东西 |
| OSS / MinIO | 仓库（干货库） | **文件数据**放这里 —— 图片、PDF、视频 |
| Elasticsearch | 智能检索柜 | **搜索数据**放这里 —— 商品搜索、日志全文检索 |
| **Quartz** ⏰ | 厨房定时闹钟 | **定时任务** —— 比如每晚 0 点自动清理过期订单 |
| **Redis Stream** 📩 | 外卖传菜窗口 | **消息队列** —— 异步任务扔进来，后厨慢慢消化 |
| **Redisson** 🔒 | 后厨保险柜钥匙 | **分布式锁** —— 多灶台抢同一份食材时不打架 |
| **Jenkins / Docker / Portainer** 🛠️ | 装修队 + 工程监理 | **运维工具** —— 自动部署、镜像管理 |
| **Spring Boot Admin / Druid Admin / SkyWalking** 📊 | 餐厅监控大屏 | **监控工具** —— 看哪个灶台慢、哪个门卡了 |

### 1.2 一条请求的"旅程"（跟着数据走一遍）

记住这张图怎么读：**实线 = 同步请求**，**虚线 = 异步 / 调度 / 监控**。

> 🧒 顾客张三走进餐厅点了一道鱼香肉丝，发生的事：

1. 张三用**手机**打开 App（用户前台 UniApp）→ 浏览器发出 **HTTP** 请求
2. 请求到达 **Nginx 大门** → Nginx 挑一个最闲的灶台（**负载均衡**），把请求转过去
3. **Spring Boot 灶台** 接到订单 → 去 **MySQL 冷柜** 取菜品信息、去 **Redis 调料架** 取活动优惠、去 **Elasticsearch 检索柜** 搜"鱼香"
4. 下单成功后 → 灶台往 **Redis Stream 传菜窗口** 扔一张纸条："扣库存、发短信、记日志"（**异步任务**）
5. 纸条被后台慢慢消费，不影响张三继续点菜
6. 同时 **Spring Boot Admin / Druid Admin / SkyWalking** 监控大屏一直在看每个灶台有没有出慢菜、报错

> 💡 **看图小技巧**：
> - 上半圈（外卖窗口/闹钟/锁）都是**支撑能力**，不直接服务顾客，但没了它们系统跑不起来
> - 右半圈（MySQL/Redis/OSS/ES）是**存储层**，业务数据各有归属，**不能混着放**
> - 下半圈（运维 + 监控）是**让系统活下去的工具**，开发完上线前必须配齐

## 二、后端技术栈：7 个角色、7 个职位

> 🧒 **费曼第 3 段 · 给高中生讲每个职位的来历**

后端不是"一个 Java"，是**七种不同职责**组合出来的。每种职责都有「主流候选人」，芋道选了谁以及为什么是它。

### 2.1 系统环境（地基）

| 框架 | 版本 | 它干啥的（一句话） | 芋道为什么选它 |
|---|---|---|---|
| **JDK** | 21 或 8 | Java 程序运行的基础环境（餐厅的地基） | 选 21 享新特性（虚拟线程、模式匹配），选 8 求稳；芋道项目**两个都支持**（是亮点） |
| **Maven** | ≥ 3.5.4 | Java 项目的包管理与构建工具（采购清单 + 物流） | 主流标配，几乎没有团队不用 |

> ⚠️ **版本陷阱**：芋道用的是 **Spring Boot 3.2.0** → 它要求 **JDK 17+**。所以**千万别拿 JDK 8 去跑最新芋道**，会直接报 `class file version 61`（Java 17）错误。详情见 [[#六、版本陷阱与踩坑]]。

### 2.2 主框架（骨架）

| 框架 | 版本 | 它干啥的（一句话） | 为什么是它 |
|---|---|---|---|
| **Spring Boot** | 3.2.0 | 让 Spring 从"一堆 XML"变成"一键启动的汽车"（见 [[05_SpringBoot 核心]]） | 生态最大，文档最全，事实标准 |
| **Spring MVC** | 6.1.1 | 处理 HTTP 请求的 MVC 框架（餐厅点菜流程） | Spring Boot 默认搭档，不用选 |
| **Spring Security** | 6.2.0 | 安全框架（门禁系统，见 [[20_Spring Security 与 OAuth2-JWT 安全认证]]） | 唯一能跟 Spring 全家桶深度整合的安全方案 |

> 💡 **芋道在 Spring Security 之上又搭了 OAuth2 + JWT**：这是企业级标配 —— 内部员工用密码登录、外部第三方用 OAuth2、移动端用 JWT 无状态认证。三套机制芋道全包，**少有脚手架做到这么全**。

### 2.3 存储层（4 种库，各管各的）

| 框架 | 版本 | 它干啥的（一句话） | 为什么是它 |
|---|---|---|---|
| **MySQL** | ≥ 5.7 | 关系型数据库（餐厅主冷柜） | 国内首选，芋道**也支持达梦（DM）和 PostgreSQL** —— 国产化/特殊场景通吃 |
| **Druid** | 1.2.20 | JDBC 连接池 + **SQL 监控**（看哪个 SQL 慢） | 阿里出品，带监控大屏，比 HikariCP 多了"可观测性" |
| **MyBatis Plus** | 3.5.4.1 | MyBatis 增强版（翻译官 + 智能助手，见 [[06_MyBatis 与 MyBatis-Plus]]） | 单表 CRUD 不用写 SQL，Wrapper 写起来爽 |
| **Dynamic Datasource** | 4.2.0 | 动态数据源（**读写分离 + 多数据源切换**） | 一个 `@DS` 注解就能切换库；多租户 / 多账套场景刚需 |
| **Redis** | ≥ 5.0 | KV 内存数据库（手边调料架，见 [[10_Redis 实战]]） | 缓存、分布式锁、消息队列都能干 |

> 💡 **为什么 MyBatis Plus 而不是 JPA / Hibernate？**
> 国内业务**复杂 SQL 多**（连表、分页、动态条件），MyBatis Plus 在"可控 SQL"和"省事"之间平衡最好。JPA 写简单 CRUD 爽，写复杂报表就抓瞎。

### 2.4 中间件（特殊任务的专用工具）

| 框架 | 版本 | 它干啥的（一句话） |
|---|---|---|
| **Flowable** | 7.0.0 | 工作流引擎（审批流的"剧本"，见 [[16_Flowable 工作流]]） |

> 💡 **芋道的工作流做得非常重**：审批流、流程设计器（BPMN.js）、会签/或签/驳回、加签减签、转办委派抄送、监听器一应俱全。**国内开源脚手架里这是 Top 1 级别**。复杂业务（合同、报销、请假）可以直接用。

### 2.5 系统监控（监控大屏）

| 框架 | 版本 | 它干啥的 |
|---|---|---|
| **Spring Boot Admin** | 3.1.8 | 看所有 Spring Boot 应用的健康状态、线程栈、内存 |

> 💡 芋道**默认不开 Admin 界面**（避免生产环境暴露），需要时单独启动 `yudao-server` 里的 `admin-monitor` 模块。

### 2.6 单元测试

| 框架 | 版本 | 它干啥的 |
|---|---|---|
| **JUnit 5** | 10.10.1 | Java 单元测试事实标准 |

> 💡 芋道的单测覆盖率不算高（业务代码为主），但**框架层和工具类**测试完备。要补单测时建议直接对着 Service 层补 Controller 单测。

### 2.7 其它工具（必备小件）

| 框架 | 版本 | 它干啥的（一句话） |
|---|---|---|
| **Springdoc（OpenAPI 3）** | 2.2.0 | 自动生成 Swagger 接口文档（替代老版 springfox） |
| **Jackson** | 2.15.3 | JSON 序列化 / 反序列化（Java 对象 ↔ JSON 字符串） |
| **MapStruct** | 1.5.5.Final | **DO / VO / DTO** 之间转换的代码生成器（编译期生成，不反射） |

> 💡 **MapStruct 为什么重要**：芋道项目里实体类分得很细（`DO` 持久层、`BO` 业务层、`VO` 表现层、`DTO` 传输层）。手工 set/get 是噩梦，MapStruct 在编译期生成转换代码，**比反射的 BeanUtils 快 5~10 倍**。

## 三、前端技术栈：5 套方案，对应 5 种场景

> 🧒 **费曼第 3 段 · 餐厅的"装修风格"也得选，不能一种风格打天下**

芋道**不是一套前端，而是给了 5 套**，对应 5 种不同场景。**这是它的杀手锏** —— 你做后台管理、做小程序、做 App、做移动端，都能直接用现成的，不用自己挑技术。

### 3.1 五套方案一览

| 方案 | 适用场景 | 核心栈 |
|---|---|---|
| ① **Vue3 + ElementPlus**（默认推荐） | 现代管理后台 | Vue3 + Vite + TS + pinia + ElementPlus + vxe-table |
| ② **Vue3 + Vben + Ant-Design-Vue** | 高端管理后台 | Vue3 + Vite + TS + pinia + Ant-Design-Vue + Vben 模板 |
| ③ **Vue2** | 老项目迁移、IE 兼容 | Vue2 + ElementUI |
| ④ **uni-app（管理后台）** | 移动端 H5 后台 | uni-app 跨端框架 |
| ⑤ **uni-app（用户 App）** | 移动 App / 小程序 | uni-app + Vue2 |

### 3.2 主流方案 ①：Vue3 + ElementPlus（推荐）

> 最常见、最容易招人、文档最多。

| 框架 | 它干啥的（一句话） |
|---|---|
| **Vue 3** | 主流前端框架（见 [[19_前端 Vue 与 ElementUI]]） |
| **Vite** | 比 webpack 快 10 倍的开发服务器（HMR 毫秒级） |
| **TypeScript** | JavaScript 的超集（**加类型检查**，少写 bug） |
| **pinia** | Vue3 的官方状态管理库（**替代 vuex**，API 更简洁） |
| **vueuse** | Vue 常用工具集（防抖、节流、复制到剪贴板……） |
| **vxe-table** | "Vue 最强表格" —— **虚拟滚动 + 万级数据 + Excel 复制** |
| **vue-i18n** | 国际化（多语言切换） |
| **vue-router** | 路由（页面跳转） |
| **windicss** | 原子化 CSS 框架（替代 tailwind，更快） |
| **iconify** | 在线图标库（**10 万+ 图标**，按需加载） |

> 💡 **为什么 ElementPlus 而不是 Ant Design？** 两者都很强。但 ElementPlus 是 Vue3 原生，文档中文友好；Ant Design 是 Vue2 时代的移植版。**新项目无脑选 ElementPlus**。

### 3.3 高端方案 ②：Vben + Ant-Design-Vue

**Vben** 是一套基于 Ant-Design-Vue 的**开箱即用中后台模板**（类似 vue-vben-admin）。优势是**视觉更精致**、**权限/字典/CRUD 抽象组件已经写好**，拿来即用。

适合：要做"看起来高大上"的管理后台、外包项目预算够、需要快速出图。

### 3.4 兼容性方案 ③：Vue2

**只在你必须用 Vue2 时才选**（老插件、IE 兼容、政府/国企老浏览器）。**新项目一律不推荐** —— Vue2 已停止大版本更新（Vue2 EOL：2023 年 12 月 31 日）。

### 3.5 跨端方案 ④ ⑤：uni-app

**uni-app** 是 DCloud 出的跨端框架，**一套代码编译到 iOS / Android / 微信小程序 / 支付宝小程序 / H5**。对中小团队是神器 —— 一个前端 = 五个端。

> ⚠️ 芋道 uni-app 版本是 **Vue2** 的（不是 Vue3），版本偏老。如果新项目要做 uni-app，**考虑直接用 uni-app Vue3 版本** + 自己接芋道后端 API。

## 四、为什么是它们不是别的（选型决策 8 问）

> 🧒 **费曼第 3 段 · 不光给答案，还要给"为什么这么选"的思路**

下次你做选型，可以直接套这个 **8 问框架**：

| # | 问题 | 芋道怎么答的 |
|---|---|---|
| 1 | **生态是否成熟**？（文档多不多、Stack Overflow 答案多不多、招人好不好招） | 全选 Java + Vue 生态——国内最大招人池 |
| 2 | **团队是否熟**？（新人能不能 1 周上手） | 全选一线主流，没有冷门框架 |
| 3 | **能不能扛住业务量**？（并发、TPS、可用性） | Nginx + Spring Boot 集群 + Redis + MySQL 经典组合，**经过双 11 验证**的方案 |
| 4 | **是否方便二次开发**？（能不能改源码、定制流程） | 全开源 + 文档齐全，**最容易二开的脚手架**之一 |
| 5 | **运维成本**？（部署、监控、告警是否方便） | 自带 Jenkinsfile + Dockerfile + Spring Boot Admin + Druid Admin + SkyWalking |
| 6 | **未来升级路径**？（3 年后还在不在、社区活不活跃） | 全选 Apache / Spring / 顶级社区项目，**不会被突然抛弃** |
| 7 | **是否国产化兼容**？（政府/国企要信创） | 数据库支持达梦（DM）；前端纯前端，无国产化问题 |
| 8 | **许可证**？（能不能商用、要不要付费） | 全 Apache 2.0 / MIT，**随便商用** |

> 💡 **面试回答套路**（背下来）：
> "我们选型的核心原则是 **'主流优先 + 生态成熟 + 可二次开发'**。每个组件都是 Apache/Spring/顶级社区项目，文档齐全、新人友好；同时预留了足够的扩展点（MyBatis 拦截器、Spring Security 扩展、数据权限注解……），方便后续做二开。"——30 秒讲完，面试官爱听。

## 五、微服务版（yudao-cloud）额外补了什么

> ⚠️ **重要前提**：本文是 `ruoyi-vue-pro` **单体版**的官方选型。`yudao-cloud` 微服务版在此基础上**多了一大堆**组件，下面这张表是社区整理的（**官方文档未列**），用以补充。

| 分类 | 微服务版新增 | 它干啥的（一句话） |
|---|---|---|
| **服务注册发现** | Nacos | 微服务的"花名册"（服务上线/下线自动同步） |
| **配置中心** | Nacos Config | 配置文件集中管理，**改配置不用重启**（推送生效） |
| **API 网关** | Spring Cloud Gateway | 微服务的**统一大门**（路由 + 鉴权 + 限流） |
| **服务调用** | OpenFeign | 像调本地方法一样调远程服务（声明式 HTTP 客户端） |
| **熔断限流** | Sentinel | 服务雪崩时的"保险丝"（见 [[14_微服务 SpringCloud 与 Dubbo]]） |
| **分布式事务** | Seata | 跨服务调用的一致性保障（**AT 模式无侵入**） |
| **分布式定时任务** | XXL-Job / PowerJob | 替代 Quartz，**可视化管理 + 弹性扩容** |
| **链路追踪** | SkyWalking | 看一个请求经过了哪些服务、哪一步慢（**APM**） |
| **消息队列（多选）** | RocketMQ / RabbitMQ / Kafka | 芋道同时支持 3 种 MQ，按业务选 |
| **分布式日志** | ELK（Logstash + ES + Kibana） | 日志集中收集 + 检索 |
| **对象存储** | MinIO（替代 OSS） | 自建对象存储，**适合内网/信创环境**（见 [[21_Minio 对象存储]]） |

> 💡 **微服务版和单体版的核心区别**：
> 单体版是"一个 Spring Boot 进程包含所有模块"；微服务版是把每个模块拆成独立进程，通过 Nacos 注册、Feign 调用、Gateway 路由、Sentinel 保护。
> **如果你的项目还没到 5 万行代码、团队不到 10 人，硬上微服务是过度设计**。先跑单体版，业务真的扛不住了再拆。

> 💡 **想深挖微服务组件**？见 [[14_微服务 SpringCloud 与 Dubbo]]、[[22_从零搭建芋道式脚手架框架]] 第 8 章"微服务化"。

## 六、版本陷阱与踩坑

> 🎓 **费曼第 4 段 · 大学生/工程师才能踩到的坑**

### 6.1 JDK 版本必须 ≥ 17（如果用最新芋道）

芋道 `2024.x` 版本基于 **Spring Boot 3.2**，Spring Boot 3 又基于 **Jakarta EE 9**（包名从 `javax.*` 全部改成 `jakarta.*`）。所以：

| JDK 版本 | 能否跑最新芋道 | 说明 |
|---|---|---|
| JDK 8 | ❌ | 跑 Spring Boot 2.x 老芋道可以，最新芋道直接报错 |
| JDK 11 | ⚠️ | 理论能跑，但官方推荐 17+，**会有边角警告** |
| JDK 17（推荐） | ✅ | Spring Boot 3 官方 LTS 版本 |
| JDK 21（尝鲜） | ✅ | 享受虚拟线程（`Thread.ofVirtual()`），芋道**已声明支持** |

> ⚠️ 如果你团队还在用 JDK 8，**先升 JDK 17 再跑芋道**。否则会报：
> ```
> java.lang.UnsupportedClassVersionError: ... class file version 61 (Java 17)
> ```

### 6.2 Spring Boot 3 的 Jakarta 迁移

所有 `javax.servlet.*`、`javax.persistence.*` 全部改成 `jakarta.*`。**芋道项目已经全部改完**，但你**自己写的代码**或**引入的第三方老 jar**如果有 `javax.*` 引用，**全部要换**：

| 老（Spring Boot 2） | 新（Spring Boot 3） |
|---|---|
| `import javax.servlet.http.HttpServletRequest;` | `import jakarta.servlet.http.HttpServletRequest;` |
| `import javax.persistence.*;` | `import jakarta.persistence.*;` |
| `import javax.validation.*;` | `import jakarta.validation.*;` |

### 6.3 Spring Security 6 的配置变化

`WebSecurityConfigurerAdapter` 在 Spring Security 6 **已被废弃**，必须改用 `SecurityFilterChain` Bean。芋道已经全部按新写法配了，但你 copy 老博客的代码时要注意：

```java
// ❌ 老写法（已废弃）
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    @Override protected void configure(HttpSecurity http) { ... }
}

// ✅ 新写法（芋道用的）
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
        .formLogin(Customizer.withDefaults());
    return http.build();
}
```

> 详细见 [[20_Spring Security 与 OAuth2-JWT 安全认证]]。

### 6.4 其它版本兼容坑

| 坑 | 现象 | 解决 |
|---|---|---|
| Node 版本太低 | `npm install` 报错 `engine "node" is incompatible` | 芋道前端要求 **Node ≥ 16** |
| Maven 用 3.0 老版本 | 构建报错 | 升到 **3.5.4+** |
| IDEA 用 2020 老版本 | Spring Boot 3 飘红、Jakarta 包不识别 | 升到 **IDEA 2022.2+** |
| Redis 用 4.x | 部分 Stream API 不可用 | 升到 **5.0+** |
| MySQL 用 5.6 | JSON 字段类型不支持 | 升到 **5.7+**（推荐 8.0） |

## 七、面试话术：30 秒讲清芋道技术选型

> 🎓 **费曼第 4 段 · 给"被问倒"的人准备的话术**

> **面试官问**："你们项目用的什么技术栈？为什么这么选？"

> ✅ **30 秒答案**：
> "我们用芋道（Yudao）做企业级中后台。后端是 **Spring Boot 3 + JDK 17 + MyBatis Plus + MySQL + Redis + Flowable**，前端是 **Vue3 + ElementPlus + Vite + TypeScript**，中间件有 **Nginx + Druid + Spring Boot Admin**。选型原则是'**主流优先、生态成熟、可二次开发**'——所有组件都是 Apache 或 Spring 顶级社区项目，文档全、招人容易；同时芋道本身预留了 MyBatis 拦截器、Spring Security 扩展点、数据权限注解等扩展位，业务能深度定制。"

> ✅ **被追问**："为什么不选 Spring Cloud Alibaba 全家桶？"
> "我们是 **ruoyi-vue-pro 单体版**起步，业务量没到非要拆微服务的程度。如果未来要拆，可以平滑迁移到 **yudao-cloud 微服务版**——芋道两个版本**模块结构一致**，迁移成本主要是部署，不是代码改写。"

> ✅ **被追问**："为什么不用 JPA？"
> "我们业务**复杂 SQL 多**（连表查询 + 动态条件 + 报表），MyBatis Plus 在'**写复杂 SQL 可控**'和'**单表 CRUD 省事**'之间平衡最好。JPA 在复杂 SQL 场景会变成 HQL 调优的噩梦。"

## 八、一句话总结

| 场景 | 结论 |
|---|---|
| 芋道技术栈选了什么 | **Spring Boot 3 + JDK 17 + MyBatis Plus + MySQL + Redis + Flowable + Vue3 + ElementPlus**，全是主流 |
| 为什么选这些 | 主流 + 生态成熟 + 可二开 + Apache/Spring 顶级社区 + 不被抛弃 + 商用免费 |
| 单体和微服务怎么选 | **< 5 万行代码 / 团队 < 10 人先用单体**，扛不住了再拆 yudao-cloud |
| 版本坑 | Spring Boot 3 要 **JDK 17+**；**`javax.*` 改 `jakarta.*`**；**Spring Security 6 用 `SecurityFilterChain`** |
