# 幂等性（防重复提交）

> **一句话概括**：同一个请求，在一段时间内只能成功执行一次。芋道用 `@Idempotent` 注解实现 —— 底层是 **Redis 存一个标记 Key**，进来先查有没有标记，有就报错"请勿重复提交"。

---

## 零、先建立整体印象：电梯按钮按两下没用

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

你进电梯按了「8楼」，等了一会儿觉得没反应，又按了一下。

电梯**不会**因此跑两趟 —— 它知道"8楼已经被按过了"，再按无效。

这就是**幂等性**：**同一件事做一次和做一百次，结果都一样**。

放在程序里，最常见的场景：

| 场景 | 会发生什么 |
|---|---|
| 用户快速双击"提交订单"按钮 | 生成 **2 笔订单** 💸 |
| 网络卡顿，前端自动重试 | 扣了 **2 次款** 💸 |
| 支付平台回调通知重复 | 订单被**重复处理** 💸 |
| 消息队列重复投递 | 库存**多扣了** 💸 |

**幂等性就是给接口装一个"电梯按钮"**：同一个请求，一段时间内只让第一次生效。

## 一、原理篇

### 1.1 核心流程（4 步）

> 🎓 **费曼第 2 段 · 给高中生讲**

```
① 方法执行前：根据【方法名 + 参数】算出一个 Key
        │
        ▼
② 去 Redis 查这个 Key 存不存在
        │
        ├── 存在 ──→ 说明正在执行 / 刚执行过 → ❌ 报错"请勿重复提交"
        │
        └── 不存在 ──→ ③ 把 Key 存进 Redis，设置过期时间（标记"正在执行中"）
                            │
                            ▼
                       ④ 执行业务方法
```

### 1.2 Key 是怎么算出来的？

默认用 **MD5(方法名 + 方法参数)**：

```
原始：cn.iocoder.yudao.module.system.controller.TestDemoController#get(123)
  ↓ MD5 摘要
Key：idempotent:a1b2c3d4e5f6...
```

> 💡 **为什么要 MD5？** 因为参数可能很长（比如一整个表单的 JSON），直接当 Redis Key 会：
> 1. 占用大量内存
> 2. 超过 Redis Key 的长度限制
> 3. 肉眼完全没法看
>
> MD5 后固定 32 位，短且唯一。

### 1.3 三个关键设计决策（官方说明）

| 决策 | 做法 | 为什么 |
|---|---|---|
| **执行完要不要删 Key？** | **不删**，等它自然过期 | 官方原话："如果希望主动删除 Key，可以用分布式锁 `@Lock` 实现幂等" |
| **执行时间超过过期时间怎么办？** | Redis 自动删掉 Key，下次请求能通过 | ⚠️ 所以要**评估方法执行时间**，别超过过期时间 |
| **方法抛异常怎么办？** | **默认删除 Key**，让下次能重试 | 参考美团 GTIS 方案。否则异常后用户在这段时间内永远无法重试 |

> 💡 官方点睛之笔：
> > "从本质上来说，`idempotent` 包提供的幂等特性，**本质上也是基于 Redis 实现的分布式锁**。"

区别在于：分布式锁抢不到会**等**，幂等抢不到直接**报错**。

## 二、应用篇

### 2.1 引入依赖

```xml
<dependency>
    <groupId>cn.iocoder.boot</groupId>
    <artifactId>yudao-spring-boot-starter-protection</artifactId>
</dependency>
```

### 2.2 加注解（就这么简单）

```java
// TestDemoController.java
@GetMapping("/get")
@Idempotent(timeout = 10, message = "重复请求，请稍后重试")   // 👈 10 秒内不允许重复
public CommonResult<TestDemoRespVO> getTestDemo(@RequestParam("id") Long id) {
    // ... 业务代码
}
```

**效果**：

| 调用次数 | 结果 |
|---|---|
| 第 1 次 | ✅ 执行成功 |
| 第 2 次（10 秒内） | ❌ 返回错误 |

```json
{
  "code": 900,
  "data": null,
  "msg": "重复请求，请稍后重试"
}
```

### 2.3 完整参数

```java
@Idempotent(
    timeout = 10,                    // 过期时间
    timeUnit = TimeUnit.SECONDS,     // 时间单位
    message = "正在添加用户中，请勿重复提交",  // 被拦截时的提示语
    keyResolver = DefaultIdempotentKeyResolver.class,  // Key 生成策略
    keyArg = "",                     // 自定义表达式（配合 ExpressionIdempotentKeyResolver）
    deleteKeyWhenException = true    // 异常时是否删除 Key
)
@PostMapping("/user/create")
public String createUser(User user) {
    userService.createUser(user);
    return "添加成功";
}
```

### 2.4 三种 Key 生成策略（重点）

默认**全局级别**（所有用户共用一把锁），想按用户或 IP 区分？换 `keyResolver`：

| 策略类 | 作用 | 使用场景 |
|---|---|---|
| `DefaultIdempotentKeyResolver` | **全局级别**：所有用户共用 | 全局性操作，如定时任务触发 |
| `UserIdempotentKeyResolver` | **用户级别**：每个用户独立 | ⭐ 最常用，如"每个用户 10 秒只能下单一次" |
| `ExpressionIdempotentKeyResolver` | **自定义级别**：用 `keyArg` 写 Spring EL 表达式 | 按订单号、手机号等任意维度 |

**示例**：

```java
// 按用户维度：每个用户 10 秒只能提交一次（而不是全站只能提交一次）
@Idempotent(timeout = 10, keyResolver = UserIdempotentKeyResolver.class,
            message = "操作太频繁，请稍后再试")
@PostMapping("/order/create")
public CommonResult<Long> createOrder(@RequestBody OrderCreateReqVO reqVO) {
    return success(orderService.createOrder(reqVO));
}

// 按自定义表达式：按订单号维度
@Idempotent(timeout = 30,
            keyResolver = ExpressionIdempotentKeyResolver.class,
            keyArg = "#reqVO.orderNo",
            message = "该订单正在处理中")
@PostMapping("/pay")
public CommonResult<Boolean> pay(@RequestBody PayReqVO reqVO) {
    return success(payService.pay(reqVO));
}
```

> ⚠️ **默认策略的坑**：不配 `keyResolver` 时是**全局**的！意味着"10 秒内全站所有用户只能操作一次"。**绝大多数业务应该用 `UserIdempotentKeyResolver`**。

## 三、进阶篇

### 3.1 幂等 vs 分布式锁 vs 限流（三个容易混淆的兄弟）

| | 幂等 `@Idempotent` | 分布式锁 `@Lock4j` | 限流 `@RateLimiter` |
|---|---|---|---|
| **管什么** | 一段时间内**只执行一次** | 同一时刻**只能一个执行** | 一段时间内**最多执行 N 次** |
| **拦不住时** | ❌ 报错 | ⏳ 等待 或 失败 | ❌ 报错（次数超了） |
| **Key 生命周期** | 到期自动删 | 执行完立即释放 | 计数窗口到期重置 |
| **典型场景** | 防止表单重复提交 | 定时任务防并发 | 接口防刷 |
| **例子** | 10 秒内只能提交 1 次 | 同一订单同时只能处理 1 个 | 每分钟最多 100 次 |

> 💡 **记忆口诀**：
> - **幂等** = 只准一次（次数 = 1）
> - **限流** = 最多 N 次（次数 = N）
> - **锁** = 同时只能一个（并发 = 1）

### 3.2 生产环境 5 个坑

| 坑 | 现象 | 解决 |
|---|---|---|
| **用了默认的全局级别** | 一个用户提交后，全站用户 10 秒内都被拦 | 99% 场景要换成 `UserIdempotentKeyResolver` |
| **过期时间 < 方法执行时间** | 方法跑 15 秒，过期设 10 秒 → 第 11 秒的请求能进来，重复执行 | 评估耗时，留足余量 |
| **异常后不能重试** | 方法抛异常但 Key 还在，用户一直被拦 | 默认会删 Key；如改了配置要检查 `deleteKeyWhenException` |
| **幂等拦不住真正的并发** | 两个请求同时进来，都查到"Key 不存在"，都通过 | 这是**检查-设置非原子**问题。芋道用 Redis `SETNX` 保证原子性；但极端并发仍需分布式锁兜底 |
| **GET 请求也加幂等** | 用户刷新页面就被拦，体验极差 | 幂等主要加在 **POST/PUT/DELETE** 写操作上 |

### 3.3 幂等的四种实现方案（面试加分）

| 方案 | 做法 | 适用 |
|---|---|---|
| **Redis Token 机制** ⭐ | 芋道用的。先算 Key，`SETNX` 抢占 | 通用，最常用 |
| **数据库唯一索引** | 给业务字段加唯一索引，重复插入报错 | 插入类操作，最可靠 |
| **乐观锁（版本号）** | `UPDATE ... WHERE version = ?` | 更新类操作 |
| **状态机** | 订单状态流转校验（待支付→已支付） | 有明确状态流转的业务 |

> 💡 **最佳实践**：**前端 + 后端 + 数据库三层防护**
> 1. **前端**：按钮点击后置灰（体验最好，但可被绕过）
> 2. **后端**：`@Idempotent` 注解（芋道方案）
> 3. **数据库**：唯一索引兜底（最后一道防线，绝对可靠）
>
> 面试说"三层防护"，比只说一层专业得多。

---

## 四、一句话总结

| 问题 | 答案 |
|---|---|
| 幂等解决什么 | 同一请求一段时间内只执行一次（防重复提交） |
| 怎么实现 | Redis 存标记 Key（`MD5(方法名+参数)`），进来先查 |
| 怎么用 | `@Idempotent(timeout = 10, message = "...")` |
| 最大坑 | 默认是**全局级别**，要换成 `UserIdempotentKeyResolver` |
| 和锁的区别 | 幂等 = 只准一次；锁 = 同时只能一个 |
| 生产建议 | 前端置灰 + 后端注解 + 数据库唯一索引，三层防护 |
