# 配置管理（Yudao 动态参数配置）

> **一句话概括**：把"偶尔要改、但改完不想重启服务"的参数（比如新用户默认密码、是否开启验证码）存到数据库里，在【基础设施 → 配置管理】菜单随时改，立即生效。

---

## 零、先建立整体印象：遥控器 vs 拆机改线

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

空调温度设成 26 度，你有两种改法：

| 方式 | 对应到程序 |
|---|---|
| ❌ **拆开外壳，改里面的线路** | 改 `application.yaml` → **重启服务**才生效 |
| ✅ **拿遥控器按一下** | 后台菜单改一下 → **立即生效** |

**配置管理就是那个遥控器。**

哪些配置适合放进去？

| 例子 | 为什么适合 |
|---|---|
| 新用户默认密码 `sys.user.init-password` | 安全策略变了要改，改完不能重启 |
| 是否开启验证码 `yudao.captcha.enable` | 调试时想临时关掉 |
| 文件上传大小限制 | 运营需求变了要调 |
| 系统名、备案号、Logo | 运营自己维护 |

哪些**不适合**？

| 例子 | 为什么不适合 |
|---|---|
| 数据库连接地址 | 改了要重连，且放数据库是"鸡生蛋"问题 |
| 端口号 | 启动就要用 |
| Redis 地址 | 同上 |

> 💡 **判断标准**：**启动时就要用到的配置放 yaml；运行中可能需要调整的配置放数据库。**

## 一、原理篇

### 1.1 表结构（`infra_config`）

```sql
CREATE TABLE `infra_config` (
  `id`         int          NOT NULL AUTO_INCREMENT COMMENT '参数主键',
  `group`      varchar(50)  NOT NULL                COMMENT '参数分组',
  `type`       tinyint      NOT NULL                COMMENT '参数类型',
  `name`       varchar(100) NOT NULL DEFAULT ''     COMMENT '参数名称',
  `key`        varchar(100) NOT NULL DEFAULT ''     COMMENT '参数键名',
  `value`      varchar(500) NOT NULL DEFAULT ''     COMMENT '参数键值',
  `sensitive`  bit(1)       NOT NULL                COMMENT '是否敏感',
  `remark`     varchar(500) DEFAULT NULL            COMMENT '备注',
  `creator`    varchar(64)  DEFAULT ''              COMMENT '创建者',
  `create_time` datetime    NOT NULL                COMMENT '创建时间',
  `updater`    varchar(64)  DEFAULT ''              COMMENT '更新者',
  `update_time` datetime    NOT NULL                COMMENT '更新时间',
  `deleted`    bit(1)       NOT NULL DEFAULT b'0'   COMMENT '是否删除',
  PRIMARY KEY (`id`)
) ENGINE=InnoDB COMMENT='参数配置表';
```

**关键字段解读**：

| 字段 | 作用 |
|---|---|
| `key` | 🔑 对应 Spring Boot 配置项名，如 `yudao.captcha.enable`、`sys.user.init-password` |
| `value` | 配置的值 |
| `group` | 分组，方便后台归类展示 |
| `type` | 类型（系统内置 / 业务自定义） |
| `sensitive` | ⚠️ **是否敏感**（敏感配置在后台脱敏显示，如 `******`） |

> 💡 `sensitive` 字段是个细节亮点：敏感配置（比如第三方密钥）在后台列表里打码显示，避免被无关人员看到。

### 1.2 读取流程

```
① 应用启动 → 从 infra_config 表加载所有配置
                    │
                    ▼
② 注入到 Spring Environment（作为配置源之一）
                    │
                    ▼
③ 代码中用 @Value("${yudao.captcha.enable}") 或
   ConfigService.getConfigValueByKey(...) 读取
                    │
                    ▼
④ 后台修改 → 更新数据库 + 刷新缓存 → 立即生效
```

## 二、应用篇

### 2.1 后台操作

菜单：【基础设施 → 配置管理】

| 操作 | 说明 |
|---|---|
| 新增 | 填 `key`、`value`、`name`、`group` |
| 修改 | 改 `value` 后立即生效 |
| 删除 | 逻辑删除（`deleted` 字段） |

### 2.2 后端读取

**方式一：像普通 Spring 配置一样用 `@Value`**

```java
@Component
public class CaptchaConfig {

    @Value("${yudao.captcha.enable:true}")   // 👈 冒号后面是默认值
    private Boolean enable;
}
```

**方式二：通过 `ConfigService` 动态读取**（芋道推荐）

```java
@Resource
private ConfigService configService;

public void someMethod() {
    // 按 key 读取配置值
    String initPassword = configService.getConfigValueByKey("sys.user.init-password");
}
```

### 2.3 前端读取

芋道提供了专门的接口：

```
GET /admin-api/infra/config/get-value-by-key?key=xxx
```

返回指定配置项的值，前端可以直接调用拿配置（比如获取系统名显示在页脚）。

## 三、进阶篇

### 3.1 配置管理 vs Nacos 配置中心（怎么选）

| | 配置管理（数据库表） | Nacos 配置中心 |
|---|---|---|
| 存储 | MySQL `infra_config` 表 | Nacos 服务端 |
| 生效方式 | 改库 + 刷新 | **自动推送**，秒级生效 |
| 谁用 | **业务参数**，运营/管理员在后台改 | **技术参数**，运维在 Nacos 控制台改 |
| 版本 | 可用（Nacos 更强） | ✅ 支持历史版本、回滚 |
| 灰度 | ❌ 无 | ✅ 支持按环境/机器灰度 |
| 微服务 | 各服务各自读库 | ✅ 统一管理所有服务 |
| 适合 | **单体版** / 业务配置 | **微服务版** / 技术配置 |

> 💡 **实际项目常见做法：两者都用**
> - **技术配置**（数据库连接池大小、线程池参数、限流阈值） → **Nacos**，运维统一管理
> - **业务配置**（新用户默认密码、系统名、是否开启某功能） → **配置管理表**，运营在后台自助改
>
> 这样职责清晰：运维管技术，运营管业务，互不干扰。

### 3.2 生产环境 4 个坑

| 坑 | 现象 | 解决 |
|---|---|---|
| **没有兜底默认值** | 数据库里没这条配置，代码读取报 `null` | `@Value("${key:默认值}")` 一定要写默认值 |
| **敏感配置明文展示** | 密钥、密码在后台被看到 | 把 `sensitive` 设为 1 |
| **高频读取打数据库** | 每次调用都查库 | 加缓存（芋道已缓存）+ 变更时刷新 |
| **value 长度不够** | `varchar(500)` 存不下长配置 | 拆分成多条配置，或改字段类型 |

### 3.3 芋道的配置分层

理解芋道完整的配置体系，能帮你快速定位"该改哪里"：

| 层级 | 存放 | 例子 |
|---|---|---|
| ① 代码硬编码 | Java 代码 | 极少，不推荐 |
| ② `application.yaml` | 配置文件 | 端口、数据库地址、Redis 地址 |
| ③ `application-local.yaml` | 本地环境配置 | 本地开发覆盖（不提交 Git） |
| ④ Nacos 配置中心 | 微服务版 | 各服务的技术参数，支持热更新 |
| ⑤ **`infra_config` 表** | **数据库** | **业务参数，后台可改**（本篇） |

## 四、一句话总结

| 问题 | 答案 |
|---|---|
| 配置管理是什么 | 把业务参数存数据库，后台可随时改，立即生效 |
| 表 | `infra_config`，核心字段 `key` / `value` / `sensitive` |
| 适合放什么 | **运行中可能需要调整的业务参数** |
| 不适合放什么 | 启动时就要用的（数据库地址、端口） |
| 和 Nacos 怎么分 | **技术参数 → Nacos；业务参数 → 配置表** |
| 最大坑 | 忘了写默认值，配置缺失时读到 `null` |
