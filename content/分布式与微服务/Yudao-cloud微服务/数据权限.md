# 数据权限（Yudao 自动 SQL 过滤）

> **一句话概括**：功能权限管"你能不能按这个按钮"，数据权限管"按下去之后你能看见几条数据"。芋道用 **MyBatis 拦截器 + SQL 重写**，在你写的 SQL 上自动拼一段 `WHERE dept_id = ?`，**业务代码一行都不用改**。

---

## 零、先建立整体印象：公司档案室

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

公司有一整面墙的档案柜（= 数据库里的一张表），里面装着全公司 500 个员工的档案。

不同职级的人来查档案，能看的范围不一样：

| 来查的人 | 能看的范围 | 对应的 SQL 条件 |
|---|---|---|
| 实习生 | 只能看自己的那份 | `WHERE user_id = 自己` |
| 部门经理 | 本部门所有人 | `WHERE dept_id = 本部门` |
| 总监 | 本部门 + 下面所有子部门 | `WHERE dept_id IN (本部门, 子部门...)` |
| 老板 | 全部 | 不加条件 |
| 特殊授权 | 指定某几个部门 | `WHERE dept_id IN (指定的部门)` |

**没有数据权限怎么办？** 每个查询接口都手写一遍 `WHERE dept_id IN (...)`。100 个接口就是 100 处硬编码。哪天组织架构调整、规则变了 —— **改 100 处，还必然漏**。

**有数据权限怎么办？** 你只管写 `SELECT * FROM system_users`，框架在 SQL 执行前偷偷帮你拼上 `WHERE dept_id IN (...)`。**你甚至不知道自己被过滤了**。

> 💡 这就是芋道数据权限的全部价值：**把"能看到多少数据"这件事，从 100 处业务代码里抽出来，变成 1 处配置。**

---

## 一、原理篇：SQL 是怎么被"偷改"的

### 1.1 核心机制：MyBatis 拦截器 + SQL 重写

> 🎓 **费曼第 2 段 · 给高中生讲清楚**

芋道在 MyBatis 执行 SQL 之前插了一道"关卡"（**拦截器**）。这道关卡做三件事：

1. 拿到你写的原始 SQL
2. 用 **JSqlParser**（一个 SQL 解析库）把 SQL 拆成语法树
3. 往 `WHERE` 后面塞一段条件，再拼回字符串，交给 MyBatis 执行

**你写的 SQL** vs **实际执行的 SQL**（官方示例）：

| 用户 | 数据范围 | 你写的 | 实际执行的 |
|---|---|---|---|
| 普通员工 | 仅本人 | `SELECT * FROM system_users` | `SELECT * FROM system_users WHERE user_id = 1` |
| 部门领导 | 本部门及以下 | `SELECT * FROM system_users` | `SELECT * FROM system_users WHERE dept_id IN (10, 11, 12)` |

### 1.2 三个拦截点（不只是 SELECT）

核心类是 `DataPermissionDatabaseInterceptor`，它有三个方法，分别处理三类 SQL：

| 方法 | 处理的 SQL | 为什么重要 |
|---|---|---|
| `#processSelect(...)` | SELECT 查询 | 查不到不该看的数据 |
| `#processUpdate(...)` | UPDATE 更新 | **改不到不该改的数据** |
| `#processDelete(...)` | DELETE 删除 | **删不到不该删的数据** |

> ⚠️ **很多人以为数据权限只管查询** —— 错。芋道连 UPDATE / DELETE 都拦。如果只拦 SELECT，用户可以靠"修改/删除接口"越权操作别人的数据，这是**严重安全漏洞**。

### 1.3 执行流程

```
Controller 调用 Service
        │
        ▼
  Mapper 执行 SQL
        │
        ▼
┌───────────────────────────────┐
│ ① MyBatis 拦截器拦下来           │
│ ② 解析当前登录用户的数据范围      │
│    （从 Role 角色表读）           │
│ ③ JSqlParser 解析 SQL 语法树     │
│ ④ 往 WHERE 塞条件                │
│ ⑤ 拼回 SQL 字符串                │
└───────────────┬───────────────┘
                ▼
        数据库执行改过的 SQL
```

## 二、应用篇：三种用法

### 2.1 用法一：后台点点点（最常用）

【系统管理 → 角色管理】菜单里，给角色设置数据范围。

芋道内置 **5 种数据范围**：

| 数据范围 | 含义 |
|---|---|
| 全部数据权限 | 不限制，看全公司 |
| 指定部门数据权限 | 手工勾选某几个部门 |
| 本部门数据权限 | 只能看自己所在部门 |
| 本部门及以下数据权限 | 本部门 + 所有子部门 |
| 仅本人数据权限 | 只能看自己的数据 |

对应实现类：`DeptDataPermissionRule`。

### 2.2 用法二：配置哪些表的哪些字段参与过滤

光有规则还不够 —— 框架不知道你的表里哪个字段是"部门ID"、哪个是"用户ID"。所以要**在每个模块里声明一次**：

```java
@Configuration(proxyBeanMethods = false)
public class DataPermissionConfiguration {

    @Bean
    public DeptDataPermissionRuleCustomizer sysDeptDataPermissionRuleCustomizer() {
        return rule -> {
            // ===== 基于【部门】过滤：哪些表用哪个字段当部门ID =====
            rule.addDeptColumn(AdminUserDO.class);            // 默认找 dept_id 字段 → WHERE dept_id = ?
            rule.addDeptColumn(DeptDO.class, "id");           // 部门表本身，用 id 字段 → WHERE id = ?

            // ===== 基于【用户】过滤：哪些表用哪个字段当用户ID =====
            rule.addUserColumn(AdminUserDO.class, "id");      // 用户表本身 → WHERE id = ?
            // rule.addUserColumn(OrderDO.class);             // 订单表默认找 user_id 字段 → WHERE user_id = ?
        };
    }
}
```

> ⚠️ **前提条件（必须满足）**：
> - 要按【部门】过滤的表，**必须有 `dept_id` 字段**（名字不一致就在第二个参数指定）
> - 要按【用户】过滤的表，**必须有 `user_id` 字段**
>
> 表设计阶段就要想好这两个字段，后补很痛苦。

### 2.3 用法三：`@DataPermission` 注解（局部开关）

数据权限**默认是全局开启的**，不需要加任何注解。`@DataPermission` 只在你要**关闭或调整**时才用：

```java
@GetMapping("/get")
@Operation(summary = "获得登录用户信息")
@DataPermission(enable = false)   // 👈 关闭数据权限
public CommonResult<UserProfileRespVO> profile() {
    // 为什么这里要关？
    // 因为「仅本人」权限下，用户查自己的部门时会被过滤掉，导致查不到部门信息
    if (user.getDeptId() != null) {
        DeptDO dept = deptService.getDept(user.getDeptId());
        resp.setDept(UserConvert.INSTANCE.convert02(dept));
    }
}
```

| 属性 | 作用 |
|---|---|
| `enable` | `true`/`false`，是否开启数据权限（**唯一常用的**） |
| `includeRules` | 项目里有 10 种规则时，指定**只有哪几种生效** |
| `excludeRules` | 指定**排除哪几种** |

### 2.4 用法四：完全自定义规则

内置的部门规则不够用？实现 `DataPermissionRule` 接口，声明成 Spring Bean 即可：

```java
@Component   // 声明为 Spring Bean，框架会自动扫描到
public class DemoDataPermissionRule implements DataPermissionRule {

    // ① 告诉框架：这个规则对哪几张表生效
    @Override
    public Set<String> getTableNames() {
        return Sets.newHashSet("system_dict_type", "system_post");
    }

    // ② 告诉框架：对这几张表，要拼什么 WHERE 条件
    @Override
    public Expression getExpression(String tableName, Alias tableAlias) {
        Long userId = SecurityFrameworkUtils.getLoginUserId();  // 当前登录用户ID
        assert userId != null;
        switch (tableName) {
            case "system_dict_type":
                // 字典表：只能看自己创建的
                return new EqualsTo(MyBatisUtils.buildColumn(tableName, tableAlias, "creator"),
                                    new LongValue(userId));
            case "system_post":
                // 岗位表：只能看自己更新过的
                return new EqualsTo(MyBatisUtils.buildColumn(tableName, tableAlias, "updater"),
                                    new LongValue(userId));
            default: return null;   // 返回 null = 这条规则不生效
        }
    }
}
```

验证效果：访问【系统管理 → 字典管理】，看 IDEA 控制台，会发现 SQL 自动多了 `AND creator = 1`。

## 三、进阶篇：坑与边界

### 3.1 三类权限，别搞混（官方明确说明）

| 类型 | 管什么 | 芋道支持吗 |
|---|---|---|
| **功能权限** | 你能不能按这个按钮 / 调这个接口 | ✅ 支持（见 [[功能权限]]） |
| **数据权限** | 按了之后能看到**多少条**数据 | ✅ 支持（本篇） |
| **字段权限** | 能看到这条数据的**哪些字段**（如看不到工资列） | ❌ **不支持**，官方说"未来提供" |

> ⚠️ 官方原话：数据权限**不支持**"指定用户只能查看数据的某些字段"。字段级别的控制属于**字段权限**，需要自己实现（比如在 VO 转换时用 `@JsonIgnore` 或自定义序列化器）。

### 3.2 数据权限 vs 多租户（最容易混淆）

| | 数据权限 | 多租户 |
|---|---|---|
| 目的 | 组织内部的**层级可见性**（经理看部门） | 租户之间的**彻底隔离**（A公司看不到B公司） |
| 粒度 | 同一张表按条件过滤 | 同一张表加 `tenant_id` 字段隔离 |
| 实现 | 多个 `DataPermissionRule` 规则 | 独立的 `TenantDatabaseInterceptor` |
| 能否关闭 | 能（`@DataPermission(enable=false)`） | 能（`@TenantIgnore`） |

两者**可以同时生效**，SQL 会同时拼上 `tenant_id = ? AND dept_id IN (...)`。

### 3.3 生产环境 5 个坑

| 坑 | 现象 | 怎么避 |
|---|---|---|
| **复杂 SQL 拼错** | `UNION`、子查询、多层嵌套时 JSqlParser 解析失败或条件拼错位置 | 复杂报表查询用 `@DataPermission(enable = false)` 关掉，自己手写条件 |
| **联表时表名冲突** | 主子查询用了同一个表，别名没处理好 | 用 `tableAlias` 参数，见 `MyBatisUtils.buildColumn(...)` |
| **性能下降** | 拼上 `dept_id IN (几百个)` 后索引失效 | 部门层级别太深；必要时给 `dept_id` 建联合索引 |
| **误伤"查自己的部门"** | 「仅本人」权限下查部门信息查不到 | 加 `@DataPermission(enable = false)`，见 2.3 示例 |
| **COUNT 分页不对** | 分页插件和数据权限插件顺序不对 | 确保数据权限拦截器在分页拦截器**之前**执行 |

### 3.4 为什么这个设计值得学

> 💡 **十年经验之谈**：数据权限是"**横切关注点**"（cross-cutting concern）的教科书案例。
> 和「日志」「事务」「权限校验」一样，它属于"每个方法都要做、但和业务逻辑无关"的事。
> 正确做法是**用拦截器/AOP 抽出去**，而不是在每个 Service 里手写。
> 面试时能把"为什么用拦截器而不用硬编码"讲清楚，比背注解有用得多。

## 四、一句话总结

| 问题 | 答案 |
|---|---|
| 数据权限解决什么 | 同一个接口，不同职级的人看到不同范围的数据 |
| 怎么实现的 | MyBatis 拦截器 + JSqlParser 重写 SQL，自动拼 `WHERE` |
| 我要写什么 | ① 后台配角色范围 ② 模块里声明表的部门/用户字段 ③ 特殊情况加 `@DataPermission` |
| 最大坑 | 复杂 SQL（UNION/子查询）可能拼错 → 关掉自己写 |
| 不支持什么 | **字段权限**（控制能看到哪些列） |
