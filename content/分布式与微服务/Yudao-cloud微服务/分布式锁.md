# 分布式锁（Yudao Redisson + Lock4j）

> **一句话概括**：多台机器同时抢同一个资源时，用 Redis 里的一把"公共锁"来排队。芋道给两种用法 —— **编程式**（Redisson，手动加锁解锁）和**声明式**（`@Lock4j` 注解，自动加锁）。

---

## 零、先建立整体印象：公共厕所的钥匙

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

一栋楼里有个**公共厕所**，只有一个坑位。钥匙挂在门口的钩子上。

规则很简单：

1. 想上厕所 → 去钩子上**拿钥匙**（加锁）
2. 钥匙没了 → 说明有人在用，你得**等着**（阻塞）或**走人**（快速失败）
3. 上完了 → 把钥匙**挂回去**（解锁）

**单机时代**：一个 JVM 里的多线程，用 `synchronized` 或 `ReentrantLock` 就行 —— 它们是"同一栋楼里的钥匙"，大家都能看见。

**分布式时代**：你有 3 台服务器（3 栋楼），各管各的 JVM。`synchronized` 只能管住自己这栋楼，**其他楼的线程根本看不见你这把锁**。

所以需要一把**所有楼都能看见的公共钥匙** → **Redis**。

```
┌─────────┐  ┌─────────┐  ┌─────────┐
│ 服务器A  │  │ 服务器B  │  │ 服务器C  │
│synchronized││synchronized││synchronized│  ← 各自管自己，互相看不见
└────┬────┘  └────┬────┘  └────┬────┘
     └────────────┼────────────┘
                  ▼
          ┌───────────────┐
          │   Redis 公共锁  │  ← 三台都认这一把
          └───────────────┘
```

## 一、原理篇

### 1.1 分布式锁要满足的 4 个条件

> 🎓 **费曼第 2 段 · 给高中生讲**

| 条件 | 大白话 | 怎么实现 |
|---|---|---|
| **互斥性** | 同一时刻只能有一个人拿到锁 | Redis `SETNX`（key 不存在才能设置成功） |
| **防死锁** | 拿到锁的人挂了，锁要能自动释放 | 给锁**设置过期时间** |
| **防误删** | 不能把别人的锁给解了 | 锁的 value 存**唯一标识**（UUID/线程ID），解锁时校验 |
| **可重入** | 同一个人可以多次拿同一把锁 | Redisson 用 Hash 结构记次数 |

> ⚠️ **自己用 `SETNX` 手写锁，90% 的人会漏掉"防误删"和"原子性"**：
> ```
> ❌ 错误示范（非原子）：
>    if (setnx(key, 1) == 1) {          // ① 加锁成功
>        expire(key, 30);                // ② 设置过期时间 —— 如果这行之前宕机，锁永远不释放！
>    }
>
> ✅ 正确做法（原子）：
>    SET key value NX EX 30              // 一条命令同时完成加锁 + 设过期时间
> ```
> **所以生产环境直接用 Redisson，别自己造轮子。**

### 1.2 Redisson 的看门狗（自动续期）⭐

**问题**：锁设了 30 秒过期，但业务逻辑跑了 40 秒 —— 锁提前过期了，别人趁虚而入。

**Redisson 的解法**：启动一个后台线程（**看门狗 Watchdog**），只要你的业务还在跑，就每隔 10 秒把锁的过期时间**重置回 30 秒**。

```
业务还在执行 → 看门狗每隔 10 秒 → EXPIRE lock 30
业务执行完   → 手动 unlock()  → 看门狗停止
```

> 💡 **注意**：看门狗只在**不指定 leaseTime** 时生效。如果你手动指定了超时时间（如 `lock.lock(10, TimeUnit.SECONDS)`），Redisson **不会**自动续期，到点就释放。

## 二、应用篇

### 2.1 用法一：编程式锁（Redisson）

**实战案例**（芋道 `yudao-module-pay` 支付通知）：

**场景**：支付平台回调通知，可能同一笔订单通知多次。要确保**同一个通知任务有且只有一个在执行**。

#### 第 ① 步：在 `RedisKeyConstants` 定义锁的 Key

```java
public interface RedisKeyConstants {
    // 支付通知任务的分布式锁，%s 是通知任务ID
    String PAY_NOTIFY_LOCK = "pay_notify:lock:%s";
}
```

#### 第 ② 步：写锁的 RedisDAO（`PayNotifyLockRedisDAO`）

```java
@Repository
public class PayNotifyLockRedisDAO {

    @Resource
    private RedissonClient redissonClient;   // Redisson 客户端

    public void lock(Long id, Long timeoutMillis, Runnable runnable) {
        // ① 拼出这把锁的 key
        String lockKey = format(PAY_NOTIFY_LOCK, id);
        // ② 获取可重入锁对象（只是个 Java 对象，还没加锁）
        RLock lock = redissonClient.getLock(lockKey);
        try {
            // ③ 尝试加锁：最多等 timeoutMillis 毫秒，锁自动释放时间 10 秒
            if (lock.tryLock(0, 10, TimeUnit.SECONDS)) {   // 注意：这里指定了 leaseTime，看门狗不生效
                runnable.run();      // ④ 拿到锁，执行业务
            } else {
                log.warn("[lock][加锁失败，跳过执行]");  // ⑤ 抢不到，跳过（快速失败）
            }
        } finally {
            lock.unlock();           // ⑥ 一定要在 finally 里释放！
        }
    }
}
```

#### 第 ③ 步：Service 里调用

```java
// PayNotifyServiceImpl
payNotifyLockRedisDAO.lock(notifyId, 1000L, () -> {
    // 这里是需要互斥执行的业务逻辑
});
```

### 2.2 用法二：声明式锁（`@Lock4j` 注解）

**注意**：芋道**默认没有引入** Lock4j（因为不是所有人都会用），需要自己加依赖：

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>lock4j-redisson-spring-boot-starter</artifactId>
</dependency>
```

在 `application-local.yaml` 配置默认行为：

```yaml
lock4j:
  acquire-timeout: 3000    # 获取锁最多等待 3 秒
  expire: 30000            # 锁 30 秒后自动释放
```

使用（**极其简单**）：

```java
@Service
public class DemoService {

    // 最简用法：用 lock4j 全局默认配置
    @Lock4j
    public void simple() {
        // do something
    }

    // 完整用法：支持 Spring EL 表达式，从参数里取 key
    @Lock4j(keys = {"#user.id", "#user.name"}, expire = 60000, acquireTimeout = 1000)
    public User customMethod(User user) {
        return user;
    }
}
```

### 2.3 两种用法怎么选

| | 编程式（Redisson） | 声明式（Lock4j） |
|---|---|---|
| 代码量 | 多（要写 DAO） | 少（一个注解） |
| 灵活度 | 高（红锁、读写锁、公平锁都支持） | 低（主要是可重入锁） |
| 依赖 | 强依赖 Redisson | 不强依赖，可换 ZooKeeper |
| 芋道推荐 | ✅ **首选** | 简单场景用 |

> 💡 **官方选型理由**（值得学习这个思考方式）：
> > "选择 Redisson 主要考虑它**支持的 Redis 分布式锁的类型较多**：可靠性较高的**红锁**、性能较好的**读写锁**等等。Lock4j 的 LockTemplate 也不错，不强依赖 Redisson，还支持 ZooKeeper。"

这是标准的**选型权衡**：要功能丰富度选 Redisson，要可替换性选 Lock4j。

## 三、进阶篇

### 3.1 Redisson 支持的锁类型

| 锁类型 | 适用场景 |
|---|---|
| **可重入锁**（`getLock`） | 最常用，同一个线程可多次获取 |
| **公平锁**（`getFairLock`） | 按请求顺序排队，避免饥饿 |
| **读写锁**（`getReadWriteLock`） | 读多写少，读读不互斥 |
| **红锁**（`RedissonRedLock`） | 多个独立 Redis 节点，可靠性最高（Redis 官方争议较大） |
| **联锁**（`RedissonMultiLock`） | 同时锁住多个资源 |

### 3.2 生产环境 6 个坑

| 坑 | 现象 | 解决 |
|---|---|---|
| **忘记释放锁** | 锁永远不释放，后续请求全阻塞 | 必须 `try-finally` 里 `unlock()` |
| **锁粒度太粗** | 锁整个方法，性能极差 | 只锁关键代码段；Key 带上业务 ID（如订单号） |
| **锁粒度太细** | 一个业务要锁 10 个资源 | 用联锁 `MultiLock` |
| **超时时间太短** | 业务没跑完锁就释放了 | 不指定 leaseTime，让看门狗自动续期 |
| **Redis 主从切换丢锁** | 主节点加锁后宕机，从节点还没同步，新主节点又能加锁 | 用红锁，或接受极小概率（业务层做幂等兜底） |
| **锁被 GC 停顿拖垮** | JVM Full GC 停顿超过锁超时 | 监控 GC；延长超时；用看门狗 |

### 3.3 分布式锁 ≠ 幂等性（重要区别）

| | 分布式锁 | 幂等性 |
|---|---|---|
| 目的 | **同一时刻**只能一个执行（**互斥**） | **一段时间内**只能执行一次（**去重**） |
| 抢不到时 | **等待**或快速失败 | **直接报错**（"请勿重复提交"） |
| 执行完 | 立即释放锁 | 不删 Key，等过期 |
| 典型场景 | 定时任务防重跑 | 用户双击提交按钮 |

> 💡 **一句话**：锁解决"同时"，幂等解决"重复"。**两个都要有**：幂等挡住用户重复点击，锁挡住集群并发。详见 [[幂等性（防重复提交）]]。

## 四、一句话总结

| 问题 | 答案 |
|---|---|
| 为什么不能用 `synchronized` | 它只能管住单个 JVM，多台服务器互相看不见 |
| 芋道两种方式 | 编程式 Redisson（推荐，功能全）/ 声明式 `@Lock4j`（简单） |
| 为什么选 Redisson | 支持红锁、读写锁等更多类型 |
| 看门狗是什么 | 后台线程自动续期，防止业务没跑完锁就过期 |
| 最大坑 | 忘记 `finally` 释放锁 / 超时时间设太短 |
| 和幂等的区别 | 锁管"同时"，幂等管"重复" |
