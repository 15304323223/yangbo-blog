# 本地缓存（Yudao 进程内缓存 + 广播刷新）

> **一句话概括**：把"几乎不变又超高频访问"的数据（角色、部门、权限、租户）放进 JVM 内存里，连 Redis 都不用查。芋道的实现有个精妙之处：**用 `volatile Map` + 整体替换** 避免并发问题，用 **Redis 发布订阅** 让所有实例一起刷新。

---

## 零、先建立整体印象：抽屉的三层

> 🧒 **费曼第 1 段 · 5 岁小孩也能懂**

找一样东西，你手边有三个地方可以放：

| 位置 | 比喻 | 拿到的速度 | 能放多少 |
|---|---|---|---|
| **手里攥着** | **本地缓存**（JVM 内存） | 🚀 极快（纳秒级） | 很少 |
| **桌上抽屉** | **Redis 缓存** | ⚡ 快（毫秒级，要走网络） | 较多 |
| **楼下仓库** | **MySQL 数据库** | 🐢 慢（要查磁盘） | 海量 |

**99% 的项目用 Redis 就够了**。但有些数据**访问频率高到离谱** —— 比如"这个功能按钮你能不能按"，每次请求都要查一次权限。

如果每次都查 Redis，一天几百万次请求就是几百万次网络往返。**不如直接放 JVM 内存里，连网络都省了。**

```
本地缓存（JVM 内存）→ Redis → MySQL
     命中率最高        兜底      最终数据源
```

## 一、原理篇

### 1.1 官方的重要说明（先看这个）⚠️

> ① 由于大家普遍反馈"本地缓存"学习成本太高，一般 Redis 缓存足够满足大多数场景的性能要求，所以**基本使用 Spring Cache + Redis 所替代**。如果你不需要本地缓存，可以忽略本章节。
> ② 项目中还保留了部分地方使用本地缓存，例如**短信客户端、文件客户端、敏感词**等。主要原因是，它们是**"有状态"的 Java 对象，无法缓存到 Redis 中**。

> 💡 **划重点**：
> - **日常业务缓存 → 用 Redis**（见 [[Redis 缓存]]）
> - **有状态的 Java 对象**（比如已初始化的 MinIO 客户端、敏感词 DFA 树）→ **只能用本地缓存**，因为它们不是简单的数据，没法序列化成 JSON 塞进 Redis

### 1.2 芋道用本地缓存的三个真实场景

| 模块 | 缓存什么 | 为什么 |
|---|---|---|
| 租户模块 | 租户信息 | 每次 API 都要校验租户是否禁用/过期 |
| 部门模块 | 部门信息 | 每次**数据权限**校验都要用 |
| 权限模块 | 权限信息 | 每次**功能权限**校验都要用 |

### 1.3 实现原理（两步）

```
┌────────────────────────────────────────────┐
│ ① 项目启动时：初始化缓存                      │
│    @PostConstruct → 从数据库读全量 → 写入 Map │
└────────────────────────────────────────────┘
                    │
                    ▼
┌────────────────────────────────────────────┐
│ ② 数据变化时：实时刷新缓存                     │
│    管理后台改了数据 → 发 Redis 广播            │
│    → 所有 JVM 实例收到 → 重新读库 → 重建 Map    │
└────────────────────────────────────────────┘
```

## 二、应用篇：以角色缓存为例

### 2.1 第 ① 步：定义 `initLocalCache()` 接口方法

```java
// RoleService.java
/**
 * 初始化角色的本地缓存
 */
void initLocalCache();
```

> 💡 **为什么要在接口里定义？** 因为刷新缓存时要通过 `RoleService` 接口调用它（消费者里注入的是接口，不是实现类）。

### 2.2 第 ② 步：实现初始化（关键代码）⭐

```java
// RoleServiceImpl.java

/**
 * 角色缓存
 * key：角色编号 {@link RoleDO#getId()}
 *
 * 这里声明 volatile 修饰的原因是，每次刷新时，直接修改指向
 */
@Getter
private volatile Map<Long, RoleDO> roleCache;

/**
 * 初始化 {@link #roleCache} 缓存
 */
@Override
@PostConstruct                                  // 👈 项目启动时自动执行
public void initLocalCache() {
    // 注意：忽略自动多租户，因为要全局初始化缓存
    TenantUtils.executeIgnore(() -> {
        // 第一步：查询数据
        List<RoleDO> roleList = roleMapper.selectList();
        log.info("[initLocalCache][缓存角色，数量为:{}]", roleList.size());

        // 第二步：构建缓存
        roleCache = CollectionUtils.convertMap(roleList, RoleDO::getId);
    });
}
```

**三个关键点，逐个讲**：

#### 关键点 1：为什么用 `volatile`？

```java
private volatile Map<Long, RoleDO> roleCache;
```

刷新缓存时是**整体替换引用**（`roleCache = 新Map`），而不是一个个 `put`。

- `volatile` 保证**可见性**：线程 A 换了新 Map，线程 B 立刻能看到
- 不整体替换的话，刷新过程中会读到"一半旧一半新"的数据

> 💡 这是**无锁化设计**的经典手法：**不可变对象 + volatile 引用整体替换**，比加锁读写快得多。

#### 关键点 2：为什么用 `TenantUtils.executeIgnore()`？

> ⚠️ **多租户最大的坑**（官方专门解释）：
> > 由于 `RoleDO` 是**多租户隔离**的，如果不用 `executeIgnore`，缓存刷新时**只会加载当前租户的角色数据**，导致其他租户的角色查不到！
>
> 所以：
> - 缓存的数据**跨租户共享** → 必须用 `TenantUtils.executeIgnore()`
> - 缓存的数据**本来就是单租户的** → 不需要用

#### 关键点 3：`@PostConstruct`

Bean 初始化完成后自动执行，项目启动时就把缓存灌满。

### 2.3 第 ③ 步：实时刷新（多实例广播）⭐

**问题**：线上部署了 3 台 JVM，你在后台改了角色。3 台机器怎么都知道要刷新？

**解法**：**Redis Pub/Sub（发布订阅）广播**。

#### ① 定义消息体

```java
@Data
@EqualsAndHashCode(callSuper = true)
public class RoleRefreshMessage extends AbstractRedisChannelMessage {
}
```

#### ② 生产者（数据变更时发消息）

```java
@Component
public class RoleProducer {

    @Resource
    private RedisMQTemplate redisMQTemplate;

    /**
     * 发送 {@link RoleRefreshMessage} 消息
     */
    public void sendRoleRefreshMessage() {
        RoleRefreshMessage message = new RoleRefreshMessage();
        redisMQTemplate.send(message);      // 广播给所有实例
    }
}
```

> ⚠️ **别忘了**：在角色的**新增 / 修改 / 删除**方法里调用 `roleProducer.sendRoleRefreshMessage()`。

```java
@Override
public void updateRole(RoleSaveReqVO updateReqVO) {
    // 1. 更新数据库
    roleMapper.updateById(bean);
    // 2. 发广播，通知所有 JVM 刷新本地缓存
    roleProducer.sendRoleRefreshMessage();
}
```

#### ③ 消费者（收到消息刷新缓存）

```java
@Component
@Slf4j
public class RoleRefreshConsumer extends AbstractRedisChannelMessageListener<RoleRefreshMessage> {

    @Resource
    private RoleService roleService;

    @Override
    public void onMessage(RoleRefreshMessage message) {
        log.info("[onMessage][收到 Role 刷新消息]");
        roleService.initLocalCache();       // 重新读库，重建 Map
    }
}
```

**完整流程**：

```
管理员在机器A上改角色
        │
        ├─→ 更新 MySQL
        │
        └─→ Redis 广播 "角色变了"
                │
        ┌───────┼───────┐
        ▼       ▼       ▼
     机器A    机器B    机器C
   刷新缓存  刷新缓存  刷新缓存
```

## 三、进阶篇

### 3.1 本地缓存 vs Redis 怎么选

| 维度 | 本地缓存 | Redis |
|---|---|---|
| 速度 | 🚀 纳秒级（内存直读） | ⚡ 毫秒级（走网络） |
| 容量 | 受 JVM 堆限制 | 独立部署，可扩容 |
| **一致性** | ⚠️ **差**（多实例要广播刷新） | ✅ 好（集中式） |
| 能否存对象 | ✅ 可存有状态 Java 对象 | ❌ 只能存序列化数据 |
| 宕机影响 | 重启后缓存清空，需重建 | 持久化，重启不丢 |
| 适合 | 极高频 + 极少变 + 数据量小 | 通用业务缓存 |

> 💡 **决策口诀**：
> **"高频、少变、量小" → 本地缓存；其他一律 Redis。**

### 3.2 Caffeine vs 手写 Map

芋道用的是**手写 `volatile Map`**，简单场景没问题。但如果需要 **LRU 淘汰 / 过期时间 / 命中率统计**，应该用 **Caffeine**：

```java
Cache<Long, RoleDO> roleCache = Caffeine.newBuilder()
    .maximumSize(10_000)                    // 最多 1 万条
    .expireAfterWrite(Duration.ofMinutes(10))  // 写入 10 分钟后过期
    .recordStats()                          // 统计命中率
    .build();
```

| | 手写 volatile Map | Caffeine |
|---|---|---|
| 淘汰策略 | ❌ 无（全量保留） | ✅ LRU / W-TinyLFU |
| 过期时间 | ❌ 无（靠广播刷新） | ✅ 支持 |
| 命中率统计 | ❌ 无 | ✅ 支持 |
| 适合 | **全量缓存**（角色/部门/字典，就那么几百条） | **部分缓存**（热点数据，需要淘汰） |

> 💡 **芋道为什么用手写 Map？** 因为缓存的是"**全量数据**"（所有角色、所有部门），本来就要全部保留，不需要淘汰策略。这种场景下手写 Map 反而更简单高效。
> 详见 [[11_本地缓存 Ehcache 与 Caffeine]]。

### 3.3 生产环境 5 个坑

| 坑 | 现象 | 解决 |
|---|---|---|
| **忘了发广播** | 数据改了，其他机器还是旧缓存 | 每个写操作都要调 `sendXxxRefreshMessage()` |
| **多租户污染** | 缓存只加载了当前租户数据 | 用 `TenantUtils.executeIgnore()`，见 2.2 |
| **内存溢出** | 缓存了几十万条数据，堆爆了 | 只缓存"量小"的数据；用 Caffeine 限制 size |
| **启动慢** | `@PostConstruct` 里查了 10 万条数据 | 加分页/分批；或改成懒加载 |
| **刷新时读到旧值** | 刷新过程中 Map 被并发读 | `volatile` + 整体替换引用（芋道方案） |

### 3.4 多级缓存架构（生产最佳实践）

```
请求
  │
  ▼
① 本地缓存 Caffeine（纳秒级）── 命中 → 返回
  │ 未命中
  ▼
② Redis（毫秒级）── 命中 → 写回本地缓存 → 返回
  │ 未命中
  ▼
③ MySQL ── 查到 → 写回 Redis + 本地缓存 → 返回
```

这就是完整的**三级缓存体系**，芋道在每个环节都有对应实现。

## 四、一句话总结

| 问题 | 答案 |
|---|---|
| 本地缓存是什么 | 把数据放 JVM 内存里，比 Redis 还快 |
| 什么时候用 | **高频 + 少变 + 量小**；或**有状态的 Java 对象**（Redis 存不了） |
| 芋道怎么用 | `volatile Map` + `@PostConstruct` 启动加载 |
| 多实例怎么同步 | **Redis Pub/Sub 广播**，所有实例一起刷新 |
| 最大坑 | ① 忘记发广播 ② **多租户污染**（要用 `TenantUtils.executeIgnore`） |
| 何时用 Caffeine | 需要 LRU 淘汰 / 过期时间 / 命中率统计时 |
