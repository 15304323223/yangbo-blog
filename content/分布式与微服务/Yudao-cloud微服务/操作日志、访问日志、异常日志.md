# 操作日志、访问日志、异常日志

> **一句话概括**：芋道有 **2 类 4 种**系统日志 —— **审计日志**（操作日志 / 登录日志，给业务人员看"谁干了什么"）和 **API 日志**（访问日志 / 错误日志，给开发看"接口怎么被调用的"）。操作日志靠 `@LogRecord` 注解手动记，另外三种全自动。

**适合谁读**：所有写后台系统的人（出事了要查日志）。
**怎么读**：「一」的操作日志最有价值（能自动做 diff），「三」的访问日志脱敏配置必看。

---

## 零、先建立整体印象：两种"摄像头"

想象一栋办公楼里的监控：

| 类型 | 类比 | 记录什么 | 给谁看 |
|---|---|---|---|
| **审计日志** | 保险柜前的摄像头 + 登记本 | 谁、什么时候、动了什么、改成啥了 | 业务人员、审计、老板 |
| **API 日志** | 楼道里的监控 | 每个请求的 URL、参数、耗时、报错堆栈 | 开发、运维 |

**具体 4 种**：

```
系统日志
├── 审计日志
│   ├── ① 操作日志   → system_operate_log 表（手动 @LogRecord）
│   └── ② 登录日志   → system_login_log 表（自动）
└── API 日志
    ├── ③ 访问日志   → infra_api_access_log 表（自动，可关）
    └── ④ 错误日志   → infra_api_error_log 表（自动）
```

---

## 一、操作日志：谁改了什么 ⭐

### 1.1 它长什么样

打开 [系统管理 → 审计日志 → 操作日志]，你会看到：

```
【新增】2021-09-16 10:00 订单创建，订单号：NO.11089999
【修改】2021-09-16 10:00 用户小明修改了订单的配送地址：从"金灿灿小区"修改到"银盏盏小区"
【修改】2026-09-06 14:30 修改了用户的【备注】从【132】修改为【1324】
```

💡 **注意第二条和第三条** —— 它能自动对比出"从 A 改成 B"。这是操作日志最有价值的能力。

### 1.2 技术选型：为什么不自己造轮子？

> 官方原话（很坦诚）：*"早期，项目确实有 operatelog 组件……随着我老友开源了 mzt-biz-log 组件，再加上希望减少项目的 starter 数量，所以决定直接使用 mzt-biz-log 组件，放到 security 组件中，而不是自己再造一个轮子。"*

- **实现**：`yudao-spring-boot-starter-security` 的 `operatelog` 包（基于 [mzt-biz-log](https://github.com/mouzt/mzt-biz-log)）
- **存储**：`yudao-module-system` 的 `system_operate_log` 表

### 1.3 场景一：记录"创建用户"

**第 1 步：定义日志常量**

```java
// LogRecordConstants.java
public interface LogRecordConstants {

    // 子类型：标识"这是用户模块的创建操作"
    String SYSTEM_USER_CREATE_SUB_TYPE = "system-user-create";

    // 成功文案模板（{{}} 是占位符，会取方法参数或返回值）
    String SYSTEM_USER_CREATE_SUCCESS =
        "创建用户成功，用户信息：{{#userSaveReqVO.username}}";
}
```

> 官方说明为什么建这个类：*"这个并非强制，只是一个使用建议。每个 yudao-module-xxx 模块下，建议都搞一个 LogRecordConstants 类，方便大家统一管理操作日志的常量。"*

💡 **好处**：文案集中管理，改文案不用翻遍代码。

**第 2 步：在 Service 方法上加 `@LogRecord`**

```java
@Service
public class UserServiceImpl implements UserService {

    @Override
    @LogRecord(
        type = "SYSTEM",                                   // 日志类型
        subType = SYSTEM_USER_CREATE_SUB_TYPE,             // 子类型
        success = SYSTEM_USER_CREATE_SUCCESS,              // 成功时的文案模板
        bizNo = "{{#userId}}"                              // 业务编号（方便关联查询）
    )
    public Long createUser(UserSaveReqVO userSaveReqVO) {
        // 业务逻辑...
        return userId;
    }
}
```

**最终效果**：`创建用户成功，用户信息：zhangsan`

### 1.4 场景二：自动 diff ⭐（本篇最有价值）

想记录"【备注】从【132】修改为【1324】"，需要 **_DIFF 函数**。

**第 1 步：在 VO 上标 `@DiffLogField`**

```java
@Data
public class UserSaveReqVO {

    @DiffLogField(name = "用户名")                 // name = 字段的中文名
    private String username;

    @DiffLogField(name = "备注")
    private String remark;

    @DiffLogField(name = "部门",
                  function = DeptParseFunction.class)   // ← 自定义翻译函数
    private Long deptId;

    @DiffLogField(name = "岗位",
                  function = PostParseFunction.class)
    private Long postIds;

    @DiffLogField(name = "性别",
                  function = SexParseFunction.class)
    private Integer sex;
}
```

**两个属性**：

| 属性 | 作用 | 例子 |
|---|---|---|
| `name` | 字段的中文名 | `"备注"` |
| `function` | **自定义翻译函数**，把 id 翻译成名字 | `DeptParseFunction` 把 `deptId=10` 翻译成"技术部" |

💡 **为什么需要 `function`？** 不指定的话，日志会记成"【部门】从【10】修改为【20】"—— 业务看不懂。指定后变成"【部门】从【技术部】修改为【市场部】"。

**第 2 步：用 `_DIFF` 函数写模板**

```java
@Override
@LogRecord(
    type = "SYSTEM",
    subType = SYSTEM_USER_UPDATE_SUB_TYPE,
    success = "修改用户信息：{_DIFF{#oldUser, #userSaveReqVO}}",   // ← _DIFF 函数
    bizNo = "{{#userSaveReqVO.id}}"
)
public void updateUser(UserSaveReqVO userSaveReqVO) { }
```

**最终效果**：
```
修改用户信息：【备注】从【132】修改为【1324】，【部门】从【技术部】修改为【市场部】
```

💡 **原理**：`{_DIFF{旧对象, 新对象}}` 会对比两个对象上标了 `@DiffLogField` 的字段，只输出**真正变了的**那些。

### 1.5 现状说明

> 官方坦白：*"由于操作日志需要手动记录，再加上是新改造的，所以目前只有少数几个地方使用了。"*

**想看更多案例？** 官方说 **CRM 模块的操作日志最全，有几十个使用案例**，照着抄就行。

## 二、登录日志

记录用户的**登录、登出**行为，**成功的、失败的都记**。

- **存储**：`system_login_log` 表
- **两个枚举**（可自定义）：
  - `LoginLogTypeEnum` —— 登录类型（账号密码 / 短信 / 三方 / 登出）
  - `LoginResultEnum` —— 登录结果（成功 / 密码错误 / 账号禁用 / 验证码错误）

💡 **实战价值**：
```
排查"账号被盗"：看登录日志，发现凌晨 3 点有个来自异地的成功登录 → 确认被盗
排查"用户说登不上"：看登录日志，发现有 20 次"密码错误" → 用户自己记错密码
安全审计：导出某账号近半年的登录 IP，看有没有异常
```

## 三、API 访问日志

### 3.1 它记录什么

**每次 API 调用的完整信息**：HTTP 请求（URL、Method、参数）、用户信息、IP、开始时间、耗时、结果。

- **实现**：`yudao-spring-boot-starter-web` 的 `ApiAccessLogFilter`（**过滤器 + 异步记录**，不阻塞请求）
- **存储**：`infra_api_access_log` 表

### 3.2 用 @ApiAccessLog 精细控制 ⭐

```java
@GetMapping("/export")
@Operation(summary = "导出岗位 Excel")
@ApiAccessLog(operateType = EXPORT)
public void export(...) { }
```

**7 个配置字段**（逐个解释）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `enable` | `true` | 是否记录。**想让某接口不记日志就设 `false`** |
| `requestEnable` | `true` | 是否记录请求参数（一般不大，所以默认记） |
| `responseEnable` | **`false`** | 是否记录响应参数（**默认不记**，因为列表接口响应很大） |
| `sanitizeKeys` | — | **脱敏字段**，如 `password`、`mobile` |
| `operateModule` | 取 `@Tag` 的 name | 操作模块：用户、岗位、部门… |
| `operateName` | 取 `@Operation` 的 summary | 操作名：新增用户、修改用户… |
| `operateType` | — | 操作类型：`GET/CREATE/UPDATE/DELETE/EXPORT/IMPORT/OTHER` |

**示例：不记录某个高频接口**

```java
@GetMapping("/get-unread-count")
@ApiAccessLog(enable = false)        // ← 未读消息数量，每秒轮询，别记日志
public CommonResult<Long> getUnreadNotifyMessageCount() { }
```

**示例：给敏感接口脱敏**

```java
@PostMapping("/login")
@ApiAccessLog(sanitizeKeys = {"password", "mobile"})   // 这两个字段打码
public CommonResult<AuthLoginRespVO> login(@RequestBody AuthLoginReqVO reqVO) { }
```

⚠️ **好消息**：`ApiAccessLogFilter` 有**全局默认脱敏配置** `SANITIZE_KEYS`，已经包含了 `password`、`accessToken`、`refreshToken` 等 —— 官方说"避免大家忘记"。

### 3.3 ❓ 为什么访问日志里要放"操作模块/操作名/操作类型"？

> 官方解释得很实在：
> *"从感受上来说，它们应该属于'操作日志'，不应该记录到'访问日志'中。但是考虑到'操作日志'需要手动记录，可能大家会'偷懒'不想记录，但是业务人员看不懂'访问日志'，所以增加了这些字段，方便大家查看。"*

💡 **说人话**：理想情况下操作日志该记全，但**程序员会偷懒**。所以芋道在访问日志里加了几个"人话字段"做兜底 —— **没写 `@LogRecord` 的接口，至少访问日志里还能看出"这是用户模块的新增操作"**。

### 3.4 本地环境默认关闭

```yaml
# application-local.yaml
yudao:
  access-log:
    enable: false      # ← 本地开发不记录，避免数据库被日志塞满
```

⚠️ **需要调试时改成 `true`**。

### 3.5 文件日志（开发调试神器）

除了落库，芋道还提供 `ApiAccessLogInterceptor`，把请求**打印到控制台**：

```
【开始请求】POST /admin-api/system/user/create  参数：{"username":"zhangsan",...}
【结束请求】耗时：23ms
```

**每次请求两条**：一条 request（URL + 参数），一条 response（耗时）。

⚠️ **生产环境默认不开启**（定位是开发调试）。

## 四、API 错误日志

记录**每次 API 的异常调用**：HTTP 请求、用户、**完整的异常堆栈**。

- **实现**：`GlobalExceptionHandler` 拦截系统异常后，异步记录（见 [[异常处理（错误码）]]）
- **存储**：`infra_api_error_log` 表

💡 **实战价值**：
```
用户报"刚才点保存报错了"
→ 去错误日志按时间、用户筛选
→ 直接看到完整堆栈（不用让用户复现、不用翻服务器日志）
```

这是**最能体现系统成熟度**的功能之一。

## 五、四种日志对比表

| | 操作日志 | 登录日志 | 访问日志 | 错误日志 |
|---|---|---|---|---|
| **表** | `system_operate_log` | `system_login_log` | `infra_api_access_log` | `infra_api_error_log` |
| **记什么** | 业务操作 + diff | 登录/登出 | 每次 API 调用 | 每次 API 异常 |
| **怎么记** | **手动** `@LogRecord` | 自动 | 自动 | 自动 |
| **给谁看** | 业务/审计 | 安全/运营 | 开发/运维 | 开发 |
| **数据量** | 小 | 中 | **巨大** ⚠️ | 小 |
| **能关吗** | 不加注解就没有 | 否 | 能（`enable=false`） | 否 |
| **所属模块** | system | system | infra | infra |

## 六、踩坑清单

| # | 坑 | 症状 | 解法 |
|---|---|---|---|
| 1 | **访问日志撑爆数据库** | 几天就几十 GB | 生产环境配定时任务定期清理（`infra_job`） |
| 2 | 日志里明码存了密码 | 安全事故 | 用 `sanitizeKeys`，或加到全局 `SANITIZE_KEYS` |
| 3 | `@LogRecord` 不生效 | 查不到操作日志 | 检查方法是不是 Spring Bean 的 public 方法（AOP 要求） |
| 4 | `_DIFF` 输出为空 | 日志里"修改用户信息："后面啥都没有 | VO 上没加 `@DiffLogField` |
| 5 | diff 显示 id 而不是名字 | "【部门】从【10】改为【20】" | 加 `function = DeptParseFunction.class` |
| 6 | 本地环境查不到访问日志 | — | `yudao.access-log.enable` 改成 `true` |
| 7 | 生产环境打印了文件日志 | 磁盘 IO 飙升 | 确认 prod 配置关闭了 `ApiAccessLogInterceptor` |
| 8 | 高频接口没关日志 | 数据库写入压力大 | 加 `@ApiAccessLog(enable = false)` |

### 💡 生产建议：访问日志的清理策略

访问日志是**唯一会无限膨胀**的。建议：

```sql
-- 定时删除 30 天前的访问日志
DELETE FROM infra_api_access_log WHERE create_time < DATE_SUB(NOW(), INTERVAL 30 DAY);

-- 或者按量保留（比如超过 500 万条就删最老的）
```

配成定时任务（芋道的 `infra_job` 表 + `@Scheduled` 或 XXL-Job）。

⚠️ **别手动删**！`DELETE` 几千万行会锁表。要**分批删**：

```sql
DELETE FROM infra_api_access_log WHERE id < xxx LIMIT 10000;  -- 循环执行
```

---

## 七、一句话总结

**4 种日志：操作日志（`@LogRecord` 手动记，用 `_DIFF` 能自动对比前后变化）、登录日志（自动）、访问日志（自动，可用 `@ApiAccessLog` 关掉或脱敏，本地默认关闭）、错误日志（自动，存完整堆栈）。生产环境注意：访问日志量巨大要定期清理，密码等敏感字段要脱敏。**
