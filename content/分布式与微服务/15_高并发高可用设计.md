# 高并发高可用设计（原理 → 应用 → 进阶）

> **一句话概括**：高并发不是"一台超级机器扛所有请求"，而是像**防洪大坝**——洪水来时，先让大坝层层分流、蓄洪、泄洪，真正打到地基（数据库）的水量小到它能轻松承受。
>
> **适合谁**：做过普通 CRUD，没扛过高并发，被问到"秒杀怎么设计"只能答"加 Redis"的人。
> **怎么读**：原理篇理解"压力流向"；应用篇两个简历真实案例（秒杀 + 大屏）是核心，代码可抄；进阶篇是面试高频题和常见翻车现场。

---

## 零、先建立整体印象：把它想象成"防洪大坝"

并发流量就像洪水，你的系统是一座大坝。水（请求）从上游涌来，大坝的职责是**不让洪水直接冲垮地基（数据库）**：

| 大坝层级 | 对应系统层级 | 干什么 | 手段 |
|---|---|---|---|
| **上游分洪渠** | CDN / 静态资源缓存 | 把不变的图片、JS、CSS 挡在最外面 | 就近分发，不走你的服务器 |
| **第一道闸门** | 网关限流 | 单位时间内只放固定数量的请求进来 | 令牌桶、计数器、Sentinel |
| **蓄洪池** | 消息队列 | 请求先进池子里排队，慢慢消化 | Kafka / RabbitMQ |
| **第二道闸门** | 本地缓存 + 线程池 | 热点数据直接手边取，不查远程 | Caffeine / Ehcache |
| **第三道闸门** | Redis | 读写极快，挡掉 90% 的读请求 | 缓存 + 分布式锁 |
| **地基（最后防线）** | MySQL / 达梦 | 真正持久化，但并发能力有限 | 读写分离、分库分表、SQL 优化 |

**核心思想**：每一层都尽量**挡掉、异步化、可降级**。打到数据库的请求应该是"过滤再过滤后的精华"。

---

## 一、原理篇：压力的流向

```
用户请求
   ↓
接入层（Nginx / Gateway）—— 限流、鉴权、路由
   ↓
应用层（Spring Boot）—— 本地缓存、线程池、业务逻辑
   ↓
缓存层（Redis）—— 热点数据、分布式锁、计数器
   ↓
数据层（MySQL / DM）—— 最终持久化
```

**每一层的目标**：
- **接入层**：把明显过量的请求直接挡回去（限流），让恶意流量连门都进不了
- **应用层**：能本地解决的就不走网络（本地缓存），能异步的就不同步（线程池、消息队列）
- **缓存层**：把 80% 的读请求挡在数据库外面（Redis 读 QPS 轻松 10 万+，MySQL 单机几千就吃力）
- **数据层**：最后那 20% 的"硬骨头"才落到数据库，且通过 SQL 优化、索引、读写分离让它吃得消

> 💡 **不是每一层都必须上**。一个日活几千的内部系统，上全套高并发架构就是过度设计。**按需分层，够用就好。**

## 二、应用篇（简历真实方案，代码可抄）

### 2.1 秒杀库存扣减（扛 5000 并发，目标 5 万~50 万）

**业务场景**：100 件商品，5 万人同时抢。核心矛盾：**不能超卖、不能少卖、不能卡死**。

#### 五层防御（逐层讲）

**① 库存放 Redis，Lua 原子扣减（防超卖）**

```lua
-- 这段 Lua 在 Redis 里原子执行：要么全成功，要么全不执行，中间不会被别的请求插队
if redis.call('get', KEYS[2]) == '1' then
    return 0                      -- 结束标记已存在，说明库存早空了，直接返回
end
local s = tonumber(redis.call('get', KEYS[1]))   -- 查当前库存
if s <= 0 then
    redis.call('set', KEYS[2], '1')              -- 库存空了，立一个"结束标记"
    return 0
end
redis.call('decr', KEYS[1])                      -- 原子减 1
return 1                                           -- 扣减成功
```
- `KEYS[1]` = 库存 key（如 `seckill:stock:1001`）
- `KEYS[2]` = 结束标记 key（如 `seckill:end:1001`）
- **为什么用 Lua？** Redis 单线程执行 Lua，这段脚本是一个**不可分割的整体**，不会被其他请求打断 → 天然防超卖
- **为什么用结束标记？** 库存清空后，后续请求直接读标记返回，不用每次都去查库存，减少 Redis 压力

**② 本地缓存存"结束标记"（防少卖 + 省网络 IO）**

库存清零后，"结束标记"同时写进本地缓存（Caffeine）。后续请求先查本地缓存：
```java
// 伪代码
if (localCache.get("seckill:end:" + productId) != null) {
    return "已售罄";    // 本地判断，0 网络开销
}
```
> 💡 本地缓存比 Redis 还快（内存直接读），但**多实例部署时不共享**。如果 A 实例的本地缓存已标记"结束"，B 实例还不知道，B 上的用户仍会去 Redis 查一次——这不叫 bug，叫"多查一次"，可接受。

**③ Zookeeper watch 清本地标记（多实例公平）**

如果运营临时补货（库存从 0 变 100），需要通知所有实例"清掉结束标记"。
- 做法：库存变更时更新 ZK 节点 → 所有实例监听（watch）这个节点 → 收到通知后清本地缓存
- 详见 [[13_Zookeeper 实战]]

**④ 防重复下单**

用户点了两下"立即抢购"，只能成功一次：
```java
// 用 Redis SETNX："用户+商品" 的组合 key，5 秒内只能有一次
String key = "seckill:ordered:" + userId + ":" + productId;
Boolean ok = redisTemplate.opsForValue().setIfAbsent(key, "1", 5, TimeUnit.SECONDS);
if (!ok) throw new ServiceException("请勿重复抢购");
```

**⑤ 接口限流 + 安全校验**

- 网关层：Sentinel 限流，比如"这个接口每秒最多 1000 个请求"，超出的直接返回"系统繁忙"
- 业务层：验证码 / 答题，防止机器刷单

#### 完整流程图
```
用户点击抢购
   ↓
验证码校验通过？
   ↓
本地缓存有"结束标记"？ → 是 → 返回"已售罄"
   ↓ 否
Redis SETNX 防重？ → 否 → 返回"请勿重复抢购"
   ↓ 是
Lua 原子扣减库存 → 成功？ → 否 → 返回"已售罄"
   ↓ 是
发消息到 MQ（异步创建订单、扣款、通知）
   ↓
返回"抢购成功，正在处理"
```
> 💡 **关键：创建订单是异步的**。用户看到"抢购成功"时，订单还没写到数据库，是 MQ 消费者在后台慢慢处理。这样响应极快，用户不用等。

### 2.2 大屏消息积压治理（简历 IPM 智慧大屏项目）

**业务场景**：几万台设备每 3 秒发一次心跳数据，并发直接打数据库会瞬间打爆。

**三级缓冲设计**：

```
设备心跳（每 3s）
   ↓
① 本地缓存（Caffeine）—— 存 "设备ID → 最后活跃时间"
   如果心跳时间比本地存的旧，直接丢弃（旧消息不要了）
   如果比本地新，更新本地缓存，继续往下走
   ↓
② Redis（4 个队列）—— 设备按 ID 哈希分到 4 个队列
   这样消费者可以并行读 4 个队列，避免单队列瓶颈
   ↓
③ 线程池（4 线程）—— 并发消费 4 个队列
   每条消息：取最新数据 → 批量写入数据库（不是一条一写）
   旧消息从队列右侧丢弃，防止 Redis 内存打爆
```

> 💡 **为什么 4 个队列 + 4 线程？** 单队列单线程是串行的，吞吐有限；分 4 路并行，吞吐提升近 4 倍。分片数不是越多越好，要匹配消费线程数。

> ⚠️ **丢消息是设计的一部分**：消费能力跟不上时，**主动丢弃旧消息**而不是无限堆积。大屏显示的是"最新状态"，3 秒前的心跳对大屏没有意义，丢了不可惜。这叫"降质保活"。

## 三、进阶篇（面试高频 + 常见翻车）

### 3.1 四种限流算法对比

| 算法 | 原理 | 优点 | 缺点 | 代表 |
|---|---|---|---|---|
| **计数器** | 固定窗口内计数，超了就拒绝 | 简单 | 窗口边界会突刺（最后 1ms 和下一秒前 1ms 各来一波，实际超了） | 简单场景 |
| **滑动窗口** | 把窗口切更细，逐片统计 | 平滑 | 实现复杂，内存占用高 | Sentinel |
| **漏桶** | 请求像水进桶，以固定速率漏出 | 输出绝对平滑 | 不能应对突发流量（桶满了直接丢） | 不太常用 |
| **令牌桶** ⭐ | 以固定速率往桶里放令牌，请求来拿令牌，有就放行 | 允许突发（桶里有存货），长期速率可控 | 实现稍复杂 | **Sentinel / Gateway 默认** |

> ✅ **生产环境首选令牌桶**：既能控制平均速率，又能应对合理范围内的突发。

### 3.2 限流 vs 熔断 vs 降级（三者别混）

| | 触发条件 | 作用 | 效果 |
|---|---|---|---|
| **限流** | 请求太多，超过阈值 | **入口控量** | 直接拒绝，返回"系统繁忙" |
| **熔断** | 下游服务故障（超时/报错太多） | **切断故障链** | 暂时不调下游，走兜底逻辑 |
| **降级** | 系统压力过大或部分功能非核心 | **关非核心保核心** | 关闭次要功能，返回简化版结果 |

**简历里的例子**：合同系统用**策略模式**做服务降级——正常走完整流程，压力大时切到"简化审批"策略，只保留关键节点。

### 3.3 超时与重试

- **超时**：简历配的是 10 秒超时。太长了拖垮线程池，太短了误杀慢请求。
- **重试**：配 3 次快速失败。**重试必须有退避**（第一次等 1s，第二次等 2s，第三次等 4s），否则故障时重试会放大压力。
- **前提**：下游必须**幂等**（见 [[12_消息队列 Kafka 与 RabbitMQ]]），否则重试会导致重复操作。

### 3.4 幂等：支付/下单/审批的保命符

三种实现方式：
1. **唯一索引**：数据库层面防重（如订单表 `UNIQUE(user_id, product_id, 时间窗口)`）
2. **Redis 去重标记**：`SETNX` 一个"已处理"标记，过期时间 = 业务容忍窗口
3. **状态机**：订单状态 = 待支付 → 已支付 → 已发货。"已支付"状态下再次收到支付回调，直接返回成功，不重复扣款

### 3.5 容量评估（面试常问"你们系统能扛多少 QPS"）

**粗略公式**：
```
系统理论 QPS ≈ 线程数 × (1000 / 单任务平均耗时 ms)

例：线程池 100 线程，平均处理 50ms
QPS ≈ 100 × (1000 / 50) = 2000
```
> 💡 实际值要用 **JMeter 压测**（见 [[18_开发工具链]]）来定，公式只是估算。压测时要**逐步加压到系统出现错误**，那个临界点就是水位线，日常运行留 30% 余量。

### 3.6 高并发常见翻车现场

| 翻车场景 | 现象 | 原因 | 解法 |
|---|---|---|---|
| **缓存穿透** | 大量请求查不存在的数据，直达数据库 | 恶意请求随机 ID | 布隆过滤器 / 缓存空值（短过期） |
| **缓存击穿** | 热点 key 过期瞬间，海量请求同时打 DB | 高并发 + key 同时过期 | 互斥锁重建 / 逻辑过期（永不过期） |
| **缓存雪崩** | 大量 key 同时过期，DB 被打爆 | 批量设置了相同过期时间 | 过期时间加随机偏移 |
| **双写不一致** | 更新了 DB 但缓存没清，或反之 | 两个操作非原子 | 先删缓存再更新 DB / 延迟双删 / Canal 同步 |
| **本地缓存多实例不一致** | A 实例缓存已更新，B 实例还是旧值 | 本地缓存不共享 | 短过期 + ZK watch 通知清缓存 |
| **消息积压** | MQ 队列长度暴涨，消费跟不上 | 消费端慢或宕机 | 扩容消费线程 / 丢弃旧消息 / 批量消费 |
| **锁竞争拖垮性能** | 加了锁但并发量高，线程全在等锁 | 锁粒度太粗 / 持锁时间长 | 细粒度锁 / 无锁化（CAS / 原子操作） |

> 💡 **面试总结一句话**："高并发设计核心是'分流'——每层都尽量挡掉请求，异步化、缓存化、降级化，让数据库只处理它该处理的量。"
