# 开发工具链（原理 → 应用 → 进阶）

> **一句话概括**：工具是放大效率的杠杆——同样一个活儿，**会用工具的人 10 分钟，不会的干一天**。这篇讲四件最常用的家伙：Git（代码存档）、Maven（依赖管理）、Arthas（线上排错）、JMeter（压力测试）。
>
> **适合谁**：只会 `git add/commit/push` 三板斧、Maven 冲突只会百度、线上出问题只会重启、压测报告看不懂的人。
> **怎么读**：每件工具都按「**原理（它凭什么能干这事）→ 应用（命令照着抄）→ 进阶 / 坑（老手踩过的雷）**」三段展开。**原理别跳过**——不理解原理，命令就只是背下来的咒语，换个场景就废。

---

## 零、先建立整体印象：把它想象成"开一家汽车 4S 店"

四件工具各管一段，用**修车厂**串起来：

| 修车厂里 | 对应工具 | 一句话 |
|---|---|---|
| **每次进厂拍一套照片存档** | Git | 记录车辆每个时刻的状态，随时能还原到某一天 |
| **配件供应链（按清单自动采购）** | Maven | 你说要什么零件，它连带着把配套的螺丝垫片一起备齐 |
| **OBD 故障诊断仪** | Arthas | 车不用拆、不用熄火，插上就能看到发动机内部实时数据 |
| **满载路试跑道** | JMeter | 模拟几十辆车同时上跑道，看车扛不扛得住 |

**记住这个类比，后面每节都能对号入座。**

## 一、Git（主力）

> 📖 **本节是速览版**。Git 的完整内容（快照模型、三对象、reflog 救援、交互式 rebase、IDEA 图形界面实操、踩坑速查表）见专篇：[[31_Git 原理、应用与进阶（含 IDEA 实战）]]。

### 原理：分布式快照

**类比**：很多人以为 Git 存的是"每次改了哪几行"（差异/diff）。**不是**——Git 存的是**每次提交后整个项目的一张完整快照**（当然内部会压缩复用，但概念上是快照）。就像每次修完车都给整车拍一套照片，而不是只记"换了轮胎"。

**三个核心对象**（理解这三个，Git 就没有秘密了）：

| 对象 | 存什么 | 人话 |
|---|---|---|
| **blob** | 文件内容 | 一张照片（一个文件的某个版本） |
| **tree** | 目录结构 | 相册的目录，记录"哪张照片放在哪个位置" |
| **commit** | 一次提交 | 一整本相册 + 拍摄时间 + 作者 + **上一本相册是哪本** |

**分支为什么那么轻？**
因为**分支只是一个指向某个 commit 的指针**——一个 40 字节的 SHA-1 哈希值而已。所以 Git 建分支是**瞬间完成**的（SVN 建分支要复制整个目录，慢得要死）。

```
main    →  C3
             ↑
feature →  C3'      ← feature 只是另一个"贴纸"，贴在另一个 commit 上
```

**`rebase` vs `merge`：两种"合代码"的姿势**

| | `merge` | `rebase` |
|---|---|---|
| 做法 | 把两条线合成一个**新的合并提交** | 把你的提交**挪到**目标分支最新处，重新播放一遍 |
| 提交历史 | 保留分叉，有个菱形 | **一条直线**，干干净净 |
| 代价 | 历史真实但乱 | **改写了历史** |

```
# merge：保留分叉，多一个 merge commit
A ─ B ─ C ──── M(合并)      ← main
       └─ D ─ E ┘           ← feature

# rebase：把 D、E "摘下来"接到 C 后面，历史变成一条线
A ─ B ─ C ─ D' ─ E'         ← 看不出曾经分过叉
```
> 💡 **怎么选**：**个人分支、还没 push 的提交 → 用 `rebase` 保持整洁；公共分支、多人协作 → 用 `merge`**（别改写别人的历史）。

### 应用（高频命令）

```bash
git rebase main              # 把当前分支变基到 main 最新处（保持线性，本地分支优于 merge）
git rebase -i HEAD~3         # 交互式改写最近 3 个提交：合并(squash)、改信息、删掉、重排
git cherry-pick <commit>     # 摘樱桃：把某个分支上的单个提交，"搬"到当前分支
git stash && git stash pop   # 暂存现场：手上活没干完，先存起来去修紧急 bug，回来再 pop 恢复
git revert <commit>          # 安全回滚：生成一个"反向提交"抵消它，【不改已有历史】
```

### 进阶 / 坑

**① 冲突怎么解？**
冲突文件里会出现三段标记：
```
<<<<<<< HEAD          ← 这一段是"你的"（当前分支）
你的代码
=======               ← 分隔线
别人的代码
>>>>>>> feature       ← 这一段是"对方的"（要合进来的分支）
```
手动改成你想要的样子 → `git add <文件>` → `git commit`。
> ⚠️ **`rebase` 过程中的冲突要"逐个提交"解决**：`git rebase --continue` 继续下一个，`--abort` 放弃重来。如果有 10 个提交都在改同一个文件，你可能要解 10 次——这就是 rebase 的代价。

**② 铁律：已经 push 的公共提交，绝对不要 `rebase`**
你 rebase 后本地历史和远程不一样，`git push` 会被拒，只能用 `-f` 强推——**这会把别人的提交抹掉**，同事拉代码时会原地爆炸。
> ✅ **要回滚已 push 的提交，用 `git revert`**（生成反向提交，历史只增不改，人人安全）。

**③ `.gitignore` 与 Git LFS**
```gitignore
target/          # Maven 编译产物
.idea/           # IDEA 配置
*.iml
*.log
```
> ⚠️ **`.gitignore` 只对"还没被跟踪的文件"生效**。如果 `target/` 已经被误提交了，要先 `git rm -r --cached target/` 把它从版本库里删掉（不删本地文件），再提交。
> 💡 **大文件（视频、数据集、设计稿）用 Git LFS**，否则 .git 目录会膨胀到几个 G，克隆一次半小时。

**④ SVN（简历上也写）**
**一句话区别**：Git 是**分布式**（人人有一份完整仓库，断网能提交、能建分支）；SVN 是**集中式**（只有一个中心服务器，断网就干瞪眼，连提交都不行）。

| | Git | SVN |
|---|---|---|
| 架构 | 分布式，本地有完整仓库 | 集中式，只有中心服务器有完整历史 |
| 断网 | 能提交、建分支、看历史 | **啥也干不了**（连提交都不行） |
| 分支 | 指针，瞬间完成，零成本 | 复制整个目录，**慢且重** |

## 二、Maven

> 📖 **本节是速览版**。Maven 的完整内容（settings.xml / pom.xml 逐段详解、多环境打包、Nexus 私服发布、依赖冲突四步法、IDEA 配置）见专篇：[[32_Maven 配置详解与实战（含 IDEA 配置）]]。

### 原理：依赖传递 + 生命周期

**类比**：你说"我要装一个发动机"，Maven 不只给你发动机，还会**自动把配套的螺丝、垫片、油管一起备齐**（依赖传递）。

**① 依赖范围（scope）**：决定这个 jar 在哪些阶段生效，也是排查"为什么打包后类找不到"的关键。

| scope | 编译 | 测试 | 运行 | 会被打包 | 典型 |
|---|---|---|---|---|---|
| **compile**（默认） | ✅ | ✅ | ✅ | ✅ | spring-core |
| **provided** | ✅ | ✅ | ❌ | ❌ | `servlet-api`（容器已提供） |
| **runtime** | ❌ | ✅ | ✅ | ✅ | MySQL 驱动 |
| **test** | ❌ | ✅ | ❌ | ❌ | JUnit |
| **system** | ✅ | ✅ | ❌ | ❌ | 本地 jar（**不推荐**） |

**两个控制传递的关键字**：
- `<optional>true</optional>`：**我这 jar 你用可以，但别把它传递给别人**（比如一个 ORM 框架同时支持 MySQL 和 Oracle，不能替用户决定用哪个）
- `<exclusions>`：**主动排除**某个传递依赖（最常用于排除冲突的旧版本、或排除掉有安全漏洞的 jar）

**② 生命周期**：`clean → compile → test → package → install → deploy`
> ⚠️ **关键理解**：执行后面任何一步，都会**自动先执行它前面的所有步骤**。所以 `mvn install` 会自动完成 compile 和 test——这也是为什么有时你只想打包却被迫跑了半天测试。

### 应用（高频命令）

```bash
mvn dependency:tree                 # 看依赖树，查冲突的【第一利器】
mvn dependency:tree -Dincludes=groupId:artifactId    # 只看某个 jar 是从哪条路引进来的
mvn -pl order -am package           # 只构建 order 模块及其依赖（-pl 指定模块，-am 同时构建依赖模块）
                                    # 多模块项目必备：不用每次都全量构建
mvn package -DskipTests             # 跳过测试打包（速度快，但别养成习惯）
mvn clean install -U                # -U 强制刷新 SNAPSHOT 依赖（别人刚推的快照包拉不下来时用）
```

**查冲突的标准操作**：
```bash
mvn dependency:tree | grep slf4j    # 看 slf4j 出现了几次、分别被谁引进来
```
输出里 `omitted for conflict with 1.7.36` 就是被"仲裁掉"的那个版本。

### 进阶 / 坑

**① 依赖冲突的两条仲裁规则**（背下来）：
1. **最短路径优先**：A → B → C → X(1.0) 和 A → D → X(2.0)，选 **X(2.0)**（路径更短）
2. **路径长度相同 → 先声明优先**：谁在 pom 里写在前头，选谁

> 💡 所以**解决冲突不是改版本号，而是"调整声明顺序"或"用 `<exclusions>` 直接排除"**。

**② 私服与多模块**
- **私服**（Nexus / Artifactory）：公司内网的 jar 仓库。**两个作用**：① 缓存中央仓库，下载快；② 存放公司自己的二方包
- **多模块**：用 parent pom 的 `<modules>` 聚合，配合 `<dependencyManagement>` 统一锁版本

**③ 版本对齐（最容易翻车的地方）**
Spring Boot 和 Spring Cloud 有**严格的版本对应关系**（比如 Boot 2.7.x 配 Cloud 2021.0.x），配错了启动就报一堆莫名其妙的错。
> ✅ **正确做法**：用 `<dependencyManagement>` 引入官方 BOM（版本清单），**所有子依赖都不写 `<version>`**，让官方帮你调好：
> ```xml
> <dependencyManagement>
>   <dependencies>
>     <dependency>
>       <groupId>org.springframework.boot</groupId>
>       <artifactId>spring-boot-dependencies</artifactId>
>       <version>${spring.boot.version}</version>
>       <type>pom</type>
>       <scope>import</scope>      <!-- import = 把官方的版本清单搬过来用 -->
>     </dependency>
>   </dependencies>
> </dependencyManagement>
> ```
> ⚠️ 注意区别：`<dependencyManagement>` **只声明版本，不实际引入**；`<dependencies>` 才是真引入。混用会导致"不需要的模块也被塞了 jar"。

## 三、Arthas（线上排查，简历技能）

### 原理：Java Agent + 字节码增强

**类比**：车跑着的时候，你不熄火、不拆发动机，**插上一个 OBD 检测仪**就能读到转速、水温、故障码。Arthas 就是 JVM 的 OBD。

**技术上怎么做到的？** 两个关键词：
- **Java Agent**：JVM 提供的一种"后门机制"，允许外部程序 Attach 到运行中的 JVM
- **字节码增强**：在不改源码、不重启的前提下，**动态修改已加载类的字节码**，在方法前后插入统计代码

所以 Arthas 能做到"热插拔"——**用完 `stop` 就完全退出，不留痕迹**。

### 应用（高频命令）

```bash
java -jar arthas-boot.jar           # 启动，会列出所有 Java 进程让你选一个 attach
dashboard                           # 总览大屏：线程、内存、GC、运行环境，一屏看完
thread -n 3                         # 最忙的 3 个线程（CPU 飙高时第一件事就是它）
thread <id>                         # 看某个线程的完整调用栈（找死锁、找卡在哪一行）
thread -b                           # 【一键找死锁】直接列出互相等待的线程
trace 类 方法                       # 跟踪方法内部每个子调用的耗时 → 精确定位慢在哪一步
watch 类 方法 "{params,returnObj}"  # 看某个方法的入参和返回值（不用加日志、不用重启）
jad 类                              # 反编译线上类 → 确认"部署的到底是不是我这版代码"
ognl '@类名@静态字段'                # 查看/修改运行时的静态变量（动态开关就靠它）
```

**典型排查动线**（背下来）：
```
CPU 飙高  → dashboard 看整体 → thread -n 3 找最忙线程 → thread <id> 看栈 → 定位代码
接口变慢  → trace 类 方法    → 看哪个子调用最慢 → 多半是慢 SQL 或慢远程调用
数据不对  → watch 看入参返回值（不用加日志重启）
怀疑没部署对 → jad 反编译确认
```

### 进阶

- **配合 [[02_JVM 原理与调优]] 做调优**：`dashboard` 里的 GC 次数、堆占用，和 `jstat` 是同一套数据，只是 Arthas 更直观
- **`redefine` 热替换**：把修改后的 `.class` 文件直接塞进运行中的 JVM，**改 bug 不用重启**

> ⚠️ **生产慎用 `redefine`**：① **重启即失效**（只是改了内存里的字节码，磁盘上的 jar 没变）；② 不能改方法签名、不能加字段；③ 出错会导致这个类彻底不可用。**它只适合紧急止血，事后必须走正常发版补齐。**

## 四、JMeter（压测，简历技能）

### 原理：多线程模拟并发

**类比**：想知道一条路能不能扛住 5000 辆车同时上，你不可能真找 5000 辆车。JMeter 的做法是——**用几百个线程，每个线程飞快地反复"发车-收车"，模拟出持续的高并发**。

### 应用

**四大组件的关系**（JMeter 的骨架就这四个）：
```
测试计划 Test Plan
  └── Thread Group 线程组        ← 定"多少人、循环多少次、几秒内启动完"
        ├── Sampler 取样器        ← 发什么请求：HTTP / JDBC / Dubbo / MQ
        ├── 定时器 Timer          ← 控制节奏：固定 QPS、固定吞吐
        ├── 断言 Assertion        ← 判断响应对不对（不只看 200，还要看内容）
        └── Listener 监听器       ← 看结果：查看结果树 / 聚合报告
```
> 💡 **固定 QPS 用「Constant Throughput Timer」**（目标吞吐量），这样压出来的才是稳定的 QPS，而不是"有多少线程就压多猛"。

**大并发怎么办？** 单机线程数有上限（一般几百个线程就开始失真），用**分布式压测**：一台主控机 + 多台压力机。

### 进阶 / 坑

**① 聚合报告怎么看**（这三个指标决定你的系统水位）：

| 指标 | 含义 | 关注点 |
|---|---|---|
| **Throughput 吞吐量** | 每秒处理多少请求（QPS/TPS） | 系统的能力上限 |
| **99% Line（99 线 RT）** | 99% 的请求在多长时间内完成 | ⭐ **比平均响应时间重要 10 倍**——平均值会被少数快请求拉低，掩盖长尾问题 |
| **Error % 错误率** | 失败请求占比 | 压到什么程度开始报错，就是拐点 |

> ✅ 简历上写"秒杀扛 5000 并发"，**就是用这三个数验证的**：5000 并发下 99 线 RT 是多少毫秒、错误率是不是 0。

**② 压测机别成了瓶颈**（最常见的翻车）
你压出"系统只能扛 2000 QPS"，可能不是系统不行，**是你的压测笔记本先扛不住了**。
> ⚠️ 判断方法：**压测时盯着压测机本身的 CPU**（超过 80% 就不可信了）和**网络带宽**。
> ✅ 解法：大并发用**分布式压测**或**云端压测机**，并且压测机和被测服务**不要部署在同一台机器**。

**③ 压测环境要"等比缩放"**
> ⚠️ 典型事故：**"压测环境跑得好好的，一上生产就挂"**。
> 原因：压测环境是 2 核 4G、数据库只有几百条测试数据、Redis 和 MySQL 挤在一台机器上。
> ✅ 正确做法：压测环境的**机器配置、数据量级、网络拓扑**都要尽量接近生产（至少同比例），或者**直接在生产低峰期做全链路压测**。

**④ 压测的目的是"定水位"，不是"跑分"**
压出拐点之后，拿这个数据去**调限流阈值和线程池参数**——比如实测单机能扛 800 QPS，那 Sentinel 的限流就设在 600~700 留些余量。详见 [[15_高并发高可用设计]]。
