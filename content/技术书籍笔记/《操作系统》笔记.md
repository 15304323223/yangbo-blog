# 《操作系统》笔记

> **一句话概括**：操作系统就是**「一台机器的管家 + 调度员」**——它管着 CPU 该谁用、内存该怎么分、磁盘该怎么读写，让上层程序感觉「我在独占整台机器」。
>
> **为什么后端要读**：你天天用的这些概念——**进程/线程、上下文切换、虚拟内存、页表、epoll、零拷贝、IO 多路复用**——**答案全在这里**。
> **适合谁**：`volatile` 只会背「保证可见性」、`epoll` 只会背「比 select 快」、`mmap`/零拷贝只会背「少一次拷贝」的人。
> **怎么读**：**四大块——进程管理 / 内存管理 / 文件系统 / IO**。**第 2 章（进程）和第 3 章（内存）和后端最相关**。

---

## 零、先建立整体印象：操作系统是「一家公司的行政部门」

| 行政部门 | 对应 OS | 一句话 |
|---|---|---|
| **排班表** | 进程调度 | 决定谁先干活、干多久 |
| **工位分配** | 内存管理 | 谁用哪块地方，怎么隔离 |
| **文件柜** | 文件系统 | 东西怎么存、怎么找 |
| **收发室** | IO 管理 | 外部来的东西怎么送进来 |
| **部门间的协调** | 进程通信 / 同步 | 怎么不打架、怎么传消息 |

**操作系统的四大功能**：

```
① 进程管理    ← 谁在用 CPU、进程怎么切换、怎么同步
② 内存管理    ← 虚拟内存、分页、页面置换
③ 文件管理    ← 文件的组织、目录、磁盘调度
④ 设备/IO 管理 ← 中断、DMA、IO 多路复用
```

## 一、进程与线程（第 2 章）⭐⭐

### 1.1 进程 vs 线程（书里的经典对比）

| 对比项 | 进程 | 线程 |
| ---- | ---- | ---- |
| **定义** | 资源分配的基本单位 | **CPU 调度的基本单位** |
| **资源** | 独立地址空间、文件、信号 | **共享所属进程的资源** |
| **私有部分** | 全部 | **栈、程序计数器、寄存器** |
| **切换开销** | **大**（要切换页表、刷新 TLB） | **小**（只切栈和寄存器） |
| **通信** | 需 IPC（管道、消息队列、共享内存） | **直接读写共享变量**（但要同步） |
| **崩溃影响** | 一个进程崩了不影响别的 | **一个线程崩了，整个进程挂掉** |

> 💡 **一句话记住**：**「进程是资源分配单位，线程是调度单位」**——这句话是面试必答。
> 💡 **为什么线程切换快**：**同一个进程的线程共享地址空间**，所以切换时**不用切换页表、不用刷新 TLB 缓存**（这是最贵的两步）。

### 1.2 进程的状态机（必背）

```
        创建
         ↓
       就绪 ←──────┐
         ↓         │
        调度     时间片用完
         ↓         │
       运行 ───────┘
         ↓ 等待 IO
       阻塞
         ↓ IO 完成
       就绪
         ↓
       终止
```

| 状态 | 说明 |
| ---- | ---- |
| **就绪（Ready）** | 万事俱备，就差 CPU |
| **运行（Running）** | 正在占用 CPU |
| **阻塞（Blocked）** | 在等 IO 或事件，**就算给它 CPU 也用不了** |
| **创建 / 终止** | 开始和结束 |

> ⚠️ **经典面试题**：**「阻塞 → 运行」不能直接转换**（必须经过就绪）：因为阻塞是「等 IO」，IO 完成后它要重新排队等 CPU。
> ⚠️ **另一个坑**：**「就绪 → 阻塞」也不能直接转换**（就绪状态还没拿到 CPU，没法发起 IO）。

### 1.3 进程调度的算法

| 算法 | 说明 | 优缺点 |
| ---- | ---- | ---- |
| **FCFS（先来先服务）** | 按到达顺序 | 简单，但长任务会拖累短任务 |
| **SJF（短作业优先）** | 谁短谁先 | 平均等待最短，但长任务可能饿死 |
| **RR（时间片轮转）** | 每人固定时间片 | 公平，适合交互式 |
| **优先级调度** | 优先级高的先 | 可能饿死低优先级（可用老化解决） |
| **多级反馈队列** ⭐ | 多级队列 + 动态调优先级 | **现代 OS 普遍采用** |

> 💡 **理解「多级反馈队列」**：新进程进最高优先级队列（时间片小）；用完了就降到下一级（时间片变大）。**这样既能快速响应短任务，又能让长任务最终跑完。**

### 1.4 上下文切换的代价

**切换时保存/恢复什么**：

```
① 程序计数器（PC）—— 执行到哪了
② 寄存器 —— 正在算的值
③ 页表基址 —— 自己的地址空间在哪（进程切换才需要）
④ 各种栈指针
```

| 切换类型 | 开销 | 原因 |
| ---- | ---- | ---- |
| **进程切换** | 大 | 换页表 + **刷 TLB** |
| **线程切换**（同进程） | 小 | 不换页表 |
| **线程切换**（跨进程） | 大 | 等于进程切换 |

> ⚠️ **为什么「线程不是越多越好」**：线程多了，**光是上下文切换就吃掉大量 CPU**。这就是 [[《Java性能权威指南》笔记]] 里「线程池不能过大」的根本原因。

### 1.5 进程同步：三个经典问题

#### ① 生产者-消费者（用信号量解决）

```java
// 信号量：empty（空位数）、full（产品数）、mutex（互斥访问缓冲区）
Semaphore empty = new Semaphore(N);   // 缓冲区有 N 个空位
Semaphore full  = new Semaphore(0);   // 一开始没有产品
Semaphore mutex = new Semaphore(1);   // 互斥锁

// 生产者
empty.acquire();       // ⚠️ 先等空位（顺序很重要！）
mutex.acquire();
// 放产品到缓冲区
mutex.release();
full.release();

// 消费者
full.acquire();
mutex.acquire();
// 从缓冲区取产品
mutex.release();
empty.release();
```

> ⚠️ **经典坑**：**P 操作的顺序不能反**——如果生产者先 `mutex.acquire()` 再 `empty.acquire()`，缓冲区满时生产者会抱着锁睡觉，消费者进不来 → **死锁**。

#### ② 读者-写者

| 策略 | 规则 |
| ---- | ---- |
| **读者优先** | 读者可以同时读；只要有读者，写者就得等（**写者可能饿死**） |
| **写者优先** | 写者来了，后面的读者也得等 |

#### ③ 哲学家进餐（死锁演示）

5 个哲学家围坐，每人需要「左右两根筷子」才能吃饭。**如果所有人都先拿左边再等右边 → 死锁。**

**解法**：
- 限制最多 4 个人同时拿筷子
- 奇数先拿左、偶数先拿右（**破坏循环等待**）
- 用 `tryLock`（拿不到就放下，退避重试）

> 📌 **Java 实战**：`tryLock` 超时降级、固定加锁顺序避免死锁——见 [[03_JUC 详细讲解]]。

### 1.6 死锁的四个必要条件（必背）⭐⭐

| 条件 | 含义 | 怎么破坏 |
| ---- | ---- | ---- |
| **互斥** | 资源一次只能被一个进程占用 | 尽量用「可共享」资源 |
| **持有并等待** | 拿着一个还等另一个 | **一次性申请所有资源** |
| **不可剥夺** | 拿到的资源不能被抢 | 用 `tryLock` 支持放弃 |
| **循环等待** | A 等 B，B 等 A | **固定加锁顺序**（最常用） |

> 💡 **最实用的破坏方法**：**「固定加锁顺序」**——所有线程都按 ID 从小到大加锁，就不会形成循环等待。

### 1.7 Java 线程与 OS 线程的映射

| 模型 | 说明 | Java 用哪个 |
| ---- | ---- | ---- |
| **一对一** | 1 个 Java 线程 = 1 个 OS 线程 | **传统 Java 线程（JDK 21 前）** |
| **多对一** | 多个用户线程映射到 1 个内核线程 | 早期「绿色线程」 |
| **多对多** | M 个用户线程 : N 个内核线程 | **JDK 21 虚拟线程（近似）** |

> 💡 **虚拟线程（JDK 21）的原理**：**大量虚拟线程挂在少量「载体线程（OS 线程）」上**——遇到 IO 阻塞时**自动让出载体线程**给别的虚拟线程用。所以**虚拟线程适合 IO 密集型**（能开百万个），但 **CPU 密集型不适合**。
> 📌 **详见** [[33_Java 8、17、21 特性全解]]（虚拟线程与 pinning）。

## 二、内存管理（第 3 章）⭐⭐⭐

> **这一章是理解 JVM 内存、`volatile`、`mmap`、零拷贝的地基。**

### 2.1 为什么要虚拟内存

| 问题（没有虚拟内存） | 虚拟内存怎么解决 |
| ---- | ---- |
| 程序要直接操作物理地址 | **每个进程有独立的虚拟地址空间** |
| 内存不够装下所有程序 | **只有用到的页才加载到物理内存**（按需分页） |
| 程序之间会互相踩内存 | **地址隔离**（进程 A 的虚拟地址映射不到进程 B 的物理内存） |
| 内存碎片 | 虚拟地址连续 ↔ 物理地址可以不连续 |

> 💡 **一句话**：**「虚拟内存让每个进程都以为自己独占整台机器。」**

### 2.2 分页与页表

```
虚拟地址 ──[页号 | 页内偏移]──┐
                              ↓ 查页表
                          [物理页号 | 页内偏移] ── 物理地址
```

| 概念 | 说明 |
| ---- | ---- |
| **页（Page）** | 虚拟地址空间分成固定大小的块（通常 **4KB**） |
| **页框（Frame）** | 物理内存分成同样大小的块 |
| **页表（Page Table）** | 记录「虚拟页 → 物理页框」的映射 |
| **MMU** | CPU 里负责地址转换的硬件 |
| **TLB** | **旁路转换缓冲**——页表的缓存（**这就是为什么进程切换要刷 TLB**） |

**多级页表**：一级页表太大（32 位系统一个进程 4MB），所以拆成多级，**只有用到的部分才建表**。

> 💡 **和 JVM 的联系**：**JVM 的「堆」是虚拟地址空间**，实际物理内存按需分配。所以「`-Xmx4g`」表示「最多用 4G 虚拟地址」，**不代表一开始就占 4G 物理内存**（除非 `-Xms4g` 且 touched）。

### 2.3 页面置换算法（必背）

| 算法 | 说明 | 特点 |
| ---- | ---- | ---- |
| **OPT（最优）** | 淘汰「将来最久不用」的 | 理论最优，**无法实现**（要知道未来） |
| **FIFO（先进先出）** | 淘汰最老的 | 简单，但**有 Belady 异常**（页框变多反而缺页更多） |
| **LRU（最近最少使用）** | 淘汰最久没用的 | **最常用**的近似 |
| **Clock（时钟）** | LRU 的低成本近似 | 实际系统常用（如 Linux） |

> ⚠️ **Belady 异常**：**只有 FIFO 会有**——增加物理页框数，缺页率反而上升。**LRU 和 OPT 不会**（它们属于「栈算法」）。

### 2.4 中断与系统调用：用户态 vs 内核态 ⭐

> **这是理解「为什么系统调用比普通函数慢」的关键。**

```
用户态（Ring 3）          内核态（Ring 0）
   你的代码        ──►       操作系统
      │      系统调用（软中断）     │
      │  ←──────────────────────  │
   继续执行      返回用户态
```

| 概念 | 说明 |
| ---- | ---- |
| **用户态** | 普通程序运行的状态，**不能直接访问硬件/内核内存** |
| **内核态** | 操作系统运行的状态，**可以执行特权指令** |
| **系统调用** | 用户态请求内核帮忙（如 `read`/`write`/`open`） |
| **中断** | 硬件通知 CPU「有事情要处理」（**会打断当前执行，保存现场**） |

**为什么系统调用贵**：
1. **状态切换**（用户态 → 内核态 → 用户态）
2. **保存/恢复上下文**
3. **可能触发调度**（如果资源没准备好，当前线程会被挂起）

> 💡 **实用价值**：**「减少系统调用」是性能优化的重要手段**——比如：
> - **缓冲 IO**（一次 `read` 读一大块，而不是一个字节一个字节读）
> - **批处理**（数据库的 `addBatch`，见 [[《Java性能权威指南》笔记]]）
> - **零拷贝**（见 3.3 节）
> - **`epoll` 一次等多个 fd**（而不是轮询）

### 2.5 内存映射（mmap）与零拷贝 ⭐⭐

**普通 IO 的拷贝次数（读文件再发出去）**：

```
磁盘 → 内核缓冲区   （① DMA 拷贝）
内核缓冲区 → 用户缓冲区  （② CPU 拷贝）
用户缓冲区 → Socket 缓冲区 （③ CPU 拷贝）
Socket 缓冲区 → 网卡   （④ DMA 拷贝）
                  ⇒ 共 4 次拷贝，4 次上下文切换
```

**零拷贝（`sendfile`）**：

```
磁盘 → 内核缓冲区 → 网卡
         ⇒ 2 次拷贝（都是 DMA），2 次上下文切换
```

| 技术 | 说明 | Java 对应 |
| ---- | ---- | ---- |
| **`mmap`** | 把文件映射到内存，读写内存即读写文件 | `FileChannel.map()` |
| **`sendfile`** | 内核直接把文件送到 socket，**不经过用户态** | `FileChannel.transferTo()` |
| **`splice`** | 类似 sendfile，支持更灵活的场景 | — |

> 💡 **Kafka 为什么快**：**大量用了零拷贝（`transferTo`）和 `mmap`**——消息落盘和消费都避免了用户态拷贝。
> 💡 **Netty 的 `ByteBuf`**：也用零拷贝思想（`CompositeByteBuf`、`slice`）减少数据复制。

### 2.6 IO 多路复用：select / poll / epoll ⭐⭐⭐

> **这是「为什么 Nginx/Redis/Netty 能撑百万连接」的答案。**

| 对比 | select | poll | **epoll** |
| ---- | ---- | ---- | ---- |
| **fd 上限** | 1024（`FD_SETSIZE`） | 无上限 | 无上限 |
| **数据结构** | 位图 | 数组 | **红黑树 + 就绪链表** |
| **每次调用** | **全量拷贝 fd 集合** | **全量拷贝** | **不用拷贝**（内核里注册一次） |
| **如何找就绪** | **O(n) 遍历** | O(n) 遍历 | **O(1) 回调通知** |
| **触发模式** | 水平触发 | 水平触发 | **支持边缘触发（ET）** |

**epoll 的核心机制**：

```
① epoll_create：在内核建一个 epoll 对象（红黑树存 fd）
② epoll_ctl：把 fd 注册进去（只需一次）
③ epoll_wait：等就绪事件——内核通过回调把就绪的 fd 放进「就绪链表」
       ↓
    直接返回就绪列表，O(1)（不用遍历所有 fd）
```

| 触发模式 | 说明 |
| ---- | ---- |
| **水平触发（LT）** | 只要缓冲区有数据就不断通知（**默认，简单**） |
| **边缘触发（ET）** | 只在状态变化时通知一次（**高效，但必须一次读完**） |

> ⚠️ **ET 模式的坑**：必须**循环读到 `EAGAIN`**，否则会丢数据。
> 💡 **为什么 epoll 快**：**「不拷贝 + 不遍历」**——fd 只注册一次、就绪事件由内核回调，而不是每次都把 100 万个 fd 传进来遍历一遍。

## 三、文件系统（第 4 章）

### 3.1 文件的物理结构

| 结构 | 说明 | 优缺点 |
| ---- | ---- | ---- |
| **连续分配** | 文件占连续的磁盘块 | 读取快，但难扩展、碎片多 |
| **链式分配** | 每块指向下一块 | 易扩展，但**只能顺序访问** |
| **索引分配** ⭐ | 用一个索引块记录所有块地址 | **支持随机访问**，现代 FS 主流 |

**inode（索引节点）**：Linux 里**每个文件对应一个 inode**，存「权限、大小、时间戳、数据块位置」——**但不存文件名**（文件名在目录项里）。

> 💡 **实用价值**：**「磁盘还有空间，但创建不了文件」**——常见原因就是 **inode 用完了**（大量小文件）。用 `df -i` 查看。

### 3.2 目录与硬链接 / 软链接

| 类型 | 说明 | 区别 |
| ---- | ---- | ---- |
| **硬链接（hard link）** | 多个文件名指向**同一个 inode** | 删掉一个名字，文件还在（`link count - 1`）；不能跨文件系统 |
| **软链接（soft link / symlink）** | 一个文件存「另一个文件的路径」 | 原文件删了，软链接就失效（断链）；可跨文件系统 |

> 📌 **Git 的「内容寻址」和 inode 的思想类似**（见 [[31_Git 原理、应用与进阶（含 IDEA 实战）]]）。

### 3.3 磁盘调度算法

| 算法 | 说明 |
| ---- | ---- |
| **FCFS** | 按请求顺序 |
| **SSTF（最短寻道）** | 离当前磁头最近的先服务（可能饿死远处请求） |
| **SCAN（电梯算法）** | 单向扫描，到端点折返 |
| **C-SCAN** | 只单向服务，回来时快速跳到起点 |

> 💡 **SSD 时代**：SSD 没有机械寻道，调度算法的重要性下降，但**「顺序读写的优势」依然存在**（页/块擦除特性）。

## 四、后端开发的「操作系统知识映射表」⭐

> **这张表把「你天天用的技术」和「OS 原理」对上号**——面试时能把技术追溯到原理，立刻加分。

| 你用的技术 | 背后的 OS 原理 | 在哪一章 |
| ---- | ---- | ---- |
| `volatile` 保证可见性 | **CPU 缓存一致性（MESI）** + 内存屏障 | 组成原理 |
| `synchronized` 重量级锁 | **互斥量 + 内核态阻塞**（涉及用户态/内核态切换） | 进程同步 |
| `ConcurrentHashMap` | **CAS（无锁）** + 分段/桶锁 | 组成原理 + 同步 |
| 线程池核心数公式 | **上下文切换开销** | 进程调度 |
| 虚拟线程 | **多对多线程模型** | 进程/线程 |
| Netty / Redis 高并发 | **epoll（IO 多路复用）** | 2.6 |
| Kafka 高性能 | **零拷贝（sendfile）+ 顺序写** | 2.5 |
| NIO `FileChannel.transferTo` | **sendfile 系统调用** | 2.5 |
| `mmap` 读写文件 | **虚拟内存 + 页表映射** | 2.5 |
| 「磁盘满但创建不了文件」 | **inode 耗尽** | 3.1 |
| 死锁排查 | **循环等待条件** | 1.6 |
| 慢在「系统调用太多」 | **用户态/内核态切换开销** | 2.4 |
| `LongAdder` 比 `AtomicLong` 快 | **伪共享（缓存行）** | 组成原理 |
| `fork()` 创建进程 | **写时复制（COW）** | 内存管理 |

### 补充：写时复制（Copy-On-Write）⭐

> **`fork()` 创建子进程时，不会立刻拷贝父进程的全部内存**——而是**共享**，**只有当某一方要「写」时，才拷贝那一页**。

```java
// Java 里的 COW 应用：CopyOnWriteArrayList
// 读操作不加锁（读的是「旧的完整副本」），写操作复制整个数组
List<String> list = new CopyOnWriteArrayList<>();

// 适用场景：读多写极少（如「配置列表」「监听器列表」）
// ❌ 不适用：写多的场景（每次写都复制整个数组，代价巨大）
```

> 💡 **Redis 的 `BGSAVE`** 也用 COW——**fork 出子进程做持久化，主进程继续服务**。

## 五、一句话总结 & 全书地图

> **「操作系统在『隔离』和『共享』之间做平衡，让每个程序都以为自己独占整台机器。」**

### 五个核心认知

1. **进程是资源单位，线程是调度单位**——线程切换快是因为共享地址空间
2. **虚拟内存让每个进程以为自己独占内存**——按需分页 + 页表映射
3. **系统调用贵在「状态切换」**——减少调用次数是优化重点
4. **epoll 快的本质是「不拷贝 + 不遍历」**——fd 注册一次，内核回调通知
5. **死锁用「固定加锁顺序」破最实用**
