# 《深入理解 Java 虚拟机》笔记

> **一句话概括**：JVM 就是**替你管内存、打扫卫生、把字节码翻译成机器码的管家**——这本书回答的核心只有一个问题：**「为什么 Java 要这么设计」**。
>
> **和已有笔记的分工**（重要）：
> - [[02_JVM 原理与调优]]（技术库正文）= **实战手册**：参数怎么配、出事怎么查
> - **本篇** = **原理深挖**：收集器为什么这样演进、类加载为什么是双亲委派、JIT 为什么能优化、这些权衡背后的逻辑
>
> **适合谁**：会用 JVM 参数但说不出「为什么用 G1 不用 CMS」、被问「JVM 内存模型和 Java 内存模型是一回事吗」答不上来的人。
> **怎么读**：**第 2、3 章（内存 + GC）是全书核心**，第 7 章（执行引擎）是拉开差距的地方，其余按需。

## 零、先建立整体印象：JVM 这本书在讲什么

全书可以拆成**三条主线**，把散落的知识点串起来：

```
主线 1：内存怎么管   ← 「对象住哪、什么时候被清走」  → 第 2、3 章

主线 3：类怎么加载   ← 「这个类从哪来、谁先加载」    → 第 8~10 章
```

用**「一家公司的运营」**类比：

| 公司里 | 对应 JVM | 一句话 |
| ---- | ---- | ---- |
| **办公区 + 仓库** | 运行时数据区 | 员工干活的地方 + 存放物料的地方 |
| **保洁团队 + 各自的打扫策略** | GC 收集器 | 有扫全楼的、有分区扫的、有边干边扫的 |

| **KPI 考核与优化** | 性能监控与调优 | 用数据说话，不是拍脑袋 |

> 💡 **本书最有价值的不是「知识点」，而是「权衡思维」**——每个设计都有取舍（吞吐量 vs 停顿时间、内存 vs 速度），理解了取舍，就理解了为什么有这么多收集器。

## 一、内存结构：这本书的「地基」（第 2 章）

### 1.1 运行时数据区（完整版）

> 正文 [[02_JVM 原理与调优]] 已用「工厂」类比讲过，这里**补充书里更细的划分**。

```
┌── 线程共享 ─────────────────────────────────────────────┐
│  堆 Heap                                                │
│    ├── 新生代 Young Gen                                 │
│    │     ├── Eden（伊甸园）：新对象出生地                  │
│    │     ├── Survivor0 / Survivor1（From / To）            │
│    │     └── 默认比例：Eden : S0 : S1 = 8 : 1 : 1          │
│    └── 老年代 Old Gen（Tenured）                          │
│  方法区（JDK 8 起由元空间 Metaspace 实现，用本地内存）        │
└─────────────────────────────────────────────────────────┘
┌── 线程私有 ─────────────────────────────────────────────┐
│  虚拟机栈（每个方法调用 = 一个栈帧）                          │
│    └── 栈帧 = 局部变量表 + 操作数栈 + 动态链接 + 方法出口     │
│  本地方法栈（native 方法）                                 │
│  程序计数器 PC（唯一不会 OOM）                              │
└─────────────────────────────────────────────────────────┘
```

### 1.2 书里最爱考的 5 个细节 ⭐

| 问题 | 答案 |
| ---- | ---- |
| **为什么元空间取代永久代？** | 永久代在堆内、大小固定、易 `PermGen OOM`；元空间用**本地内存**，且**混淆在堆外便于类卸载** |
| **`-Xss` 调的是什么？** | 每个**线程栈**的大小（默认约 512K~1M），调大能防 `StackOverflowError` 但会减少可创建线程数 |
| **什么对象直接在老年代分配？** | ① **大对象**（超过 `-XX:PretenureSizeThreshold`）；② **长期存活对象**（年龄到 `-XX:MaxTenuringThreshold`，默认 15）；③ **动态年龄判定**（Survivor 中同龄对象总和 > 一半） |
| **TLAB 是什么？** | **Thread Local Allocation Buffer**——每个线程在 Eden 里独占一小块，分配对象无需加锁（**这是「对象分配几乎无锁」的关键**） |
| **逃逸分析能干嘛？** | ① **栈上分配**（对象不逃逸就放栈上，随方法结束自动销毁）；② **标量替换**（把对象拆成基本类型）；③ **锁消除**（不可能被竞争的锁直接删掉） |

> ⚠️ **书里特别强调**：**栈上分配现实中很少见**（HotSpot 实现受限），别指望它能解决内存问题。真正有效的是**标量替换**和**锁消除**。

### 1.3 「JVM 内存模型」vs「Java 内存模型」——最容易混的概念 ⭐⭐

> 这是面试**高频且高区分度**的题，书里专门澄清：

| 概念 | 英文 | 讲的是什么 | 在哪一章 |
| ---- | ---- | ---- | ---- |
| **JVM 运行时数据区** | Runtime Data Area | **物理存在**：堆、栈、方法区等**内存区域怎么划分** | 第 2 章 |
| **JMM（Java 内存模型）** | Java Memory Model | **规范**：多线程下**共享变量的可见性、有序性、原子性怎么保证** | 第 12 章 |

> 💡 **一句话区分**：
> - **运行时数据区**回答「**内存放在哪**」（物理布局）
> - **JMM** 回答「**多线程读写共享变量时，什么时候能看到对方的值**」（并发规范）
> - 两者**完全不同**，但经常被混为一谈——**面试时能把这两个分开讲，立刻加分**

## 二、垃圾回收：本书的「灵魂」（第 3 章）⭐⭐

> **本章是全书最重要的章节**，也是面试主战场。核心是三件事：**怎么判定死、怎么收、用什么收**。

### 2.1 怎么判定「对象已死」

| 方法 | 说明 | 为什么最终选了它 |
| ---- | ---- | ---- |
| **引用计数法** | 每个对象记一个被引用数，为 0 就回收 | ❌ **无法解决循环引用**（A→B→A），HotSpot 不用 |
| **可达性分析（Root Tracing）** ✅ | 从 **GC Roots** 出发，走不到的 = 可回收 | ✅ 能解决循环引用，工程上可行 |

**GC Roots 有哪些**（背下来）：
- 虚拟机栈中（栈帧的局部变量表）引用的对象
- 方法区中**静态属性**引用的对象
- 方法区中**常量**引用的对象
- 本地方法栈中 **JNI** 引用的对象
- **JVM 内部引用**（基本类型对应的 Class 对象、常驻异常对象、系统类加载器）
- **被同步锁持有**的对象（`synchronized`）
- **JMXBean、JVM TI 中的回调、本地代码缓存**等

> 💡 **「不可达」不等于「立刻死」**：对象被判定不可达后，还有**一次自我拯救机会**——如果它重写了 `finalize()` 且没被调用过，会被放进 `F-Queue` 等待一次 `finalize()`。**但书里明确说：`finalize()` 是「永远不该使用」的，已被 JDK 9 标记为 deprecated。**

### 2.2 三种基本回收算法

| 算法 | 做法 | 优点 | 缺点 | 用在哪 |
| ---- | ---- | ---- | ---- | ---- |
| **标记-清除** | 标记活对象 → 清掉死的 | 简单 | **碎片多**、效率低 | CMS |
| **标记-复制** | 把活的复制到另一半 → 清空原区 | 无碎片、效率高 | **浪费一半空间** | 新生代（8:1:1 就是这个原因） |
| **标记-整理** | 标记活对象 → 全部往一端移 | **无碎片** | 移动成本高、需 STW | 老年代 |

> 💡 **为什么要分代？** 因为对象的生命特征不同——**「弱分代假说」：绝大多数对象朝生夕死**。所以：
> - **新生代**：对象大批死亡 → 用**复制算法**（只复制少数活着的，划算）
> - **老年代**：对象存活率高 → 用**标记-清除/整理**（复制成本太高）

### 2.3 GC 收集器演进史（本书精华，也是最大差异点）⭐⭐⭐

> **正文 [[02_JVM 原理与调优]] 只讲「怎么配」，这里讲「为什么这样演进」。**

```
          单线程         多线程         并发           分区         着色指针
            ↓              ↓             ↓              ↓            ↓
        ┌────────┐   ┌──────────┐  ┌─────────┐   ┌────────┐  ┌──────────┐
新生代  │ Serial │   │ ParNew   │  │ Parallel│   │        │  │          │
        │        │   │          │  │ Scavenge│   │        │  │          │
        └────────┘   └──────────┘  └─────────┘   │  G1    │  │   ZGC    │
        ┌────────┐   ┌──────────┐  ┌─────────┐   │        │  │ Shenan-  │
老年代  │Serial  │   │   CMS    │  │Parallel │   │        │  │ doah     │
        │  Old   │   │(并发标记) │  │  Old    │   │        │  │          │
        └────────┘   └──────────┘  └─────────┘   └────────┘  └──────────┘
        JDK1.3      JDK1.5-1.8    JDK1.7-1.8     JDK7-9默认   JDK11+(ZGC实验)
```

**逐个讲「它解决了什么问题、又留下什么问题」**：

| 收集器 | 引入版本 | 解决的问题 | 遗留的问题 | 算法 |
| ---- | ---- | ---- | ---- | ---- |
| **Serial** | JDK 1.3 | 简单可靠（单核时代够用） | **全程 STW**，多核浪费 | 复制（新生代）/ 标整（老年代） |
| **ParNew** | JDK 1.3 | Serial 的**多线程版**，搭配 CMS | 仍是 STW（只是快些） | 复制 |
| **Parallel Scavenge** | JDK 1.7 | **追求吞吐量**（适合后台批处理） | 停顿时间不保证 | 复制 |
| **Serial Old** | JDK 1.3 | 老年代单线程版 | 全程 STW | 标整 |
| **Parallel Old** | JDK 1.6 | 老年代多线程版，配合 Parallel Scavenge | 停顿时间不保证 | 标整 |
| **CMS** ⭐ | JDK 1.5 | **追求低停顿**（并发标记，用户线程不咋停） | **① 碎片多 ② 并发模式失败（Concurrent Mode Failure）③ 浮动垃圾** | 标记-清除 |
| **G1** ⭐⭐ | JDK 7，**JDK 9 默认** | **分区（Region）+ 可预测停顿模型**：可指定 `MaxGCPauseMillis` | ① 仍有 STW（但可控）② 大堆下 Region 管理开销 ③ 记忆集（RSet）占内存 | 整体标整 + 局部复制 |
| **ZGC** ⭐ | JDK 11 实验，**JDK 15 转正** | **亚毫秒级停顿（<10ms）**，且停顿与堆大小无关 | 需要大内存、CPU 占用高 | **着色指针 + 读屏障** |
| **Shenandoah** | JDK 12 | 类似 ZGC 目标（低停顿） | 与 ZGC 二选一 | 转发指针 + 读屏障 |

> 💡 **一句话理解演进逻辑**：
> **Serial（单线程省事）→ Parallel（多线程提吞吐）→ CMS（并发求低停顿）→ G1（分区求可控停顿）→ ZGC（着色指针求极致低停顿）**
> 每一步都在**「吞吐量 ↔ 停顿时间 ↔ 内存占用」**这个不可能三角里找新的平衡点。

**为什么 G1 是分区（Region）的？**
- 传统分代是**物理连续**的大块内存，G1 把堆切成**约 2048 个大小相等的 Region**（1~32MB）
- 每个 Region 可以是 Eden / Survivor / Old / Humongous（大对象）
- **G1 优先回收「回收收益最高」的 Region**（Garbage First，名字来源）
- 所以 G1 能**设定目标停顿时间**——因为它是「挑着收」，不是「整代收」

### 2.4 三色标记与并发标记的问题 ⭐（拉开差距的知识点）

> **并发标记时，用户线程还在改引用，怎么保证不漏标？** ——这是 CMS/G1 的核心难题。

**三色标记法**：
- ⚪ **白色**：还没被访问（最终仍是白色 = 可回收）
- 🔘 **灰色**：自己访问过了，但引用的对象还没访问完
- ⚫ **黑色**：自己和引用的对象都访问完了

**并发时可能出现的两种错误**：

| 错误 | 场景 | 后果 |
| ---- | ---- | ---- |
| **对象消失（漏标）** | 黑色对象新增了对白色对象的引用，同时灰色对象断开了对该白色对象的引用 | **本该存活的对象被误回收 → 严重 bug** |
| **浮动垃圾** | 标记完成后，用户线程又产生了新的垃圾 | 本轮不清，等下轮（可接受） |

**解决办法——两种屏障**：

| 方案 | 做法 | 谁用 | 代价 |
| ---- | ---- | ---- | ---- |
| **增量更新（Incremental Update）** | 黑色对象**新增引用**时，把它重新变灰 | **CMS** | 需要重新扫描 |
| **原始快照（SATB, Snapshot At The Beginning）** | 灰色对象**删除引用**时，把被删的引用记下来，最后以这些为根重扫 | **G1 / Shenandoah** | 需要额外的记录空间 |

> 💡 **面试话术**：「并发标记要解决漏标问题，方案分两类——CMS 用增量更新（记新增的引用），G1 用原始快照 SATB（记删除的引用）。本质都是**在并发修改下保证「不该回收的绝不回收」，代价是可能多留一些浮动垃圾等下轮**。」

### 2.5 记忆集与卡表（跨代引用怎么找）

> **问题**：新生代 GC 时，怎么知道「老年代里有没有对象引用了我」？总不能让全老年代都扫一遍。

**解法：记忆集（Remembered Set）+ 卡表（Card Table）**

- 把老年代分成一个个 **512 字节的「卡页」（Card Page）**
- 用一个 `byte[]` 数组（卡表）标记「这张卡里有没有跨代引用」
- 新生代 GC 时，**只扫卡表里被标记的卡**，不用全扫

> 💡 **这就是典型的「用空间换时间」+「用精度换效率」**——不精确到对象，精确到「512 字节的块」就够了。

### 2.6 常用参数速查（书里给的推荐）

```bash
# ============ 通用 ============
-Xms4g -Xmx4g                    # 堆初始 = 最大（避免动态扩容抖动）
-Xmn2g                           # 新生代大小（约堆的 1/3 ~ 1/2）
-XX:MetaspaceSize=256m           # 元空间初始阈值（防动态扩容触发 Full GC）
-XX:MaxMetaspaceSize=512m        # ⚠️ 必须设上限，防类加载器泄漏吃光机器内存

# ============ G1（JDK 9+ 默认，推荐）============
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200         # 目标停顿（是目标不是保证）
-XX:G1HeapRegionSize=8m          # Region 大小（1~32MB，2 的幂）
-XX:InitiatingHeapOccupancyPercent=45   # 触发并发标记的堆占用阈值（默认 45%）

# ============ ZGC（超大堆 + 低延迟）============
-XX:+UseZGC
-XX:+ZGenerational               # JDK 21+：分代 ZGC（默认，性能更好）

# ============ GC 日志（生产必开）============
-Xlog:gc*:time,level,tags:file=gc.log:time=trace:filecount=5,filesize=100M
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/logs/dump.hprof
```

> 📌 **参数的含义与排查流程**见正文 [[02_JVM 原理与调优]]，本书只讲「为什么这么配」。
> 💡 **本书观点**：**「调优的第一步不是调参数，是开 GC 日志」**——没有日志的调优都是拍脑袋。

### 2.7 内存分配与回收的「优先级策略」（书里的完整清单）

对象分配时的决策顺序（**背这个顺序，比背算法有用**）：

```
new 一个对象
  ↓
① 逃逸分析：对象没逃逸 → 栈上分配 / 标量替换（理想情况，现实很少见）
  ↓ 逃逸了
② TLAB：在当前线程的 TLAB 里分配（无锁，快）
  ↓ TLAB 不够
③ Eden：在 Eden 分配（需要 CAS 或加锁）
  ↓ Eden 满了
④ 触发 Young GC → 活着的进 Survivor
  ↓ 大对象
⑤ 直接进老年代（-XX:PretenureSizeThreshold）
  ↓ 年龄够了 / 动态年龄判定
⑥ 晋升老年代
  ↓ 老年代满了
⑦ Full GC（最坏情况 → 甚至 OOM）
```

## 三、字节码与执行引擎：代码怎么跑起来（第 6、7 章）

### 3.1 字节码：class 文件的结构

> **一句话**：`.java` 编译成 `.class`（字节码），JVM 把字节码**解释或编译**成机器码执行。

**class 文件的组成（书里的「魔数」考点）**：

| 项 | 说明 |
| ---- | ---- |
| **魔数（Magic Number）** | 开头 4 字节固定 `CAFEBABE`（咖啡宝贝）——JVM 靠它识别「这是不是 class 文件」 |
| **版本号** | 次版本 + 主版本（如 JDK 8 = 52.0）。**「不支持的 class 版本」报错就是这里对不上** |
| **常量池** | 字面量 + 符号引用（**占 class 文件最大比例**） |
| **访问标志** | 是类还是接口、public 还是 final |
| **字段/方法表** | 字段和方法的信息 |
| **属性表** | 附加信息（如 `Code` 属性存字节码指令） |

> 💡 **实用价值**：遇到 `UnsupportedClassVersionError` 时，用 `javap -verbose Xxx.class | head` 看主版本号，就知道它编译用的是哪个 JDK。

### 3.2 解释器 vs JIT 编译器（热点代码探测）

**JVM 执行字节码的两种方式**：

| 方式 | 说明 | 优缺点 |
| ---- | ---- | ---- |
| **解释执行** | 逐条把字节码翻译成机器码 | 启动快，但持续跑慢 |
| **即时编译（JIT）** | 把**热点代码**编译成本地机器码缓存起来 | 启动慢（要编译），但跑起来快 |

**HotSpot 的「混合模式」**：
- 大部分代码解释执行（省编译开销）
- **热点代码**（方法调用次数 or 循环回边次数超阈值）→ 触发 JIT

**两个编译器（C1 / C2）**：

| 编译器 | 别名 | 优化程度 | 适用 |
| ---- | ---- | ---- | ---- |
| **C1** | Client Compiler | 轻量、快 | 启动阶段、短生命周期 |
| **C2** | Server Compiler | 激进、优化深 | 长跑的服务端 |

**分层编译（Tiered Compilation，JDK 7+ 默认）**：5 个层级，逐层加深优化
- 0 层：解释执行
- 1~3 层：C1 编译（不同优化强度）
- 4 层：C2 编译（最激进）

> 💡 **为什么分层编译是最优解**：**「先快后优」**——服务刚启动时用 C1 快速编译保证响应，等热点稳定了再用 C2 深度优化。**这就是为什么 JVM 服务「启动慢、跑久了快」。**

### 3.3 JIT 的经典优化（面试爱问）

| 优化 | 说明 | 例子 |
| ---- | ---- | ---- |
| **方法内联** | 把短方法的代码直接「贴」到调用处 | `getX()` 被内联后没有调用开销——**这是最重要的优化之一** |
| **逃逸分析** | 见 1.2 节 | 栈上分配 / 标量替换 / 锁消除 |
| **公共子表达式消除** | 重复计算的表达式只算一次 | `a*b + a*b` → `tmp=a*b; tmp+tmp` |
| **数组边界检查消除** | 能证明不越界就删掉检查 | 循环里 `for(i=0;i<arr.length;i++)` 的检查可省 |
| **分支预测** | 推测 `if` 走哪个方向 | 和 CPU 的分支预测配合 |
| **去虚拟化** | 只有一个实现时，把虚调用变直调 | 接口只有一个实现类时 |

> ⚠️ **书里的重点提醒**：**JIT 优化会导致「JVM 行为看起来反直觉」**——比如：
> - **「加了日志/B 方案就自己好了」**：代码结构变了，JIT 不优化了，**bug 被「掩盖」而非修复**
> - **压测结果不可信**：需要**预热**（让热点代码完成编译），否则测的是解释执行的性能
> - 用 `-XX:-TieredCompilation` 或 `-Xint` 可以对比、验证

### 3.4 常见源码到字节码的对照

```java
// 源码
public int add(int a, int b) {
    return a + b;
}
```

```bash
# 反编译（javap -c）后的字节码
public int add(int, int);
  Code:
     0: iload_1        # 把第 1 个 int 参数（a）压入操作数栈
     1: iload_2        # 把第 2 个 int 参数（b）压入操作数栈
     2: iadd           # 弹出两个 int，相加，结果压回栈
     3: ireturn        # 返回栈顶的 int
```

> 💡 **读字节码的价值**：理解 `i++` 和 `++i` 的区别、`String` 拼接为什么会生成 `StringBuilder`、`finally` 为什么会复制代码块——**这些「面试题」的答案都在字节码里**。

## 四、类加载机制：类是怎么进入 JVM 的（第 8~10 章）

### 4.1 类的一生（7 个阶段）

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
      └────── 连接（Linking）──────┘
```

| 阶段 | 做什么 | 关键点 |
| ---- | ---- | ---- |
| **加载** | 读 class 文件，生成 `Class` 对象 | 可通过类加载器从网络、jar、动态生成 |
| **验证** | 检查字节码是否合法、安全 | 4 个阶段：文件格式/元数据/字节码/符号引用 |
| **准备** | **为静态变量分配内存并设「零值」** | ⭐ `static int a = 5` 此时 `a = 0`，赋值在初始化阶段 |
| **解析** | 把符号引用替换成直接引用 | 可以延迟到运行时 |
| **初始化** | **执行 `<clinit>()`**（静态变量赋值 + 静态代码块） | ⭐ **「主动引用」才会触发** |

> ⚠️ **准备阶段考点的坑**：`static final int A = 5` **在准备阶段就是 5**（因为 `final` 常量在编译期就确定了）；但 `static int A = 5` 准备阶段是 0，初始化才变 5。

**6 种「主动引用」会触发初始化**（背下来）：
1. `new`、读写静态字段（**非 final**）、调用静态方法
2. `java.lang.reflect` 反射调用
3. 初始化子类时，先初始化父类
4. 虚拟机启动时的主类（`main` 方法所在类）
5. `MethodHandle` 解析结果对应的类
6. **接口的默认方法（default method）被实现类调用**（JDK 8+）

> 💡 **其余引用都是「被动引用」，不触发**——比如「通过子类引用父类的静态字段」只初始化父类、「定义数组」不初始化数组元素类、「引用常量」不初始化类。

### 4.2 双亲委派模型 ⭐⭐

**三层类加载器**：

| 加载器 | 加载什么 | 实现语言 |
| ---- | ---- | ---- |
| **启动类加载器（Bootstrap）** | `<JAVA_HOME>/lib` 下的核心库（`rt.jar` 等） | C++ |
| **扩展类加载器（Extension）** | `<JAVA_HOME>/lib/ext`（JDK 9+ 改为 Platform ClassLoader） | Java |
| **应用程序类加载器（Application）** | `classpath` 下的类（**我们自己写的类就在这里**） | Java |

**双亲委派的工作流程**：

```
收到加载请求
  ↓
① 先委派给父加载器（一路向上到 Bootstrap）
  ↓
② 父加载器尝试加载；能加载就返回
  ↓
③ 父加载器加载不了（不在它的路径里），才回到自己加载
```

```
        Bootstrap（最顶层，先试）
            ↑ 委派
        Extension
            ↑ 委派
        Application
            ↑ 委派
        自定义 ClassLoader
```

**为什么要有双亲委派？**

| 原因 | 说明 |
| ---- | ---- |
| **安全** | 防止用户自己写个 `java.lang.String` 把核心类替换掉（**否则可以注入恶意代码**） |
| **唯一性** | 同一个类只被加载一次，保证 `Class` 对象唯一（`==` 比较才成立） |
| **一致性** | 核心类库的行为在所有环境一致 |

> 💡 **打破双亲委派的经典案例**：**JDBC 用 `Thread.currentThread().getContextClassLoader()`**——因为 `DriverManager` 在 `rt.jar` 里（Bootstrap 加载），但它要加载的 `com.mysql.Driver` 在 classpath 下（Application 加载）。**父加载器看不到子加载器的类，所以用「线程上下文类加载器」绕开双亲委派。**
>
> 其他打破的例子：Tomcat（每个 webapp 一个 ClassLoader 实现隔离）、OSGi、热部署。

### 4.3 类的生命周期结束（卸载条件）

一个类被卸载，需要**同时满足**（很严格）：
1. 该类的**所有实例**都被回收
2. 加载该类的 **ClassLoader** 已被回收
3. 该类的 **`Class` 对象**没有被引用（没有反射、没有被其他地方用到）

> ⚠️ **这就是「Metaspace OOM」的根源**：如果自定义 ClassLoader 被一直引用（如静态缓存），它加载的所有类都卸不掉 → 元空间持续增长。**排查方式**：`jmap -clstats <pid>` 看类加载器统计。

## 五、编译期优化与泛型（第 10、11 章）

### 5.1 泛型：编译期的「障眼法」

> **核心认知**：**Java 泛型是「编译期的语法糖」——编译后泛型信息被擦除（类型擦除）。**

```java
// 源码
List<String> list = new ArrayList<>();
list.add("a");
String s = list.get(0);

// 编译后（擦除后）
List list = new ArrayList();
list.add("a");
String s = (String) list.get(0);   // ⭐ 编译器自动插入强转
```

**所以**：
- **泛型不能用于运行时判断**：`if (obj instanceof List<String>)` 编译不过
- **不能 `new T()`**、不能 `new T[]`（运行时不认识 T）
- **静态方法不能直接用类的泛型参数**
- **擦除导致的重载冲突**：`f(List<String>)` 和 `f(List<Integer>)` 擦除后签名一样，编译报错

> 💡 **为什么设计成擦除**：为了**兼容老版本**（JDK 5 之前没有泛型），保证 `.class` 层面不变。**这是妥协的结果**，Java 的泛型因此被称为「伪泛型」。

### 5.2 自动装箱的坑

```java
Integer a = 127, b = 127;
System.out.println(a == b);        // true（IntegerCache 缓存 -128~127）

Integer c = 128, d = 128;
System.out.println(c == d);        // false（超出缓存，new 了新对象）

// ⚠️ 经典 bug：三元表达式会自动拆箱
Integer x = null;
Integer y = true ? x : 0;          // NPE！因为要拆箱比较
```

> 💡 **规则**：**比较包装类型永远用 `equals()`，别用 `==`**。详见 [[《Effective Java》笔记]]。

## 六、高效并发：JMM 与线程安全（第 12 章）

> 正文 [[03_JUC 详细讲解]] 已详细讲 JUC 工具类，这里补充**书里的底层原理**。

### 6.1 Java 内存模型（JMM）三大特性

| 特性 | 含义 | 保证手段 |
| ---- | ---- | ---- |
| **原子性** | 操作不可中断 | `synchronized` / `Lock` / 原子类 |
| **可见性** | 一个线程改了，另一个能立刻看到 | `volatile` / `synchronized` / `final` |
| **有序性** | 禁止指令重排导致的乱序 | `volatile` / `synchronized` / happens-before |

### 6.2 volatile 的两层语义 ⭐

```java
volatile boolean flag = false;
```

| 语义 | 说明 |
| ---- | ---- |
| **可见性** | 写 `volatile` 变量后，**立刻刷回主内存**；读之前**先从主内存刷新** |
| **禁止重排** | 通过**内存屏障（Memory Barrier）**禁止指令重排 |

**内存屏障的四种**（书里的细节）：

| 屏障 | 作用 |
| ---- | ---- |
| **LoadLoad** | 读读有序 |
| **StoreStore** | 写写有序 |
| **LoadStore** | 读写有序 |
| **StoreLoad** | 写读有序（**开销最大，volatile 写后必插**） |

> ⚠️ **`volatile` 保证可见性和有序性，但【不保证原子性】**——`volatile int i; i++;` 依然有并发问题（因为 `i++` 是「读-改-写」三步）。

### 6.3 happens-before 规则（书里列了 8 条）

| 规则 | 说明 |
| ---- | ---- |
| **程序顺序规则** | 同一线程内，前面的操作 happens-before 后面的 |
| **监视器锁规则** | 解锁 happens-before 后续的加锁 |
| **volatile 变量规则** | volatile 写 happens-before 后续的 volatile 读 |
| **传递性** | A→B，B→C，则 A→C |
| **start() 规则** | 线程 A 调用 B.start()，A 之前的操作对 B 可见 |
| **join() 规则** | B.join() 返回后，B 的所有操作对 A 可见 |
| **中断规则** | interrupt() happens-before 被中断线程检测到中断 |
| **finalize() 规则** | 对象初始化完成 happens-before finalize() 开始 |

> 💡 **happens-before 是「判断有没有并发 bug」的推理工具**：如果两个操作之间**没有** happens-before 关系，且它们访问同一共享变量、至少有一个是写——那就**存在数据竞争**。

### 6.4 锁优化（书里的「锁升级」细节）

**synchronized 的锁状态演进**：

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
       （一个线程）（CAS 自旋）（OS 互斥量）
```

| 锁状态 | 适用场景 | 开销 |
| ---- | ---- | ---- |
| **偏向锁** | 只有一个线程反复进入 | 几乎零开销（记个线程 ID） |
| **轻量级锁** | 少量线程交替进入 | CAS 自旋 |
| **重量级锁** | 多线程激烈竞争 | 系统调用，阻塞（开销大） |

> ⚠️ **重要更新**：**JDK 15 起偏向锁已被默认禁用（JEP 374）**，JDK 18 彻底移除。原因是它维护成本高、在无竞争场景收益已被其他优化覆盖。**面试时知道这个变化会加分。**

> 📌 **锁竞争的线上排查方法**（`jstack` 同地址配对法）见 [[03_JUC 详细讲解]]。

## 七、性能调优与故障诊断（第 4、5 章 + 附录）

> **书里的核心方法论：先看数据，再下结论。** 正文 [[02_JVM 原理与调优]] 已给排查流程，这里补充**书里的工具体系**。

### 7.1 命令行工具矩阵

| 工具 | 用途 | 一句话 |
| ---- | ---- | ---- |
| `jps` | 列出 Java 进程 | 「有哪些 Java 在跑」 |
| `jstat` | 统计 GC / 类加载信息 | 「GC 有多频繁」 |

```bash
# jcmd 是书里推荐的「新一代瑞士军刀」

jcmd <pid> VM.system_properties        # 看系统属性

```

### 7.2 可视化工具

| 工具 | 用途 |
| ---- | ---- |
| **JConsole** | 入门级监控（线程、内存、GC） |
| **VisualVM** | 功能更强的图形化（可装插件） |
| **JMC（Java Mission Control）** | **生产级低开销采样**（配合 JFR） |
| **JFR（Java Flight Recorder）** | **飞行记录仪**——低开销记录 JVM 所有事件 |
| **MAT（Memory Analyzer）** | **分析 dump 的王者** |

```bash
# JFR：书里最推荐的「生产可用」诊断方式（开销约 1~2%）
-XX:StartFlightRecording=duration=60s,filename=app.jfr,settings=profile
# 或运行时开启
jcmd <pid> JFR.start duration=60s filename=app.jfr
```

### 7.3 MAT 分析 dump 的四步法

1. **看 Leak Suspects（泄漏嫌疑报告）**——MAT 直接给你结论
2. **看 Dominator Tree（支配树）**——谁占内存最多
3. **看 Histogram（直方图）**——哪个类的对象最多
4. **看 Path to GC Roots**——这个对象为什么没被回收（谁引用着它）

> 💡 **书里的黄金经验**：**「找泄漏的关键不是「谁大」，而是「谁在持续增长」」**。所以**要抓两个时间点的 dump 做对比（Delta）**，而不是只看一次。

## 八、常见 OOM / 报错速查（书里的诊断表）

| 报错 | 原因 | 排查方向 |
| ---- | ---- | ---- |
| `Java heap space` | 堆内存不足 | 内存泄漏 / 大对象 / 堆设置过小 |
| `GC overhead limit exceeded` | GC 花了 98% 时间却回收不到 2% | 几乎全是内存泄漏 |
| `Metaspace` / `PermGen space` | 元空间不足 | 类加载器泄漏 / 动态代理太多 / `MaxMetaspaceSize` 太小 |
| `Direct buffer memory` | 堆外直接内存不足 | NIO / Netty 的 `ByteBuf` 未释放 |
| `unable to create new native thread` | 创建线程失败 | 线程数超限 / 栈内存 `-Xss` 太大 / 系统 ulimit |
| `StackOverflowError` | 栈溢出（不是 OOM） | 递归没有出口 / 栈帧太大 |
| `OutOfMemoryError: Requested array size exceeds VM limit` | 数组申请过大 | 数值计算溢出 |
| `Killed`（无 Java 异常） | **被容器 OOMKilled** | JVM 堆 + 堆外 > 容器限制（见正文容器化坑） |

## 九、一句话总结 & 全书地图

> **「JVM 的所有设计，都是在吞吐量、停顿时间、内存占用这不可能三角里做取舍。」**

### 五个核心认知

1. **内存分代是为了「因地制宜」**——新生代多复制、老年代多整理
2. **收集器的演进 = 从「省事」到「求吞吐」到「求低停顿」**——每一步都在找新平衡
3. **「JVM 内存模型」和「JMM」是两件事**——一个是物理布局，一个是并发规范
4. **JIT 让 JVM「越跑越快」，也让 bug「时有时无」**——理解优化才能理解诡异现象
5. **调优靠数据不靠猜**——先开 GC 日志，再看 JFR，最后才动参数
