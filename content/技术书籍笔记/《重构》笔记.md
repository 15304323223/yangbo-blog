# 《重构》笔记（Refactoring）

> **一句话概括**：**在不改变外部行为的前提下，小步、安全地改善代码结构**——重构不是「重写」，是**「每次改动都顺手把结构弄好一点」**。
>
> **适合谁**：接手过「不敢动」的老代码、想加功能但发现结构不允许、被「改一处崩三处」折磨过的人。
> **与《代码整洁之道》的关系**：**两本互为表里**——[[《代码整洁之道》笔记]] 讲「什么是好代码」，本书讲「**怎么把坏代码改过去**」。
> **怎么读**：**核心是三样东西——① 什么是「坏味道」② 对应什么手法 ③ 怎么用测试保住安全**。第 2 章「坏味道」是全书的目录，**先看它**。

---

## 零、先建立整体印象：重构就是「边开车边修车」

> 书里最重要的隐喻：**重构不是「停车大修」，而是「行驶中换轮胎」**——你必须保证车一直在跑（行为不变），同时把零件换新。

用一个贯穿全文的场景——**整理一间乱糟糟的储物间**：

| 整理储物间 | 对应重构 | 一句话 |
|---|---|---|
| **看见一坨杂物** | 识别坏味道 | 先知道「哪里不对」 |
| **把同类东西归到一个箱子** | 抽取方法/类 | 让相关的东西待在一起 |
| **给箱子贴标签** | 重命名 | 起个好名字，一眼知道里面是什么 |
| **两步挪一个箱子** | 小步重构 | 每次只改一点，随时可停 |
| **挪之前先拍照** | 写测试 | 有测试才敢动手 |
| **搬完检查一遍** | 跑测试 | 行为没变才算成功 |

**三条铁律**：

1. **行为不变**——重构**绝不**改变「代码做什么」，只改「代码长什么样」
2. **小步前进**——一次只做一个小改动，每步都跑测试，随时可以停
3. **测试是前提**——**没有测试的重构 = 赌博**（这是书里反复强调的第一原则）

## 一、重构的核心心法

### 1.1 为什么要重构（书里的四个理由）

| 理由 | 说明 |
| ---- | ---- |
| **① 改进设计** | 代码会「腐烂」——改需求时随手打的补丁会让结构越来越烂，重构是「反腐烂」 |
| **② 让代码更好懂** | 读代码的时间远超写代码，**让代码好懂 = 提高整个团队效率** |
| **③ 帮助找 bug** | 重构过程中会更深入理解代码，**很多 bug 是在重构时「顺手发现」的** |
| **④ 提高开发速度** | 结构好的代码加功能更快——**重构不是拖慢进度，是给未来加速** |

### 1.2 什么时候该重构 / 什么时候不该

| ✅ 该重构 | ❌ 不该重构 |
| ---- | ---- |
| **加新功能之前**（先整理再添加） | **代码根本不能跑**（先修 bug） |
| **修 bug 的时候**（顺手清理） | **临近交付 deadline**（这时候改风险大） |
| **code review 时发现坏味道** | **没有测试保护**（先补测试） |
| **理解代码时的「顺手改善」** | **推倒重写更快时**（重构 ≠ 重写） |

> 💡 **书里的经典提醒**：**「三次法则」**——第一次做某件事直接做；第二次做类似的事会皱眉但照做；**第三次再做类似的事，就该重构了**。

### 1.3 重构与「重写」的区别（很重要）

| | 重构 | 重写 |
| ---- | ---- | ---- |
| **行为** | 保持不变 | 可能改变（甚至从零设计） |
| **风险** | 低（小步 + 测试） | 高（一次性大改） |
| **时间** | 持续穿插在日常开发中 | 一次性大投入 |
| **结果** | 结构逐步改善 | 全部推倒重来 |

> ⚠️ **书里的警告**：**「重写往往是灾难的开始」**——因为老代码里藏着大量「不知道为什么这么写」的业务规则，重写时会全部丢掉。**能用重构解决的，别重写。**

## 二、坏味道（Bad Smells）：全书的目录 ⭐⭐

> **「坏味道」= 代码里让你皱眉的信号**——它不一定是 bug，但往往预示着「以后会出问题」。**这一节是全书的索引，**看到坏味道就翻到对应手法。

### 2.1 24 种坏味道速查表（按出现频率排序）

| # | 坏味道 | 症状 | 对应手法 |
| ---- | ---- | ---- | ---- |
| 1 | **神秘命名** | `data`、`temp`、`handle`、`aaa` | 重命名 |
| 2 | **重复代码** ⭐⭐ | 同样的逻辑出现 2 次以上 | 抽取方法/父类/工具类 |
| 3 | **过长函数** ⭐⭐ | 超过一屏 | 抽取方法、以查询取代临时变量 |
| 4 | **过长参数列表** | 参数 > 3 个 | 引入参数对象、保持对象完整 |
| 5 | **全局数据** | 到处能改的 static 变量 | 封装成类、依赖注入 |
| 6 | **可变数据** | 到处被改的字段 | 拆分变量、消除设值方法 |
| 7 | **发散式变化** | 一个类因为多个原因被改 | 拆类（单一职责） |
| 8 | **霰弹式修改** | 改一个功能要改 N 个类 | 内联、搬移 |
| 9 | **依恋情结** | 方法总访问别的类的数据 | 搬移方法/字段 |
| 10 | **数据泥团** | 几个参数总一起出现 | 抽成对象 |
| 11 | **基本类型偏执** | 用 `String` 表示钱、用 `int` 表示状态 | 引入值对象、枚举 |
| 12 | **重复的 switch** | 同一个 switch 出现在多处 | 多态替代 |
| 13 | **循环语句** | 到处是 for 循环 | 管道替代（Stream） |
| 14 | **冗赘的元素** | 没用的类、方法、参数 | 内联、移除 |
| 15 | **夸夸其谈通用性** | 「以后可能用得到」的抽象 | 折叠层级、内联 |
| 16 | **临时字段** | 只有某些情况下才用的字段 | 引入局部变量、抽类 |
| 17 | **过长的消息链** | `a.getB().getC().getD().getE()` | 隐藏委托、抽取方法 |
| 18 | **中间人** | 类只做转发，没别的功能 | 移除中间人、内联 |
| 19 | **内幕交易** | 两个类私下大量交换数据 | 搬移、隐藏委托 |
| 20 | **过大的类** | 一个类什么都管 | 拆类 |
| 21 | **异曲同工的类** | 两个类做类似的事 | 重构签名、抽取父类 |
| 22 | **纯数据类** | 只有字段和 getter/setter | 把行为搬进来 |
| 23 | **被拒绝的遗赠** | 子类用不到父类的部分方法 | 委托替代继承 |
| 24 | **注释** | 注释太多，是在替烂代码还债 | 用重构替代注释 |

> 💡 **最该先治的三种**：**重复代码、过长函数、神秘命名**——它们出现频率最高、收益最大。

### 2.2 坏味道的「病因」分类（书里的深层逻辑）

| 病的根源 | 对应坏味道 |
| ---- | ---- |
| **代码「长得像」但「意思不同」** | 重复代码（最危险的重复） |
| **代码「意思相同」但「长得不同」** | 异曲同工的类 |
| **改一个东西要改很多地方** | 霰弹式修改、重复 switch |
| **很多东西挤在一起** | 过大的类、过长函数、数据泥团 |
| **该在一起的分开了 / 该分开的挤一起** | 依恋情结、内幕交易、中间人 |
| **多余的东西** | 冗赘的元素、夸夸其谈通用性 |

## 三、重构手法分类（书里的「工具箱」）

> 书里收录了 **60+ 种手法**，按类型分组。这里**只列最常用的**，够日常用。

### 3.1 最常用的 6 组手法

#### ① 提炼（把「一块」变成「一个函数/类」）

| 手法 | 怎么用 | 什么时候用 |
| ---- | ---- | ---- |
| **提炼函数** ⭐⭐ | 把一段代码抽成方法 | 函数太长、有注释分隔的块、想加注释解释 |
| **提炼变量** | `if (o.beenDelinquent() && o.isVeteran())` → 抽成变量 | 表达式太长看不懂 |
| **提炼类** | 把一堆相关字段和方法搬去新类 | 类太大、某个字段只被少数方法用 |
| **内联函数** | 函数体比函数名还清楚时，删掉函数 | 函数调用没带来价值 |

```java
// ❌ 重构前
public void printOwing() {
    // 打印横幅
    System.out.println("***********************");
    System.out.println("**** 客户欠款明细 ****");
    System.out.println("***********************");

    // 计算欠款
    double outstanding = 0.0;
    for (Order o : orders) {
        outstanding += o.getAmount();
    }

    // 打印明细
    System.out.println("客户名：" + name);
    System.out.println("欠款额：" + outstanding);
}
```

```java
// ✅ 重构后：每段被「提炼」，主函数成了「目录」
public void printOwing() {
    printBanner();
    double outstanding = getOutstanding();
    printDetails(outstanding);
}

private void printBanner() {
    System.out.println("***********************");
    System.out.println("**** 客户欠款明细 ****");
    System.out.println("***********************");
}

private double getOutstanding() {
    return orders.stream().mapToDouble(Order::getAmount).sum();
}

private void printDetails(double outstanding) {
    System.out.println("客户名：" + name);
    System.out.println("欠款额：" + outstanding);
}
```

> 💡 **注意**：原文有 3 处注释（「打印横幅」「计算欠款」「打印明细」）——**这三处注释正好对应三个方法的「该叫什么名字」**。**注释是「该提炼函数」的强烈信号**。

#### ② 搬移（把东西放到该在的地方）

| 手法 | 说明 |
| ---- | ---- |
| **搬移函数** | 方法用的数据在别的类？搬过去 |
| **搬移字段** | 字段被别的类用得更多？搬过去 |
| **内联类 / 隐藏委托** | 中间人类没用？合并掉 |

#### ③ 重组数据

| 手法 | 说明 |
| ---- | ---- |
| **以对象取代基本类型** ⭐ | `String phone` → `PhoneNumber` 值对象 |
| **以查询取代临时变量** | 把「算出来存起来」的变量变成方法 |
| **引入参数对象** | 3+ 参数一起出现 → 抽对象 |
| **类取代类型码** | `int status` → `enum` / 状态类 |

```java
// ❌ 重构前：基本类型偏执
public class Order {
    private String status;          // "PAID" / "UNPAID" / "CANCELLED"，靠字符串约定
    private int amountCents;        // 用 int 表示钱（单位靠脑子记）
}

// ✅ 重构后：用值对象 + 枚举把「约定」变成「类型」
public enum OrderStatus {
    UNPAID, PAID, CANCELLED;

    public boolean isPayable() { return this == UNPAID; }
}

public class Order {
    private OrderStatus status;         // 编译期就能检查
    private Money amount;               // 自带单位，不会算错

    public boolean canPay() { return status.isPayable(); }
}
```

#### ④ 简化条件表达式 ⭐

| 手法 | 说明 |
| ---- | ---- |
| **分解条件表达式** | 复杂 `if` 的条件抽成方法 |
| **卫语句替代嵌套条件** ⭐ | 提前返回，减少嵌套层数 |
| **以多态取代条件表达式** ⭐ | switch/if-else 链 → 多态 |
| **合并条件表达式** | 多个 `if` 结果相同 → 合并 |
| **引入特例（Null Object）** | 用空对象替代 `null` 判断 |

```java
// ❌ 重构前：嵌套地狱
public double getPayAmount(Employee e) {
    double result;
    if (e.isSeparated()) {
        result = separatedAmount();
    } else {
        if (e.isRetired()) {
            result = retiredAmount();
        } else {
            if (e.isDead()) {
                result = deadAmount();
            } else {
                result = normalPayAmount();
            }
        }
    }
    return result;
}
```

```java
// ✅ 重构后：卫语句提前返回，一眼看清
public double getPayAmount(Employee e) {
    if (e.isDead()) return deadAmount();
    if (e.isSeparated()) return separatedAmount();
    if (e.isRetired()) return retiredAmount();
    return normalPayAmount();
}
```

#### ⑤ 重构 API

| 手法 | 说明 |
| ---- | ---- |
| **函数改名 / 移除参数 / 添加参数** | 让签名更清晰 |
| **以查询取代命令 / 以命令取代查询** | 有副作用的用 setXxx，无副作用的用 getXxx |
| **保持对象完整** | 传整个对象而不是拆散的几个字段 |
| **移除设值方法** | 让对象不可变（创建后不可改） |

```java
// ❌ 重构前：查询函数改名看不出「有副作用」——而且参数拆得太多
// 备注：此函数还会记录日志并增加计数器
public BigDecimal calc(Order o, String code, boolean flag) { ... }

// ✅ 重构后：签名+命名让行为更显式
public BigDecimal calculateDiscount(Order order, Coupon coupon) { ... }
```

> 💡 **注意原注释「此函数还会记录日志并增加计数器」**——**一个「算折扣」的函数不该有降低库存/记日志的副作用**。这正是应该「分离命令与查询」的信号。

#### ⑥ 处理继承

| 手法 | 说明 |
| ---- | ---- |
| **函数上移 / 字段上移** | 共同点抽到父类 |
| **函数下移 / 字段下移** | 只有子类用 → 移到子类 |
| **以委托取代继承** ⭐ | 继承了但「用不到」，改委托 |

```java
// ❌ 重构前：「继承一个 Stack 只是为了复用方法」
public class Stack<T> extends ArrayList<T> {     // 「被拒绝的遗赠」
    public void push(T e) { add(e); }
    public T pop() { return remove(size() - 1); }
    // 问题：ArrayList 的 get(0)、remove(0)、addAll... 全都暴露了，破坏了栈的语义
}

// ✅ 重构后：用委托——只暴露该暴露的
public class Stack<T> {
    private final Deque<T> elements = new ArrayDeque<>();

    public void push(T e) { elements.push(e); }
    public T pop() { return elements.pop(); }
    public boolean isEmpty() { return elements.isEmpty(); }
}
```

> ⚠️ **书里的原则**：**「优先使用组合，而非继承」**——继承是「最强耦合」，只有真的是「is-a」且「所有父类方法都用得上」才用继承。

## 四、Java 实战：一次完整的重构演练

### 场景：订单结算服务（真实项目常见）

```java
// ❌ 重构前：坏味道全都有
public class OrderService {

    public Map<String, Object> settle(Long orderId, String userType, boolean isVip, String couponCode) {
        // 1. 查订单
        Order o = jdbcTemplate.queryForObject("select * from orders where id = ?", Order.class, orderId);
        // 2. 算原价
        double total = 0;
        for (OrderItem it : o.getItems()) {
            total += it.getPrice() * it.getQty();
        }
        // 3. 会员折扣
        if ("USER".equals(userType)) {
            if (isVip) {
                total = total * 0.8;
            } else {
                total = total * 0.95;
            }
        } else if ("MERCHANT".equals(userType)) {
            total = total * 0.6;
        }
        // 4. 优惠券
        if (couponCode != null && !couponCode.isEmpty()) {
            if (couponCode.startsWith("MAN")) {
                total = total >= 200 ? total - 50 : total;
            } else if (couponCode.startsWith("ZHE")) {
                total = total * 0.9;
            }
        }
        // 5. 返回
        Map<String, Object> r = new HashMap<>();
        r.put("code", 200);
        r.put("total", total);
        return r;
    }
}
```

**坏味道清单**：

| 坏味道 | 位置 |
| ---- | ---- |
| **过长函数** | 整个 `settle` 一个方法 40 行 |
| **过长参数列表** | 4 个参数（`userType`/`isVip`/`couponCode` 总一起出现） |
| **嵌套条件** | 会员折扣 + 优惠券双层 if |
| **基本类型偏执** | `String userType`、`double total`（钱用 double！） |
| **重复 switch** | 折扣逻辑以后别处也要用 |
| **注释替代方法** | `// 1. 查订单` 等注释 = 该提炼 5 个方法 |

```java
// ✅ 重构后：职责分离，每层都干净

// ① 参数对象（替代过长参数列表）
public record SettleCommand(Long orderId, UserType userType, boolean vip, String couponCode) {}

// ② 值对象（替代基本类型偏执）
public record Money(BigDecimal cents) {
    public Money multiply(BigDecimal rate) {
        return new Money(cents.multiply(rate).setScale(0, RoundingMode.HALF_UP));
    }
}

// ③ 折扣策略（替代嵌套 if + 多态）
public interface DiscountPolicy {
    Money apply(Money amount, SettleCommand cmd);
}

@Service
@RequiredArgsConstructor
public class OrderSettleService {
    private final OrderRepository orderRepository;
    private final List<DiscountPolicy> policies;      // 所有折扣策略（Spring 自动注入）

    /** 主流程——读起来像目录 */
    public SettleResult settle(SettleCommand cmd) {
        Order order = loadOrder(cmd.orderId());
        Money original = calculateOriginalPrice(order);
        Money finalPrice = applyDiscounts(original, cmd);
        return SettleResult.success(finalPrice);
    }

    private Order loadOrder(Long orderId) {
        Order order = orderRepository.findById(orderId);
        if (order == null) throw new BizException(ErrorCode.ORDER_NOT_FOUND);
        return order;
    }

    private Money calculateOriginalPrice(Order order) {
        return order.getItems().stream()
                .map(item -> item.getPrice().multiply(BigDecimal.valueOf(item.getQty())))
                .reduce(Money.ZERO, Money::add);
    }

    private Money applyDiscounts(Money original, SettleCommand cmd) {
        Money result = original;
        for (DiscountPolicy policy : policies) {    // 加新折扣只需新增一个策略类
            result = policy.apply(result, cmd);
        }
        return result;
    }
}
```

> 💡 **收益对比**：
> - 加一种新折扣 → **只写一个新策略类**，不用改 `settle`
> - 金额用 `Money` 值对象 → **不会出现浮点误差**
> - 每个方法都能单独测
> - 主流程 5 行读完

## 五、重构的安全网：测试 ⭐⭐

> **书里反复强调的第一原则**：**「重构的第一步是确保有一组可靠的测试。」**

### 5.1 为什么测试是前提

```
没有测试 → 改代码 → 不知道有没有改坏 → 不敢改 → 代码越来越烂
有测试   → 改代码 → 立刻知道有没有改坏 → 敢改 → 代码持续改善
```

### 5.2 重构时的测试策略

| 策略 | 说明 |
| ---- | ---- |
| **小步跑测试** | **每做一个手法就跑一次**（不是攒到最后跑） |
| **先补测试** | 要重构的代码没测试？**先写测试锁住当前行为**（哪怕是错的） |
| **测试要快** | 慢测试会让你懒得跑（见 F.I.R.S.T.） |
| **别改测试的期望值** | 重构**不改行为**，所以**测试应该一直绿**。红了 = 重构改坏了 |

> ⚠️ **一个关键认知**：**「测试锁住的是当前行为，不是正确行为」**——如果代码当前行为就是错的，那就先写个测试锁住这个「错」，重构完结构后再单独修 bug。**重构和修 bug 要分开做。**

---

## 六、重构的「工作流」（书里推荐的做法）

### 6.1 标准节奏

```
① 确定要重构的「坏味道」
      ↓
② 跑一遍测试，确认现在是「绿的」
      ↓
③ 做一个小手法（比如「提炼函数」）
      ↓
④ 立刻跑测试 → 绿？继续；红？撤销重来
      ↓
⑤ 提交（每次手法成功就 commit，方便回滚）
      ↓
⑥ 回到 ③，直到满意
```

> 💡 **「每次成功手法就提交」很重要**——重构过程中如果搞乱了，可以直接 `git reset --hard` 回到上一个干净点，**不用从头来**。

### 6.2 与日常开发的结合

| 时机 | 做法 |
| ---- | ---- |
| **加新功能前** | 先看看要改的地方结构好不好，不好就先重构（**「两顶帽子」**：先戴重构帽，再戴加功能帽） |
| **修 bug 前** | 先重构到「bug 变得显而易见」，再修 |
| **code review 后** | 把 review 提的问题顺手重构掉 |
| **每天下班前 15 分钟** | 挑一个最臭的函数重构 |

> 💡 **书里最重要的一个概念——「两顶帽子」**：
> **重构时只戴「重构帽」**（只改结构，不加功能）；
> **加功能时只戴「加功能帽」**（只加行为，不改结构）。
> **千万别同时戴两顶帽子**——那会让你分不清「是重构改坏了，还是新功能有 bug」。

## 七、一句话总结 & 全书地图

> **「重构是让代码在『行为不变』的前提下，持续变好的纪律。」**

### 五个核心认知

1. **重构 ≠ 重写**——小步改，行为不变，风险低
2. **写测试是重构的前提**——没有测试的重构是赌博
3. **「坏味道」是重构的索引**——看到味道就翻手法
4. **「两顶帽子」不能同时戴**——重构和加功能分开做
5. **重构是持续动作**——不是项目末期的大工程，是每天的顺手
