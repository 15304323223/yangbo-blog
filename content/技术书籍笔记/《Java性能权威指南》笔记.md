# 《Java 性能权威指南》笔记

> **一句话概括**：**性能不是「玄学」，是「测量」**——这本书教你**从 JVM 到 OS 到数据库，一层层找出真正的瓶颈**，而不是凭感觉调参数。
>
> **和已有笔记的分工**：
> - [[《深入理解Java虚拟机》笔记]] = **原理**（为什么这样设计）
> - [[02_JVM 原理与调优]] = **实战手册**（参数怎么配）
> - **本篇** = **性能方法论**（怎么测、怎么定位、怎么系统化调优）
>
> **适合谁**：压测数字看不懂、调优靠猜、只会加内存加机器的后端开发者。
> **本书的核心态度**：**「过早优化是万恶之源」——先测量，再优化；不测量就调优，等于闭眼开车。**

## 零、先建立整体印象：性能调优的「五层排查法」

> 书里最重要的方法论：**性能问题的答案，永远藏在「哪一层」**——不搞清楚在哪一层，调什么都是碰运气。

用**「一家餐厅出餐慢」**类比：

| 餐厅里的问题 | 对应技术层 | 排查工具 |
|---|---|---|
| **厨房只有 1 个厨师** | CPU / 线程 | `top`、`jstack`、火焰图 |
| **备菜台太小，厨师抢着用** | 内存 / GC | GC 日志、`jstat`、JFR |
| **点菜单传得慢** | 网络 / IO | `tcpdump`、`ss`、链路监控 |
| **冰箱只有一把钥匙** | 锁竞争 | `jstack`、JFR |
| **隔壁桌的菜要先上** | 数据库 / 外部依赖 | 慢 SQL 日志、APM |

**核心方法论（本书反复强调的）**：

```
① 明确目标（要优化什么指标：吞吐量？延迟？内存？）
      ↓
② 建立基线（优化前先测一次，不然怎么知道优化有效？）
      ↓
③ 找到瓶颈（用工具量出来，不是猜）
      ↓
④ 只改一个变量（改完再测，才知道是不是它起的作用）
      ↓
⑤ 验证并记录（优化前后对比，写进文档）
```

> ⚠️ **书里最反直觉的话**：**「大多数性能问题都和 GC 无关」**——人们总觉得慢就是 GC，但实际上**慢 SQL、锁竞争、网络往返**才是最常见的元凶。

## 一、性能调优的「三条铁律」

### 1.1 铁律一：先测量，再优化

> **书里的原话**：*"不测量就优化，是最常见的错误。"*

| ❌ 错误做法 | ✅ 正确做法 |
| ---- | ---- |
| 「JVM 慢？加大堆内存」 | 先看 GC 日志，确认是不是 GC 问题 |
| 「接口慢？加缓存」 | 先用 APM 看慢在哪个环节 |
| 「压测 QPS 低？加线程」 | 先看是 CPU 瓶颈还是 IO 瓶颈 |
| 「凭经验把 `-Xmx` 调大」 | 先看堆实际用多少 |

### 1.2 铁律二：只改一个变量

> **书里的实验方法**：**「优化是一个受控实验」**——一次只改一个东西，改完测，才知道是不是它起的作用。**同时改 5 个参数，你永远不知道哪个有效。**

### 1.3 铁律三：别过早优化

> **引用 Knuth 的名言**：*"过早优化是万恶之源。"*
> - **正确顺序**：**先做对（correctness）→ 再做快（performance）**
> - **只优化「真正的热点」**——80% 的时间花在 20% 的代码上
> - **别为了「可能快 1ms」牺牲可读性**

## 二、JIT 编译：性能的第一道门（第 4 章）

### 2.1 为什么需要「预热」⭐

> **这是压测最容易踩的坑**：**没预热的压测结果毫无意义。**

```
服务刚启动 → 代码「解释执行」→ 慢
      ↓ 跑了一段时间（热点代码被 JIT 编译）
      ↓ 代码「编译执行」→ 快
```

**分层编译的五个层级**：

| 层级 | 编译方式 | 特点 |
| ---- | ---- | ---- |
| 0 层 | 解释执行 | 启动快，跑得慢 |
| 1~3 层 | C1 编译 | 轻量优化，快 |
| 4 层 | C2 编译 | 深度优化，最慢编译但跑最快 |

> 💡 **实践含义**：
> - **压测前必须预热**（跑几分钟让热点代码升到 C2）
> - **服务启动阶段慢是正常的**（在解释/C1 阶段）
> - **`-XX:TieredStopAtLevel=1`** 可加快启动（适合短生命周期应用）

### 2.2 JIT 的「诡异现象」——性能反直觉

| 现象 | 原因 |
| ---- | ---- |
| **「加了日志就好了」** | 代码结构变了，JIT 不再做某个激进优化，bug 被「掩盖」 |
| **「压测第一分钟慢，后面快」** | 预热不够，还没到 C2 |
| **「同一个方法，有时候快有时候慢」** | JIT **去优化（Deoptimization）**——优化被撤销后重新解释 |
| **「线上和本地表现不一样」** | 机器 CPU/内存不同，JIT 优化决策不同 |

### 2.3 关键参数

```bash
-XX:+PrintCompilation              # 打印编译日志（看哪些方法被编译了）
-XX:ReservedCodeCacheSize=256m     # 代码缓存大小（太小会停止编译！）
-XX:+TieredCompilation             # 分层编译（默认开）
-XX:TieredStopAtLevel=1            # 只到 C1（加快启动，牺牲峰值性能）
--XX:-TieredCompilation            # 关闭分层（对比测试用）
-Xint                              # 纯解释执行（定位「是不是 JIT 的锅」）
```

> 💡 **调试技巧**：**性能诡异时，加 `-Xint` 跑一遍**——如果加了 `-Xint` 反而「正常」了，说明是 JIT 优化引起的问题。

## 三、垃圾回收：性能的主要战场（第 5、6 章）

### 3.1 评估 GC 的三个指标

| 指标 | 含义 | 影响 |
| ---- | ---- | ---- |
| **吞吐量（Throughput）** | 用户代码执行时间 / 总时间 | 影响单位时间处理量 |
| **延迟（Latency）** | 单次 GC 停顿时间 | 影响单请求响应时间（**最影响用户体验**） |
| **内存占用（Footprint）** | GC 本身消耗的内存 | 影响服务器成本 |

> ⚠️ **不可能三角**：**这三者不能同时最优**。追求低延迟就要牺牲吞吐量（如 CMS/ZGC），追求高吞吐就要忍受长停顿（如 Parallel）。

### 3.2 收集器选型（书里的决策表）

| 场景 | 推荐收集器 | 理由 |
| ---- | ---- | ---- |
| **小型应用 / 容器（< 4G）** | G1（默认） | 均衡 |
| **批处理 / 后台任务** | Parallel | 追吞吐量，停顿不重要 |
| **大堆 + 低延迟（Web 服务）** | G1 | 可预测停顿 |
| **超大堆 + 极致低延迟** | ZGC | 亚毫秒停顿，与堆大小无关 |
| **老代码 / JDK 8** | CMS（若还在用） | 已被 G1 取代 |

> 📌 **收集器的原理与演进**见 [[《深入理解Java虚拟机》笔记]]；**参数模板**见 [[02_JVM 原理与调优]]。

### 3.3 「堆大小该设多少」——书里的答案

> **书里的方法论**：**「不要猜，用数据算。」**

```
① 先确定最大堆（-Xmx）
      ↓
② 观察 Full GC 后的「存活对象」大小
      ↓
③ 老年代应该至少是「存活对象大小」的 1.5~2 倍
      ↓
④ 新生代 = 堆的 1/3 ~ 1/2
      ↓
⑤ 目标：Full GC 越少越好（理想是几乎没有）
```

| 参数 | 建议 | 理由 |
| ---- | ---- | ---- |
| `-Xms` = `-Xmx` | **一定相等** | 避免运行时扩容抖动 |
| `-Xmn` | 堆的 1/3 ~ 1/2 | 太小 YGC 频繁，太大老年代被挤 |
| `-XX:SurvivorRatio` | 默认 8（Eden:S0:S1 = 8:1:1） | 一般不动 |
| `-XX:MaxTenuringThreshold` | 默认 15 | 一般不动 |

### 3.4 GC 问题速查

| 症状 | 可能原因 | 排查/解决 |
| ---- | ---- | ---- |
| **Young GC 频繁** | 新生代太小 / 对象创建太快 | 加大新生代 / 找「大量临时对象」 |
| **Full GC 频繁** | 老年代不足 / 内存泄漏 / 元空间扩容 | 加大老年代 / 抓 dump 找泄漏 / `MetaspaceSize` |
| **单次 STW 很长** | 堆太大 / 收集器不合适 | 换 G1/ZGC / 减小堆 |
| **并发模式失败（CMS）** | 老年代增长快于 GC 速度 | 提高 `CMSInitiatingOccupancyFraction` / 换 G1 |
| **`GC overhead limit exceeded`** | GC 花了 98% 时间只回收 2% | 内存泄漏，抓 dump |

## 四、堆内存分析：找出「谁在吃内存」（第 7 章）

### 4.1 堆分析的标准流程

```bash
# 第 1 步：观察（不侵入）
jstat -gcutil <pid> 1s 1000     # 每秒一次，共 1000 次——看 GC 频率和堆增长趋势
jcmd <pid> GC.heap_info         # 各区占用

# 第 2 步：抓两次 dump（关键！）
jcmd <pid> GC.heap_dump /tmp/heap1.hprof
# ... 等 10~30 分钟（让泄漏更明显）
jcmd <pid> GC.heap_dump /tmp/heap2.hprof

# 第 3 步：MAT 对比分析
#   → 打开两个 dump，用「Compare Basket」对比
#   → 看哪个类的对象「持续增长」← 这才是泄漏的线索
```

> ⚠️ **书里的黄金法则**：**「找泄漏不是看『谁大』，而是看『谁在持续增长』」**——一个大缓存（占 1G 但稳定）不是泄漏；一个 `List` 每分钟多 100 个对象，那才是。

### 4.2 MAT 的四种视图

| 视图 | 用途 |
| ---- | ---- |
| **Histogram** | 按类统计对象数和大小——「哪个类对象最多」 |
| **Dominator Tree** | 按「支配关系」排序——「谁真正占着最多内存」 |
| **Leak Suspects** | MAT 自动分析——**「疑似泄漏报告」（先看这个）** |
| **Path to GC Roots** | 「这个对象为什么没被回收」——**找到泄漏的引用链** |

### 4.3 常见「内存大户」

| 类型 | 典型问题 |
| ---- | ---- |
| **大数组** | `byte[]` / `char[]` / `int[]` 占了大部分堆 |
| **重复的 String** | 大量相同字符串没走 `intern()` |
| **HashMap / ConcurrentHashMap** | 只增不减的缓存（应设上限 + TTL） |
| **集合的「空壳」** | 大量空 `ArrayList`（默认容量 10，未扩容但对象本身有开销） |
| **框架内部** | MyBatis 的缓存、Spring 的 Bean、Tomcat 的 Session |
| **ThreadLocal** | 线程池场景下不 remove（⚠️ 高频坑） |

### 4.4 堆外内存

> **书里特别提醒**：**「堆没问题不代表没内存问题」**——**堆外内存（Direct Memory、Metaspace、线程栈、JNI）也会 OOM。**

```bash
# 开启 NMT（Native Memory Tracking）—— 追踪堆外内存
-XX:NativeMemoryTracking=summary

# 查看堆外内存分布
jcmd <pid> VM.native_memory summary
```

| 堆外区域 | 常见问题 |
| ---- | ---- |
| **Metaspace** | 类加载器泄漏（见 [[《深入理解Java虚拟机》笔记]]） |
| **Direct Memory** | NIO/Netty 的 `ByteBuf` 未释放 |
| **线程栈** | 线程太多（每线程 1M，1000 线程就是 1G） |
| **代码缓存** | `ReservedCodeCacheSize` 太小导致停止编译 |

## 五、线程与同步：并发的性能（第 9 章）

### 5.1 线程池大小的「正确算法」⭐

> **书里给出了明确公式**（而不是「CPU 核数 + 1」这种模糊说法）：

```
线程数 = CPU 核数 × 目标 CPU 利用率 × (1 + 等待时间 / 计算时间)
```

**实际应用**：

| 任务类型 | 计算时间 : 等待时间 | 线程数（8 核为例） |
| ---- | ---- | ---- |
| **CPU 密集型** | 1 : 0 | 8 ~ 9（接近核数） |
| **IO 密集型（一般）** | 1 : 1 | 16（2 倍核数） |
| **IO 密集型（重）** | 1 : 9 | 80（10 倍核数） |

> ⚠️ **书里的重要提醒**：**「公式只是起点，必须实测」**——因为「等待时间」本身受很多因素影响（网络、DB、下游）。**正确做法是压测找拐点**。

### 5.2 「只有一个线程在干活」的原因排查

| 原因 | 检查方法 |
| ---- | ---- |
| **线程数太少** | 看线程池配置 |
| **锁竞争** | `jstack` 看大量线程 `BLOCKED` |
| **任务本身很快**（并发没意义） | 看单任务耗时 |
| **有全局锁**（如 `synchronized` 方法） | `jstack` 看锁持有者 |
| **IO 阻塞**（所有线程都卡在下游） | `jstack` 看线程栈顶 |

> 📌 **锁竞争的线上定位方法**（`jstack` 同地址配对法）见 [[03_JUC 详细讲解]]。

### 5.3 伪共享（False Sharing）—— 性能的隐形杀手 ⭐

> **书里讲的经典优化**：**两个线程改「同一个缓存行」里的不同变量，会相互踩脚，导致缓存失效。**

```java
// ❌ 反例：两个变量在同一个缓存行（64 字节）里
public class Counter {
    public volatile long count1 = 0;   // 线程 A 改这个
    public volatile long count2 = 0;   // 线程 B 改这个
    // 表面上互不干扰，实际上在「同一个缓存行」里，会相互 invalidate
}

// ✅ 正例：填充（padding）让它们在不同缓存行
public class Counter {
    public volatile long count1 = 0;
    public long p1, p2, p3, p4, p5, p6, p7;   // 填充 56 字节
    public volatile long count2 = 0;
}

// ✅✅ 现代写法（JDK 8+）：@Contended 注解（需加 -XX:-RestrictContended）
public class Counter {
    @sun.misc.Contended
    public volatile long count1 = 0;
    @sun.misc.Contended
    public volatile long count2 = 0;
}
```

> 💡 **为什么**：CPU 缓存以**缓存行（64 字节）**为单位。两个变量在同一行，一个改了，另一个的缓存就失效了——**看起来无锁，实际在互相等待**。
> 📌 **原理见** [[《计算机组成原理》笔记]]（MESI 协议）。

### 5.4 常见的并发性能陷阱

| 陷阱 | 问题 | 解法 |
| ---- | ---- | ---- |
| **过度同步** | `synchronized` 范围太大 | 缩小同步范围 |
| **使用 `Hashtable`/`Vector`** | 全表锁 | 换 `ConcurrentHashMap` |
| **`Collections.synchronizedMap`** | 全表锁 | 换 `ConcurrentHashMap` |
| **`AtomicLong` 高竞争** | CAS 失败重试 | 换 `LongAdder`（分段累加） |
| **自己 `new Thread`** | 无节制创建 | 用线程池 |
| **`Executors.newFixedThreadPool`** | 无界队列 OOM | 手写 `ThreadPoolExecutor` |

> 📌 **`LongAdder` vs `AtomicLong` 的实测对比**（800ms vs 90ms）见 [[03_JUC 详细讲解]]。

## 六、数据库性能（第 12 章）

> **书里的观点**：**「大多数 Web 应用的瓶颈在数据库」**——JVM 调半天不如一条慢 SQL 优化。

### 6.1 JDBC 的四个关键优化

| 优化 | 说明 | 收益 |
| ---- | ---- | ---- |
| **预编译（PreparedStatement）** | 语句编译一次，多次执行 | 快 + 防 SQL 注入 |
| **批处理（addBatch / executeBatch）** | 多条语句一次发送 | **大幅减少网络往返** |
| **连接池（HikariCP）** | 复用连接 | 避免频繁建连 |
| **合适的 fetchSize** | 一次取多少行 | 避免一次拉太多或太少 |

```java
// ✅ 批处理示例
try (PreparedStatement ps = conn.prepareStatement("insert into t values (?, ?)")) {
    for (Data d : list) {
        ps.setLong(1, d.id());
        ps.setString(2, d.name());
        ps.addBatch();                      // 攒起来
        if (++count % 1000 == 0) {
            ps.executeBatch();              // 每 1000 条发一次
        }
    }
    ps.executeBatch();                      // 最后一批
}
```

### 6.2 事务与锁

| 问题 | 后果 | 解法 |
| ---- | ---- | ---- |
| **长事务** | 持有锁时间长，阻塞别人 | 事务里不做远程调用/大量计算 |
| **锁等待** | 响应变慢 | 缩短事务 + 合理索引 |
| **死锁** | 相互等待 | 固定加锁顺序 |
| **隔离级别过高** | 并发差 | 按需选（一般 `READ_COMMITTED`） |

### 6.3 连接池大小——书里的反直觉结论

> **书里的案例**：**「连接池不是越大越好」**——过大反而更慢（因为 DB 的连接是稀缺资源，CPU 上下文切换、锁竞争增加）。

| 连接池大小 | 效果 |
| ---- | ---- |
| **太小** | 请求排队 |
| **适中** | 最优 |
| **太大** | **变慢**（DB 端竞争加剧） |

> 💡 **经验公式**：`连接数 ≈ CPU 核数 × 2 + 有效磁盘数`。**但必须实测**。

## 七、性能测试方法论（第 2 章）

### 7.1 测试的四个陷阱 ⭐

| 陷阱 | 说明 | 怎么避免 |
| ---- | ---- | ---- |
| **没有预热** | 测的是「解释执行」的性能 | 先跑几分钟预热 |
| **测试太短** | 没到稳态 | 至少跑 10~30 分钟 |
| **只看平均** | 平均值掩盖了长尾 | **看 P99、P999** |
| **不隔离环境** | 和别的服务抢资源 | 独立环境 |

### 7.2 要看哪些指标

| 指标 | 含义 | 重要性 |
| ---- | ---- | ---- |
| **吞吐量（TPS/QPS）** | 每秒处理多少 | ⭐⭐⭐ |
| **平均响应时间** | 所有请求的平均 | ⭐（**会被长尾掩盖**） |
| **P95 / P99 / P999** | 95%/99% 请求的响应时间 | ⭐⭐⭐ **最重要** |
| **最大响应时间** | 最慢那个 | ⭐⭐ |
| **错误率** | 失败请求比例 | ⭐⭐⭐ |
| **CPU / 内存 / GC** | 资源占用 | ⭐⭐ |

> ⚠️ **书里强调**：**「关注 P99 而不是平均值」**——用户感受到的是「最慢的那些请求」，不是平均值。**平均值 50ms 但 P99 是 5s 的系统，体验是灾难。**

### 7.3 压测工具的选择

| 工具 | 特点 |
| ---- | ---- |
| **JMeter** | 功能全，GUI 友好 |
| **wrk / wrk2** | 轻量，高并发 |
| **Gatling** | 代码化，适合 CI |
| **ab** | 最简单，但功能弱 |

---

## 八、性能优化的「优先级清单」（书里的总结）

> **按「收益/成本」排序，从上往下做**：

| 优先级 | 优化项 | 典型收益 |
| ---- | ---- | ---- |
| **1** | **慢 SQL / 缺索引** | 常常 10~100 倍 |
| **2** | **N+1 查询** | 经常 10 倍以上 |
| **3** | **不必要的外部调用** | 直接省掉 |
| **4** | **缓存**（本地 + Redis） | 数倍 |
| **5** | **批处理 / 合并请求** | 数倍 |
| **6** | **线程池优化** | 数倍（IO 密集场景） |
| **7** | **JVM 参数调优** | 10%~50% |
| **8** | **代码级微优化** | 通常 <10% |

> 💡 **书里的核心观点**：**「先解决架构和数据库层面的大问题，再考虑 JVM 调参」**——很多人把顺序搞反了，在 JVM 参数上抠半天，却放着慢 SQL 不管。

---

## 九、一句话总结 & 全书地图

> **「性能是测出来的，不是猜出来的；瓶颈往往不在你以为的地方。」**

### 五个核心认知

1. **先测量，再优化**——不测量就调优 = 碰运气
2. **一次只改一个变量**——优化是受控实验
3. **压测必须预热**——不然测的是 JIT 之前的性能
4. **看 P99 不看平均值**——用户感受的是长尾
5. **绝大多数性能问题不在 GC**——先查 SQL 和锁
