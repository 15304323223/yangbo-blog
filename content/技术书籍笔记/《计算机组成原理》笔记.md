# 💻 《计算机组成原理》笔记 —— 一切性能问题的物理根源

> **一句话总纲**：**软件的性能上限，是硬件画好的圈。** 你写的每一行 Java 最终都要变成 CPU 的取指-译码-执行；你抱怨的每一次「慢」，要么是没喂饱 CPU，要么是 CPU 在等内存。
>
> **怎么读这篇**：不要当考研书读。**带着「Java 里那些看不懂的词」来读**——`volatile` 的内存屏障、`MESI`、伪共享、`long` 的原子性、`String` 不可变的代价、数组为什么比链表快——答案全在这一层。

## 零、整体印象：一台「工厂」

先建立一个能挂住所有细节的画面。

```
        ┌─────────────────────────────────────────────┐
        │            一 座 工 厂（计算机）              │
        ├─────────────────────────────────────────────┤
        │                                             │
        │  【CPU = 车间】                              │
        │   ├─ 控制器（CU）  = 车间主任：发号施令        │
        │   ├─ 运算器（ALU）= 流水线工人：干活的         │
        │   └─ 寄存器组     = 工人手上的活儿（最快）     │
        │                                             │
        │  【缓存 Cache = 车间门口的货架】              │
        │   L1（手边）→ L2（门口）→ L3（楼层的公共柜）   │
        │                                             │
        │  【主存 DRAM = 城郊大仓库】                   │
        │   东西全但取货慢（约 100 个时钟周期）          │
        │                                             │
        │  【磁盘/SSD = 另一个城市的仓库】              │
        │   极大极慢（快几百上千倍差距）                │
        │                                             │
        │  【总线 = 厂区里的传送带】                    │
        │   所有人共用，所以会「堵」                     │
        └─────────────────────────────────────────────┘
```

> 💡 **这张图先记住一句**：**离 CPU 越近的存储，越快、越小、越贵。** 后面所有的缓存、伪共享、内存屏障、局部性优化——都是围着这一句转。

### 0.1 硬件速度量级表（务必背下来）

| 层级 | 典型延迟 | 类比（1 个时钟周期 = 1 秒） | 容量量级 |
| ---- | ---- | ---- | ---- |
| 寄存器 | < 1 周期 | 手上的活儿 | 几百字节 |
| L1 Cache | ~4 周期 | 从桌上拿 | 32~64 KB |
| L2 Cache | ~12 周期 | 从抽屉拿 | 256 KB~1 MB |
| L3 Cache | ~40 周期 | 从柜子里拿 | 几 MB~几十 MB |
| 主存 RAM | ~200 周期 | 去楼下取快递 | 几 GB~几百 GB |
| SSD | ~10 万周期 | **去隔壁城市取货** | TB 级 |
| 机械硬盘 | ~千万周期 | **坐飞机去取货** | TB 级 |
| 同机房网络 RTT | ~亿周期 | **去月球取货** | — |

> ⚠️ **这张表是性能调优的「物理常识」**。为什么「减少一次数据库查询」比「省几行 Java 代码」值钱一万倍？因为数据库查询要走网络 + 磁盘。为什么 G1 要避免 Full GC？因为 Full GC 意味着全量访问主存，直接掉到「去楼下取快递」的量级。

## 一、CPU 是怎么干活的

### 1.1 指令周期的五步

CPU 干活是**无脑循环**，就五步，永不停歇：

```
① 取指（Fetch）     从 PC 指向的地址取一条指令
② 译码（Decode）    解析这条指令要干什么（操作码 + 操作数）
③ 执行（Execute）   ALU 算 / 访存 / 跳转
④ 访存（Memory）    需要时读写内存
⑤ 写回（Writeback） 结果写回寄存器
        ↓
   PC 自增（或跳转到新地址）
        ↓
    回到 ①
```

**寄存器里的几个关键角色**：

| 寄存器 | 作用 | 类比 |
| ---- | ---- | ---- |
| **PC**（Program Counter） | 下一条指令的地址 | 车间主任手里的排产单 |
| **IR**（Instruction Register） | 当前正在执行的指令 | 正在看的那一页 |
| **MAR**（地址寄存器） | 要访问哪个内存地址 | 快递单上的门牌号 |
| **MDR**（数据寄存器） | 取回/要写的数据 | 快递盒子本身 |
| **ACC**（累加器） | 运算的临时结果 | 工作台上的半成品 |
| **PSW**（程序状态字） | 标志位（溢出、零、正负、中断） | 质量警示灯 |

> 💡 **对 Java 的意义**：JVM 里的「操作数栈」是**模拟**这套寄存器模型。JVM 指令（`iload`/`iadd`/`istore`）就是「把变量压栈、弹两个出来相加、把结果存回」——**它就是一台抽象的、栈式的 CPU**。看懂指令周期，`.class` 字节码就不再是天书。

### 1.2 流水线（Pipeline）—— 性能的第一个魔法

**问题**：五步串行做，每一步都要等上一步，CPU 大量时间在空转。

**解法**：把它变成流水线——**同一时刻，不同的指令处在不同的阶段**。

```
串行（无流水线）：       流水线（5 级）：
指令1: 取指 译码 执行 访存 写回      时钟1: 指令1-取指
指令2:                   取指 译码 ...  时钟2: 指令1-译码 | 指令2-取指
指令3:                                时钟3: 指令1-执行 | 指令2-译码 | 指令3-取指
                                        ...
耗时：5 条指令 = 25 周期            耗时：5 条指令 ≈ 9 周期
```

**理想吞吐**：k 级流水线 → 每周期完成 1 条指令（CPI = 1），加速比趋近 k。

#### 但流水线有「三险」

| 冲突类型 | 原因 | 例子 | 解决 |
| ---- | ---- | ---- | ---- |
| **结构冒险** | 硬件资源冲突（同一部件被两条指令同时要） | 取指和访存都要访问主存 | 指令/数据 Cache 分离 |
| **数据冒险** | 后一条指令要用的数据还没算出来 | `a=b+c; d=a+e;` | **转发/旁路**、插入气泡、编译器重排 |
| **控制冒险** | 遇到跳转，不知道下一条取哪 | `if (x>0) {...}` 分支 | **分支预测** + 预测失败要清空流水线 |

> ⚠️ **这是「一切性能玄学」的总源头**：
> - **分支预测失败代价极大**（要丢掉整条流水线的活儿，10~20 周期）→ 所以**有序数组的遍历比无序快**（分支预测器能学会规律），这是为什么 `Arrays.sort()` 后求和有时更快。
> - **数据冒险 → 所以 CPU 会乱序执行** → 乱序执行需要内存屏障来「拉回正轨」→ **这就是 `volatile` 的物理起源**。
> - **控制冒险 → 所以「方法内联」「循环展开」能提速**（减少跳转）。

### 1.3 乱序执行与内存屏障 —— 直通 `volatile`

现代 CPU 为了填满流水线，**不按程序顺序执行**：只要数据没依赖，后面的指令可以先跑。

```
程序顺序：  ① 读 flag   ② 读 data
CPU 实际：  ② 读 data   ① 读 flag     ← 如果这俩没依赖，CPU 可能换序！
```

**这在单线程无害**（结果一样），**在多线程会出命案**。

#### 四种内存屏障（Java 内存模型的地基）

| 屏障 | 作用 | x86 上 | Java 里 |
| ---- | ---- | ---- | ---- |
| **LoadLoad** | 前面读不能排到后面读之后 | 通常不需要（x86 强序） | — |
| **StoreStore** | 前面写不能排到后面写之后 | 需要 `sfence` | `volatile` 写在普通写后 |
| **LoadStore** | 前面读不能排到后面写之后 | 通常不需要 | — |
| **StoreLoad** | 前面写不能排到后面读之后 | **`mfence`（最贵）** | **`volatile` 写** |

```java
// volatile 写 = 前面所有写 + StoreLoad 屏障
volatile boolean flag = false;
int data = 1;

data = 42;          // ① 普通写
flag = true;        // ② volatile 写 —— 屏障保证 ① 对其它线程可见（在 ② 之前）
```

> ✅ **一句话记住**：`volatile` 不是「锁」，是**告诉 CPU 和编译器「别在这儿乱排」**。它保证可见性和有序性，但不保证原子性（`i++` 依然不安全）。
>
> 📎 延伸：`final` 字段的特殊语义、`synchronized` 的 `monitorenter/exit` 隐含屏障、`Unsafe`、`VarHandle` 的 acquire/release——**本质都是这一层屏障的不同包装**。

### 1.4 CISC vs RISC 与 Java 的关系

| | CISC（x86） | RISC（ARM） |
| ---- | ---- | ---- |
| 指令 | 复杂、变长、一条干很多事 | 简单、定长、一条只干一件事 |
| 谁做优化 | 硬件（微码） | 编译器 |
| 典型 | Intel / AMD 服务器 | 手机、Apple M 系列、鲲鹏 |

> 💡 **Java 的应对**：JVM 是**栈式虚拟机**，字节码是**抽象的、与硬件无关的**。JIT 编译时才把字节码翻译成目标平台的机器码（x86 用 CISC 优化，ARM 用 RISC 优化）。**「一次编写，到处运行」的代价就是多了一层翻译**——这也是 JIT 预热的原因。

## 二、存储层次与缓存 —— 全篇最重要

### 2.1 为什么要有 Cache

**核心矛盾**：CPU 每周期能算好几个操作，但内存 200 周期才回一次数据。**CPU 有 99% 的时间在等内存**（这叫「存储墙」）。

**解法**：在 CPU 和内存之间塞几层小的、快的 Cache，靠**局部性原理**把常用的数据搬过来。

#### 局部性原理（Cache 能生效的全部前提）

| 类型 | 含义 | 例子 |
| ---- | ---- | ---- |
| **时间局部性** | 刚访问过的，很可能马上又访问 | 循环里的变量 `i` |
| **空间局部性** | 访问了 `a[i]`，很可能接着访问 `a[i+1]` | 数组遍历 |

```java
// 空间局部性的教科书级例子
// 列优先遍历二维数组（Java 里 array[i][j] 是「行优先」存储）
int[][] arr = new int[4096][4096];

// ❌ 慢：跳着访问，每次 visit 都可能触发 Cache Miss
for (int j = 0; j < 4096; j++)
    for (int i = 0; i < 4096; i++)
        sum += arr[i][j];

// ✅ 快：顺序访问，一条 Cache Line 搬进来能用好几次
for (int i = 0; i < 4096; i++)
    for (int j = 0; j < 4096; j++)
        sum += arr[i][j];
```

> ⚠️ **差距可能是 5~10 倍**。同一段逻辑、同样的运算量，只因访问顺序不同。**这就是「局部性」的威力**——它不是玄学，是 Cache Line 的物理搬运。

### 2.2 Cache Line —— 64 字节的「搬运单元」

**关键事实**：Cache 不是按字节搬，是**按块搬**。这块叫 **Cache Line**，x86 上 **64 字节**。

```
一次内存访问的完整路径：
CPU 要 arr[0]
    ↓
查 L1 → 没有（Miss）
    ↓
查 L2 → 没有（Miss）
    ↓
查 L3 → 没有（Miss）                ← 这三跳加起来 ~250 周期
    ↓
去主存取「arr[0] 所在的那一整条 64 字节」（= arr[0..15] 共 16 个 int）
    ↓
逐层填回 L3 → L2 → L1 → 给 CPU
    ↓
下次访问 arr[1] → L1 命中！（~4 周期）
```

> 💡 **推论（极其重要）**：
> - **一个 `int` 只有 4 字节，但搬进来时顺手搬了 16 个**。所以**顺序访问几乎是免费的**。
> - **链表为什么慢？** 节点在堆上散布，每次 `next` 都可能跨 Cache Line → 每次都是 Miss。
> - **为什么 `ArrayList` 通常比 `LinkedList` 快**，哪怕插入删除理论复杂度更高？**因为数组的空间局部性碾压了链表的理论优势**。这是新手最爱踩的认知坑。

### 2.3 缓存一致性协议 MESI —— 多核的地基

**问题**：多核 CPU，每个核有自己的 L1/L2。核 A 改了 `x`，核 B 的 L1 里还是旧值，怎么办？

**解法**：**MESI 协议**——给每条 Cache Line 打一个状态标签。

| 状态 | 含义 | 本核有副本 | 其它核有副本 | 内存是最新 |
| ---- | ---- | ---- | ---- | ---- |
| **M**（Modified） | 我改了，别人都没有 | ✅ | ❌ | ❌（脏） |
| **E**（Exclusive） | 只有我有，和内存一致 | ✅ | ❌ | ✅ |
| **S**（Shared） | 好几个核都有，都和内存一致 | ✅ | ✅ | ✅ |
| **I**（Invalid） | 我的副本失效了，别用 | ❌ | — | — |

**核心动作**：**写之前必须先拿到独占权**。

```
核A 要写 x：
  如果 x 在核A 是 S 状态（多个核共享）
      ↓
  核A 发「Invalidate」消息，让核B/C/D 把 x 标为 I
      ↓
  等所有核都回 ACK（这就是「同步」的开销）
      ↓
  核A 把 x 改为 M，安心写入
```

> ⚠️ **MESI 的代价 = 多线程写共享变量的代价**。为什么高并发下「减少共享、多用局部变量」能提速？因为局部变量在寄存器/栈上，**根本不参与 MESI**。

#### 2.3.1 伪共享（False Sharing）—— 最隐蔽的性能杀手

**场景**：两个线程各自改一个**不同的**变量，却慢得离谱。

**原因**：这俩变量**落在了同一条 Cache Line 里**。

```java
// ❌ 伪共享：a 和 b 挨着，位于同一条 64 字节 Cache Line
class Counter {
    volatile long a;   // 线程 1 拼命加
    volatile long b;   // 线程 2 拼命加
}
// 结果：两个线程互相让对方的核心 Cache Line 失效 → 来回抢总线 → 比单线程还慢！
```

```
Cache Line（64 字节）
┌──────────────────────┬──────────────────────┐
│   a（线程1 在改）     │   b（线程2 在改）     │
└──────────────────────┴──────────────────────┘
   线程1 写 a → 核2 的整条 Line 失效 → 线程2 得重新从内存加载（连 a 一起）
   线程2 写 b → 核1 的整条 Line 失效 → 线程1 得重新加载（连 b 一起）
                    ↑ 这叫「缓存行乒乓」，缓存彻底白建了
```

**解法**：**把变量撑开，各占一条 Line**。

```java
// ✅ 方案一：手动填充（Java 8 前的做法）
class PaddedCounter {
    volatile long a;
    long p1, p2, p3, p4, p5, p6, p7;   // 7×8=56 字节，撑满 64
    volatile long b;
}

// ✅ 方案二：@Contended（Java 8+，需要 -XX:-RestrictContended）
@sun.misc.Contended
class Counter {
    volatile long a;
    volatile long b;
}
```

> 💡 **JDK 里的真实应用**：`ConcurrentHashMap` 的 `CounterCell`、`Thread` 的 `threadLocalRandomSeed`、`Striped64`（`LongAdder` 的爹）都用了 `@Contended`。**`LongAdder` 比 `AtomicLong` 在高并发下快，本质就是把热点拆到不同的 Cache Line 上。**

### 2.4 缓存的三种映射方式

| 方式 | 规则 | 冲突情况 | 实际使用 |
| ---- | ---- | ---- | ---- |
| **直接映射** | 内存块 % Cache 行数 → 只能放那一个位置 | 冲突最严重 | 简单场景 |
| **全相联** | 想放哪放哪 | 无冲突，但比较电路贵 | 小容量 TLB |
| **组相联**（主流） | 先定组（直接映射），组内随便放（全相联） | 折中 | **现代 CPU 都是 N 路组相联** |

### 2.5 写策略

| 策略 | 行为 | 特点 |
| ---- | ---- | ---- |
| **写直达**（Write Through） | 改 Cache 的同时改内存 | 简单、一致性好、**慢** |
| **写回**（Write Back） | 只改 Cache，标 M，淘汰时才写回内存 | **快**、主流 |

> 💡 **写回策略是 MESI 里 M 状态存在的原因**，也是为什么多线程下「谁持有最新值」这么复杂。`volatile` 的 `StoreStore` 屏障某种程度上就是强制「及时刷出去」。

## 三、CPU 指令级优化与 Java 的对应

### 3.1 指令重排的三个层级

```
① 编译器重排    javac / JIT 优化时调整顺序
② CPU 乱序执行  硬件层面填流水线
③ 内存系统重排   Store Buffer / Invalidate Queue 导致的「看起来」换序
                    ↓
        三者叠加 = 你写的代码顺序 ≠ 实际执行顺序
```

> ⚠️ **`synchronized`/`volatile`/`final` 的全部意义，就是在某一层拦住重排。** 只有 `final` 是编译器层面的保证，其余靠屏障。

### 3.2 JIT 做的几件大事（HOTSPOT）

| 优化 | 做什么 | 收益 |
| ---- | ---- | ---- |
| **方法内联**（Inlining） | 把被调用方法的字节码塞进调用方 | **最重要**——它解锁了后面所有优化 |
| **逃逸分析**（Escape Analysis） | 分析对象会不会「跑出去」 | 栈上分配、**标量替换**、锁消除 |
| **标量替换** | 把对象拆成几个局部变量 | 减少堆分配与 GC 压力 |
| **锁消除**（Lock Elision） | 证明锁没有竞争就删掉 | 免掉 monitor 开销 |
| **循环展开** | 减少跳转次数 | 提升流水线效率 |
| **分支预测**（CPU 层） | 猜分支走向 | 猜错清空流水线，代价高 |
| **分层编译** | C1 快速编译 → C2 深度优化 | 兼顾启动与峰值 |

```java
// 逃逸分析 + 标量替换的经典例子
public int calc() {
    Point p = new Point(1, 2);   // 对象没逃逸出方法
    return p.x + p.y;            // JIT 可直接优化成 return 1 + 2; 根本不分配对象！
}
```

> ✅ **所以「JVM 调优」的第一课是「别乱调 JVM 参数」**——JIT 已经很聪明了。你要做的是：**给足预热时间、避免超大方法（会拒绝内联）、别写出阻碍逃逸分析的代码**。

### 3.3 内联的门槛（实战相关）

| 参数 | 含义 | 默认值 |
| ---- | ---- | ---- |
| `-XX:MaxInlineSize` | 字节码小于此值必内联 | 35 字节 |
| `-XX:FreqInlineSize` | 热点方法的内联上限 | 325 字节 |
| `-XX:MaxInlineLevel` | 内联嵌套层数 | 9 |
| `-XX:InlineSmallCode` | 内联后代码大小上限 | 1000 字节 |

> ⚠️ **实践推论**：**Getter/Setter 短小是为了能被内联**。**方法过长会失去内联资格**。这是「代码整洁之道：函数要短」的**硬件级理由**——两本书在这里打通了。

## 四、存储系统：从寄存器到磁盘的完整链条

### 4.1 主存的组织

| 概念 | 说明 |
| ---- | ---- |
| **存储单元** | 每个单元存 1 字节，有唯一地址 |
| **地址总线** | 决定最大寻址空间（32 位 → 4 GB，这就是 32 位 JVM 堆上限的原因） |
| **数据总线** | 一次能并行传多少位（64 位） |
| **DRAM vs SRAM** | DRAM 用电容（需刷新、便宜、慢）→ 主存；SRAM 用触发器（不需刷新、贵、快）→ Cache |
| **行缓冲（Row Buffer）** | DRAM 按行激活，**同一行内连续访问快得多** |

> 💡 **为什么 32 位 JVM 堆最多 1.5~2G**？不止是 4G 地址空间上限，还要给系统、方法区、线程栈、直接内存留位置。**这就是「硬件限制了软件」的活标本。**

### 4.2 磁盘与 SSD

| | 机械硬盘 HDD | 固态硬盘 SSD |
| ---- | ---- | ---- |
| 原理 | 磁头 + 盘片旋转 | 闪存颗粒（浮栅晶体管） |
| 随机读 | 极慢（寻道 + 旋转延迟，**毫秒级**） | 快（几十微秒） |
| 顺序读 | 尚可 | 极快 |
| 擦写寿命 | 无限制 | 有限（**写放大**） |
| 关键优化 | **顺序化**（把随机 IO 变顺序 IO） | **对齐 + TRIM** |

#### 4.2.1 对 Java 后端的直接启示

```
❌ 随机小 IO（最差）        →  ✅ 顺序大 IO（最优）
MySQL 随机主键插入           →  自增主键
逐条 INSERT                  →  批量 INSERT（rewriteBatchedStatements=true）
小文件一堆                    →  合并大文件（Kafka 就是这样做的）
B+ 树随机跳                    →  LSM-Tree 顺序写（LevelDB/RocksDB/HBase）
```

> ⚠️ **「Kafka 为什么快」的终极答案在这儿**：**顺序写磁盘 + 页缓存 + 零拷贝**。它把「随机写」这个最慢的动作彻底消灭了——用顺序追加日志换取吞吐。

#### 4.2.2 为什么 Redis 要「避免大 key」

**物理原因**：Redis 单线程 + 大 key 操作（如 `SMEMBERS` 一个大 Set）会长时间占住 CPU；同时**大 key 分发/回收会引发内存抖动**。底层上，大对象跨越更多 Page，**加重了内存管理和网络传输负担**。

### 4.3 校验码（数据完整性）

| 校验 | 能检几位错 | 能纠错 | 用在哪 |
| ---- | ---- | ---- | ---- |
| **奇偶校验** | 1 位（奇数个错） | ❌ | 简单串口 |
| **海明码** | 2 位 | ✅ 1 位 | ECC 内存 |
| **CRC** | 突发错误 | ❌ | 网络包（以太网）、**Kafka 消息**、ZIP |
| **校验和** | 有限 | ❌ | TCP/IP |

> 💡 **Java 里的 CRC**：`java.util.zip.CRC32`、Kafka 每条消息带的 CRC32、Hadoop 块校验。**「消息在网络上会不会被改坏」这件事，靠的就是这一层。**

### 4.4 ECC 内存与「位翻转」

服务器内存带 ECC（纠错码），能自动纠正单比特错误。**为什么重要？** 因为内存条受宇宙射线、电路噪声影响，**单个 bit 真的会自己翻转**。这就是：
- 「为什么不能用浮点数存钱」之外的另一层理由；
- 「静默数据损坏」（Silent Data Corruption）的物理来源；
- 分布式存储为什么要多副本 + 校验。

## 五、总线与 IO —— NIO / 零拷贝的地基

### 5.1 总线的三种类型

| 总线 | 传什么 | 特点 |
| ---- | ---- | ---- |
| **数据总线** | 数据 | 双向，宽度决定一次传多少位 |
| **地址总线** | 地址 | 单向，宽度决定寻址空间 |
| **控制总线** | 控制信号 | 读写、中断、时钟 |

**瓶颈真相**：**所有部件共享总线 → 总线是稀缺资源**。这就是为什么：
- 多核抢总线（伪共享的物理原因）；
- DMA 很重要（让磁盘直接和内存对话，**不占用 CPU**）；
- 零拷贝有价值（**减少数据在总线上的搬运次数**）。

### 5.2 中断与 DMA

```
无 DMA（PIO 模式）：  磁盘 → CPU 寄存器 → 内存        （CPU 全程搬运，浪费）
有 DMA：            磁盘 → 内存（DMA 控制器直接搬）   （CPU 只收一个中断）
```

> ✅ **DMA 的意义**：**把 CPU 从「搬运工」解放成「决策者」**。这是所有「提升吞吐」优化的原型——**让专业的部件干专业的事**。

### 5.3 零拷贝（Zero-Copy）—— Kafka/Netty 的杀手锏

**传统文件发送（4 次拷贝 + 4 次上下文切换）**：

```
磁盘 →[DMA]→ 内核 Buffer →[CPU]→ 用户 Buffer →[CPU]→ Socket Buffer →[DMA]→ 网卡
       ①                  ②              ③                  ④
```

**sendfile 零拷贝（2 次拷贝 + 2 次切换）**：

```
磁盘 →[DMA]→ 内核 Buffer ──────[DMA]──────→ 网卡
       ①                          ②
        （数据根本不进用户空间！）
```

```java
// Java 的零拷贝入口
FileChannel.transferTo(position, count, targetChannel);   // Linux: sendfile
FileChannel.transferFrom(sourceChannel, position, count); //
Files.copy() / Files.write() 底层可能用它
```

> 💡 **为什么 Kafka 吞吐这么高**：`FileChannel.transferTo` + 页缓存 + 顺序写。**用户态和内核态来回倒腾数据的开销被彻底消除了。**

### 5.4 页缓存（Page Cache）与 Java 的关系

**关键认知**：**你「写文件」并没有真的写到磁盘，只是写进了内核的页缓存**。

```
write() 调用 → 数据进了内核 Page Cache → 调用就返回了（异步）
                                            ↓
                              OS 在合适时机刷盘（pdflush / writeback）
```

> ⚠️ **这带来两个必须知道的事实**：
> 1. **「写成功」≠「已落盘」**。MySQL 的 `innodb_flush_log_at_trx_commit`、Kafka 的 `acks=all` 就是在控制这个。
> 2. **Java NIO 的 `MappedByteBuffer`** 就是 mmap 的封装——**堆外内存**，不受 `-Xmx` 约束，出问题报的是 **OOM: Map failed** 而不是 Heap OOM。

## 六、后端开发者的「硬件知识映射表」

**这张表是全篇的落脚点。** 每个 Java 里「说不清为什么」的东西，都能对应到硬件机制。

| Java / 后端概念 | 硬件根源 | 说明 |
| ---- | ---- | ---- |
| `volatile` 可见性 | **StoreLoad 屏障** + MESI | 强制刷到主存并让其它核失效 |
| `volatile` 不保证原子性 | `i++` 是「读-改-写」三步，非单条指令 | 需 `AtomicInteger`/`synchronized` |
| `synchronized` 开销 | MESI 独占权 + 屏障 + 总线锁 | 无竞争时偏向锁/轻量级锁可避免 |
| **伪共享** | **Cache Line 64 字节 + MESI 失效** | 用 `@Contended` 填充 |
| **`LongAdder` 比 `AtomicLong` 快** | 拆到不同 Cache Line（Striped64） | 高并发场景首选 |
| **数组比链表快** | **空间局部性 + Cache Line 预取** | 理论复杂度不是全部 |
| **`String` 不可变** | 可安全共享、可缓 hash、线程安全 | 代价是拼接产生新对象 |
| **`StringBuilder` 比 `+` 快** | 循环里 `+` 每次都新建对象 | 编译器对常量拼接有优化 |
| **`Integer` 缓存 -128~127** | 减少对象创建（`IntegerCache`） | `==` 陷阱的来源 |
| **`long` 写非原子（32 位 JVM）** | 32 位总线分两步写 64 位 | 加 `volatile` 解决 |
| **`final` 字段安全发布** | 编译器插入 StoreStore 屏障 | 构造函数里不逸出 `this` |
| **栈上分配 / 标量替换** | 逃逸分析 | 减少 GC 压力 |
| **线程池核心数公式** | CPU 核数 + IO 等待 | IO 密集需更多线程掩盖延迟 |
| **P99 比平均值重要** | 流水线/GC/网络抖动的长尾 | 平均值骗人 |
| **顺序读写快** | **磁盘寻道 vs 顺序 + 预读** | Kafka/MySQL 自增主键 |
| **零拷贝** | sendfile 减少总线搬运 | Kafka/Netty |
| **堆外内存 OOM** | mmap / DirectByteBuffer 不受 `-Xmx` 管 | 报 `Map failed` |
| **`Unsafe` 为什么快** | 绕过 JVM 检查，直连内存 | CAS、屏障、堆外操作 |
| **NUMA 架构的影响** | 多路 CPU，访问本地内存快 | 大内存服务器要绑核 |

> 💡 **怎么用这张表**：**面试问到「为什么」时，能说到这一层就赢了 90% 的人。** 大多数人只知道「要这么写」，说不出「为什么硬件逼你这么做」。

## 七、指令集与性能的实战推论

### 7.1 几条「反直觉但正确」的结论

| 结论 | 理由 |
| ---- | ---- |
| **有序数组的遍历求和可能比无序快** | 分支预测器能学会规律，减少流水线清空 |
| **`for (int i=0; i<list.size(); i++)` 在 `LinkedList` 上是 O(n²)** | 每次 `get(i)` 都要从头遍历 |
| **两个「独立」变量并发写会互相拖慢** | 伪共享 |
| **减小对象大小能提速** | 同样容量下 Cache 能装更多对象，命中率上升 |
| **`byte[]` 处理二进制比 `String` 好** | 无编码转换、无对象头开销 |
| **避免「巨型对象」** | 跨多 Cache Line，还容易进老年代 |
| **`ArrayList` 预设容量能少一次数组拷贝** | 扩容是 `Arrays.copyOf`，全量复制 |

### 7.2 缓存友好的编码习惯

```java
// ✅ 编码习惯清单
// 1. 优先数组 / ArrayList，慎用 LinkedList
// 2. 二维数组按行遍历（Java 是行优先）
// 3. 循环内少调用 size()（尤其 LinkedList）
// 4. 热点计数器用 LongAdder 而非 AtomicLong
// 5. 避免伪共享：@Contended 或手动填充
// 6. 小对象、短生命周期（利于栈上分配）
// 7. 对象池慎用（可能反而增加 GC 压力）
// 8. 用基本类型的地方别用包装类
```

## 八、一句话总结

```
硬件决定了软件的「物理上限」：

  存储墙      →  Cache 必须存在        →  局部性原理 / Cache Line / 伪共享
  流水线      →  必须解决三种冒险      →  分支预测 / 乱序执行 / 内存屏障
  多核一致性  →  MESI 必须存在         →  volatile / 内存屏障 / 伪共享
  总线稀缺    →  减少搬运才有收益      →  零拷贝 / DMA / 缓冲
  磁盘极慢    →  顺序化是唯一出路      →  Kafka / 自增主键 / 批处理

读了这本书你会明白：
  ✔ 为什么 volatile 能保证可见性 —— 屏障 + MESI
  ✔ 为什么 LongAdder 比 AtomicLong 快 —— Cache Line 隔离
  ✔ 为什么函数要短 —— 内联门槛 35/325 字节
  ✔ 为什么 Kafka 快 —— 顺序写 + 零拷贝 + 页缓存
  ✔ 为什么 32 位 JVM 堆上不去 —— 地址总线宽度
  ✔ 为什么链表常常输给数组 —— 空间局部性

一句话：
  「性能优化的每一步，都是在跟硬件的物理规律做交易。」
```
