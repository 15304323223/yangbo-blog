# 《代码整洁之道》笔记（Clean Code）

> **一句话概括**：代码写出来是**给人读的，顺便能在机器上跑**——你花 10 分钟随便写，别人（包括三个月后的你自己）要花 10 小时看懂，这笔账永远不划算。
>
> **适合谁**：代码能跑但被 review 打回、接手过「屎山」、写过超过 500 行的方法、命名永远用 `data`/`temp`/`list1` 的人。
> **怎么读**：全书 17 章，但**真正改变你的一天之内就能改的是前 6 章**（命名 / 函数 / 注释 / 格式 / 对象数据结构 / 错误处理）。先看「一、核心心法」，再按需跳到具体章节。
> **作者的狠话**：*"代码的整洁程度，和你能多快读懂它成正比。读代码的时间远超写代码的时间（保守估计 10:1），所以让代码易读，就是在提高整个团队 10 倍的效率。"*

---

## 零、先建立整体印象：把代码当成「写给下一个人的信」

书里最有名的比喻：**你写代码时，不是「给编译器看」，而是「给下一个维护者看」**——而那个维护者，很可能是**三个月后的你自己**。

用一个贯穿全文的场景——**写一封信给未来的接盘侠**：

| 写代码时 | 信里的对应 | 一句话 |
|---|---|---|
| **命名** | 信纸上的称呼和措辞 | 别喊「喂」，要喊「张工」 |
| **函数** | 信件的段落 | 一段只讲一件事 |
| **注释** | 页边的批注 | 批注写得越多，越说明正文没说清 |
| **错误处理** | 「如果这事办不成」的备选方案 | 别把失败伪装成正常 |
| **格式** | 排版和分段 | 挤成一团的信没人读得下去 |
| **单元测试** | 寄出前的自查清单 | 没检查过的信别寄 |

**核心心法三句话**：

1. **代码是「写一次、读一百次」的**——优化阅读体验的收益是乘以 100 的
2. **整洁 = 照顾好细节**（命名、缩进、小函数），不是「架构好不好」
3. **「能跑」不是终点，「能读」才是**——能跑但不整洁的代码，会持续产生利息（技术债）

## 一、核心心法：整洁代码的「不变式」

### 1.1 什么算「整洁」？五位大师的定义

| 大师 | 定义 | 大白话翻译 |
| ---- | ---- | ---- |
| **Bjarne Stroustrup**（C++ 之父） | 优雅而高效：逻辑直白，依赖最少，错误处理完整，几乎没有多余的代码 | **不给自己找麻烦** |
| **Grady Booch**（UML 之父） | 简单直接：读起来像「精心书写的散文」 | **读着顺** |
| **Dave Thomas**（《程序员修炼之道》） | 除了原作者，其他人也能读懂、能改 | **别人敢动** |
| **Michael Feathers**（《修改代码的艺术》） | 你努力让它看起来「本来就该是这样」 | **看不出改过的痕迹** |
| **Ron Jeffries**（极限编程创始人） | 无重复、单一职责、表达清楚、抽象最小化 | **四把尺子** |

> 💡 **一句话记住**：**「读起来不费劲、别人敢改、改起来不出事」**——这三条比任何教条都实用。

### 1.2 本书的「四把尺子」（贯穿全书）

任何代码，都可以用这四条快速体检：

| 尺子 | 问题 | 违反时的症状 |
| ---- | ---- | ---- |
| **无重复（DRY）** | 同样的逻辑是不是出现了两次以上？ | 改需求要改 5 个地方，漏一个就出 bug |
| **单一职责（SRP）** | 这个函数/类是不是只干一件事？ | 名字里带「And」「Or」「Manager」「Util」 |
| **表达清楚** | 光看名字能不能知道它干什么？ | 需要写注释解释「这行是干嘛的」 |
| **抽象适度** | 是不是过度设计了？ | 为了「将来可能」，加了三层用不上的接口 |

## 二、命名：最难也最值钱的技能 ⭐

> 书里的原话：*"命名是编程中最难的事情之一——但也是投入产出比最高的。"*

### 2.1 命名的六条铁律

| 铁律 | ❌ 反例 | ✅ 正例 | 为什么 |
| ---- | ---- | ---- | ---- |
| **名副其实** | `int d; // 经过的天数` | `int elapsedDays;` | 名字本身就是注释，不需要额外解释 |
| **避免误导** | `List<Account> accountList`（实际是 `Map`） | `Map<Long, Account> accountsById` | 类型提示错 = 埋雷 |
| **做有意义的区分** | `a1, a2` / `data, data2` / `ProductInfo` vs `ProductData` | `source` / `destination` | 数字和废话后缀没有信息量 |
| **用能读出来的名字** | `genymdhms`（生成年月日时分秒） | `generationTimestamp` | 人念不出来的名字没法在会议上讨论 |
| **用可搜索的名字** | `int e;` | `int maxRetries;` | 单字母只适合局部循环变量 `i/j/k` |
| **避免编码** | `m_phoneStr`（匈牙利命名法） | `phone` | 现代 IDE 不需要类型前缀 |

### 2.2 Java 实战：命名改造对照

```java
// ❌ 反例：典型的「能跑但读不懂」
public class DataProcessor {
    private List<int[]> d;                      // d 是什么？每个 int[] 又是什么？
    private int e;

    public void proc(List<int[]> l) {           // proc 处理什么？l 是什么？
        for (int[] t : l) {
            if (t[0] > 100) {                   // 魔法数 100 + 下标 0，全靠猜
                e++;
            }
        }
    }
}
```

```java
// ✅ 正例：名字自带说明书
public class OrderStatisticsCalculator {
    /** 每个元素是 [订单金额(分), 商品数量]，下标含义明确 */
    private final List<int[]> orderSlices = new ArrayList<>();
    /** 大额订单计数器 */
    private int largeOrderCount;

    /** 大额订单的门槛，单位：分（100 元） */
    private static final int LARGE_ORDER_THRESHOLD_CENTS = 10_000;

    public void countLargeOrders(List<int[]> orders) {
        for (int[] order : orders) {
            int amountCents = order[AMOUNT_INDEX];   // 用常量替代魔法下标 0
            if (amountCents > LARGE_ORDER_THRESHOLD_CENTS) {
                largeOrderCount++;
            }
        }
    }
}
```

> ⚠️ **注意**：书里特别提醒**不要为了短而短**。`cntOfLrgOrd` 比 `largeOrderCount` 短，但没人愿意读第二个。**清晰 > 简短**。
> 💡 **一个实用检查法**：如果命名的过程让你不得不加注释说明，说明这个名字还能再改。**能改名字解决的，别用注释解决**。

### 2.3 类名 / 方法名的约定

| 类型 | 应该用什么 | ❌ 不该用 |
| ---- | ---- | ---- |
| **类名** | 名词/名词短语：`Customer`、`WikiPage`、`AddressParser` | 动词（`Manager`、`Processor`、`Data`、`Info`——**这些词是「我不知道它干嘛」的信号**） |
| **方法名** | 动词/动词短语：`postPayment`、`deletePage`、`save` | 名词、以及 `handle`、`process`、`doIt` 这类**万能废词** |
| **返回布尔** | `is`/`has`/`can`/`should` 开头：`isEmpty()`、`hasPermission()` | `flag`、`status`、`check()` |
| **避免双关** | `add` 一个词不要既表示「加法」又表示「插入集合」 | 一个词一个意思 |

## 三、函数：越短越好，只做一件事 ⭐⭐

> 书里的原话：*"函数的第一规则是短小，第二规则是更短小。函数应该短到 20 行以内。"*
> 作者甚至展示了著名的 **FitNesse 项目**——大部分函数只有 **3~5 行**。

### 3.1 函数的六条规矩

| 规矩 | 说明 | 判据 |
| ---- | ---- | ---- |
| **短小** | 理想 20 行内，超过一屏就该拆 | 屏幕上放不下 = 太长了 |
| **只做一件事** | 一个函数只做「一件事」，判断标准：**能不能再拆出一个函数** | 能拆就是做了多件事 |
| **每个函数一个抽象层级** | 一个函数里的语句应该在同一「详细程度」 | 别把 `calculatePay()` 和 `salary = base * rate` 混在一个函数 |
| **switch 要封装** | switch 语句尽量**只出现一次**，用多态替代 | 到处都是 `switch(type)` = 加类型就要改 N 处 |
| **参数越少越好** | 0 个最理想，1 个其次，2 个可接受，**3 个以上要封装成对象** | 参数 >3 基本是「函数做了多件事」 |
| **无副作用** | 函数名要如实反映它做的所有事 | `checkPassword()` 里偷偷改了 Session（这就是"副作用"） |

### 3.2 三段式重构演示：从「一坨」到「整洁」

**❌ 反例：一个函数干了五件事**（真实项目里太常见了）

```java
public class OrderService {
    public Map<String, Object> handle(Long orderId) {
        // ① 查订单
        Order o = orderMapper.selectById(orderId);
        // ② 校验状态
        if (o == null || o.getStatus() != 0) {
            return Map.of("code", 500, "msg", "订单状态异常");
        }
        // ③ 扣库存
        for (OrderItem i : o.getItems()) {
            Stock s = stockMapper.selectBySku(i.getSku());
            s.setNum(s.getNum() - i.getNum());
            stockMapper.updateById(s);
        }
        // ④ 改状态
        o.setStatus(1);
        orderMapper.updateById(o);
        // ⑤ 发消息
        rabbitTemplate.convertAndSend("order.exchange", "order.paid", orderId);
        return Map.of("code", 200, "msg", "success");
    }
}
```

**问题清单**（对照上面的六条规矩）：
- ❌ 太长（一屏看不完）
- ❌ 做了五件事（查/校验/扣库存/改状态/发消息）
- ❌ 抽象层级混乱（`orderMapper.selectById` 是高级操作，`s.setNum(s.getNum()-i.getNum())` 是低级操作）
- ❌ 返回 `Map<String,Object>`——调用了还得猜 key 是什么
- ❌ 用 500/200 魔法数

**✅ 正例：拆成同抽象层级的「故事」**

```java
public class OrderService {

    /** 支付成功的处理流程——读起来像一段「故事的目录」 */
    public PayResult handleOrderPaid(Long orderId) {
        Order order = loadOrder(orderId);            // ① 加载
        validatePayable(order);                      // ② 校验
        deductStock(order);                          // ③ 扣库存
        markOrderPaid(order);                        // ④ 改状态
        notifyPaymentSuccess(order);                 // ⑤ 发消息
        return PayResult.success(orderId);
    }

    // 每个小函数只做一件事，且处于同一抽象层级
    private Order loadOrder(Long orderId) {
        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            throw new BizException(ErrorCode.ORDER_NOT_FOUND);
        }
        return order;
    }

    private void validatePayable(Order order) {
        if (order.getStatus() != OrderStatus.UNPAID) {
            throw new BizException(ErrorCode.ORDER_STATUS_INVALID);
        }
    }

    private void deductStock(Order order) {
        for (OrderItem item : order.getItems()) {
            stockService.deduct(item.getSku(), item.getNum());  // 细节下沉到 stockService
        }
    }

    private void markOrderPaid(Order order) {
        order.setStatus(OrderStatus.PAID);
        order.setPaidTime(LocalDateTime.now());
        orderMapper.updateById(order);
    }

    private void notifyPaymentSuccess(Order order) {
        rabbitTemplate.convertAndSend(
                RabbitConst.ORDER_EXCHANGE,
                RabbitConst.PAID_ROUTING_KEY,
                order.getId());
    }
}
```

> 💡 **对比一眼看出的收益**：
> - 主函数 `handleOrderPaid()` **读起来就是一个目录**，5 行看清整个流程
> - 想知道「扣库存怎么扣」，跳到 `deductStock()`；想知道「怎么校验」，跳到 `validatePayable()`
> - **改扣库存逻辑不会碰到校验逻辑**——降低出错概率
> - 每个函数都能单独写单元测试

### 3.3 三参数以上 → 封装成对象

```java
// ❌ 反例：4 个参数，调用时全靠顺序记忆，写错了编译器也不报错
public void createUser(String name, String phone, String email, int age) { }

// 调用处：这俩 String 反了根本看不出来
createUser("张三", "13800138000", "z@x.com", 25);

// ✅ 正例：参数对象 + 建造者
public record CreateUserCommand(String name, String phone, String email, int age) {
    public static Builder builder() { return new Builder(); }
    // ... Builder 省略
}

createUser(CreateUserCommand.builder()
        .name("张三")
        .phone("13800138000")
        .email("z@x.com")
        .age(25)
        .build());
```

### 3.4 switch 语句：用多态替代

```java
// ❌ 反例：每加一种支付方式，就要改这个 switch（违反开闭原则）
public BigDecimal calcFee(String payType, BigDecimal amount) {
    switch (payType) {
        case "ALIPAY":  return amount.multiply(new BigDecimal("0.006"));
        case "WECHAT":  return amount.multiply(new BigDecimal("0.006"));
        case "UNIONPAY":return amount.multiply(new BigDecimal("0.005"));
        default: throw new IllegalArgumentException("未知支付方式");
    }
}
```

```java
// ✅ 正例：谁需要知道费率，谁自己实现（策略模式 + 枚举工厂）
public interface PayChannel {
    BigDecimal calcFee(BigDecimal amount);
}

public enum PayChannelType {
    ALIPAY(BigDecimal.valueOf(0.006)),
    WECHAT(BigDecimal.valueOf(0.006)),
    UNIONPAY(BigDecimal.valueOf(0.005));

    private final BigDecimal rate;
    PayChannelType(BigDecimal rate) { this.rate = rate; }

    public BigDecimal calcFee(BigDecimal amount) { return amount.multiply(rate); }
}
```

## 四、注释：好东西用错了就是坏东西

> 书里的反直觉观点：*"注释最多只能弥补代码表达力的不足。如果你发现自己需要写注释，先想想能不能改代码。"*
> **「注释是失败的味道」**——每一次写注释，都该问：**能不能用代码替掉它？**

### 4.1 什么注释是「好」的

| 好注释 | 例子 |
| ---- | ---- |
| **法律信息** | 版权声明、许可证（必须写） |
| **信息不足时的补充** | 说明某个返回值可能为 `null` 的**原因** |
| **对意图的解释** | 解释「为什么这么写」，而非「写了什么」 |
| **警告** | `// ⚠️ 这里必须用 synchronized，否则并发下会脏读` |
| **TODO** | `// TODO(zhangsan 2026-10): 等 B 端接口上线后替换` |

### 4.2 什么注释是「坏」的（重点！）

| 坏注释 | ❌ 例子 | 怎么改 |
| ---- | ---- | ---- |
| **重复代码** | `i++; // i 自增` | 删掉 |
| **误导性** | `// 返回用户列表` 但实际返回的是 `Map` | 改注释或改代码 |
| **噪音** | 每个 getter 上写 `/** 获取 name */` | 全删 |
| **位置标记** | `// ====== 以下为工具方法 ======` | 拆类 |
| **注释掉的代码** | 一整段被 `//` 注释的历史代码 | **直接删**（Git 里有记录，留着只会腐烂） |
| **该用函数名表达的** | `// 判断是否为大额订单` `if (a > 10000)` | 抽成 `isLargeOrder(a)` |

### 4.3 Java 实战：坏注释 → 好代码

```java
// ❌ 反例：注释在替代码「还债」
// 检查用户是否有权限，如果有则返回 true
// p 是 permission code，u 是 user
// 注意：admin 一定返回 true
public boolean check(String p, User u) {
    return u.isAdmin() || u.getPerms().contains(p);
}
```

```java
// ✅ 正例：把注释里的信息「翻译」进代码，注释就不需要了
public boolean hasPermission(User user, Permission permission) {
    return user.isAdmin() || user.getPermissions().contains(permission);
}
```

> 💡 **一句话记住**：**能用好名字和好结构表达的，绝不用注释**。注释只留「代码表达不了的**原因**」。

## 五、格式：让你的代码「看上去就该是这样」

> 书里说：*"代码格式关乎沟通，而沟通是开发者的头等大事。"*

### 5.1 垂直格式（从上到下）

| 规则 | 说明 |
| ---- | ---- |
| **文件大小** | 理想 **200 行以内**，上限约 500 行。大文件改成「类」 |
| **概念间加空行** | 不同概念的分隔用空行，密切相关的行靠在一起 |
| **变量声明靠近使用处** | **别在方法顶部声明所有变量**（C 语言遗留习惯） |
| **相关函数靠近** | 调用者放在被调用者上面（像读报纸，先看标题） |
| **从上到下阅读** | 顶层函数在前，细节逐层向下展开 |

```java
// ✅ 垂直顺序示范：读起来像读一篇「倒金字塔结构」的新闻
public class OrderService {

    // ① 入口（最高抽象层）放在最上面
    public PayResult pay(PayCommand cmd) {
        Order order = loadOrder(cmd.orderId());
        validate(order);
        doPay(order, cmd.payChannel());
        return PayResult.success(order.getId());
    }

    // ② 一层层往下，细节越来越具体
    private Order loadOrder(Long id) { ... }
    private void validate(Order order) { ... }
    private void doPay(Order order, PayChannel channel) { ... }
}
```

### 5.2 水平格式（行内）

| 规则 | 说明 |
| ---- | ---- |
| **行宽** | 上限 **120 字符**（书里建议 80~120，团队统一即可） |
| **空格强调优先级** | `a*b + c/d` —— 乘除优先级高，两边不加空格；加减两边加 |
| **缩进统一** | 一个项目只能用一种（4 空格 或 2 空格 或 Tab），**别混** |
| **不手动对齐** | ❌ `int a    = 1;` `int bbbb = 2;` —— IDE 格式化会打乱 |
| **团队规则优先** | 用统一的 formatter 配置文件，**让别人格式化你的代码不该产生 diff** |

> 💡 **落地建议**：Java 项目用 **Google Java Format** 或 **Alibaba P3C** 插件 + `.editorconfig` + CI 检查，**把格式化交给工具，别在 review 里争论空格**。

## 六、错误处理：把「失败」当成一等公民 ⭐

> 书里强调：*"错误处理很重要，但如果它搞乱了主要逻辑，就是错误的。"*
> **错误处理的关键是：主要逻辑和错误处理要分离。**

### 6.1 六条规矩

| 规矩 | ❌ 反例 | ✅ 正例 |
| ---- | ---- | ---- |
| **用异常而非返回码** | `int code = doSth(); if (code == -1) ...` | `throw new BizException(...)` |
| **先写 try-catch-finally** | 写完逻辑再包 try | 先定好失败怎么办，再写成功路径 |
| **别返回 `null`** | `return null;` 调用方忘了判空就 NPE | 返回空集合 `Collections.emptyList()` 或 `Optional` |
| **别传 `null`** | `method(null)` | 用重载/参数对象/`Objects.requireNonNull` |
| **异常要有信息量** | `throw new RuntimeException()` | 带上下文：`throw new BizException(ORDER_NOT_FOUND, "订单不存在: " + id)` |
| **别在 catch 里吞异常** | `catch (Exception e) { }` | 至少记录日志，或包装后重抛 |

### 6.2 Java 实战：从「吞异常」到「带上下文抛」

```java
// ❌ 反例：经典的「吞异常三连」
public User getUser(Long id) {
    try {
        return userMapper.selectById(id);   // 查不到返回 null，调用方 NPE
    } catch (Exception e) {
        e.printStackTrace();                // ① 只打印，日志系统抓不到
        return null;                        // ② 返回 null
    }                                       // ③ 异常信息全丢了
}
```

```java
// ✅ 正例：失败路径明确，信息完整
public User getUser(Long id) {
    if (id == null) {
        throw new IllegalArgumentException("用户 id 不能为空");
    }
    User user = userMapper.selectById(id);
    if (user == null) {
        // 带上「什么操作 + 什么参数」——排查时一眼定位
        throw new BizException(ErrorCode.USER_NOT_FOUND, "用户不存在, id=" + id);
    }
    return user;
}
```

> ⚠️ **书里最强调的一点**：**别用异常做流程控制**（比如用 `try { ... } catch (NumberFormatException)` 来判断字符串是不是数字）。异常的开销大，且语义不清。
> 💡 **Java 8+ 的处理**：返回「可能没有」的结果用 `Optional<T>`；返回「可能为空」的集合用 `Collections.emptyList()`。详见 [[《Effective Java》笔记]]。

## 七、边界：把外部依赖「关在门外」⭐

> 书里的核心思想：*"我们很少能控制第三方代码，所以要写「学习测试」和「适配器」，把外部的不确定性隔离在我们能掌控的边界内。"*

### 7.1 边界处理的三个手法

| 手法 | 做什么 | 收益 |
| ---- | ---- | ---- |
| **学习性测试** | 给第三方 API 写测试，验证「它的行为是不是我以为的那样」 | 不用猜文档，出问题能立刻定位是它变了还是你错了 |
| **适配器模式** | 用接口把第三方包起来，业务代码只依赖自己的接口 | 换供应商只改一个适配器 |
| **别传递内部类型** | 别把第三方库的类型（如 `Map<String,Object>`、`HttpResponse`）暴露给业务层 | 升级第三方库不会引发全项目改动 |

```java
// ❌ 反例：业务代码直接依赖第三方 SDK 的类型和异常——换库就要全改
public Order queryFromThirdParty(Long id) {
    ThirdPartyResponse resp = ThirdPartySdk.get(id);   // 业务代码被 SDK 污染
    if (resp.getCode() != 0) throw new RuntimeException(resp.getMsg());
    return JSON.parseObject(resp.getData(), Order.class);
}
```

```java
// ✅ 正例：适配器隔离——业务只依赖自己定义的接口
public interface OrderQueryClient {
    Order queryById(Long orderId);
}

@Component
public class ThirdPartyOrderQueryAdapter implements OrderQueryClient {
    @Override
    public Order queryById(Long orderId) {
        try {
            ThirdPartyResponse resp = ThirdPartySdk.get(orderId);
            if (resp.getCode() != 0) {
                throw new BizException(ErrorCode.THIRD_PARTY_ERROR, resp.getMsg());
            }
            return JSON.parseObject(resp.getData(), Order.class);
        } catch (ThirdPartyException e) {
            // 第三方异常统一翻译成自己的异常
            throw new BizException(ErrorCode.THIRD_PARTY_ERROR, "查询订单失败: " + orderId, e);
        }
    }
}
```

### 7.2 「整洁的边界」还包含什么

- **日志一定要记**：调用第三方前后都记（含耗时），出事能甩锅也能自证
- **超时一定要设**：所有外部调用必须有超时，否则一个慢依赖能拖垮整个服务
- **降级预案要写**：第三方挂了返回什么兜底值？——**在写代码时就决定，别等出事**

## 八、单元测试：整洁代码的「安全网」⭐

> 书里的名言：*"测试代码和生产代码一样重要。它也需要被维护、被保持整洁。"*
> 还有一个核心概念：**F.I.R.S.T.**

### 8.1 F.I.R.S.T. 原则

| 字母 | 原则 | 含义 |
| ---- | ---- | ---- |
| **F** | **Fast**（快） | 测试必须跑得快，否则你不会频繁跑 |
| **I** | **Independent**（独立） | 测试之间不能相互依赖，任何一个都能单独跑 |
| **R** | **Repeatable**（可重复） | 任何环境都能跑，不依赖「今天是不是周三」 |
| **S** | **Self-Validating**（自验证） | 结果只能是「通过」或「失败」，不用人肉看输出 |
| **T** | **Timely**（及时） | **在写生产代码之前或同时写**（TDD），别等上线前补 |

### 8.2 三条设计规矩

| 规矩 | 说明 |
| ---- | ---- |
| **每个测试一个断言概念** | 一个测试只验证一件事，失败时一眼知道是哪坏了 |
| **一个测试一个 Arrange-Act-Assert** | 准备 → 执行 → 断言，三段清晰 |
| **测试代码也要整洁** | 测试代码的「重复」可以被允许，但必须可读；**测试里的 bug 比生产代码的 bug 更危险** |

### 8.3 Java 实战：JUnit 5 风格

```java
class OrderServiceTest {

    private OrderService orderService;

    @BeforeEach
    void setUp() {
        orderService = new OrderService(new InMemoryOrderRepository());
    }

    @Test
    @DisplayName("未支付订单可以支付成功")
    void should_pay_successfully_when_order_is_unpaid() {
        // Arrange 准备
        Order order = anUnpaidOrder().withId(1L).build();
        orderService.save(order);

        // Act 执行
        PayResult result = orderService.pay(1L);

        // Assert 断言
        assertThat(result.isSuccess()).isTrue();
        assertThat(orderService.getById(1L).getStatus()).isEqualTo(OrderStatus.PAID);
    }

    @Test
    @DisplayName("已支付订单再次支付抛出业务异常")
    void should_throw_when_order_already_paid() {
        Order order = aPaidOrder().withId(2L).build();
        orderService.save(order);

        assertThatThrownBy(() -> orderService.pay(2L))
                .isInstanceOf(BizException.class)
                .hasFieldOrPropertyWithValue("errorCode", ErrorCode.ORDER_STATUS_INVALID);
    }
}
```

> 📌 **关联**：芋道项目的测试基类（`BaseDbUnitTest` / `BaseMockitoUnitTest`）和断言工具见 [[单元测试]]。

## 九、类与系统：越大越难维护

### 9.1 类的组织原则

| 原则 | 说明 | 判据 |
| ---- | ---- | ---- |
| **类应该短小** | 书里的标准：**类的职责可用「25 个词以内」描述完** | 描述它需要「而且……」= 违反 SRP |
| **单一职责（SRP）** | 一个类只有一个「改变的理由」 | 改业务要动它、改数据库也要动它 = 该拆 |
| **内聚性高** | 类里方法用的实例变量越多，内聚性越高 | 有些方法不用某字段 = 那个字段该搬走 |
| **为修改而组织** | 类应该对扩展开放、对修改封闭 | 加一个类型要改 N 个 switch |
| **方法参数与实例变量** | 参数越多越该考虑「是不是该做成字段/对象」 | 方法参数 > 3 且总是一起出现 = 抽对象 |

### 9.2 系统级「整洁」：依赖注入与领域分离

```java
// ❌ 反例：硬编码依赖，没法测试、没法换实现
public class OrderService {
    private final OrderMapper mapper = new OrderMapperImpl();   // new 死了
}
```

```java
// ✅ 正例：依赖注入——「构造时传入」，谁决定用什么由上层说了算
@Service
@RequiredArgsConstructor   // Lombok 生成构造器，字段 final 保证不可变
public class OrderService {
    private final OrderMapper orderMapper;
    private final StockService stockService;
}
```

> 💡 **书里的观点**：**「系统」的整洁靠「关注点分离」——把初始化的逻辑（new 对象、装配依赖）和运行时的业务逻辑分开**。Spring 的 IoC 就是这一思想的工程化。详见 [[05_SpringBoot 核心]]。
> 📌 **关联**：类的拆分手法、坏味道识别见 [[《重构》笔记]]。

## 十、并发：整洁的并发代码

> 书里提醒：*"并发总是很难，即使对专家而言。所以并发代码要单独写、单独测、单独隔离。"*

### 10.1 三条核心建议

| 建议 | 说明 |
| ---- | ---- |
| **分离并发代码** | 把线程管理、同步逻辑**集中**在一个地方，别散落在业务代码里 |
| **限制共享数据** | 共享可变数据是万恶之源——能不变就不变，能局部就局部 |
| **用线程安全的容器** | 别自己 `synchronized` 包 `ArrayList`，用 `ConcurrentHashMap` / `CopyOnWriteArrayList` |
| **线程池要自定义** | **别用 `Executors.newFixedThreadPool()`**（无界队列会 OOM），手写 `ThreadPoolExecutor` |
| **执行器抽象** | 用 `ExecutorService` 接口，别直接 `new Thread()` |

### 10.2 Java 实战：并发三件套

```java
// ❌ 反例：自己 new Thread + 手写同步 + 共享可变 Map
public class Counter {
    private Map<String, Integer> counts = new HashMap<>();   // 非线程安全！

    public void count(String key) {
        synchronized (this) {                                 // 锁太粗，全串行
            counts.put(key, counts.getOrDefault(key, 0) + 1);
        }
    }
}
```

```java
// ✅ 正例：并发容器 + 原子类 + 自定义线程池
@Service
public class MetricsCollector {
    // ① 并发容器：内部已做分段/无锁优化，不用自己加锁
    private final ConcurrentMap<String, LongAdder> counters = new ConcurrentHashMap<>();

    // ② 自定义线程池（拒绝策略、队列都有界，避免 OOM）
    private final ExecutorService pool = new ThreadPoolExecutor(
            4,                                   // 核心线程数
            8,                                   // 最大线程数
            60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(1000),      // ⚠️ 有界队列
            new ThreadFactoryBuilder().setNameFormat("metrics-%d").build(),
            new ThreadPoolExecutor.CallerRunsPolicy());  // 满了让调用者跑，形成背压

    public void count(String key) {
        counters.computeIfAbsent(key, k -> new LongAdder()).increment();  // 无锁自增
    }
}
```

> 📌 **关联**：JUC 的完整原理（AQS、CAS、锁升级、线程池参数测算）见 [[03_JUC 详细讲解]]；`volatile` 的底层内存屏障见 [[《操作系统》笔记]]。

## 十一、坏味道速查表（可当 review 清单）

> 书里 + 结合《重构》整理的**高频坏味道**，**代码 review 时逐条对照**。

| 坏味道 | 症状 | 药方 |
| ---- | ---- | ---- |
| **名字含糊** | `data`、`temp`、`info`、`handle` | 改成名副其实的名字 |
| **函数太长** | 超过一屏 | 拆成同抽象层级的小函数 |
| **函数做多件事** | 名字里有「And」 | 拆开 |
| **参数太多** | > 3 个 | 封装成参数对象 |
| **重复代码** | 同样的逻辑出现 2+ 次 | 抽取公共方法/父类/工具类 |
| **注释掉代码** | `// oldMethod();` | 删除（Git 里有） |
| **魔法数** | `if (status == 3)` | 抽成常量/枚举 |
| **深嵌套** | `if` 套 `for` 套 `if` | 卫语句提前返回、抽方法 |
| **返回 null** | `return null` 到处是 | 空对象 / `Optional` / 空集合 |
| **吞异常** | `catch(Exception e) {}` | 记日志 + 包装重抛 |
| **类太大** | 500 行以上的类 | 按职责拆分 |
| **数据泥团** | 总是一起出现的几个参数 | 抽成对象 |
| **依恋情结** | 方法总在访问别的类的数据 | 把方法搬到数据所在的类 |
| **switch 泛滥** | 到处都是同一个 switch | 多态替代 |
| **过长的导入/继承链** | 类/包依赖过深 | 拆包、面向接口 |

## 十二、从「读过」到「用上」：落地清单

读书最大的问题是「读完就忘」。**这四条是真正能让你改变的**：

| 动作 | 具体做法 | 收益 |
| ---- | ---- | ---- |
| **① 装上 P3C + formatter** | IDEA 装 Alibaba Java Coding Guidelines + Google Java Format | 立刻消灭 80% 的格式/命名问题 |
| **② 定一条团队命名规范** | 写进团队文档，review 时按它来 | 命名统一后，代码「像一个人写的」 |
| **③ 改代码前先重构** | 想加功能前，先看看要不要先拆结构（结合 [[《重构》笔记]]） | 避免在烂结构上继续堆 |
| **④ 每周挑一个「函数最长」的重构** | 用小步重构 + 测试保护 | 持续改善，不停留在抱怨 |

> 💡 **最重要的一句**：**「整洁」不是一个状态，而是一个持续的动作**——代码不是一次写成整洁的，是**每次改动时都让它更整洁一点**。
> 书里的「童子军军规」：**「离开时，比你来的时候，让它更干净一点。」**

## 十三、一句话总结 & 全书地图

> **「代码是写给人读的。让代码易读，是程序员最核心的专业素养。」**

### 核心结论（五条）

1. **命名和函数是收益最高的两项投资**——一天内就能改，终身受益
2. **注释是失败的味道**——能用代码表达的，别用注释
3. **小函数 + 单一职责 + 清晰命名** = 整洁的 90%
4. **错误处理和边界要「显式」**——别用 null、别吞异常、别暴露第三方类型
5. **整洁是持续动作，不是一次性工程**——童子军军规
