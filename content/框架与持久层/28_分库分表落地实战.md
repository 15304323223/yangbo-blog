# 分库分表落地实战（从为什么到怎么做，ShardingSphere 全流程）

> **一句话概括**：当单表数据量太大（千万级以上）、单库扛不住压力时，把一张表拆成多张表、一个库拆成多个库，让数据分散存储、并行处理。但分库分表不是银弹——它会带来跨库查询、分布式事务、主键生成、数据迁移等一系列复杂度，只有真的需要时才做。
>
> **适合谁**：单表数据量越来越大查询变慢、听说过分库分表但说不清具体怎么落地、面试被问「分库分表后怎么分页查询」「分布式事务怎么解决」答不上来的人。

---

## 零、先建立印象：把它想象成「图书馆分书架」

一个图书馆只有一个书架（单库单表），书越来越多，找一本书要翻半天，借书还书都排队。

怎么办？
1. **分表**：按书的类别分多个书架（文学、科技、历史…），找书直接去对应书架
2. **分库**：建多个图书馆（东城馆、西城馆…），读者就近借书，分散压力

| 图书馆 | 分库分表 |
|---|---|
| 一个书架放不下 | 单表数据量太大（千万/亿级） |
| 借书排队太久 | 单库 QPS 太高，连接池满 |
| 按类别分书架 | 分表（按某个字段取模/范围） |
| 建多个图书馆 | 分库（多个数据库实例） |
| 找书要知道去哪个书架 | 路由规则（分片键 + 分片算法） |
| 跨类别找书要跑多个书架 | 跨库查询问题 |

## 一、什么时候才需要分库分表？

### 1.1 不要过早分库分表！

```
分库分表 = 复杂度爆炸
能不做就不做，能晚做就晚做。
```

**先试试这些方案，都不行了再分库分表：**
1. **加索引**：90% 的慢查询是索引问题
2. **优化 SQL**：避免全表扫描、避免大事务、避免 SELECT *
3. **读写分离**：一主多从，写走主库，读走从库
4. **缓存**：Redis 挡在数据库前面，热点数据不查库
5. **归档冷数据**：历史数据迁到归档表/归档库，主表只留热数据
6. **升级硬件**：换更好的 CPU、更大的内存、SSD 换 NVMe

### 1.2 真正需要分库分表的信号

| 信号 | 阈值（参考） |
|---|---|
| 单表数据量 | 5000 万行以上（MySQL InnoDB 单表建议不超过 2000 万） |
| 单库 QPS | 持续 5000+，读写分离和缓存都扛不住 |
| 单库连接数 | 经常打满 max_connections |
| 磁盘 IO | 持续 80%+ |
| 数据量增长 | 每月增长百万级，且持续增长 |

> 💡 **经验值**：MySQL InnoDB 单表 2000 万行是一个经验阈值，超过后 B+ 树层级变深，查询性能明显下降。但这不是绝对的，如果表很窄（字段少）、查询都走索引，5000 万也能跑；如果表很宽、查询复杂，500 万就可能慢。

## 二、分库分表的方式

### 2.1 垂直拆分 vs 水平拆分

```
垂直拆分：按业务/字段拆
水平拆分：按数据行拆
```

| 拆分方式 | 说明 | 示例 |
|---|---|---|
| **垂直分库** | 按业务模块拆到不同的库 | 用户库、订单库、商品库 |
| **垂直分表** | 把宽表按字段拆成多张表 | 订单基本信息表 + 订单扩展信息表 |
| **水平分库** | 同一个表的数据分散到多个库 | 订单库1、订单库2、订单库3 |
| **水平分表** | 同一个库内，一张表拆成多张表 | order_0、order_1、order_2 |

**垂直分库示例：**
```
原来：一个库包含用户、订单、商品所有表
现在：
  user_db   → 用户相关表
  order_db  → 订单相关表
  product_db → 商品相关表
```

**水平分表示例：**
```
原来：一张 order 表，1 亿条数据
现在：
  order_0  → user_id % 4 = 0 的数据
  order_1  → user_id % 4 = 1 的数据
  order_2  → user_id % 4 = 2 的数据
  order_3  → user_id % 4 = 3 的数据
```

### 2.2 分片算法（怎么决定数据去哪张表）

| 算法 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **取模（Hash）** | `user_id % 分片数` | 数据均匀，实现简单 | 扩容麻烦（需要重新分布数据） |
| **范围（Range）** | 按 ID 范围/时间范围分 | 扩容简单，范围查询快 | 数据可能不均匀（热点） |
| **一致性 Hash** | 虚拟节点环 | 扩容只影响部分数据 | 实现复杂，数据可能不均匀 |
| **枚举（List）** | 按固定值分（如地区） | 符合业务逻辑 | 分片数固定，不好扩容 |
| **时间** | 按年月分表 | 历史数据好归档 | 最新表热点严重 |

**取模 vs 范围怎么选？**
```
取模：数据均匀，但跨分片范围查询慢（要查所有分片）
范围：范围查询快（只查相关分片），但可能数据热点
```

> 💡 **实战建议**：大多数场景用**取模**。如果经常需要按时间范围查询，用**时间分表**（按月/按季）。如果需要频繁扩容，用**一致性 Hash**。

### 2.3 分片键怎么选？

```
分片键 = 用来决定数据去哪张表的字段
选对分片键 = 成功了一半
```

**选分片键的原则：**
1. **查询频率最高**：大部分查询都带这个字段，能直接定位到分片
2. **数据分布均匀**：这个字段的值分布均匀，不会导致某些分片数据特别多
3. **不可变**：这个字段的值不会变，否则数据要迁移
4. **业务关联**：关联查询的表用相同的分片键，能做到同库关联

**常见场景的分片键：**
| 业务 | 分片键 | 原因 |
|---|---|---|
| 订单表 | user_id | 用户查自己的订单，带 user_id |
| 订单表 | order_id | 按订单号查，订单号本身包含分片信息 |
| 日志表 | create_time | 按时间范围查，按月分表好归档 |
| 用户表 | user_id | 按用户 ID 查 |

> ⚠️ **经典坑**：订单表用 user_id 分片，但后台管理要按订单状态查所有订单（不带 user_id），就要查所有分片，性能很差。解法：后台查询走从库/ES，或者冗余一张按状态分片的表。

## 三、ShardingSphere 落地实战

### 3.1 什么是 ShardingSphere？

```
ShardingSphere = 开源的分布式数据库中间件
三大产品：
  1. ShardingSphere-JDBC：轻量级 Java 框架，在应用层做分库分表（最常用）
  2. ShardingSphere-Proxy：数据库代理，对应用透明（像用普通数据库一样）
  3. ShardingSphere-Sidecar：服务网格模式（云原生）
```

### 3.2 ShardingSphere-JDBC 快速集成

```xml
<!-- Maven 依赖 -->
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core-spring-boot-starter</artifactId>
    <version>5.4.0</version>
</dependency>
```

```yaml
# application.yml 配置
spring:
  datasource:
    # 数据源名称
    names: ds0,ds1
    ds0:
      type: com.zaxxer.hikari.HikariDataSource
      driver-class-name: com.mysql.cj.jdbc.Driver
      jdbc-url: jdbc:mysql://localhost:3306/order_db_0?useUnicode=true&characterEncoding=utf8
      username: root
      password: xxx
    ds1:
      type: com.zaxxer.hikari.HikariDataSource
      driver-class-name: com.mysql.cj.jdbc.Driver
      jdbc-url: jdbc:mysql://localhost:3306/order_db_1?useUnicode=true&characterEncoding=utf8
      username: root
      password: xxx

  shardingsphere:
    rules:
      sharding:
        tables:
          # 订单表配置
          t_order:
            # 实际数据节点：ds0.t_order_0, ds0.t_order_1, ds1.t_order_0, ds1.t_order_1
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..1}
            # 分库策略：按 user_id 取模，2个库
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: database-inline
            # 分表策略：按 order_id 取模，2张表
            table-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: table-inline
        # 分片算法
        sharding-algorithms:
          database-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}
          table-inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 2}
```

```java
// 业务代码完全不用改，正常用 MyBatis-Plus
@Mapper
public interface OrderMapper extends BaseMapper<Order> {
    // 正常写 SQL，ShardingSphere 自动路由到正确的库和表
}
```

### 3.3 分布式主键（分库分表后自增 ID 会重复！）

```
问题：每个库的表都有自己的自增 ID，分库后 ID 会重复
解法：用分布式 ID 生成器
```

**ShardingSphere 内置雪花算法（Snowflake）：**
```yaml
spring:
  shardingsphere:
    rules:
      key-generators:
        snowflake:
          type: SNOWFLAKE
          props:
            worker-id: 1  # 工作节点 ID，每个实例不同
      tables:
        t_order:
          key-generate-strategy:
            column: order_id
            key-generator-name: snowflake
```

**雪花算法 ID 结构（64位）：**
```
1位符号位 + 41位时间戳 + 10位工作节点ID + 12位序列号
```
- 41位时间戳：可用 69 年
- 10位工作节点：支持 1024 个节点
- 12位序列号：每毫秒最多生成 4096 个 ID

> 💡 **优点**：高性能、趋势递增、不依赖数据库
> **缺点**：依赖服务器时钟（时钟回拨会导致 ID 重复）、ID 不是连续的

## 四、分库分表带来的问题与解决方案

### 4.1 跨库关联查询（Join）

```
问题：订单表在 ds0，用户表在 ds1，关联查询要跨库
解法：
```

| 方案 | 说明 | 适用场景 |
|---|---|---|
| **字段冗余** | 订单表冗余用户名，不用关联 | 冗余字段不常变 |
| **全局表** | 字典表/配置表每个库都存一份，同步更新 | 数据量小、变更少 |
| **应用层组装** | 先查订单，再批量查用户，内存里组装 | 数据量不大 |
| **宽表** | 把关联数据提前聚合到一张宽表 | 报表、查询密集 |
| **ES 同步** | 数据同步到 ES，复杂查询走 ES | 复杂查询、多条件筛选 |

### 4.2 分布式事务

```
问题：一个操作要写多个库，怎么保证原子性？
解法：
```

| 方案 | 一致性 | 性能 | 适用场景 |
|---|---|---|---|
| **2PC（XA）** | 强一致 | 低 | 对一致性要求极高、并发不高 |
| **TCC** | 最终一致 | 中 | 资金、库存等核心业务 |
| **Saga** | 最终一致 | 中 | 长事务、流程多 |
| **本地消息表** | 最终一致 | 高 | 大多数业务场景 |
| **MQ 事务消息** | 最终一致 | 高 | 有 MQ 基础设施 |

> 💡 **实战建议**：90% 的场景用**最终一致**（本地消息表/MQ），不要上来就用强一致。强一致性能差、实现复杂，只有金融支付等核心场景才需要。参考 [[23_分布式锁实现原理与实战]] 中的分布式事务部分。

### 4.3 跨库分页查询

```
问题：order by create_time limit 10000, 10，要查所有分片再归并排序
解法：
```

1. **禁止深度分页**：产品上限制最多翻 100 页，或者用「上一页/下一页」游标分页
2. **禁止跨分片排序**：排序字段必须是分片键，或者业务上接受不精确排序
3. **ES 同步**：分页查询走 ES，ES 天生支持分布式分页
4. **二次查询**：先查各分片的 ID，归并排序后再回表查详情（性能差，不推荐）

### 4.4 扩容（分片数不够了怎么办？）

```
问题：原来 2 个库，数据量增长，要扩到 4 个库
解法：
```

| 方案 | 说明 | 停机时间 |
|---|---|---|
| **停机迁移** | 停服 → 全量数据重新分布 → 改配置 → 启动 | 几小时 |
| **双写迁移** | 新数据双写（新旧分片）→ 历史数据迁移 → 校验 → 切读 → 停旧 | 零停机 |
| **一致性 Hash** | 扩容只影响 1/N 的数据，不用全量迁移 | 少量迁移 |

> 💡 **实战建议**：一开始就规划足够的分片数（比如先分 8 个逻辑分片，只部署 2 个物理库，后面扩容只需要把逻辑分片迁移到新物理库）。或者用一致性 Hash 减少扩容影响。

### 4.5 数据迁移（从单库到分库分表）

```
步骤：
1. 双写：新数据同时写旧库和新分片
2. 历史数据迁移：写脚本把旧数据按分片规则导入新分片
3. 数据校验：对比新旧数据，确保一致
4. 切读：读流量切到新分片
5. 观察：观察 1-2 周，确认没问题
6. 停旧：停止双写，下线旧库
```

## 五、分库分表 vs 其他方案选型

| 方案 | 适用数据量 | 复杂度 | 性能 | 成本 |
|---|---|---|---|---|
| 单库单表 + 索引优化 | < 2000 万 | 低 | 好 | 低 |
| 读写分离 | 读多写少 | 低 | 好 | 中 |
| 缓存 + 归档 | 热点集中 | 中 | 很好 | 中 |
| **分库分表** | **> 5000 万 / 高 QPS** | **高** | **好** | **高** |
| NewSQL（TiDB/OceanBase） | 亿级以上 | 中 | 好 | 高（运维成本） |

> 💡 **醍醐灌顶**：分库分表是「没办法的办法」。它解决了性能问题，但引入了跨库查询、分布式事务、扩容、迁移等一大堆复杂度。能不用就不用——先把索引、SQL、缓存、读写分离、归档做到极致，真的扛不住了再分。

## 六、面试口述总结

> **为什么要分库分表？**
> 单表数据量太大（千万级以上）查询变慢，单库 QPS 太高扛不住。分库分表把数据分散存储、并行处理，提升性能和容量。
>
> **分库分表有哪些方式？**
> 垂直拆分（按业务/字段拆）和水平拆分（按数据行拆）。水平拆分又分水平分库和水平分表。
>
> **分片算法有哪些？**
> 取模（Hash）、范围（Range）、一致性 Hash、枚举、时间。大多数场景用取模，按时间查询用时间分表。
>
> **分片键怎么选？**
> 选查询频率最高、数据分布均匀、不可变、业务关联的字段。比如订单表用 user_id，因为用户查自己的订单都带 user_id。
>
> **分库分表后有什么问题？**
> 跨库关联查询（字段冗余/全局表/ES）、分布式事务（最终一致/2PC/TCC）、跨库分页（禁止深分页/ES）、扩容（双写迁移/一致性 Hash）、分布式主键（雪花算法）。
>
> **什么时候不需要分库分表？**
> 数据量不到 2000 万、QPS 不高的时候。先优化索引、SQL、加缓存、读写分离、归档冷数据，这些都不行了再分库分表。分库分表复杂度很高，是最后的手段。
