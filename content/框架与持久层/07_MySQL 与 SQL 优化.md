# MySQL 与 SQL 优化（原理 → 应用 → 进阶）

> **一句话概括**：MySQL 优化不是"加索引就够了"，而是理解"数据怎么存、查询怎么找、锁怎么抢"——**从存储结构到索引设计到事务隔离，层层递进**。
>
> **适合谁**：能写 CRUD，但 `EXPLAIN` 看不懂、索引建了没效果、被问到"幻读怎么解决"一脸懵的人。
> **怎么读**：原理篇的 B+树和 MVCC 是地基；应用篇的 EXPLAIN 和深分页是日常武器；进阶篇的分库分表和死锁是面试硬菜。

---

## 零、先建立整体印象：把它想象成"图书馆"

| 图书馆 | 对应 MySQL | 一句话 |
|---|---|---|
| **书架（每格 16KB）** | 数据页（Page） | InnoDB 按页存数据，一页固定 16KB |
| **目录柜** | 索引（B+树） | 快速定位书在哪格，不用逐格翻 |
| **书的编号规则** | 聚簇索引 | 按主键顺序摆书，书本身就是目录 |
| **便签条（写书名+编号）** | 二级索引 | 便签条上只写书名和编号，要取书还得按编号去找 |
| **借阅记录本** | undo log | 记录每本书之前的版本，方便回退 |
| **阅览室隔离区** | MVCC + 锁 | 不同读者看到不同版本的书，互不干扰 |

## 一、原理篇

### 1.1 InnoDB 怎么存数据：页与 B+树

**页（Page）**：InnoDB 读写数据的最小单位是**16KB 的页**，不是一行一行读。哪怕你只查一行，MySQL 也会把整页（周围几十上百行）一起读进内存。

**B+树索引**：
- **聚簇索引（主键索引）**：叶子节点存的是**整行数据**。按主键顺序排列，所以主键建议用自增整数（顺序插入，页不分裂）。
- **二级索引（普通索引）**：叶子节点存的是**主键值**。查到主键后，还要回聚簇索引取整行——这叫**回表**。

```sql
-- 有二级索引 idx_name(name)
SELECT * FROM users WHERE name = '张三';
-- ① 在 idx_name 查到 name='张三' 对应的主键 id=5
-- ② 拿着 id=5 回聚簇索引取整行数据 → 回表

SELECT id, name FROM users WHERE name = '张三';
-- ① 在 idx_name 查到 id=5, name='张三'
-- ② 要查的列（id, name）索引里都有 → 不用回表！这叫【覆盖索引】
```

> 💡 **覆盖索引是免费优化**：查询的列正好都在索引里，MySQL 只读索引不读数据页，快得多。

### 1.2 索引失效：为什么建了索引却没用上

| 失效场景 | 原因 | 正确写法 |
|---|---|---|
| 联合索引 `(a,b,c)` 查 `b=1` | 不满足**最左前缀**：B+树先按 a 排，没 a 就无从找起 | 查 `a=1 AND b=1` 或单独查 `a=1` |
| `WHERE YEAR(create_time) = 2024` | 对列做函数运算 → 优化器算不出索引值 | `WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01'` |
| `WHERE name LIKE '%张%'` | 前模糊 `%` → 不知道第一个字是什么，B+树没法定位 | `LIKE '张%'`（后模糊）可以用索引 |
| `WHERE age = '18'`（age 是 int） | 隐式类型转换 → 先把每行的 age 转字符串再比 | 传对类型：`WHERE age = 18` |
| `WHERE status <> 1` | `<>` / `!=` 优化器通常放弃索引（认为要查大部分） | 改写成 `IN` 范围，或确认数据分布后强制索引 |

> 💡 **排查口诀**：`EXPLAIN` 看 `key` 列——如果为 NULL，说明没走索引，对照上面表格排查。

### 1.3 事务隔离与 MVCC

**四种隔离级别**（从松到严）：

| 级别 | 问题 | 说明 |
|---|---|---|
| 读未提交 | 脏读、不可重复读、幻读 | 几乎不用 |
| 读已提交 | 不可重复读、幻读 | Oracle 默认；同事务内两次读可能结果不同 |
| **可重复读** ⭐ | 幻读（MySQL 默认） | 同事务内两次读结果一样；InnoDB 用 Next-Key Lock 防幻读 |
| 串行化 | 无 | 完全串行，性能极差，几乎不用 |

**MVCC（多版本并发控制）**：
- 每行数据背后藏着两个隐藏列：`trx_id`（最后修改它的事务号）和 `roll_pointer`（指向 undo log 的指针）
- `undo log` 存着这行数据的历史版本
- 事务启动时生成一个 **ReadView**（快照），后面读数据时，根据 ReadView 判断哪个版本对自己可见
- **结果**：读不加锁！写才加锁。读写不阻塞，并发性能高。

**Next-Key Lock（记录锁 + 间隙锁）**：
- **记录锁**：锁某一行
- **间隙锁**：锁一个范围（如 `id BETWEEN 10 AND 20`），防止别的事务在这个范围插新行
- **组合 = Next-Key Lock**：既锁行又锁间隙 → **解决幻读**

> ⚠️ **幻读 vs 不可重复读**：不可重复读是"同一事务两次读，某行数据变了"；幻读是"同一事务两次读，**多出了之前没有的行**（别人插进来的）

## 二、应用篇（代码与命令）

### 2.1 建索引：覆盖索引是免费午餐

```sql
-- 场景：高频按 user_id + status 查订单，且只返回 id 和 status
-- 建联合索引，把查询的列都包进去 → 覆盖索引，不用回表
CREATE INDEX idx_user_status ON orders(user_id, status, id);

-- 查询
SELECT id, status FROM orders WHERE user_id = 100 AND status = 1;
-- EXPLAIN 的 Extra 列显示 "Using index" = 完美，只读索引不读数据页
```

### 2.2 EXPLAIN 解读：优化器的"体检报告"

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1;
```

| 列 | 看什么 | 含义 |
|---|---|---|
| `type` | 访问类型 | `const`（主键/唯一索引，最快）> `ref`（普通索引）> `range`（范围）> `index`（全索引扫描）> `ALL`（全表扫描，最慢） |
| `key` | 用了哪个索引 | 为 NULL = 没走索引 |
| `rows` | 预估扫描行数 | 越小越好； millions 级要警惕 |
| `Extra` | 额外信息 | `Using index`（覆盖索引，好）；`Using filesort`（额外排序，坏）；`Using temporary`（临时表，坏） |

> 💡 **优化目标**：`type` 至少 `ref`，杜绝 `ALL`；`Extra` 不要出现 `filesort` 和 `temporary`。

### 2.3 深分页优化（`LIMIT 100000, 20` 为什么慢）

**问题**：`LIMIT 100000, 20` 需要先把前 100020 行排好序，再扔掉前 100000 行。**越往后翻越慢。**

**解法一：延迟关联（先查 id 再 join）**
```sql
-- 先在内层查 id（覆盖索引，极快），再拿这 20 个 id 去取完整数据
SELECT * FROM orders
JOIN (
    SELECT id FROM orders WHERE user_id = 100 ORDER BY id LIMIT 100000, 20
) t USING(id);
```

**解法二：游标分页（推荐用于翻页）**
```sql
-- 前端传上一页最后一条的 id
SELECT * FROM orders WHERE user_id = 100 AND id > :lastId ORDER BY id LIMIT 20;
-- 复杂度永远是 O(20)，和翻到第几页无关
```
> 💡 **游标分页缺点**：不支持跳页（不能直接点到第 50 页），只适合"加载更多"场景。

## 三、进阶篇（面试深挖 + 生产注意）

### 3.1 三大范式 vs 反范式

- **第一范式**：列不可再分（地址拆成省/市/区）
- **第二范式**：非主键列必须依赖全部主键（联合主键时不能有部分依赖）
- **第三范式**：非主键列必须直接依赖主键（不能传递依赖：A→B→C，C 应该独立成表）

> 💡 **规范化的代价是多表 join**。读多写少的报表场景，**适度冗余**（反范式）换性能是常见做法。比如订单表直接冗余用户姓名，避免每次查订单都 join 用户表。

### 3.2 分库分表

**什么时候拆**：单表超 **1000 万行** 或 **100GB**，或写入 QPS 超过单机承受。

| 拆分维度 | 怎么做 | 注意 |
|---|---|---|
| **垂直拆分** | 按业务拆表：用户表、订单表、日志表放不同库 | 跨库 join 要用应用层拼装 |
| **水平拆分** | 按用户 id / 时间分片：用户 1~1000 万在 A 库，1000~2000 万在 B 库 | 跨片查询/排序/聚合是噩梦；用 ShardingSphere 等中间件 |

> ⚠️ **分库分表是最后手段**。先优化索引、加缓存、读写分离，真扛不住再拆。拆完复杂度指数级上升。

### 3.3 读写分离

一主多从：写走主库，读走从库。**注意主从延迟**——刚写完主库立刻读从库，可能读到旧数据。
- 解法：关键读（如支付后查订单状态）**强制走主库**；非关键读（列表页）走从库。

### 3.4 死锁排查

```sql
SHOW ENGINE INNODB STATUS;   -- 看 LATEST DETECTED DEADLOCK 段落
```
**业务预防**：所有事务按**固定顺序**加锁（比如都先锁 user 表再锁 order 表），破坏循环等待条件。

### 3.5 其他面试常问

- **Online DDL**：大表加字段用 `pt-osc`（Percona Toolkit）或 `gh-ost`，避免锁表导致业务中断
- **`COUNT(*)` 慢**：InnoDB 要逐行统计。解法：用 `EXPLAIN` 估算，或 Redis 维护计数器
- **`SELECT *` 的代价**：① 无法覆盖索引；② 网络传输量大；③ 容易回表。**永远明确列名。**
- **常见慢查询根因**：缺索引、索引失效、深分页、大事务锁等待、N+1 查询（ORM 懒加载循环触发）
