# 本地缓存 Ehcache 与 Caffeine（原理 → 应用 → 进阶）

> **一句话概括**：本地缓存就是**你手边的便签本**——查东西不用跑去档案室（Redis/数据库），直接翻开就看得见，快 10 倍。但缺点是只有你一个人看得见，别人不知道你写了什么。
>
> **适合谁**：知道 Redis 能做缓存，但不知道"本地缓存比 Redis 还快"、没听过 Caffeine、多级缓存不知道怎么搭的人。
> **怎么读**：原理篇理解"为什么本地缓存更快但有代价"；应用篇 Caffeine 代码直接可抄；进阶篇的多级缓存模式是面试加分项。

---

## 零、先建立整体印象：把它想象成"手边的便签本"

| 场景 | 对应缓存层级 | 速度 | 共享范围 |
|---|---|---|---|
| **大脑瞬间想起的事** | CPU 寄存器/L1 | 纳秒 | 单核 |
| **手边的便签本** | **本地缓存（Caffeine）** | **微秒** | **单实例** |
| **办公室公共白板** | Redis | 毫秒 | 所有实例共享 |
| **档案馆** | MySQL / 达梦 | 几十毫秒 | 持久化 |

**核心权衡**：本地缓存比 Redis 快一个数量级，但**多实例之间不共享**。适合"读极多、写极少、变化不频繁、允许短暂不一致"的数据。

---

## 一、原理篇：为什么需要本地缓存

### 1.1 本地缓存 vs Redis 的对比

| | 本地缓存（Caffeine） | Redis |
|---|---|---|
| **速度** | 微秒级（同 JVM 内存访问） | 毫秒级（+ 网络 RTT） |
| **容量** | 受单机内存限制（几百 MB） | 可集群扩展（几十 GB） |
| **共享性** | ❌ 仅当前实例可见 | ✅ 所有实例共享 |
| **一致性** | 多实例间不一致 | 强一致 |
| **适用数据** | 热点配置、结束标记、字典、用户会话 | 通用缓存、分布式锁、计数器 |

> 💡 **简历里的真实用法**：
> - 秒杀场景：本地缓存存"结束标记"，库存清零后请求直接本地判断，0 网络开销
> - 大屏场景：设备状态存本地缓存，比最新才更新，旧请求直接丢弃

### 1.2 淘汰算法：怎么决定便签本写满了撕哪页

| 算法 | 思路 | 问题 |
|---|---|---|
| **LRU**（最近最少用） | 很久没翻的那页撕掉 | 突发大批量只读一次的数据会把真正的热点挤出去 |
| **LFU**（最少使用） | 翻得最少的那页撕掉 | 老热点积累太高，新热点上不来 |
| **W-TinyLFU** ⭐ | **窗口期 + 频率过滤**：新数据先放窗口试一段时间，真的频繁访问才进主缓存 | Caffeine 默认，**命中率最高** |

> 💡 **不用背公式，记住结论**：Caffeine 的 W-TinyLFU 比传统 LRU/LFU 命中率高 10%~30%，**新项目直接用它**。

## 二、应用篇（代码，照着抄）

### 2.1 Caffeine（首选，简历风控系统在用）

```java
Cache<String, Object> cache = Caffeine.newBuilder()
    .maximumSize(10_000)                    // ① 便签本最多存 1 万条，满了自动淘汰
    .expireAfterWrite(10, TimeUnit.MINUTES) // ② 写进去 10 分钟后自动过期（防脏数据常驻）
    .expireAfterAccess(5, TimeUnit.MINUTES) // ③ 如果 5 分钟没人读，也过期（清冷门数据）
    .softValues()                           // ④ JVM 内存紧张时，允许 GC 回收缓存值（兜底防 OOM）
    .recordStats()                          // ⑤ 开启命中率统计，方便监控
    .build();

// ⑥ 获取：缓存有就直接返回；没有就自动调用 loader 从 DB/Redis 加载，
//    且【并发请求同一个 key 时只加载一次】（single-flight，防击穿）
Object value = cache.get(key, k -> loadFromDatabase(k));
```

**关键参数解释**：
- `maximumSize`：**必须设上限**，否则无限增长 → OOM。设为预计热点数据量的 1.5~2 倍。
- `expireAfterWrite` vs `expireAfterAccess`：前者是"写进去后固定过期"（适合配置类）；后者是"最后一次读后过期"（适合会话类）。**不要两个同时设**，逻辑会混乱。
- `softValues`：内存紧张时 GC 可回收，比 `weakValues` 更温柔（weak 一有 GC 就回收，太激进）。

**刷新而不是过期（防冷启动击穿）**：
```java
Cache<String, Object> cache = Caffeine.newBuilder()
    .refreshAfterWrite(1, TimeUnit.MINUTES)   // ① 写后 1 分钟，后台线程自动刷新值
    .build(k -> loadFromDatabase(k));
// 效果：用户永远读到缓存，不会触发同步加载；后台 quietly 更新
```

### 2.2 Ehcache（老牌，功能最全）

```xml
<!-- ehcache.xml -->
<cache alias="user">
  <key-type>java.lang.String</key-type>
  <value-type>com.example.User</value-type>
  <expiry>
    <ttl unit="minutes">10</ttl>     <!-- 10 分钟过期 -->
  </expiry>
  <heap unit="entries">1000</heap>    <!-- 堆内缓存 1000 条 -->
  <offheap unit="MB">100</offheap>   <!-- 堆外缓存 100MB（不受 GC 影响） -->
  <disk unit="GB">1</disk>           <!-- 磁盘持久化 1GB（重启不丢） -->
</cache>
```

**Ehcache 的三级存储**：
1. **堆内**：最快，但受 GC 影响（对象多了 GC 压力大）
2. **堆外**：直接操作操作系统内存，不受 GC 影响，但序列化/反序列化有开销
3. **磁盘**：重启不丢，但慢得多

**Spring 集成**：
```java
@Cacheable(value = "user", key = "#userId")   // 先查缓存，没有才执行方法
public User getUser(Long userId) { ... }

@CacheEvict(value = "user", key = "#userId")  // 更新后清缓存
public void updateUser(Long userId, User user) { ... }
```

> 💡 **什么时候选 Ehcache**：需要**磁盘持久化**（重启不丢）、**集群复制**（多实例间同步缓存）、**堆外存储**（大缓存防 GC）。否则 Caffeine 更轻更快。

## 三、进阶篇（多级缓存 + 面试）

### 3.1 多级缓存标准模式（简历大屏/秒杀都在用）

```
用户请求
   ↓
① 本地缓存（Caffeine）—— 微秒级
   ↓ 未命中
② Redis —— 毫秒级
   ↓ 未命中
③ 数据库（MySQL/DM）—— 几十毫秒
   ↓
回写 Redis + 回写本地缓存（可选，看一致性要求）
```

> 💡 **回写策略**：
> - **强一致**：查 DB 后只写 Redis，本地缓存不设或设极短 TTL
> - **最终一致**：查 DB 后同时写 Redis 和本地缓存，本地 TTL 设 1~5 分钟
> - **只读缓存**：本地缓存 TTL 短（30 秒），靠 ZK watch / MQ 广播失效通知

### 3.2 多实例不一致：怎么破

**问题**：A 实例本地缓存了"配置值 = 1"，后台改了数据库变成 2，但 A 不知道，还读 1。

**三种解法**：

| 解法 | 原理 | 适用 |
|---|---|---|
| **短 TTL** | 设 30 秒~5 分钟过期，到期自动重查 | 变化不频繁、容忍秒级延迟 |
| **广播失效** | 数据变更时发 MQ / ZK 通知，所有实例收到后 `cache.invalidate(key)` | 变化频繁、需要尽快一致 |
| **不做处理** | 接受短暂不一致 | 读多写极少、变化影响小（如字典、配置） |

> 💡 **简历秒杀的解法**：ZK watch 监听节点，库存补货时触发回调清本地缓存（见 [[13_Zookeeper 实战]]）。

### 3.3 冷启动击穿

**问题**：服务刚启动，本地缓存是空的，瞬间几千请求同时进来，每个都去查 DB/Redis → 压力暴增。

**Caffeine 的默认保护**：`cache.get(key, loader)` 自带 **single-flight**——同一个 key 的并发请求只会有一个去加载，其余等待结果。

**额外保险**：启动时预热（preheat）——服务启动后先异步把热点数据刷进本地缓存。

### 3.4 选型建议

| 场景 | 推荐 |
|---|---|
| 新项目、纯内存、追求极致性能 | **Caffeine** |
| 需要磁盘持久化（重启不丢） | Ehcache |
| 需要堆外内存（大缓存防 GC） | Ehcache（offheap） |
| 需要多实例缓存同步 | Ehcache（集群复制）或直接用 Redis |
| Spring 注解缓存 | 两者都支持，`@Cacheable` 通用 |

### 3.5 常见翻车

- **本地缓存无限容量 → OOM**：`maximumSize` 是生命线，必须设
- **TTL 过长 → 数据长期不一致**：配置类设 5~10 分钟，热点数据设 30 秒~2 分钟
- **把本地缓存当全局状态用**："所有实例共享标记"不能用本地缓存实现，那是 Redis/ZK 的活
- **缓存命中率低还硬上**：`recordStats()` 看命中率，低于 50% 说明缓存没意义，别浪费内存
