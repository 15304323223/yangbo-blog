# Redis 实战（原理 → 应用 → 进阶）

> **一句话概括**：Redis 是一个**放在内存里的超级货架**——读写比数据库快 100 倍，能当缓存、能当锁、能计数、能排队。但它是内存数据库，**数据会丢、容量有限、不能代替 MySQL**。
>
> **适合谁**：知道 Redis 能缓存，但说不清持久化怎么配、分布式锁为什么不用 `SETNX`、缓存穿透/击穿/雪崩怎么防的人。
> **怎么读**：原理篇了解"货架上有哪些货格"；应用篇两个代码（Redisson 锁 + Lua 扣减）直接可抄；进阶篇三个坑（穿透/击穿/雪崩）是面试必考。

---

## 零、先建立整体印象：把它想象成"超市的内存货架"

| 超市货架 | 对应 Redis | 一句话 |
|---|---|---|
| **常温货架（最快拿取）** | String / Hash / List / Set / ZSet | 最常用的五种货格，各有所长 |
| **库存快照（每晚拍照）** | RDB 持久化 | 每隔一段时间拍张照，恢复快但可能丢最近的数据 |
| **进货流水账（每笔都记）** | AOF 持久化 | 每笔操作都记本子上，几乎不丢但文件大 |
| **热门商品贴本地海报** | 本地缓存（Caffeine） | 最热的数据再抄一份放应用服务器手边，更快 |
| **收银台限流栏杆** | 分布式锁 / 计数器 | 同一时间只允许一个人结账 |

> 💡 **Redis 不是银弹**：它快是因为数据在内存里，但内存贵、会丢、容量有限。**冷数据、大对象、需要复杂查询的，统统回 MySQL。**

## 一、原理篇

### 1.1 五种数据结构：什么场景用什么

| 类型 | 像什么 | 适合场景 | 不适合 |
|---|---|---|---|
| **String** | 单个商品 | 缓存一个对象（JSON）、计数器、`SETNX` 锁 | 存关联性强的多字段数据 |
| **Hash** | 一格抽屉（里面多个小格子） | 存对象属性（如用户信息：`name`、`age`、`city`） | 字段太多（> 512）性能降 |
| **List** | 排队队伍 | 消息队列（`LPUSH` + `RPOP`）、最新 N 条记录 | 随机访问中间元素 |
| **Set** | 不重复名单 | 共同好友、标签集合、抽奖去重 | 需要排序 |
| **ZSet** | 带分数的排行榜 | 热搜排行、延时队列（按时间分数） | 数据量极大时内存涨 |

**ZSet 做延时队列**（面试常问）：
```java
// ① 把任务按"执行时间戳"当分数塞入 ZSet
redisTemplate.opsForZSet().add("delay:queue", taskId, System.currentTimeMillis() + 5000);
// ② 消费者轮询：取分数 <= 当前时间的任务
Set<Object> tasks = redisTemplate.opsForZSet().rangeByScore("delay:queue", 0, System.currentTimeMillis());
```

### 1.2 持久化：数据怎么从"易失"变"可靠"

Redis 是内存数据库，宕机数据就没了。持久化是两道保险：

| 方式 | 原理 | 优点 | 缺点 | 配置 |
|---|---|---|---|---|
| **RDB** | 定时把内存数据拍成快照文件 | 文件小、恢复快 | 会丢最后一次快照后的数据 | `save 900 1`（900 秒内有 1 次写就拍） |
| **AOF** | 把每条写命令追加到日志文件 | 几乎不丢数据（最多丢 1 秒） | 文件大、恢复慢 | `appendfsync everysec`（每秒刷盘，折中） |
| **混合（4.0+）** | RDB 快照头 + AOF 增量日志 | 启动快、丢得少 | 最推荐 | `aof-use-rdb-preamble yes` |

> 💡 **生产推荐开混合持久化**：既有 RDB 的快速恢复，又有 AOF 的精细日志。

## 二、应用篇（代码，照着抄）

### 2.1 分布式锁：为什么推荐 Redisson

**不用 `SETNX` 的原因**：
- `SETNX` 设了锁，但业务没执行完锁就过期了 → 别人进来，两个线程同时在临界区
- `SETNX` 解锁时 `DEL` 可能误删别人的锁（自己的锁过期了，别人的锁刚好创建，你 `DEL` 把别人的删了）

**Redisson 的解法**：
```java
RLock lock = redissonClient.getLock("order:" + orderId);

try {
    // ① 尝试加锁：最多等 3 秒，拿到后持有 10 秒
    //    但"看门狗"会自动续期：业务没执行完，每隔 10/3 秒自动续成 30 秒
    if (lock.tryLock(3, 10, TimeUnit.SECONDS)) {
        // ② 临界区：操作共享资源（扣库存、改余额...）
        deductStock(order);
    }
} finally {
    // ③ 释放锁：Redisson 用唯一 value + Lua 脚本删除，保证"只删自己的"
    lock.unlock();
}
```
- **看门狗（Watch Dog）**：加锁后启动一个后台线程，每隔 `leaseTime / 3` 检查一次，如果业务还没完就自动续期。**业务崩溃 → 看门狗线程也死 → 锁到期自动释放**——不会死锁。

### 2.2 原子扣减解决超卖（简历秒杀场景）

```lua
-- 这段 Lua 在 Redis 单线程里原子执行，不会被插队
-- KEYS[1] = 库存 key，如 "seckill:stock:1001"
-- KEYS[2] = 结束标记 key，如 "seckill:end:1001"

if redis.call('get', KEYS[2]) == '1' then
    return 0                      -- 已立结束标记，库存早空了，直接返回失败
end

local stock = tonumber(redis.call('get', KEYS[1]))
if stock <= 0 then
    redis.call('set', KEYS[2], '1')   -- 库存归零，立个"结束标记"
    return 0
end

redis.call('decr', KEYS[1])       -- 原子减 1，这一步不会被其他请求打断
return 1                          -- 扣减成功
```

> 💡 **为什么不用 `SETNX` 锁 + `DECR`？** 可以，但多一步锁操作，多一次网络往返。Lua 脚本是"一把梭"，一次请求搞定判断 + 扣减，**无锁竞争、无线程切换开销**。
>
> ⚠️ **多实例不公平问题**：A 实例本地缓存了"结束标记"，B 实例没有。解法：ZK watch 通知清标记（见 [[13_Zookeeper 实战]]）。

## 三、进阶篇（面试必考 + 生产事故）

### 3.1 缓存三大坑

| 坑 | 现象 | 原因 | 解法 |
|---|---|---|---|
| **穿透** | 大量请求查不存在的数据，直达 DB | 恶意请求随机 ID / 缓存没命中 | ① 缓存空值（短 TTL，如 30 秒）；② **布隆过滤器**（先查过滤器，肯定不存在直接拒） |
| **击穿** | 热点 key 过期瞬间，海量请求同时打 DB | 高并发 + key 同时过期 | ① 互斥锁重建（只有一个线程去 DB 查，查完写缓存）；② **逻辑过期**（key 永不过期，异步线程刷新） |
| **雪崩** | 大量 key 同时失效 / Redis 宕机，DB 被打爆 | 批量设了相同过期时间 / 集群故障 | ① 过期时间加随机偏移（`TTL + random(0, 300)`）；② Redis 集群高可用；③ 限流降级兜底 |

> 💡 **穿透、击穿、雪崩的区别**：穿透是"查不存在的东西"；击穿是"热点 key 刚好过期"；雪崩是"一片 key 同时挂了"。

### 3.2 缓存与数据库一致性

**Cache-Aside（旁路缓存，最常用）**：
```
读：先查缓存 → 有就返回；没有查 DB → 写缓存 → 返回
写：先更新 DB → 再删缓存（不是更新缓存！）
```
> 💡 **为什么删缓存而不是更新缓存？** 并发下"更新缓存"容易脏：A 改 DB → B 改 DB → B 更新缓存 → A 更新缓存（A 覆盖了 B 的新值）。**删缓存**让下次读时从 DB 重新加载，虽然多一次读，但保证最终一致。

**延迟双删**：更新 DB → 删缓存 → 等 500ms（等主从同步）→ 再删一次缓存。进一步降低脏读概率。

**强一致场景**：用 Canal 订阅 MySQL binlog，DB 变了自动同步删 Redis 缓存。

### 3.3 大 key / 热 key

- **大 key**：一个 key 占了几百 MB（比如把整个用户列表塞一个 String）。`redis-cli --bigkeys` 排查。**解法**：拆成多个小 key（Hash 分桶）。
- **热 key**：一个 key 被百万 QPS 访问（比如"全站配置"）。**解法**：本地缓存（Caffeine）兜底，Redis 变"二级缓存"。简历大屏项目就是这个思路。

### 3.4 集群模式怎么选

| 模式 | 原理 | 适用 |
|---|---|---|
| **单机** | 一台 Redis | 开发/测试，或数据量极小 |
| **主从** | 一主多从，从复制主 | 读多写少，但手动故障转移 |
| **哨兵** | 主从 + 自动故障转移 | 中小规模，自动切主 |
| **Cluster** ⭐ | 16384 个哈希槽分片，多主多从 | **生产首选**，自动分片、自动故障转移 |

> 💡 简历项目用"单机伪集群"上线够用，生产环境必须上 Redis Cluster。

### 3.5 Pipeline vs Lua

| | Pipeline | Lua |
|---|---|---|
| **原子性** | ❌ 非原子（中间可能被其他命令插队） | ✅ 原子（单线程执行整个脚本） |
| **用途** | 批量命令减少网络往返（RTT） | 需要"判断+操作"一气呵成的场景 |
| **例子** | 批量 `GET` 100 个 key | 秒杀扣减、限流计数 |

### 3.6 常见坑速查

- **key 不加业务前缀**：`user:1001` 和 `order:1001` 可能冲突 → 统一前缀：`app:user:1001`
- **TTL 不设**：Redis 变成"只进不出"，内存迟早打爆 → 所有 key 必须有过期时间
- **`KEYS *` 阻塞**：在大库上执行 `KEYS *` 会遍历全部 key，阻塞几十秒 → 用 `SCAN` 分批遍历
- **内存打爆**：设 `maxmemory` + 淘汰策略（`allkeys-lru` 最常用）；ZSet 排行榜要定期 `ZREMRANGEBYRANK` 裁剪
