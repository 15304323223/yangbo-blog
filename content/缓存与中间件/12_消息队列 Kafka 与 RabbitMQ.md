# 消息队列 Kafka 与 RabbitMQ（原理 → 应用 → 进阶）

> **一句话概括**：消息队列就是**快递驿站**——你（生产者）把包裹放下就走，不用等收件人（消费者）来取；驿站帮你存着，收件人按自己的节奏来拿；双十一包裹太多时，驿站缓冲一下，不会直接把分拣中心压垮。
>
> **适合谁**：知道 MQ 能"解耦异步"，但说不清 Kafka 和 RabbitMQ 有什么区别、消息丢了怎么办、怎么保证不重复消费的人。
> **怎么读**：原理篇理解"快递驿站怎么运作"；应用篇两段代码直接可抄；进阶篇"三大难题"是面试必考。
>
> 📖 **RabbitMQ 专篇**：Exchange 路由、七个真实场景、可靠性五道防线、14 个必踩的坑、同类 MQ 对比与选型，见 [[35_RabbitMQ 实战详解（场景·用法·弊端·举一反三）]]。

## 零、先建立整体印象：把它想象成"快递驿站"

| 快递场景 | 对应 MQ | 一句话 |
|---|---|---|
| **寄件人放下包裹就走** | 异步 | 生产者发完消息立刻返回，不用等消费者处理完 |
| **寄件人不认识收件人** | 解耦 | 生产者不知道消费者是谁，加新的消费者不用改生产者代码 |
| **双十一包裹太多，驿站缓冲** | 削峰 | 突发流量进队列暂存，消费者按自己的能力慢慢处理 |
| **每个小区一个分站点** | Partition / Queue | 并行处理，多个消费者同时干活 |
| **签收确认** | Ack | 消费者处理完告诉 MQ "我收到了"，MQ 才删消息 |

## 一、原理篇：MQ 解决的三件事 + 两个框架

### 1.1 为什么用 MQ（解耦 / 异步 / 削峰）

**① 解耦**：
```
不用 MQ：订单系统 → 直接调短信接口 + 邮件接口 + 日志接口
         问题：加一个"微信通知"，要改订单系统的代码

用 MQ：  订单系统 → 发一条"订单已创建"消息到 MQ → 完事儿
         短信服务、邮件服务、日志服务各自从 MQ 取消息处理
         加微信通知？再部署一个微信服务取消息就行，订单系统一行不改
```

**② 异步**：
```
不用 MQ：用户下单 → 写数据库(50ms) → 发短信(200ms) → 发邮件(300ms) → 记日志(100ms) → 返回"下单成功"
         总耗时：650ms，用户等得着急

用 MQ：  用户下单 → 写数据库(50ms) → 发消息到 MQ(5ms) → 返回"下单成功"
         短信/邮件/日志后台慢慢处理
         总耗时：55ms，用户感知极快
```

**③ 削峰**：
```
场景：平时每秒 100 单，促销活动瞬间涨到每秒 1 万单

不用 MQ：1 万请求直接打数据库 → 数据库 CPU 100% → 全站卡顿 → 订单丢失

用 MQ：  1 万请求先丢进 MQ 队列 → 数据库按每秒 1000 的能力慢慢消费
         队列会积压，但系统不崩，活动结束后再慢慢消化
```

### 1.2 Kafka：高吞吐的"物流分拨中心"

**核心概念**：

| 概念 | 像什么 | 说明 |
|---|---|---|
| **Topic** | 快递线路名（如"北京-上海"） | 消息的分类，生产者按 Topic 发，消费者按 Topic 收 |
| **Partition** | 分拨站的装卸口 | 一个 Topic 分多个 Partition，每个 Partition 独立消费 → **并行处理** |
| **Offset** | 包裹编号 | 消费者读到第几个了，记在自己的小本本上 |
| **Consumer Group** | 一个快递公司的车队 | 一个 Group 里的消费者共同消费一个 Topic，**同组不重复消费** |
| **ISR** | 可信司机名单 | 副本同步列表，只有 ISR 里的副本才算"可靠" |

**Kafka 为什么快？**
- **顺序写盘**：像写日记一样 append，比随机写快 100 倍
- **零拷贝**：数据从磁盘直接发到网卡，不经过应用层内存
- **批量 + 压缩**：攒一批消息一起发，减少网络往返

### 1.3 RabbitMQ：灵活路由的"智能快递柜"

**核心概念**：

| 概念 | 像什么 | 说明 |
|---|---|---|
| **Exchange** | 分拣机器人 | 收到消息后，按规则分到不同的 Queue |
| **Queue** | 快递柜格子 | 消息真正存放的地方，消费者从这里取 |
| **Binding** | 分拣规则 | "订单消息 → 放进短信队列和邮件队列" |
| **Routing Key** | 收件人地址 | Exchange 根据 Routing Key 决定消息进哪个 Queue |

**四种交换机**：

| 类型 | 规则 | 场景 |
|---|---|---|
| **direct** | 精确匹配 Routing Key | `order.notify` 只进 `notify` 队列 |
| **topic** | 通配符匹配 | `order.*` 匹配所有以 `order.` 开头的 |
| **fanout** | 广播，无视 Routing Key | 一条消息进所有绑定的队列 |
| **headers** | 按消息头匹配 | 复杂条件路由 |

> 💡 **一句话区分**：Kafka 是"大吞吐量、简单模型"；RabbitMQ 是"复杂路由、低延迟、可靠性高"。

## 二、应用篇（代码，照着抄）

### 2.1 Kafka 消费幂等（防重复消费）

**问题**：Kafka 消费者重启后可能重复消费（offset 没提交或提交失败）。

**解法**：用 Redis `SETNX` 做去重标记——同一个消息只处理一次。

```java
@KafkaListener(topics = "order-event", groupId = "order-consumer")
public void onMessage(ConsumerRecord<String, String> record) {
    // ① 构造唯一去重 key：topic + partition + offset 全局唯一
    String dedupKey = "mq:dedup:" + record.topic() + ":"
                      + record.partition() + ":" + record.offset();

    // ② SETNX：只有第一次能设置成功，重复消息会返回 false
    Boolean isNew = redisTemplate.opsForValue()
        .setIfAbsent(dedupKey, "1", 24, TimeUnit.HOURS);

    if (Boolean.TRUE.equals(isNew)) {
        // ③ 第一次收到 → 真正处理
        handleOrderEvent(record.value());
    } else {
        // ④ 重复消息 → 直接丢弃
        log.info("重复消息，跳过：{}", dedupKey);
    }
}
```

### 2.2 RabbitMQ 手动 Ack（防消息丢失）

**问题**：消费者拿到消息后还没处理完就崩溃了，消息丢了怎么办？

**解法**：手动 Ack——处理完再告诉 MQ "我收到了"，没处理完 MQ 会重新发。

```java
@RabbitListener(queues = "notify-queue")
public void onMessage(Message message, Channel channel) throws IOException {
    long deliveryTag = message.getMessageProperties().getDeliveryTag();

    try {
        // ① 处理业务逻辑
        sendNotification(message.getBody());

        // ② 处理成功 → 手动确认（multiple=false 只确认这一条）
        channel.basicAck(deliveryTag, false);

    } catch (Exception e) {
        log.error("消费失败", e);

        // ③ 处理失败 → 否定确认
        // requeue=false：不进原队列，直接进死信队列（DLQ）
        // requeue=true：重回队列，稍后重试（可能无限循环，慎用）
        channel.basicNack(deliveryTag, false, false);
    }
}
```

> 💡 **死信队列（DLQ）**：专门收"被拒收、过期、处理失败"的消息，事后人工排查或自动重试。

## 三、进阶篇（三大难题 + 面试热点）

### 3.1 消息丢失：怎么保证消息不丢（三段防护）

```
生产者 ──→ MQ ──→ 消费者
   ↑         ↑          ↑
   ①         ②          ③
```

| 阶段 | 风险 | 解法 |
|---|---|---|
| **① 生产者发送时** | 网络抖动，消息没到 MQ | 开启 **Producer Confirm**，MQ 收到后回 ACK，没收到重发 |
| **② MQ 存储时** | MQ 宕机，内存里的消息没了 | Kafka 开 **副本 + ISR**；RabbitMQ 开 **队列持久化 + 消息持久化** |
| **③ 消费者处理时** | 消费者拿到消息还没处理完就挂了 | **手动 Ack**，处理完才确认；失败进死信队列 |

> 💡 **面试话术**："消息防丢分三段：生产者 Confirm + MQ 持久化/副本 + 消费者手动 Ack，三段都做好才能做到不丢。"

### 3.2 重复消费： already 在应用篇讲了，核心就是幂等

幂等实现三选一：
1. **唯一索引**：数据库层面防重（如订单表 `UNIQUE(business_id)`）
2. **Redis 去重标记**：应用篇 2.1 的 `SETNX` 方案
3. **状态机**："已处理"状态直接返回成功（见 [[15_高并发高可用设计]]）

### 3.3 顺序消费

**问题**：用户先下单、再付款、再发货，如果 MQ 消费顺序乱了，先执行"发货"再执行"付款"就全乱了。

**解法**：
- **Kafka**：同一个 `userId` 的订单用相同的 key，Kafka 保证**同 key 同 Partition**，同 Partition 内消息有序
- **RabbitMQ**：一个队列只配一个消费者，天然有序（但吞吐低）
- **业务层兜底**：消息里带"前序状态"，消费时校验"当前状态是否允许执行此操作"，不允许就延迟重试

### 3.4 消息积压（简历大屏实战）

**现象**：设备每 3 秒发心跳，消费端处理不过来，MQ 队列长度暴涨。

**解法三板斧**：
1. **扩容消费者**：Kafka 加 Partition + 加消费者实例（一个 Partition 只能被一个消费者消费，所以 Partition 数 ≥ 消费者数）
2. **本地缓存 + 线程池**：消费者里用本地缓存去重，只处理最新心跳（旧的心跳丢弃）
3. **临时分流**：建一个新 Topic，把积压消息导过去，原 Topic 恢复正常消费

> 💡 **监控**：Kafka 看 `consumer lag`（积压量），RabbitMQ 看队列长度，超阈值自动告警。

### 3.5 Kafka vs RabbitMQ 选型

| | Kafka | RabbitMQ |
|---|---|---|
| **吞吐量** | 极高（百万级/秒） | 高（万级/秒） |
| **延迟** | 毫秒级 | 微秒级 |
| **消息持久** | 持久化 + 副本 | 持久化 + 队列 |
| **路由能力** | 弱（Topic 级别） | **强**（Exchange 灵活路由） |
| **适用场景** | **日志、埋点、心跳、流数据** | **业务通知、异步任务、延时队列** |
| **重放能力** | **支持**（按 offset 重放历史） | 不支持（消费完就删） |

> ✅ **简历里的用法**：大屏设备心跳 → Kafka（高吞吐、可重放）；短信/邮件通知 → RabbitMQ（低延迟、可靠）。
