# XXL-JOB 分布式任务调度实战（从入门到生产落地）

> **一句话概括**：XXL-JOB 是美团开源的分布式任务调度平台，解决「定时任务在多实例下重复执行」「任务管理分散在各服务里不好统一管理」「任务失败了不知道」这些问题。调度中心负责任务触发和管理，执行器负责任务执行，二者解耦，弹性扩容。
>
> **适合谁**：还在用 `@Scheduled` 写定时任务、多实例部署时任务重复执行、任务失败了全靠用户反馈才知道、面试被问「分布式任务调度怎么实现」答不出方案的人。

---

## 零、先建立印象：把它想象成「餐厅的传菜系统」

| 餐厅传菜系统 | XXL-JOB |
|---|---|
| **菜单（调度中心）** | 写着「几点做什么菜」，统一管理所有任务 |
| **厨师（执行器）** | 实际做菜的人，可以有多个厨师，弹性扩容 |
| **传菜员（调度）** | 到点了把菜单递给厨师，告诉厨师做什么菜 |
| **出餐口（回调）** | 厨师做完菜，告诉传菜员「做好了」 |
| **多个厨师做同一道菜？** | 不会，调度中心只会把任务分给一个厨师（路由策略） |

**传统 `@Scheduled` 的问题：**
1. **多实例重复执行**：部署 3 个实例，每个实例都跑一遍定时任务，数据重复
2. **不好统一管理**：任务分散在各个服务里，不知道有哪些定时任务、什么时候跑
3. **没有失败告警**：任务执行失败了，没人知道，直到用户反馈
4. **不能动态修改**：改 cron 表达式要改代码、重新发布
5. **不能手动触发**：想手动跑一次任务，只能等定时时间到或者写接口

XXL-JOB 全部解决。

## 一、核心架构与概念

### 1.1 架构图

```
┌─────────────────────────────────────────────────┐
│              调度中心（Admin）                     │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐        │
│  │ 任务管理  │ │ 调度器    │ │ 日志管理  │        │
│  │ (增删改查)│ │ (触发)   │ │ (执行记录)│        │
│  └──────────┘ └──────────┘ └──────────┘        │
│         │           │                              │
│         │  HTTP 调用  │                             │
└─────────┼───────────┼──────────────────────────────┘
          │           │
    ┌─────▼─────┐ ┌──▼──────┐ ┌─────────┐
    │ 执行器 A   │ │ 执行器 B │ │ 执行器 C │
    │ (服务1)    │ │ (服务2)  │ │ (服务3)  │
    └───────────┘ └─────────┘ └─────────┘
```

### 1.2 核心概念

| 概念 | 说明 |
|---|---|
| **调度中心（Admin）** | 统一管理任务的平台，负责任务配置、触发、日志、告警。独立部署，不依赖业务 |
| **执行器（Executor）** | 实际执行任务的应用，集成 XXL-JOB 客户端，注册到调度中心 |
| **任务（Job）** | 一个定时任务，包含：任务名、cron 表达式、执行器、路由策略、阻塞策略等 |
| **JobHandler** | 任务的具体执行逻辑，用 `@XxlJob` 注解标记的方法 |
| **调度日志** | 每次任务执行的记录：执行时间、执行结果、耗时、日志输出 |

### 1.3 调度模型

```
调度中心 → 到点触发 → HTTP 调用执行器 → 执行器执行 JobHandler → 返回结果 → 调度中心记录日志
```

> 💡 **关键设计**：调度中心和执行器是**解耦**的。调度中心只负责「到点了叫你」，具体执行逻辑在执行器里。执行器可以随时扩容，调度中心自动发现。

## 二、快速上手：30 分钟跑通

### 2.1 部署调度中心

```bash
# 1. 下载源码
git clone https://github.com/xuxueli/xxl-job.git

# 2. 初始化数据库（执行 doc/db/tables_xxl_job.sql）
mysql -u root -p < doc/db/tables_xxl_job.sql

# 3. 修改调度中心配置（xxl-job-admin/src/main/resources/application.properties）
# 数据库地址
spring.datasource.url=jdbc:mysql://127.0.0.1:3306/xxl_job?useUnicode=true&characterEncoding=UTF-8&autoReconnect=true
spring.datasource.username=root
spring.datasource.password=xxx
# 报警邮箱（可选）
spring.mail.host=smtp.qq.com
spring.mail.username=xxx@qq.com
spring.mail.password=xxx

# 4. 打包启动
cd xxl-job-admin
mvn clean package
java -jar target/xxl-job-admin-2.4.0.jar

# 5. 访问控制台
# http://localhost:8080/xxl-job-admin
# 默认账号：admin / 123456
```

### 2.2 业务服务集成执行器

```xml
<!-- Maven 依赖 -->
<dependency>
    <groupId>com.xuxueli</groupId>
    <artifactId>xxl-job-core</artifactId>
    <version>2.4.0</version>
</dependency>
```

```yaml
# application.yml 配置
xxl:
  job:
    admin:
      addresses: http://127.0.0.1:8080/xxl-job-admin  # 调度中心地址
    executor:
      appname: order-service-executor  # 执行器名称，调度中心配置时用
      address: ""          # 执行器地址，为空自动注册
      ip: ""               # 执行器 IP，为空自动获取
      port: 9999           # 执行器端口（不是服务端口，是 XXL-JOB 通信端口）
      logpath: ./logs/xxl-job/jobhandler  # 日志路径
      logretentiondays: 30  # 日志保留天数
```

```java
// 配置类
@Configuration
public class XxlJobConfig {
    @Value("${xxl.job.admin.addresses}")
    private String adminAddresses;
    @Value("${xxl.job.executor.appname}")
    private String appName;
    @Value("${xxl.job.executor.port}")
    private int port;
    @Value("${xxl.job.executor.logpath}")
    private String logPath;
    @Value("${xxl.job.executor.logretentiondays}")
    private int logRetentionDays;

    @Bean
    public XxlJobSpringExecutor xxlJobExecutor() {
        XxlJobSpringExecutor executor = new XxlJobSpringExecutor();
        executor.setAdminAddresses(adminAddresses);
        executor.setAppname(appName);
        executor.setPort(port);
        executor.setLogPath(logPath);
        executor.setLogRetentionDays(logRetentionDays);
        return executor;
    }
}
```

### 2.3 编写任务（JobHandler）

```java
@Component
public class OrderJobHandler {

    // 方式一：方法注解（推荐，简单）
    @XxlJob("closeTimeoutOrder")
    public void closeTimeoutOrder() {
        // 业务逻辑：关闭超时未支付的订单
        log.info("开始关闭超时订单...");
        orderService.closeTimeoutOrders();
        log.info("关闭超时订单完成");
    }

    // 方式二：带参数的任务
    @XxlJob("exportDailyReport")
    public void exportDailyReport() {
        // 获取任务参数（调度中心配置时可以传参数）
        String param = XxlJobHelper.getJobParam();
        log.info("导出日报，参数：{}", param);
        reportService.exportDaily(param);
    }

    // 方式三：分片广播任务（大数据量处理）
    @XxlJob("batchProcessData")
    public void batchProcessData() {
        // 分片参数
        int shardIndex = XxlJobHelper.getShardIndex();  // 当前执行器的分片序号
        int shardTotal = XxlJobHelper.getShardTotal();  // 总分片数

        log.info("分片处理：{}/{}", shardIndex, shardTotal);

        // 按分片取模，每个执行器只处理一部分数据
        List<Data> dataList = dataService.getDataByShard(shardIndex, shardTotal);
        dataList.forEach(this::process);
    }
}
```

### 2.4 调度中心配置任务

1. 登录控制台 → 执行器管理 → 新增执行器（AppName 填 `order-service-executor`）
2. 任务管理 → 新增任务：
   - 执行器：选刚才创建的
   - 任务描述：关闭超时订单
   - 路由策略：第一个（或轮询、随机）
   - Cron：`0 0/5 * * * ?`（每 5 分钟）
   - JobHandler：`closeTimeoutOrder`（和注解里的名字一致）
3. 启动任务 → 查看调度日志

## 三、核心特性深入理解

### 3.1 路由策略（多执行器时选哪个执行）

| 策略 | 说明 | 适用场景 |
|---|---|---|
| **第一个** | 固定选第一个在线的执行器 | 任务只需要一个实例执行 |
| **最后一个** | 固定选最后一个在线的执行器 | 同上 |
| **轮询** | 按顺序轮流执行 | 任务执行时间均匀，负载均衡 |
| **随机** | 随机选一个 | 简单场景 |
| **一致性 HASH** | 相同任务总是路由到同一个执行器 | 任务需要本地缓存、有状态 |
| **最不经常使用** | 选使用次数最少的 | 负载均衡 |
| **最近最久未使用** | 选最久没执行任务的 | 负载均衡 |
| **故障转移** | 依次尝试，失败了换下一个 | 高可用要求高 |
| **忙碌转移** | 选最空闲的执行器 | 任务执行时间不均匀 |
| **分片广播** | 所有执行器都执行，每个执行器处理一部分数据 | 大数据量批处理 |

> 💡 **分片广播是 XXL-JOB 的杀手级特性**：比如要处理 100 万条数据，部署 5 个执行器，每个执行器处理 20 万条，并行处理，速度提升 5 倍。用 `XxlJobHelper.getShardIndex()` 和 `getShardTotal()` 实现。

### 3.2 阻塞处理策略（任务还没跑完，下一次又到点了）

| 策略 | 说明 |
|---|---|
| **单机串行** | 新任务进队列，等当前任务跑完再执行（默认） |
| **丢弃后续调度** | 新任务直接丢弃，不执行 |
| **覆盖之前调度** | 终止当前任务，直接执行新任务 |

**怎么选？**
- 任务执行时间 < 调度间隔：用单机串行（默认）
- 任务执行时间 > 调度间隔，且每次执行都重要：单机串行（会堆积，但不会丢）
- 任务执行时间 > 调度间隔，且只关心最新数据：覆盖之前调度
- 任务执行时间 > 调度间隔，且跳过一次没关系：丢弃后续调度

### 3.3 失败处理与告警

```
1. 任务执行失败 → 调度中心记录失败日志
2. 配置了失败重试次数 → 自动重试（最多重试 N 次）
3. 配置了告警邮箱 → 发送失败告警邮件
4. 可以在「调度日志」里查看失败原因，支持「执行一次」手动重跑
```

**告警配置：**
- 任务配置时填写「报警邮箱」，多个邮箱用逗号分隔
- 调度中心配置邮件服务器（spring.mail.*）
- 任务失败、重试失败都会发邮件

### 3.4 任务依赖（子任务）

```
任务 A 执行成功后 → 自动触发任务 B → 任务 B 成功后触发任务 C
```

配置方式：任务配置时填写「子任务ID」，多个用逗号分隔。父任务成功后自动触发子任务。

适用场景：数据处理流水线（抽取 → 清洗 → 转换 → 加载）。

## 四、生产环境最佳实践

### 4.1 调度中心高可用

```
问题：调度中心挂了怎么办？
答案：调度中心集群部署 + 数据库共享
```

```
        ┌─────────────┐
        │   Nginx/LB  │
        └──────┬──────┘
               │
    ┌──────────┼──────────┐
    │          │          │
┌───▼───┐ ┌───▼───┐ ┌───▼───┐
│ Admin1 │ │ Admin2 │ │ Admin3 │  ← 多个调度中心实例
└───┬───┘ └───┬───┘ └───┬───┘
    │          │          │
    └──────────┼──────────┘
               │
        ┌──────▼──────┐
        │   MySQL 集群  │  ← 共享数据库，调度信息存在这里
        └─────────────┘
```

**原理**：调度信息存在数据库里，多个 Admin 实例共享数据库。通过数据库行锁保证同一个任务只会被一个实例触发。任何一个实例挂了，其他实例继续工作。

### 4.2 执行器最佳实践

```
1. 执行器端口不要和服务端口冲突（服务用 8080，XXL-JOB 用 9999）
2. 执行器 AppName 要有意义，按服务名命名（order-service-executor）
3. 任务执行时间长的，用分片广播，多实例并行处理
4. 任务里不要写死循环，要能正常退出
5. 任务里的异常要捕获，不要让异常导致执行器崩溃
6. 大任务要做进度记录，方便排查和手动恢复
```

### 4.3 任务设计规范

```
1. 幂等性：任务重复执行不能导致数据重复（参考接口幂等笔记）
2. 可重入：任务执行到一半失败了，重新执行能从断点继续
3. 数据量控制：一次不要查太多数据，分页处理，避免 OOM
4. 超时控制：任务里的远程调用要设置超时，避免任务卡死
5. 日志规范：关键节点打日志（开始、结束、异常、进度），方便排查
6. 参数化：任务参数从调度中心传，不要写死在代码里
```

### 4.4 与 Spring `@Scheduled` 对比

| 对比项 | @Scheduled | XXL-JOB |
|---|---|---|
| 多实例重复执行 | ❌ 会重复 | ✅ 路由策略保证只执行一次 |
| 统一管理 | ❌ 分散在各服务 | ✅ 调度中心统一管理 |
| 动态修改 cron | ❌ 改代码重发布 | ✅ 控制台直接改 |
| 手动触发 | ❌ 要写接口 | ✅ 控制台点一下 |
| 失败告警 | ❌ 自己实现 | ✅ 内置邮件告警 |
| 执行日志 | ❌ 自己查 | ✅ 控制台查看 |
| 分片处理 | ❌ 自己实现 | ✅ 内置分片广播 |
| 任务依赖 | ❌ 自己实现 | ✅ 子任务配置 |
| 学习成本 | 低 | 中 |
| 运维成本 | 0 | 需要部署调度中心 |

> 💡 **选型建议**：简单项目、单实例部署，用 `@Scheduled` 就够了。微服务、多实例、任务多、需要统一管理，上 XXL-JOB。

## 五、常见坑与解决方案

| 坑 | 现象 | 解法 |
|---|---|---|
| **执行器注册不上** | 调度中心看不到执行器 | 检查 admin.addresses 配置是否正确；检查执行器端口是否被占用；检查网络是否通 |
| **任务触发了但没执行** | 调度日志显示成功，但业务没跑 | 检查 JobHandler 名字是否和注解一致；检查执行器日志有没有报错 |
| **任务重复执行** | 多实例都执行了 | 检查路由策略是不是「分片广播」（分片广播会所有实例都执行）；确认执行器注册是否正常 |
| **调度中心时间不准** | 任务触发时间不对 | 同步服务器时间（NTP），调度中心和执行器时间要一致 |
| **日志看不到** | 调度日志里没有输出 | 检查执行器 logpath 配置；确认任务里用的是 `XxlJobHelper.log()` 而不是普通 log |
| **任务卡死** | 任务一直处于「运行中」 | 任务里有死循环或远程调用没超时；杀掉执行器进程，任务会自动标记失败 |
| **数据库连接池满** | 调度中心报连接池耗尽 | 调度中心连接池调大；检查是不是有慢查询 |

## 六、面试口述总结

> **XXL-JOB 的架构？**
> 调度中心 + 执行器。调度中心独立部署，负责任务管理、触发、日志、告警。执行器集成在业务服务里，注册到调度中心，实际执行任务。二者通过 HTTP 通信，解耦，弹性扩容。
>
> **怎么解决多实例重复执行？**
> 路由策略。调度中心触发任务时，根据路由策略（轮询、随机、第一个等）选一个执行器来执行，不会所有执行器都执行。如果用「分片广播」策略，才会所有执行器都执行，但每个执行器处理一部分数据。
>
> **分片广播是什么？**
> 所有执行器都执行任务，但每个执行器通过 `getShardIndex()` 和 `getShardTotal()` 拿到自己的分片序号和总分片数，按取模只处理一部分数据。适合大数据量批处理，多实例并行，提升处理速度。
>
> **阻塞策略有哪些？**
> 单机串行（排队等）、丢弃后续调度（直接丢）、覆盖之前调度（终止当前跑新的）。根据任务执行时间和重要性选择。
>
> **XXL-JOB 和 @Scheduled 怎么选？**
> 简单项目单实例用 @Scheduled，零成本。微服务多实例、任务多、需要统一管理、失败告警、手动触发，用 XXL-JOB。
